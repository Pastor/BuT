# Takt — Язык описания автоматных моделей

**Takt** (Typed, Automata, Known Timing) — предметно-ориентированный язык (DSL) для моделирования
конечных автоматов (FSM) и компонентных систем. Компилятор реализован на Rust.

> **Язык создан в учебных целях.** Его основная задача — показать принципы
> **автоматного подхода к разработке**: описание поведения состояниями и
> переходами, детерминированное исполнение по тактам и порождение из одной
> модели кода для разных платформ.
>
> При этом язык **применим и промышленно** — и именно поэтому он такой
> строгий: учебный пример, который врёт, ничему не учит, а прошивка, которая
> врёт, стоит дороже. Отсюда потактовые сверки эталона с целями, проверки чужих
> инструментов (`cc`, `iec2c`, `verilator`, `yosys`, `clippy`) и запрет
> молчаливых расхождений.

## 1. Введение

### Целевая аудитория

Этот документ предназначен для:

- **Разработчиков встраиваемых систем**, которые проектируют управляющую логику на основе
  конечных автоматов и нуждаются в формальном и читаемом способе её описания.
- **Исследователей и инженеров** в области верификации, желающих описывать поведение систем
  на высоком уровне абстракции.
- **Опытных разработчиков** (C/C++/Rust), знакомых с понятиями FSM, которые хотят изучить
  синтаксис и семантику Takt.
- **Преподавателей и студентов** — язык сделан в учебных целях, и его основная задача —
  показать принципы автоматного подхода к разработке на работающем инструменте, а не
  на схеме в презентации.

### Соглашения по нотации

| Обозначение      | Смысл                              |
|------------------|------------------------------------|
| `ключевое_слово` | Литерал: пишется дословно          |
| `идентификатор`  | Любое имя, выбранное пользователем |
| `[ ... ]`        | Необязательный элемент             |
| `{ ... }`        | Повторение (0 и более раз)         |
| `a \| b`         | Альтернатива                       |

Полная грамматика в формате ISO EBNF — в приложении документа
[«Грамматика»](book/src/appendix-grammar/index.typ) (описание языка живёт
в `book/`).

### Привет, мир!

Минимальная программа — модель со стартовым состоянием:

```lam
model Hello {
    start World;
}

start Main = Hello;
```

Запустить компилятор:

```sh
cargo build --release --bin taktc
./target/release/taktc compile --target c hello.takt -o out/
```

В `out/` появятся `hello.h` и `hello.c`.

> **Толчейн.** Версия компилятора Rust зафиксирована файлом
> [`rust-toolchain.toml`](rust-toolchain.toml) (стабильный `1.97.1`) — `rustup`
> поставит её сам при первом вызове `cargo`, отдельных действий не требуется.
> `Cargo.lock` отслеживается репозиторием, поэтому состав зависимостей
> воспроизводим побайтно; MSRV — `1.97`.

## 2. Назначение DSL

### Учебная задача

Takt сделан **в учебных целях**. Его основная задача — показать принципы
**автоматного подхода к разработке**:

- поведение системы описывается **состояниями и переходами**, а не потоком управления;
- исполнение **детерминировано и разбито на такты** — поведение модели воспроизводимо;
- из **одной** модели порождается код для разных платформ, и расхождение между ними —
  дефект инструмента, а не свойство языка;
- модель пригодна для **проверки** (симуляция, инварианты, верификация LTL) до того,
  как появится железо.

Всё остальное в языке — типы, порты, адреса, цели генерации — служит этой задаче:
показать автоматный подход не на схеме, а на программе, которая компилируется и
исполняется.

**Промышленное применение при этом не исключено — оно и объясняет строгость.**
Язык пригоден для реальных управляющих систем, а раз так, учебная модель и
прошивка обязаны вести себя одинаково: отсюда потактовые сверки эталона со всеми
целями, прогон порождённого кода чужими инструментами (`cc`, `iec2c`,
`verilator`, `yosys`, `clippy`) и правило «молчаливое расхождение — дефект».

### Проблема

Традиционный подход — писать конечные автоматы вручную на C — приводит к рутинному коду,
который сложно верифицировать и сопровождать. Типичная реализация FSM на C требует:
`switch-case` по состояниям, ручного управления флагами входа/выхода, указателей MMIO вместо
типизированных портов.

### Решение

Takt предлагает:

- **Декларативный синтаксис** для FSM вместо `switch-case` на C.
- **Компиляцию в C**: сгенерированный код оптимален и пригоден для встраиваемых систем.
- **Формальную семантику**: типизация, детерминированность переходов, диагностика.
- **Никакого времени выполнения**: ни сборщика мусора, ни кучи — только стек и порты.

### Парадигма

Takt — **декларативный, ориентированный на состояния** язык:

- **Модели** (`model`) — основные строительные блоки; каждая модель — один FSM.
- **Состояния** (`start`, `state`) — узлы автомата; логика выполняется в их блоках.
- **Переходы** (`ref`, `next`) — рёбра автомата с условиями или безусловные.
- **Параллельная и последовательная композиция** (`|`, `+`) — сборка систем из компонентов.

### «Дзен» языка

| Принцип            | Смысл                                                   |
|--------------------|---------------------------------------------------------|
| **Явность**        | Переходы описаны явно — нет скрытой передачи управления |
| **Локальность**    | Каждая модель инкапсулирует состояния и данные          |
| **Минимализм**     | Язык содержит только необходимые конструкции            |
| **Встраиваемость** | Нет GC, времени выполнения или кучи — только стек и порты         |

### Сравнение с C

| Концепция          | C (switch-case)        | Takt                      |
|--------------------|------------------------|--------------------------|
| Состояние          | `enum` + переменная    | `state`/`start`          |
| Переход            | `case` с `goto`        | `ref Цель: условие;`     |
| Вход в состояние   | ручная флаг-переменная | `enter { ... }`          |
| Параллелизм        | потоки / ручная логика | `M1 \| M2`               |
| Последовательность | вложенный switch       | `M1 + M2`                |
| Порты              | указатели MMIO         | `in`/`out` внутри модели |
| Типизация          | слабая                 | строгая статическая      |

## 3. Термины и сущности домена

### Глоссарий

| Термин                  | Определение                                                         |
|-------------------------|---------------------------------------------------------------------|
| FSM                     | Конечный автомат (Finite State Machine)                             |
| Модель                  | Объявление конечного автомата (`model M { ... }`)                   |
| Состояние               | Узел автомата (`start` или `state`)                                 |
| Переход                 | Смена активного состояния (`ref` или `next`)                        |
| Условие                 | Булево выражение для `ref`-перехода                                 |
| `cond`                  | Именованное условие — псевдоним для переиспользования               |
| Порт                    | Переменная, отображённая на аппаратный адрес или интерфейс модели   |
| Композиция              | Объединение моделей: последовательная (`+`) или параллельная (`\|`) |
| `enter`/`exit`/`always` | Именованные блоки кода с семантикой жизненного цикла                |
| `next`                  | Безусловный переход в следующее состояние                           |
| DSL                     | Domain-Specific Language — предметно-ориентированный язык           |

### Структура программы

Программа Takt — это последовательность **элементов верхнего уровня**:

| Конструкция          | Описание                                     |
|----------------------|----------------------------------------------|
| `import "file.takt";` | Импорт другого файла                         |
| `type T = ...;`      | Псевдоним типа                               |
| `var x: T := v;`     | Глобальная переменная                        |
| `const C: T := v;`   | Константа                                    |
| `fn f(...) {...}`    | Функция                                      |
| `extern fn f(...);`  | Прототип внешней функции                     |
| `enum E {...}`       | Перечисление                                 |
| `struct S {...}`     | Структура                                    |
| `model M {...}`      | Конечный автомат                             |
| `cond C = ...;`      | Именованное условие                          |
| `start Main = ...;`  | Точка входа (составная модель или псевдоним) |

Модель на Takt — это автомат: состояния, переходы по условиям и тела, которые
исполняются на такте.

```takt
model Watchdog {
    in kick: bit := 0;              // вход: сигнал «система жива»
    out alarm: bit := 0;            // выход: авария
    var idle: u8 := 0;              // внутренний счётчик простоя

    const LIMIT := 5;               // выдержка в тактах

    start Watching {
        always {                    // тело исполняется каждый такт
            if kick { idle := 0; } else { idle := idle + 1; }
        }
        ref Tripped: idle >= LIMIT; // переход по условию
    }

    state Tripped {
        always { alarm := 1; }
    }
}

start Root = Watchdog;              // корневая модель единицы компиляции
```

## 5. Семантика

Ключевые решения языка — тезисно; каждое подробно раскрыто в документе.

- **Присваивание `:=`, сравнение `=`.** Знаки разведены в стиле ST/IEC 61131-3;
  оператор `==` из языка **выведен**. Знак `=` служит ещё и связкой в
  определениях имён (`type T = …`, `cond C = …`, `start Main = …`).
  → [«Выражения»](book/src/05-expressions/index.typ)
- **Такт — шаг логики автомата, а не единица времени.** Частота тактирования
  произвольна; физические величины приходят с датчиков, а не считаются тактами.
  Вход в стартовое состояние **не расходует такт**: тело стартового состояния
  исполняется на такте 1. → [«Модель исполнения»](book/src/11-execution/index.typ)
- **Симулятор — эталон поведения.** Все цели генерации обязаны вести себя так
  же; потактовые сверки прогоняют трассы симулятора против порождённого кода.
  → [«Цели генерации»](book/src/14-targets/index.typ),
  [«Симуляция»](book/src/15-simulation/index.typ)
- **Переполнение целых нормировано.** Беззнаковое — обёртка `mod 2ⁿ` одинаково у
  эталона и всех целей; знаковое — **ошибка программы**.
  → [«Типы»](book/src/03-types/index.typ)
- **Диагностика вместо тишины.** Неопределённый случай даёт код (`SE-…`, `SIM-…`,
  `ST-…`, `SV-…`, `RS-…`), а не молчаливое умолчание.
  → [«Диагностика»](book/src/16-diagnostics/index.typ),
  [приложение «Ошибки и предупреждения»](book/src/appendix-errors/index.typ)

## 6. Примеры

Корпус примеров живёт в двух каталогах и делится по роли:

- `examples/*.takt` — **прикладные модели** (штабелятор, лифт, регулятор). Их
  гоняют проверки предкоммита: компиляция всеми целями, потактовые сверки с
  эталоном, снимки порождённого кода, прогон сценариев.
- `examples/language/*.takt` — **примеры языка**: объявления, выражения,
  управление, свойства и время, композиция и подключение. Они показывают
  конструкции, часть которых восемью целями не переводится по существу
  (вставка `assembly`, LTL-формулы, обращение к ячейке `#АДРЕС`), поэтому
  трансляцией не проверяются — но обязаны разбираться и быть в каноне
  форматтера.

Покрытие конструкций языка примерами считается машинно и не может падать:
непокрытая конструкция роняет прогон, называя её поимённо. Областей счёта три —
корпус `examples/` целиком, подкаталог примеров языка `examples/language/` и
примеры документа `book/src/**`; у каждой свой список узаконенного долга.

### Минимальный конечный автомат

```lam
model Minimal {
    start Idle;
    state Active;
    state Done;
}

start Main = Minimal;
```

### Светофор с таймером

```lam
type u8 = [bit;8];

model TrafficLight {
    var timer: u8 := 0;

    start Red {
        enter  { timer := 0; }
        always { timer := timer + 1; }
        ref Green: timer = 255;
    }

    state Green {
        enter  { timer := 0; }
        always { timer := timer + 1; }
        ref Yellow: timer = 100;
    }

    state Yellow {
        enter  { timer := 0; }
        always { timer := timer + 1; }
        ref Red: timer = 50;
    }
}

start Entry = TrafficLight;
```

### Кнопка и светодиод (направленные порты, внешние функции)

```lam
type u8 = [bit;8];

extern fn debug(msg: u8);

fn toggle(val: u8) -> u8 { return ~val; }

model ButtonLED {
    var state: u8 := 0;

    in  BTN: bit;   // входной порт — кнопка
    out LED: u8;    // выходной порт — светодиод

    start Idle {
        ref Active: BTN = 1;
    }

    state Active {
        enter {
            state := toggle(state);
            LED   := state;
            debug(state);
        }
        next Idle;
    }
}

start M = ButtonLED;
```

### Управление лифтом (параллельная композиция)

```lam
type u8 = [bit;8];

enum Command { Up, Down, Stop }

var command: Command := Stop;

model Motor {
    start Idle {
        ref Up:   command = Up;
        ref Down: command = Down;
        enter { elevator_motor_stop := true; }
    }
    state Up {
        ref Stop: command = Stop | elevator_motor_sensor_u;
        always   { elevator_motor_up := true; }
    }
    state Down {
        ref Stop: command = Stop | elevator_motor_sensor_d;
        always   { elevator_motor_down := true; }
    }
    state Stop {
        next Idle;
        always { elevator_motor_stop := true; }
    }

    out elevator_motor_up:      bit;
    out elevator_motor_down:    bit;
    out elevator_motor_stop:    bit;
    in  elevator_motor_sensor_u: bit;
    in  elevator_motor_sensor_d: bit;
}

start Main = Cabin | Motor;   // параллельный запуск
```

### Пример с ошибкой и исправлением

```lam
// ОШИБКА: нет начального состояния
model Bad {
    state A;
    state B;
}

// ИСПРАВЛЕНИЕ: добавляем start
model Good {
    start A;   // ← начальное состояние обязательно
    state B;
}
```

### Композиция моделей

```lam
model Init    { start S; }
model Startup { start S; }
model Run     { start S; }
model Halt    { start S; }

start System = (Init + Startup) + (Run | Halt);
```

### Симуляция: вычисления в теле блока

Симулятор (`takt-sim`) исполняет тела `enter`/`exit`/`always` и вычисляет
условия переходов. Значения приводятся к **объявленному типу** переменной при
записи — как в C.

Состояние, объявленное **реализацией** (`state P = A + B { next Done; }`),
симулятор исполняет как композицию: шаги тикаются по очереди, а переход `next`
берётся только по завершении последнего — на том же такте, что и в порождённом
C. Потактовое совпадение симулятора, цели `c` и цели `sv` на обеих формах
композиции проверяется тройной сверкой (`takt-sim/tests/conformance_sv_tests.rs`).

```lam
var temperature: u8 := 0;

start Idle {
    always {
        var delta: u8 := 1;          // локальная переменная блока
        temperature := temperature + delta;
    }
    ref Heating: temperature > 10;   // переход по вычисленному значению
}

state Heating {
    enter { temperature := temperature + 5; }
}
```

Прогон: `temperature` растёт на 1 за такт; на 11-м такте условие `> 10`
выполняется, происходит переход в `Heating`, и его `enter` добавляет ещё 5.

### Проектирование состояний: состояние обязано удерживать управление

Частая ошибка проектирования — написать «шаг работы» там, где нужно «состояние
работы». Условия рёбер проверяются **каждый такт**, поэтому ребро, истинное сразу
после входа, выпускает управление раньше, чем состояние сделало работу.

**Контрпример** — охлаждение снимает 3 градуса за такт, а выйти можно при любой
положительной температуре:

```lam
start Cooling {
    always {
        for var i: u8 := 0; i < 3; i := i + 1 {
            if temperature > 0 { temperature := temperature - 1; }
        }
    }
    ref Done: temperature <= 0;   // мертво: сюда не попасть никогда
    ref Idle: temperature > 0;    // сработает на ПЕРВОМ такте: 101 → 98 > 0
}
```

Войдя со 101, модель уходит на первом же такте — охладив на 3 градуса из 101.
`Done` недостижим **при любом нагреве**: попасть в него можно, лишь войдя в
`Cooling` уже охлаждённым.

**Пример** — выход только по завершении работы; куда идти дальше, решает
отдельное условие:

```lam
cond Cooled = temperature = 0;
cond CyclesDone = count >= MAX_COUNT;

start Cooling {
    always {
        for var i: u8 := 0; i < 3; i := i + 1 {
            if temperature > 0 { temperature := temperature - 1; }
        }
    }
    ref Done: Cooled & CyclesDone;
    ref Idle: Cooled & !CyclesDone;
}
```

Приём: условия выхода — **непересекающиеся и покрывающие**, и оба требуют
`Cooled`. Состояние удерживает управление, пока не выполнит работу.

Оба фрагмента проверены прогоном (`takt-sim/tests/data/scenario/`), а
`examples/comprehensive.takt` построен на этом приёме: его сценарий
`Idle → Heating → Cooling → … → Done` **исполняется** и проверяется
достижимости — каждый пример каталога обязан иметь либо контракт сценария, либо
объявленное исключение с причиной.

**Усечение по типу** совпадает с поведением C (проверяется автоматической
сверкой с кодом, порождённым `taktc -t c`):

```lam
var x: u8 := 0;

start Idle {
    always {
        x := 255;
        x := x + 1;   // → 0   (обёртка mod 2⁸, как uint8_t в C)
        x := 300;     // → 44  (300 mod 256)
        x := 1 << 8;  // → 0   (продвижение до int, затем усечение при записи)
    }
}
```

### Симуляция: вызов функции и сравнение с вариантом `enum`

```lam
enum Mode { Auto = 0, Manual = 1 }

var mode: Mode := Manual;
var eta:  u8   := 0;

fn chebyshev(a: u8, b: u8, c: u8) -> u8 {
    var t: u8 := 0;
    t := a;
    if b > t { t := b; }
    if c > t { t := c; }
    return t;
}

start Idle {
    always { eta := chebyshev(5, 3, 7); }   // → 7 (метрика Чебышёва)
    ref Active: mode = Manual;              // сравнение с вариантом enum
}

state Active {
}
```

Примеры выше соответствуют фикстурам `takt-sim/tests/data/eval/` и покрыты
интеграционными тестами (`takt-sim/tests/eval_tests.rs`), поэтому не могут
разойтись с реальным поведением.

### Где ошибка: `файл:строка:колонка`

Диагностика с позицией в исходнике печатается в формате `rustc`/`gcc` — он
машиночитаем и кликабелен в редакторах:

```text
$ taktc compile -t c -I lib main.takt
lib/badsem.takt:4:18: Ошибка компиляции [SE-002]: Ссылка 'Nowhere' не найдена
```

Назван **тот файл, где ошибка**, а не тот, что компилировали: ошибку внутри
импортированной библиотеки чинить нужно в библиотеке. При вложенном импорте
(`main → lib → deep`) назван самый внутренний файл — настоящий виновник.

Нумерация строк и колонок — с единицы; колонка считается в символах. Диагностика
без позиции в исходнике (например, ошибка кодогенерации) печатается **без**
префикса: выдуманные координаты отправили бы искать ошибку не туда.

### Сколько ошибок за прогон

Компилятор сообщает **все** ошибки, которые может назвать за один разбор, а не
первую:

```text
$ taktc compile -t c broken.takt
broken.takt:2:18: Ошибка компиляции [SY-002]: нераспознанный токен ';' …
broken.takt:4:19: Ошибка компиляции [SY-002]: нераспознанный токен ';' …
broken.takt:7:1:  Ошибка компиляции [SY-002]: нераспознанный токен '}' …
```

Сообщения идут **сверху вниз по файлу** и не повторяются. Языковой сервер
подчёркивает ровно тот же набор — обе среды спрашивают одну функцию, а не решают
каждая по-своему.

Есть граница, и она осознанная: ошибки **построения** дерева (разрешение имён,
типы, композиция) по-прежнему выдаются по одной. После такой ошибки дерево
неполно, и продолжать разбор значило бы сообщать о следствиях вместо причин.

Зато выдаются они **на любой глубине вложенности**: тело `if`, `else`, цикла и
ветви `match` проверяется так же, как верхний уровень блока. Прежде ошибка
внутри вложенного тела **глоталась**, и оператор молча выпадал из порождённого
кода — программа принималась, но исполняла не то, что написано. Теперь опечатка
внутри трижды вложенного цикла даёт ту же диагностику, что и в первой строке
блока; заодно на операторах заработал предел вложенности (`SE-062`).
Ошибки же **проверок** (несколько начальных состояний, недопустимое значение,
границы массива и т. п.) идут по готовому дереву и высказываются все, включая
вложенные модели.

Симулятор печатает позицию в том же формате — и это **одна и та же** функция, а
не договорённость: формат позиции задан один раз для всех инструментов.

```text
$ simulation -I lib main.takt --steps 3
Ошибка: lib/badsem.takt:4:18: [SE-002] Ссылка 'Nowhere' не найдена
```

Ошибки разбора симулятор показывает **все** сразу (`taktc` — первую): каждая со
своей позицией.

**`CC-018`: непереводимое условие — ошибка, а не мёртвый автомат.** Если условие
`ref`-перехода не транслируется в C, компиляция **прекращается** с указанием
целевого состояния, позиции `ref` в исходнике и исходной причины:

```text
Ошибка компиляции [CC-018]: условный переход в состояние 'Work' не переводится
в C: BitAccess на float-порт не поддерживается в условии
  примечание: причина [CC-001]: BitAccess на float-порт не поддерживается в условии
```

Прежде такой переход **молча** заменялся комментарием: `taktc` печатал
«Скомпилировано» и завершался с кодом `0`, а порождённый C собирался без
замечаний — но автомат терял ребро. Ошибка ломает ровно те сборки, которые были
сломаны и раньше, просто незаметно.

#### Условие по состоянию другой модели: `S(Модель) = Состояние`

`S(Модель)` — встроенная функция: **текущее состояние** модели. В C переводится
сравнением поля состояния в порождённой структуре:

```lam
model Pong {
    start Go {
        ref Stop: S(Ping) = Done;   // ждём, пока Ping не окажется в Done
    }
    state Stop;
}
```

```c
if (main->entry.ping0.state == SREF_PING_DONE) { … }
```

База пути зависит от родства: своя под-модель адресуется через свою структуру
(`model->…`), а модель-сестра — от корня (`main->…`), потому что корневая
структура владеет всеми под-моделями по значению. Работает и `!=`.

Имя состояния ищется **в модели-аргументе**, а не в той, где записано условие:
`S(Ping) = Done` — это `Done` **модели `Ping`**. Несуществующее состояние даёт
`SE-033` на стадии семантики.

**Скобки прозрачны**: `(S(Ping)) = Done`, `S((Ping)) = Done` и
`S(Ping) = (Done)` (любая вложенность) дают тот же результат, что бесскобочная
форма, — семантика канонизирует их в единой воронке разбора условий. Прежде они
отвергались с `SE-025`.

### Ошибки симуляции (SIM)

умолчанию и не «пропускает» невычислимое молча**: любая из этих ошибок
останавливает прогон и даёт **ненулевой код возврата**.

| Код     | Описание                                                            |
|---------|---------------------------------------------------------------------|
| SIM-001 | Деление или остаток на ноль                                         |
| SIM-002 | Сдвиг на отрицательное число или ≥ 64 бит                           |
| SIM-003 | Значение не помещается в знаковый тип назначения                    |
| SIM-004 | Переполнение внутреннего 64-битного представления                   |
| SIM-005 | Операция не определена для операндов таких типов                    |
| SIM-006 | Значение нельзя привести к типу назначения                          |
| SIM-007 | Тип не поддерживается симулятором (например, структуры)             |
| SIM-008 | Не удалось разобрать вещественный литерал                           |
| SIM-009 | Переменная не найдена                                               |
| SIM-010 | Ошибка доступа к массиву (не массив, нецелый индекс, выход за границы) |
| SIM-011 | Ошибка доступа к биту (не целое, номер бита вне 0..64)              |
| SIM-013 | Сравнение с состоянием или моделью пока не поддерживается           |
| SIM-014 | Конструкция не поддерживается симулятором (строки и др.)            |
| SIM-015 | Пустое выражение/условие не может быть вычислено                    |
| SIM-016 | Неразрешённый узел не может быть вычислен                           |
| SIM-017 | Оператор пока не поддерживается симулятором                         |
| SIM-018 | Превышен предел итераций цикла (100 000)                            |
| SIM-019 | Внешняя функция без тела: симуляция значения невозможна             |
| SIM-020 | Встроенная функция пока не поддерживается симулятором               |
| SIM-021 | Неверное число аргументов при вызове функции                        |
| SIM-022 | Превышена глубина рекурсии (256)                                    |
| SIM-023 | Функция не вернула значение                                         |
| SIM-024 | `break`/`continue` вне цикла                                        |
| SIM-025 | Нарушен инвариант / Guard-формула (assert языка Takt)                |
| SIM-030 | Порт с таким именем не найден в сценарии симуляции                   |
| SIM-031 | Имя порта в сценарии двусмысленно — нужна форма `Модель::порт`       |
| SIM-032 | Длина позиционного массива не совпадает с числом портов (предупреждение) |

**Контрпример — деление на ноль:**

```lam
var d: u8 := 0;
var x: u8 := 1;

start Idle {
    always { x := 10 / d; }
}
```

```
ОШИБКА вычисления на шаге 1: деление на ноль (SIM-001)
Симуляция остановлена: результат недостоверен.
```

**Контрпример — внешняя функция со значением:** у `extern fn` нет тела, поэтому
вычислить результат нельзя; симулятор отказывает, а не подставляет ноль.

```lam
extern fn calc() -> u8;

var x: u8 := 0;

start Idle {
    always { x := calc(); }
}
```

```
ОШИБКА вычисления на шаге 1: внешняя функция 'calc' не имеет тела:
симуляция значения невозможна (SIM-019)
```

> `extern fn` **без** возвращаемого значения (процедура) — не ошибка: вызов
> считается no-op, поскольку в симуляции нет платформенного слоя.

### Структуры в симуляторе

Структуры **представимы и исполняются**: `var p: Point := {1, 2}` наблюдается как
структура (`Value::Struct`, объявленный порядок полей), `p.x` читается, `p.x := 7`
пишется точечно (не трогая `p.y`), `p.y := 300` при `y: u8` усекается до `44` —
как в порождённом C (сверено `cc`). Копия `q := p` разрешена; **сравнение
структур `p = q` не определено** (ошибка `SIM-005`) — согласование с C, который
запрещает `==` на структурах. Диагностики вместо тихой порчи: неизвестное поле
(`SIM-027`), `p.0` у структуры (`SIM-029`), поле у не-структуры (`SIM-012`),
арность `{…}` (`SIM-026`), несовпадение типа при `q := p` (`SIM-028`).

Ограничения: структура **без** инициализатора (`var p: Point;`) получает нулевые
поля; загрузка структур через `--load-state` не реализована (сохранение — да).

### Файл сценария симуляции

Сценарий — массив шагов; шаг подаёт значения входных портов и, при желании,
проверяет результат такта (`guard`). Порты называются **по имени**:

```json
[
  {
    "in_ports": {"floor_sensor_f2_bottom": 1},
    "guard": {"out": {"door_open": 1}, "vars": {"current_floor": 2}}
  },
  { "guard": {"vars": {"current_floor": 2}} }
]
```

Перечисляются только **меняющиеся** порты: значения удерживаются между тактами,
как уровень на реальном входе. Длину прогона задаёт `-n`, а сценарий — входы:
когда его шаги кончились, прогон идёт дальше с последними поданными значениями, поэтому выдержку в 180 000 тактов не приходится расписывать по
шагам. Без `-n` длину задаёт сам сценарий. Одноимённые порты разных под-моделей уточняются
именем модели (`"Cabin::sensor"`). Несуществующее имя — и имя порта не
того направления — дают `SIM-030`, двусмысленное голое имя `SIM-031`: сценарий,
отставший от модели, обязан сказать об этом, а не молчать.

Позиционная форма (массив значений по алфавитному порядку имён) поддерживается
для старых файлов:

```json
[{ "in_ports": [1, 0], "guard": { "out": [0] } }]
```

**Она хрупка не только для чтения.** Индекс — это место имени в алфавитном
списке портов, поэтому добавление или переименование порта сдвигает весь массив,
и шаг начинает описывать другое событие — молча. Проба: один
добавленный порт превратил шаг «датчик этажа 2 активен» в «верхний датчик этажа 1
активен», и поймал это только `guard`. Расхождение длины массива с числом портов
даёт предупреждение `SIM-032`.

### Известные ограничения симулятора

- Строки в выражениях не поддерживаются — `SIM-014`.
- Сравнение с состоянием (`S(Ping) = End`) и моделью — `SIM-013`.
- Загрузка **структурных** значений через `--load-state` не реализована (скаляры,
  массивы и порты сохраняются/загружаются штатно).

> Потактовые трассы симулятора и порождённого C **совпадают с такта 1** (фича
> 0033 выровняла вход в стартовое состояние — см. §5 «Семантика первого такта»);
> прежнее «смещение из-за служебных INIT-тактов» устранено.

### Структура сообщения об ошибке

```
Уровень:  Debug | Info | Warning | Error
Тип:      ParserError | SyntaxError | DeclarationError |
          TypeError | CastError | SemanticError | Warning
Позиция:  файл, строка, столбец (начало и конец)
Заметки:  дополнительный контекст
```

### Типичные ошибки пользователей

- Забытое `start` в модели → SE-011.
- Использование `:=` вместо `=` в условии (`if`, `cond`, `ref`) → присваивание
  вместо сравнения (в большинстве позиций условия — ошибка разбора).
- Запись в `in`-порт или чтение из `out`-порта → ошибка направления.
- Перекрывающиеся условия в `ref` → SE-042, недетерминированный переход.

## 8. Интеграция и реализация

### Конвейер компиляции

```
Исходный файл (.takt)
        │
        ▼
┌─────────────────┐
│   Лексер        │  lexer.rs — токены с позиционной информацией
└────────┬────────┘
         ▼
┌─────────────────┐
│   Парсер        │  LALRPOP (LR(1)) — Абстрактное синтаксическое дерево
└────────┬────────┘
         ▼
┌─────────────────┐
│   Семантический │  7 проходов → семантическое дерево + диагностика
│   анализатор    │
└────────┬────────┘
         ▼
┌─────────────────┐
│   Генератор C   │  c_header.rs (.h) + c_source.rs (.c)
└─────────────────┘
```

**Детерминированная генерация.** Один и тот же `.takt` компилируется в
**байт-в-байт одинаковый** код от прогона к прогону — для всех целей (`c`,
`c-hal`, `plantuml`, `st`, `st-at`, `rust`, `sv`, `sv-mmio`). Порядок эмиссии задаётся **типом контейнера**
(`BTreeMap`, алфавитный порядок), а не привычкой отдельного генератора, поэтому
воспроизводимость получают все цели разом. Это делает возможными
codegen-снапшоты и осмысленный дифф порождённых файлов, а главное —
стабильный **ABI** прошивки: числовые значения `enum` портов и состояний
одинаковы при любой пересборке. Гарантируется проверкой `precheck.sh` (два прогона
на пример × цель → `diff -r`).

### Семантические проходы

| № | Проход            | Описание                                               |
|---|-------------------|--------------------------------------------------------|
| 0 | Скелет            | Извлечение имён моделей/состояний, загрузка импортов   |
| 1 | Композиция        | Разрешение составных состояний (`+ M1 M2`, `M1 \| M2`) |
| 2 | Выражения         | Разрешение переменных, вывод типов, порты              |
| 3 | Условия (`cond`)  | Разрешение именованных условий                         |
| 4 | Именованные блоки | Разрешение `enter`/`exit`/`always`                     |
| 5 | Функции           | Разрешение тел функций                                 |
| 6 | Переходы (`ref`)  | Замена `Condition::Unresolved` на разрешённые условия  |

### Запуск компилятора

```sh
# Компиляция в C
taktc compile --target c input.takt -o output/

# Результат:
# output/input.h  — заголовочный файл
# output/input.c  — реализация

# Способ сборки параметризованных моделей (по умолчанию — assign)
taktc compile --target c --parameters=specialize input.takt -o output/

# Форма автомата в порождённом коде (по умолчанию — switch)
taktc compile --target c --fsm=table input.takt -o output/
```

#### Форма автомата: `switch` или таблица переходов

Флаг **`--fsm=switch|table`** (**все** цели, кроме `plantuml`: диаграмма
переходов и есть отношение переходов, второй его формы у неё быть не может)
выбирает, как цель печатает автомат. Умолчание `switch` — переход стоит
**внутри** ветви `case`, рядом с блоками `always`. Форма `table` печатает
**отношение переходов данными**: на каждую модель — таблица строк «откуда →
страж → действие → куда» и диспетчер, который её просматривает:

```c
/* цель c: строка несёт указатели на функцию-страж и функцию-действие */
static const Counter_Transition COUNTER_TRANSITIONS[] = {
    { COUNTER_LOW,  Counter_guard_0, Counter_action_0, COUNTER_HIGH },
    { COUNTER_HIGH, Counter_guard_1, Counter_action_1, COUNTER_LOW  },
};
```

**Идиома принадлежит целевому языку** — это не вкус, а свойство языка:

| Цель | Строки | Страж и действие |
|------|--------|------------------|
| `c`, `c-hal` | `static const` массив структур | указатели на функции |
| `rust` | `static` массив структур | **номер** строки + `match` в методе: тип стража зависит от параметра метода (`tick<H: Hal>`), и указатель на функцию в `static` невыразим |
| `st`, `st-at` | четыре константных массива (`TAKT_TRANS_FROM`, `…_GUARD`, `…_ACTION`, `…_TO`) | номер + `CASE`: указателей на функции в IEC 61131-3 нет вовсе, а массив структур в `VAR CONSTANT` MatIEC не принимает |
| `sv`, `sv-mmio` | `localparam`-векторы `…_TRANS_FROM`/`…_TRANS_TO` с частичным выбором `[i*W +: W]` | `case (i)` внутри `for` со статической границей: цикл разворачивается при элаборации, давая ту же приоритетную цепочку. Распакованный и упакованный двумерный массив `verilator` принимает, а `yosys` отвергает — форма выбрана **обоими** инструментами |

Форма учебная и промышленная разом: таблицу видно глазами (её можно вычитать,
сверить со спецификацией, распечатать), а поведение у обеих форм **одно** —
диспетчер берёт первую строку с совпавшим состоянием и истинным стражем, то есть
тот же порядок, в котором цель печатает рёбра формой `switch`. Тождественность
контролирует потактовая сверка эталона с обеими прошивками, а не факт компиляции.

**Композиция выражается таблицей вся.** Реализация одной моделью (`= M`, включая
корневую обёртку), параллельная (`A | B`) и последовательная (`A + B`) — у
каждой завершение есть предикат: `M_is_done(…)`, конъюнкция готовностей ветвей и
«цепочка на последнем шаге, и он завершён» соответственно. Машина шагов цепочки
при этом остаётся в теле такта: она ведёт переходы **внутри** состояния, а
таблица — выход **наружу**. Прочие цели флага не принимают: `--fsm=table` с
целью `st` — ошибка CLI с перечислением поддерживающих целей, а не молчаливый
`switch`.

**Подстановка тела функции — `--inline=off|auto` и атрибуты объявления.**
Перед `fn` можно написать атрибут: `[inline]` требует подставить тело в каждое
место вызова, `[noinline]` — оставить вызов вызовом. Атрибут действует **всегда**
и на **все** цели: подстановку делает семантика, печатники о ней не знают.
Ключ `--inline=auto` добавляет эвристику — тело не длиннее пяти операторов и
один…три вызова; умолчание `off`, то есть вывод корпуса прежний байт-в-байт.
Подстановка меняет форму, а не поведение (контроль — потактовая сверка эталона с
прошивкой), и выражается она для тела с **единственным хвостовым** `return`:
иначе под явным атрибутом приходит `SE-128`, а под эвристикой вызов остаётся.
Адресат правила — цель `st` (вызов `FUNCTION` в ПЛК остаётся вызовом) и
отладочные сборки `c`/`rust`, где инлайна компилятора нет.

Флаг `--parameters=assign|specialize` выбирает **форму** порождённого кода для
моделей с параметрами: `assign` держит одну модель и присваивает значения полям
экземпляров, `specialize` порождает копию модели на каждую различную настройку
(тогда неизменяемый параметр становится константой). Поведение программы от
выбора не зависит; семантику параметров описывает раздел документа
[«Модели и состояния»](book/src/04-models-states/index.typ).

#### Отображение типов Takt в типы C

| Тип Takt | Тип C | Пример объявления |
|---------|-------|-------------------|
| `bit` | `uint8_t` | `var fl: bit;` → `uint8_t fl;` |
| `bool` | `bool` | `var b: bool;` → `bool b;` |
| `u8`/`u16`/`u32`/`u64` (`[bit;N]`) | `uint{N}_t` | `var b: u8;` → `uint8_t b;` |
| `i8`/`i16`/`i32`/`i64` | `int{N}_t` | `var n: i16;` → `int16_t n;` |
| `float` | `double` (по умолчанию) | `var r: float;` → `double r;` |
| `float` при `--float-width=32` | `float` | `var r: float;` → `float r;` |
| `[T;N]`, где `T` ≠ `bit` | `T name[N]` | `var data: [u8;4];` → `uint8_t data[4];` |
| перечисление | `uint{N}_t` по максимуму варианта | `enum Mode {…}` → `uint8_t mode;` |
| структура | одноимённая `struct` | `var p: Point;` → `Point p;` |
| `unit` | `void` | тип возврата процедуры |

**Бит-вектор — упакованный вектор, не массив**. `[bit;N]` — это
способ записать целое из N бит: при **N ≤ 64** в C он **скаляр** `uint{W}_t`, где
`W` — ширина, округлённая вверх до 8/16/32/64 (`[bit;8]` ≡ `u8` → `uint8_t`,
`[bit;12]` → `uint16_t`). При **N > 64** — массив слов `uint64_t[⌈N/64⌉]`
(`[bit;128]` → `uint64_t[2]`): типа `uint128_t` в C нет, поэтому широкий
бит-вектор упаковывается в слова, а не отвергается. Настоящий массив — `[T;N]` с
**любым другим** элементом (`T` ≠ `bit`); в C он объявляется `T name[N]`.

**`float` — 8 байт по умолчанию.** `double` совпадает по точности с симулятором
(f64), поэтому проверка модели до синтеза сходится с прошивкой. Для платформ,
где 8-байтное чтение недопустимо, — `--float-width=32`; в цели `c-hal` это
меняет и ширину доступа к регистру порта (8 → 4 байта).

**Инициализация массива — только агрегатом.** Массив в C не присваивается,
поэтому `_init` заполняет его поэлементно:

```lam
var arr: [u8;4] := {0, 0, 0, 0};   // → model->arr[0] = 0; … model->arr[3] = 0;
```

Скалярный инициализатор массива (`var arr: [u8;4] := 0;`) цель `c` **отвергает**
(`CC-017`): язык не определяет, значит ли это «обнулить весь массив» или
«записать в первый элемент».

### Генерация Structured Text (IEC 61131-3)

Третья цель наряду с `c` и `plantuml` — **ST**, стандартный язык ПЛК. Модель Takt
ложится на него естественно: модель → `FUNCTION_BLOCK`, состояния → `CASE state OF`.

```sh
# Библиотека блоков: порты — входы/выходы FUNCTION_BLOCK, адреса не эмитятся
taktc compile -t st examples/stacker.takt -o out/

# Программа для ПЛК целиком: порты размещены по адресам
taktc compile -t st-at --address-map examples/elevator.plc.map examples/elevator.takt -o out/
```

**Цели `st` и `st-at` асимметричны — и это не косметика:**

| | `st` | `st-at` |
|---|---|---|
| Что порождает | **библиотеку блоков** | **программу для ПЛК целиком** |
| Порты | `VAR_INPUT` / `VAR_OUTPUT` блока | `VAR_GLOBAL … AT %IX256.0`; блоки видят их через `VAR_EXTERNAL` |
| Обёртка | не нужна | **обязательна**: `CONFIGURATION`/`RESOURCE`/`TASK`/`PROGRAM` |
| `--address-map` | игнорируется | потребляется |

Асимметрия навязана стандартом: `VAR_GLOBAL` **вне** `CONFIGURATION` недопустим,
тогда как отдельный `FUNCTION_BLOCK` принимается сам по себе.

#### Отображение

| Takt | ST |
|---|---|
| `model M` | `FUNCTION_BLOCK M` |
| состояния | `CASE state OF`; `INIT` — ветвь `0` (холодный старт ПЛК обнуляет `VAR`) |
| `ref T: cond;` (несколько) | `IF … ELSIF …` — порядок объявления сохраняется |
| `always` / `enter` / `exit` | тело ветви / инлайн в переход / перед `enter` цели |
| `M1 \| M2` | экземпляры под-блоков, последовательные вызовы, завершение по конъюнкции `is_done` |
| `M1 + M2` | вложенный `CASE` по счётчику шагов |
| `bit`/`bool` → `BOOL`, `u8`→`USINT`, `i16`→`INT`, `float`→**`LREAL`** | `INT` в IEC — **16-битный** |
| `[u8; 4]` | `ARRAY [0..3] OF USINT` |
| `enum` | целое + именованные константы `<Enum>_<Вариант>` |
| `fn` | `FUNCTION`; возврат — присваивание **имени функции** |

#### Чего ожидать: ограничения IEC 61131-3

Модель Takt опирается на общий доступ к состоянию, которого в IEC нет ни у
функций, ни между POU. Всё разделяемое выражается **явной передачей**, поэтому
порождённый ST многословнее исходника:

- **Перечисления** не становятся перечислимым типом: явные значения вариантов —
  фича 3-й редакции, широко не поддержанная. Вместо этого целое + константы.
  В **телах** литерал печатается **по целевому типу** (как в `rust`/`sv`):
  `command := Stop` даёт `command := Command_Stop` (а не `:= 2`), а `flag := 0`
  при `flag : BOOL` — `flag := FALSE`. Так вывод согласован с объявлениями;
  значение без соответствующего варианта печатается числом (не догадываться).
- **Битового доступа `x.0` нет**: разворачивается в маску
  `(USINT_TO_BYTE(x) AND 16#01) <> 16#00`.
- **Побитовые операции** определены на битовых строках, а не на числах:
  `n & m` → `BYTE_TO_USINT(USINT_TO_BYTE(n) AND USINT_TO_BYTE(m))`.
- **`extern fn` невыразим**: `FUNCTION` обязана иметь тело, не может быть без
  параметров и не может возвращать `VOID`. Эмитится заглушка + предупреждение
  **`ST-009`** — в ПЛК она **ничего не сделает**, тело надо написать вручную.
- **LTL-формулы** не транслируются → предупреждение **`ST-010`**.

#### Внешняя карта адресов

`elevator.takt` написан под МК-адресацию (`0x10000000`) — для ПЛК это абсурдные
локации. Модель при этом **корректна** (для целей `c`/`c-hal`), поэтому её не
правят: ПЛК-локации держат отдельно, во внешней карте
([`examples/elevator.plc.map`](examples/elevator.plc.map)):

```
// Входы → %IX
sensors_1 = 0x0;      // → %IB0 вместо %IB268435456
```

Приоритет источников: inline `:=` < оператор `address` < внешняя карта. Наложение
поверх inline даёт предупреждение `SE-050` на каждый порт — по замыслу.

#### Символьные адреса и `--define` (платформенные символы)

Выражение адреса — и у оператора `address`, и у inline-инициализатора — не
обязано быть литералом: оно **вычисляется** при сборке. В нём допустимы имена и
целочисленная арифметика (`+ - * / % << >> & | ^ ~`, унарные `+`/`-`, скобки):

```lam
const BTN_ADDR: u32 := 0x00200000;   // дефолт платформы, задокументирован в модели

in  BTN: bit;
out LED: bit;

address BTN = BTN_ADDR;              // символ
address LED = BTN_ADDR + 4;          // арифметика: модель описывает раскладку
```

Имя берётся **сначала** из `--define`, затем из `const` модели. Так один `.takt`
живёт на всех ревизиях: базу даёт платформа, раскладку — модель.

```sh
taktc compile -t c-hal -D BTN_ADDR=0x00300000 model.takt -o build/
taktc compile -t c-hal -DBASE=0x00200000 --address-map stm32.map model.takt -o build/
```

Три формы флага равнозначны и повторяемы: `--define N=V`, `-D N=V`, `-DN=V`.
Значение — литерал в **той же** грамматике, что запись внешней карты:
`0x…`/десятичное с необязательным `:бит` (`-D PIN=0x00200000:3`). Арифметика
остаётся **в модели**, где её видит ревьюер и форматтер, а не в командной строке.

**Границы (важно).**

- **Define виден только выражениям адреса.** Логика автомата от флагов сборки не
  зависит: `-D LIMIT=99` **не** изменит `ref Stop: cnt = LIMIT;` — там `const`
  сохраняет своё значение. Иначе флаг сборки мог бы молча переписать
  верифицированную модель.
- **Define — не источник адреса.** Приоритет остаётся прежним: inline `:=` <
  `address` < внешняя карта. `-D BTN=0x…` при отсутствии inline/`address`/карты
  адреса **не создаст** (даст `SE-052` и `DF-004`).
- **Адрес потребляет только `-t c-hal`** (и `st-at`). Вывод цели `c` от `-D` не
  зависит вовсе.

**Контрпримеры.**

```lam
const BTN_ADDR: u32 := 0x00200000;
address BTN = BTN_ADDR;      // + `-D BTN_ADDR=0x00300000`
// → адрес 0x00300000 (define главнее), предупреждение SE-053: перекрытие заметно

address LED = NOWHERE;       // → SE-054: символ не определён — назван по имени
address LED = x;             // x — var  → SE-055: адрес обязан быть известен при сборке
const A: u32 := B;
const B: u32 := A;
address LED = A;             // → SE-055: циклическая ссылка (не зависание)
```

| Код | Уровень | Условие |
|---|---|---|
| `SE-053` | предупреждение | define перекрыл одноимённую `const` в выражении адреса |
| `SE-054` | ошибка в `c-hal`/`st-at`, иначе предупреждение | неопределённый символ в выражении адреса |
| `SE-055` | ошибка в `c-hal`/`st-at`, иначе предупреждение | выражение не сворачивается в константу (`var`/порт/цикл) |
| `DF-001` | ошибка | негодный формат `--define` (нет `=`, негодное имя) |
| `DF-002` | ошибка | негодный литерал значения define |
| `DF-003` | ошибка | повторный `--define` для одного имени |
| `DF-004` | предупреждение | define не использован ни одним выражением адреса |

> До   выражение адреса
> принимало **только литералы**: `address BTN = BTN_ADDR;` и
> `address BTN = 0x100000 + 4;` **молча теряли адрес**, а пользователь получал
> `SE-052` «порт не имеет адреса» — сообщение о следствии вместо причины.

#### Экспорт карты наружу — `taktc address-map`

Разрешённую карту адресов можно **выгрузить** для сторонних инструментов
(генераторы HAL, отладчики, платформенные скрипты) — подкомандой
`taktc address-map`. Экспортируется **фактически разрешённая** карта: та же, что
потребляет `-t c-hal`, с учётом приоритета источников.

```sh
taktc address-map model.takt                                  # формат map в stdout
taktc address-map --emit json --address-map plat.map model.takt -o ports.json
```

Два формата:

| `--emit` | Назначение |
|---|---|
| `map` (умолчание) | `.ld`-подобный формат — **тот же**, что читает `--address-map`. Даёт **круговой рейс** `export → import → export` байт-в-байт: выгрузку можно подать обратно как `--address-map`. |
| `json` | Машиночитаемая выгрузка: на порт — имя, тип, направление, адрес (hex-строка), бит, источник; плюс `format`/`format_version`. Перечень источников **открыт** (потребитель обязан терпеть незнакомое значение). |

Выгрузка `map` для модели с тремя источниками адреса (inline / `address` /
внешняя карта):

```text
BTN = 0x40000000;
LED = 0x00200004;
SW = 0x00300000:3;
```

Правила выгрузки:

- **Порт без адреса опускается** в `map` (а `0x0` **не** подставляется — в
  выгрузке он неотличим от настоящего адреса); в `json` — явная пометка
  `"address": null`.
- **`SE-052`** (достижимый порт без адреса) **обрывает** экспорт (ненулевой код)
  — неполную карту наружу не отдаём, как и при сборке `c-hal`.
- Предупреждения (`SE-050` наложение, `SE-051` висячая запись) идут в **stderr**;
  **stdout** — чистая выгрузка (её целиком разбирает `--address-map`).
- **CMSIS-SVD не поставляется**: `--emit svd` → ошибка. У Takt нет данных, которых
  требует его схема (peripherals, reset-значения, достоверная разрядность), а
  правдоподобный-но-неверный SVD для отладчика хуже его отсутствия.

Одноимённые порты разных под-моделей в **выгрузке** (`.ld`/`json`) схлопываются
по имени — побеждает последний (плоский формат не различает их; круговой рейс
`.ld` требует одной записи на имя). Это **только** ограничение выгрузки: сама
карта адресов квалифицирована моделью, поэтому цель `c-hal` даёт
**каждому** одноимённому порту его собственный адрес (прежде адрес первого молча терялся).

#### Проверка порождённого

Валидность ST доказывает внешний транспилятор **MatIEC `iec2c`** — юнит-тесты
проверяют лишь, что генератор напечатал задуманное. `precheck.sh` прогоняет проверка
по всему корпусу; установка — `scripts/ensure-iec2c.sh` (см. «Необязательные
зависимости»).

> Проверка доказывает, что ST **валиден и компилируется**, но **не** что он ведёт
> себя как модель. Поведенческую эквивалентность даёт только сверка трасс.

### Генерация Rust (профиль `no_std`)

Пятая цель — **`no_std` Rust**: прошивка микроконтроллера. Ниша та же, что у
цели `c` (МК, HAL, жёсткое реальное время), поэтому цель обязана отвечать, что
она даёт **сверх** `c`. Ответ не «Rust лучше», а конкретные, зафиксированные в
репозитории дефекты цели `c`, которые здесь не воспроизводятся **by
construction**:

| Дефект цели `c` | В цели `rust` |
|---|---|
| У модели без под-моделей не эмитится typedef корня → порождённый C **не компилируется** | тип корня — обычная `struct`, отдельного объявления не требует |
|: `[u8;4]` → `uint4_t` (типа не существует), `bit` → `int`, `Rational` → `float` ≠ f64 симулятора | `[u8; 4]` → `[u8; 4]`, `bit` → `bool`, `Rational` → `f64` — **точно** |
| `void *userdata` + указатели на функции: типобезопасности нет | `H: Hal` — параметр типа, проверяет компилятор |
| класс дефектов памяти | `#![forbid(unsafe_code)]` в шапке модуля |

```sh
taktc compile -t rust examples/elevator_mini.takt -o out/
# out/elevator_mini.rs
```

**Как подключить.** Порождается **один `.rs`-файл** — `Cargo.toml` генератор не
порождает и им не владеет (имя пакета, версия, edition, зависимости — ваши).
Файл подключается как модуль:

```rust
#![no_std]

#[path = "elevator_mini.rs"]
pub mod elevator_mini;

use elevator_mini::{ElevatorMini, Hal, InBitPort, OutBitPort};

/// Аппаратный слой поверх регистров вашей платы.
pub struct Board {
    inputs: u64,
}

impl Hal for Board {
    fn read_bit(&mut self, port: InBitPort) -> bool {
        (self.inputs >> (port as u8 as u32)) & 1 != 0
    }
    fn write_bit(&mut self, port: OutBitPort, value: bool) {
        let _ = (port, value); // здесь — запись в GPIO
    }
}

pub fn run() {
    let mut model = ElevatorMini::new(Board { inputs: 0 });
    model.init();
    loop {
        model.tick();
        if model.is_done() {
            break;
        }
    }
}
```

> Пример прогнан дословно (`rustc --edition 2021 --crate-type=lib -D warnings`)
> на выводе `examples/generated/rust/elevator_mini.rs`.

**`userdata` исчезает как понятие.** Состояние аппаратного слоя живёт в самом
типе-реализации, поэтому привести его не к тому типу невозможно, а «забыть
проставить колбэк» невозможно **by construction**: без `hal` модель не
конструируется.

**Модель без ввода-вывода конструируется без аргументов** — и тогда рядом с
`new()` печатается `impl Default`. Это не украшение:
`clippy::new_without_default` требует его от любого публичного конструктора без
параметров, и без `Default` порождённый модуль не собрался бы **у вас** под
`-D warnings`. Аргумент у `new` появляется ровно тогда, когда модели
транзитивно нужен HAL — то есть если у неё (или у её под-модели) есть порт либо
`extern fn`.

**Атрибута `#![no_std]` в порождённом файле Нет — и это намеренно.** Он допустим
только в корне крейта; в файле, подключённом через `mod`, он даёт
предупреждение «the `#![no_std]` attribute can only be used at the crate root» —
то есть ломал бы **вашу** сборку под `-D warnings`. `no_std` — свойство крейта, а
не модуля: модуль просто не обращается к `std`, поэтому подключается и в
`no_std`-крейт, и в обычный (проверено). Совместимость доказывает проверка
`precheck.sh`: он кладёт вывод в корень с `#![no_std]` и компилирует.

**Проверочный крейт: `examples/generated/rust/`.** Порождённые примеры собраны в
Cargo-пакет — аналог `CMakeLists.txt` цели `c`. Он **не входит в workspace**
репозитория (своя таблица `[workspace]`): его содержимое перезаписывает `taktc`,
и под `cargo check`/`clippy` корня попадать не должно. Раскладка ровно в два
уровня — в корне порождённое (`elevator.rs`, …), в `src/` рукописное, — потому
что проверка заворачивает **каждый** `.rs` из корня в `#![no_std]`-крейт, а каркас и
`main`-ы печатают, то есть требуют std.

```sh
cargo run --manifest-path examples/generated/rust/Cargo.toml --bin stacker
```

На модель приходится один `main` (`src/bin/<модель>.rs`): он прогоняет автомат на
подставном железе и проверяет наблюдаемое поведение через `assert!` — у
`stacker`, например, приёмку груза и разряд батареи посреди дороги. Это второй
проверка цели, и проверяет он не то же, что первый: `rustc` + `clippy` доказывают,
что вывод **компилируется**, а молча неверная трансляция (перепутанный
приоритет, потерянный переход) компилируется тоже. `precheck.sh` гоняет оба.

**Границы цели** (каждая — диагностика, а не тихий пропуск):

| Код | Когда |
|---|---|
| `RS-004` | имя даёт `Self`/`self` — непредставимо ни как идентификатор, ни как `r#Self` (отдельное правило языка). Прочие ключевые слова спасает регистр (`type` → `Type`) или `r#type` |
| `RS-005` | два имени слипаются после приведения регистра (`floor_sensor` и `FloorSensor`) |
| `RS-011` | конструкция не транслируется (срез массива, `**`, строка вне `debug`) |
| `RS-014` | тип не представим; `RS-015` — `--float-width=32` (цель всегда даёт `f64`) |
| `RS-016` | тип порта не ложится на метод HAL (составной) |
| `RS-018` | чтение выходного порта либо запись во входной |
| `RS-021` | последовательная композиция (`+`) вложена в шаг другой `+` |
| `RS-022` | нужен HAL, но он в этой области недоступен |
| `RS-026` | имя объявления даёт поле, которое цель печатает сама: `state`, `shared`, `hal`, механизм времени, аккумулятор `every`, шаг цепочки, экземпляр под-модели |

**Функции получают состояние модели параметрами.** `fn`, читающая порт или
переменную модели, порождается свободной и получает нужное **параметром**: порт,
`extern fn` и `debug` требуют `hal: &mut H` (он идёт **последним** — иначе
`f(&mut hal, hal.read_u8(…))` заимствовал бы `hal` дважды), переменная модели —
параметр по значению. Нужда считается транзитивно по графу вызовов. В цели `c`
этого нет: там функция берёт `const Model *model` и читает через него всё сразу.

**Под-модель получает общие переменные корня структурой `Shared`.** Такт
под-модели не может взять указатель на корень (`self.cabin.tick(&mut self)` —
двойное заимствование), поэтому общие переменные свёрнуты в `<Root>Shared` и идут
**одним** параметром `&mut Shared` (`hal` — последним). Так арность
такта не зависит от числа общих переменных, и заглушки `#[allow]` в выводе нет.
Модель без разделяемых переменных `Shared` не получает.

Ловушки стандартной библиотеки, как у цели `st` (модель `Concat` ломает вывод),
здесь **нет**: `Box`/`Option`/`String` как имена моделей принимаются — Rust
различает пространство пользователя и прелюдию.

**Карта адресов   не
потребляется**: порты идут через HAL — это аналог режима `c`, а не `c-hal`.
`--address-map` с `-t rust` ничего не разместит. MMIO-режим (`rust-hal`) —
кандидат в расширения. `alloc` не используется: динамических структур в Takt нет.

**Идиоматичный возврат.** Takt всегда пишет `return` явно, а в Rust идиома —
хвостовое выражение (clippy: `return x;` последним оператором это
`needless_return`). Генератор сворачивает завершающий `return x;` в `x`, **включая
завершающий `if/else`**: `if c { return a; } else { return b; }` →
`if c { a } else { b }` (рекурсивно, цепочка `else if` — так же). Сворачивается
только когда сворачиваемы **обе** ветки; `if` без `else` и ранние выходы
сохраняют `return`.

**Проверка.** Порождённый `.rs` обязан приниматься `rustc` **и** `clippy` под
`-D warnings` (`precheck.sh`). Проверка **бесплатен**: инструменты уже являются
зависимостями проекта — в отличие от арбитра ST (`iec2c` собирается из
исходников). Политика `-D warnings` — не поза: она вынудила генератор не эмитить
недостижимые варианты состояний и лишний `hal`, то есть сделала вывод честнее.

> Как и у ST, проверка доказывает, что Rust **компилируется**, но не что он ведёт
> себя как модель. Поведенческую эквивалентность даёт только сверка трасс.

### Генерация SystemVerilog (FPGA/ASIC)

Шестая цель и **первая аппаратная**. У `c`, `st` и `rust` такт модели — итерация
цикла: кто-то зовёт `_tick`. Здесь **такт Takt ≡ фронт тактового сигнала**
`posedge clk`, и это первое, что нужно понять автору модели: код не исполняется —
он **становится схемой**.

```sh
taktc compile -t sv examples/stacker.takt -o out/
# out/stacker.sv — один module на корневую модель
```

#### Служебные порты `clk` и `rst_n`

Модулю нужны два сигнала, которых в языке Takt нет. Их добавляет генератор:

```systemverilog
module stacker (
    input  logic clk,                 // служебный порт цели sv: в .takt его нет
    input  logic rst_n,               // служебный порт цели sv: сброс, активный низкий
    // … далее порты модели: сперва входы, затем выходы
    input  logic [7:0] task_stack_no, // in  task_stack_no: u8
    input  logic task_valid,          // in  task_valid: bit
    output logic cmd_fork,            // out cmd_fork: bit
    output logic is_done              // терминальность модели
);
```

> Показана выборка портов: полный заголовок `stacker.sv` несёт **11 входных
> портов модели и 6 выходных** плюс служебные `clk`/`rst_n` и `is_done`.
> Порядок — служебные, входы, выходы; внутри группы алфавитный (детерминизм).

Заводить `clock`/`reset` в самом языке было бы **ложью для четырёх целей из
пяти**: у прошивки и ПЛК такта как сигнала не существует. Поэтому `clk`/`rst_n` —
имена **цели**, а не ключевые слова языка. Порт модели с таким именем даёт
`SV-007`, и та же модель по-прежнему компилируется в `c`/`st`/`rust`.

#### Сброс несёт стартовое состояние — синтетического `INIT` нет

```systemverilog
always_ff @(posedge clk) begin
    if (!rst_n) begin
        state <= STACKER_STACKER;                       // стартовое состояние
        stacker_lift_controller_state <= STACKER_LIFT_CONTROLLER_LIFT_IDLE;
        cmd_fork <= 0;                                  // enter стартового состояния
    end else begin
        state <= state_next;
        stacker_lift_controller_state <= stacker_lift_controller_state_next;
    end
end
```

**Сдвиг такта равен нулю на любой глубине вложенности — и достаётся даром.** У
цели `c` синтетическое состояние `INIT` стоило по такту на уровень, и его
потребовалось *убирать* правкой.
Здесь его нет вовсе: регистр состояния физически не может «побыть в `INIT`», а
ветвь сброса кладёт стартовые состояния **всех** уровней одним фронтом. Проверено
автоматически против настоящего RTL на глубинах 1, 2 и 3
(`takt-sim/tests/conformance_sv_tests.rs`).

Отсюда единственное требование: **`enter` стартового состояния обязан быть
константным** (`SV-008`) — ветвь сброса синтезируется в цепь сброса триггеров и
выражений не вычисляет. Обход: перенести вычисление в `always` того же состояния
(вход такта не стоит, поведение не изменится). Именованная константа `const`
годится — она становится `localparam`.

#### Автомат: two-process

`always_comb` считает следующее состояние (**блокирующие** присваивания),
`always_ff` защёлкивает (**неблокирующие**). Это решение про семантику, а не про
стиль: тело состояния Takt императивно, и `v := 1; w := v;` обязано дать `w = 1` —
как в симуляторе и в `c`.

Фрагмент порождённого `stacker.sv` (под-модель `LiftController`, приведён
дословно):

```systemverilog
unique case (stacker_lift_controller_state)
    STACKER_LIFT_CONTROLLER_LIFT_IDLE: begin
        if (stacker_lift_request_next) begin
            cmd_fork_next = 1;                    // enter LiftOperating — инлайн
            stacker_lift_controller_state_next = STACKER_LIFT_CONTROLLER_LIFT_OPERATING;
        end
    end
    STACKER_LIFT_CONTROLLER_LIFT_OPERATING: begin
        if (((stacker_lift_request_next && (!stacker_lift_op_next)) && sense_loaded)) begin
            cmd_fork_next  = 0;
            stacker_lift_done_next = 1;
            stacker_lift_controller_state_next = STACKER_LIFT_CONTROLLER_LIFT_DONE;
        end
        else if ((!stacker_lift_request_next)) begin
            cmd_fork_next = 0;
            stacker_lift_controller_state_next = STACKER_LIFT_CONTROLLER_LIFT_IDLE;
        end
    end
endcase
```

Переходы — цепочка `if / else if`: **первый сработавший выигрывает**, как `break`
в C. Порядок рёбер значим.

#### Композиция `M1 | M2`: такт один на всю схему

Здесь преимущество RTL видно прямо. В `c` под-модели тикают **последовательно**,
и такт стоит суммы их работ; в RTL они работают **параллельно**, за один фронт.

Плата — **уплощение**: один `module` на корневую модель, логика под-моделей
инлайнится в общий `always_comb`. Иерархия модулей SV дерево моделей не
повторяет, и это не небрежность. `M1 | M2` в Takt означает «последовательно внутри
такта, в порядке объявления»: модель, идущая позже, видит записи предыдущей **в
том же такте**. Модуль-на-под-модель дал бы **комбинационную петлю** — проверено:
`verilator` отвечает `UNOPTFLAT`. Уплощение разрывает цикл там же, где его
разрывает такт в C. Регистры состояний при этом независимы.

#### Отображение типов

| Takt | C | **SystemVerilog** |
|---|---|---|
| `bit` | `int` — 32 бита на один провод | **`logic`** — один триггер |
| `bool` | `bool` | `logic` |
| `u8` / `i16` | `uint8_t` / `int16_t` | `logic [7:0]` / `logic signed [15:0]` |
| `[u8; 4]` | `uint4_t` — типа не существует | `logic [7:0] data [0:3]` |
| `enum` | целое | `typedef enum logic [W-1:0] { … }` — имена видны в осциллограмме |
| `float` | `float` (f32) | **ошибка `SV-003`** |

Разрядность **буквальна**: в RTL машинного слова нет, округлять до 8/16/32/64 не
требуется. Ширина перечисления считается **по диапазону значений** (не по числу
вариантов): `enum Action { Idle = 670 }` требует десяти бит.

**Контракт обращения к порту — один на все категории.** Колбэк HAL принимает
`(порт, индекс, значение, userdata)` на запись и `(порт, индекс, userdata)` на
чтение: у скалярного порта индекс нулевой, у `[bit;N]` это **номер разряда**, у
массива — номер элемента. Массив-порт остаётся Одним портом, и потому
`bus[i] := 7` с переменным индексом переводится так же, как с литеральным.

```c
void    (*write_bit)(Probe_Out_BitPort port, uint8_t bit, bool val, void *userdata);
void    (*write_numeric)(Probe_Out_NumericPort port, uint8_t index, int64_t val, void *userdata);
int64_t (*read_numeric)(Probe_In_NumericPort port, uint8_t index, void *userdata);
```

Два контракта на одно действие («порт целиком» и «элемент порта») разошлись
бы при первой правке, а реализующему HAL пришлось бы держать две функции,
делающие одно и то же.

**Состояние стабильно.** Автомат не покидает состояние сам: уйти можно только
по переходу (`ref`/`next`). Пока перехода нет, состояние остаётся активным, и
его `always` исполняется каждый такт — `start Run { always { lamp := 1; } }`
держит лампу зажжённой, а не гасит её на втором такте. Работу автомата
завершает состояние, у которого нет ни переходов, ни исполняемого каждый такт
тела; `enter` и `exit` одноразовы и состояние не удерживают.

#### Сравнение целей

| | `c` | `c-hal` | `st` | `rust` | **`sv`** |
|---|---|---|---|---|---|
| Платформа | МК | МК | ПЛК | МК | **FPGA/ASIC** |
| Такт | вызов `_tick` | вызов `_tick` | скан-цикл | вызов `tick()` | **фронт `clk`** |
| `out cmd_fork: bit` | колбэк `write_bit(порт, разряд, значение, ud)` | `*(volatile*)0x500` | `VAR_OUTPUT` | метод трейта | **`output logic`** |
| `out bus: [u8;4]` | Один порт, элемент — индексом обращения | база + `индекс × ширина` | четыре `VAR_OUTPUT` | четыре порта | **шина** |
| `bit` | `int` (32 бита) | `int` | `BOOL` | `bool` | **`logic`** (1 провод) |
| `float` | `float` | `float` | `LREAL` | `f64` | **запрещён `SV-003`** |
| `extern fn` | прототип | прототип | заглушка | метод трейта | **запрещён `SV-005`** |
| Адрес порта | не эмитит | **потребляет** | `st-at` потребляет | не эмитит | **`sv-mmio` потребляет** |
| Вход в старт | бесплатен (после 0033) | бесплатен | стоит такта | бесплатен | **бесплатен конструктивно** |
| `M1 \| M2` | последовательно, такт = сумма | то же | то же | то же | **параллельно, такт один** |

Карта адресов (`--address-map`) «голой» целью `sv` **не потребляется**: у неё
каждый порт — вывод кристалла, а не MMIO-адрес. Адрес-потребляющий вариант SV —
парная цель **`sv-mmio`** (по образцу `c-hal` к `c`): порт **с**
адресом становится битом **регистрового файла** на шинно-агностичном синхронном
интерфейсе (`reg_addr`/`reg_wdata`/`reg_wen`/`reg_rdata`), порт **без** адреса —
портом модуля. Направление принадлежит биту: одно слово регистра несёт биты
обоих направлений. Автомат тот же, что у `sv`; цель `sv` байт-в-байт неизменна.

**Состав интерфейса зависит от модели**. Регистровый интерфейс
эмитится, только если у модели есть адресованные порты; сигналы **записи**
(`reg_wdata`, `reg_wen`) — только если есть хотя бы один **входной** такой порт.
Модель, у которой все адресованные порты выходные, доступна шине лишь на чтение,
и её ядро получает три сигнала вместо четырёх: обещать вход данных, которому
нечего писать, значит оставить его висеть — `verilator -Wall` отвечает на это
`UNUSEDSIGNAL`.

Адаптер шины следует за ядром: при ядре без записи он не заводит проводов к
несуществующим выводам, а сигналы записи протокола (их состав задан шиной, а не
моделью) честно поглощает. Цикл записи APB при этом завершается штатно —
`pready = 1`, `pslverr = 0`, — но значение выходного регистра остаётся тем, что
вычислил автомат: выход принадлежит модели, а не шине.

#### Границы цели — и почему это границы, а не недоделки

Каждый запрет — не «пока не сделано», а свойство синтезируемого RTL. Диагностика
называет цели, где модель по-прежнему валидна.

| Код | Что | Почему |
|---|---|---|
| `SV-003` | `float` в типе **без** `--float-as-q` | В синтезируемом RTL плавающей точки **не существует**. `real` языка SV пригоден только для симуляции — синтезатор его отвергает. Снимается флагом `--float-as-q=m.n`: `float → q(m, n)`, синтезируемо. Без флага угадывать точность генератор не вправе — отсюда ошибка, а не умолчание |
| `SV-005` | `extern fn` | Вызова внешнего кода в RTL нет. DPI-C — механизм симуляции; аппаратный аналог «внешней функции» — отдельный модуль со своим интерфейсом, а `extern fn` не описывает ни портов, ни тактов, ни латентности |
| `SV-006` | `inout` | Двунаправленный порт — трёхстабильная шина, требующая сигнала `oe` (`assign pad = oe ? val : 1'bz;`). Takt его не выражает, и вывести нельзя: модель не сообщает, когда порт ведёт линию, а когда слушает |
| `SV-007` | порт с именем `clk`, `rst_n`, `is_done`, `state`, `state_next` | Эти имена генератор объявляет сам |
| `SV-008` | неконстантный `enter` стартового состояния | Ветвь сброса — цепь сброса триггеров, она не вычисляет |
| `SV-012` | имя = ключевое слово SystemVerilog (`fork`, `wire`, `time`, …) | Их около 250, и многие — обиходные имена автоматики. Аналог ловушки `Concat` у цели `st` |
| `SV-002` | цикл в теле, досрочный возврат из функции, `match`, срез массива | Цикл в RTL обязан разворачиваться в схему, то есть иметь границы, известные на этапе синтеза. Возврат печатается присваиванием имени функции (`return` не принимает yosys) и исполнение не прерывает |

**Композиция** — и параллельная `|`, и **последовательная `+`**.
Цепочке `A + B + (C | D) + E` даётся регистр шага (`<state>_step`): в
`always_comb` активен ровно один шаг, продвижение по завершении предыдущего
(«такт после», как `break` в C), последний шаг переводит родительское состояние.
`A + (B + C)` уплощается в плоскую цепочку; прямая вложенная `+` внутри
параллельного шага (`(A + B) | C`) даёт явную `SV-002` — не молча стоящий автомат.

Из корпуса цель транслирует `stacker.takt`, `elevator_mini.takt`,
`regulator.takt`, `pid_regulator.takt` и `batch_cycle.takt`. Последний заведён
специально под `+`:
до него список состоял из моделей на `|`, и последовательная композиция под проверка
**не подавалась** — синтез на ней прогоняли вручную. Отвергаются:
`elevator.takt` — `SV-005` (8 `extern fn`); `comprehensive.takt` — `SV-002` (цикл
`for`); `extend_complex.takt` — `SV-005` (`extern fn has_flag`; композиция `+`
тут поддержана, препятствие — не она).

Вне объёма: один тактовый домен и один сброс; CDC, множественные домены,
SDC/XDC, потолок частоты. Уплощение даёт длинную комбинационную цепь — это плата
за точную семантику `|`.

#### Как проверить вывод: нужны Оба инструмента

```sh
verilator --lint-only -Wall out/stacker.sv
yosys -p "read_verilog -sv out/stacker.sv; synth -top stacker"
```

**Одного мало, и это проверено, а не предположено.** Инструменты ловят
**непересекающиеся** классы дефектов:

| Проба | `verilator --lint-only -Wall` | `yosys … synth` |
|---|---|---|
| `real` в `always_ff` | **принял молча**, код 0 | `ERROR: TOK_REAL`, код 1 |
| комбинационная петля | `UNOPTFLAT`, код 1 | **синтезировал молча**, код 0 |
| `return` в функции | **принял молча**, код 0 | `syntax error`, код 1 |
| ширина перечисления мала | `ENUMITEMWIDTH`, код 1 | **синтезировал молча**, код 0 |

То есть расхожее «`--lint-only` даёт проверку синтеза» **неверно**: Verilator —
линтер и симулятор, для него `real` легален. Оба проверки стоят в `precheck.sh` и в
CI.

> Оба проверки доказывают, что RTL **валиден и синтезируем**, но не что он ведёт
> себя как модель: молча неверная трансляция синтезируется тоже. Поведенческую
> эквивалентность даёт только потактовая сверка трасс с симулятором
> (`conformance_sv_tests.rs`) — и она у цели `sv` строже, чем у `c`: сверяется
> значение на **каждом** такте.

#### Тестбенчи и осциллограммы для GTKWave

Для **каждого** транслируемого примера (`stacker`, `elevator_mini`, `regulator`,
`pid_regulator`, `batch_cycle`) заведён рукописный тестбенч в
`examples/generated/sv/tb/`; отсутствие парного тестбенча у
обязательного примера валит проверка. Тестбенч делает две вещи:
прогоняет порождённый модуль на осмысленном сценарии, проверяя наблюдаемое
поведение `assert`-ами, и снимает осциллограмму `<module>.vcd` для
[GTKWave](https://gtkwave.sourceforge.net/):

```sh
# из examples/generated/sv/
verilator --binary --timing --trace --top-module tb tb/stacker_tb.sv stacker.sv -o simtb
(cd tb && ../obj_dir/simtb)     # пишет tb/stacker.vcd (и печатает OK/ошибку assert)
gtkwave tb/stacker.vcd
```

Сценарий — **замкнутая среда**: положение и датчики подаются обратной связью с
выходов модуля (тележка «телепортируется» к скомандованной цели, кабина ползёт к
целевому этажу), поэтому автомат проходит весь рабочий цикл без ручной подгонки
тактов. Обратная связь идёт только через регистры — комбинационной петли нет.

Тестбенч — **принадлежность проверки, а не продукта**: `taktc` его не порождает. Он проверяет «событие когда-нибудь произошло» (устойчиво к
сдвигу такта); потактовую *эквивалентность* по-прежнему доказывает строгая
сверка `conformance_sv_tests.rs`. Сборку и прогон тестбенчей `precheck.sh`
выполняет отдельным проверкой — провал `assert` валит предкоммит; при отсутствии
`verilator` шаг мягко пропускается локально (в CI обязателен).

### Канонический форматтер (`taktc fmt`)

Приводит `.takt` к единому детерминированному стилю: воспроизводимые диффы,
отсутствие споров о форматировании, проверяемость в CI.

```sh
taktc fmt examples/            # отформатировать каталог на месте (рекурсивно, *.takt)
taktc fmt --check examples/    # проверить: код возврата ≠ 0, если нужен формат (CI)
cat a.takt | taktc fmt --stdin  # из stdin в stdout (редакторы, конвейеры)
```

Гарантии:

- **Идемпотентность:** `fmt(fmt(x)) == fmt(x)`.
- **Семантика не меняется:** `parse(fmt(x))` структурно равен `parse(x)`.
  Скобки, написанные автором, сохраняются; операторы `:=`/`=` не подменяются.
- **Комментарии сохраняются** — все три вида (`//`, `///`, `/* */`), в ведущей и
  хвостовой позиции. Пустые строки восстанавливаются, но не более одной подряд.
- **Выбор автора между синонимами сохраняется:** `while` не переписывается в
  `loop`, `: [Guard] x;` — в `: x;`.
- **Отказ вместо порчи:** если конструкция не поддержана печатью, `taktc fmt`
  сообщает об этом и возвращает ненулевой код — файл не трогается.

То же ядро используют `taktc fmt`, LSP (`textDocument/formatting`) и будущая
интеграция с IDE, поэтому стили инструментов не расходятся.

### Верификация модели (`taktc verify`)

Проверяет LTL-свойства модели методом **model checking** — исчерпывающим
перебором прогонов автомата, а не тестами. Ответ «свойство держится» —
доказательство, а не отсутствие найденных нарушений.

```sh
taktc verify model.takt                            # проверить все `: [LTL] φ;` файла
taktc verify --property "F Done" model.takt        # проверить одно свойство
taktc verify -p "G (Fault -> F Idle)" model.takt   # короткая форма
taktc verify --scope all model.takt                # + модели из import (по умолчанию: свой файл)
taktc verify --trace model.takt                    # + дамп конвейера (отладка)
```

Код возврата: `0` — все свойства держатся; `1` — есть нарушение, непроверяемое
свойство или ошибка разбора (пригодно для CI).

#### Что означает атом: абстракция управления

**Атом LTL — имя состояния.** `Fault` истинно ровно в те такты, когда автомат
находится в состоянии `Fault`. Проверяются свойства **управления**:

| Свойство | Формула | Смысл |
|---|---|---|
| Достижимость | `F Done` | автомат рано или поздно окажется в `Done` |
| Живость (отклик) | `G (Fault -> F Idle)` | после сбоя система обязана вернуться в `Idle` |
| Инвариант порядка | `G (Open -> X Closing)` | сразу за `Open` идёт только `Closing` |
| Отсутствие залипания | `G F Idle` | автомат бесконечно часто возвращается в `Idle` |

Модель абстрагируется до **графа переходов**: вершины — состояния, рёбра —
`ref`-переходы. **Условия переходов игнорируются** (любой `ref` считается
возможным), данные (`var`, порты, `cond`) в разметку не входят.

Важное следствие: если **все** выходы из состояния под условием, автомат вправе
задержаться в нём — такт, в котором ни один guard не сработал, состояния не
меняет (так же работает порождённый C). Поэтому у такого состояния есть переход
«в себя», и `F Done` на модели ниже **не держится** — прогон, вечно стоящий в
`Work`, реален:

```lam
var ready: bit := false;
start Work { ref Done: ready = 1; }   // ready может не стать 1 никогда
state Done;
```

Безусловный `ref` такой петли не даёт: он срабатывает на каждом такте.

Отсюда два следствия, которые нужно понимать при чтении вердикта:

- **«Держится» — надёжно.** Прогонов у абстракции не меньше, чем у реальной
  модели, поэтому свойство, истинное на всех прогонах абстракции, истинно и на
  всех реальных.
- **«Нарушено» — контрпример **в абстракции**.** Он может оказаться недостижим
  по данным (например, guard `error = 1` в реальности выполняется всегда, а
  абстракция считает, что он может и не сработать). Вывод помечает это явно.

#### Пример: свойство держится

```lam
// holds.takt — из Fault выход только через Recovery в Idle: [LTL] G (Fault -> F Idle);

var error: bit := false;

start Idle {
    ref Fault: error = 1;
    ref Idle: error = 0;
}
state Fault { ref Recovery; }
state Recovery { ref Idle; }
```

```text
$ taktc verify holds.takt
СВОЙСТВО ДЕРЖИТСЯ: G (Fault -> F Idle)

Проверено свойств: 1; все держатся
```

#### Контрпример: свойство нарушено

Отличие от примера выше **ровно одно** — у `Fault` появилась самопетля, и
автомат научился залипать в сбое навсегда:

```lam
// fails.takt: [LTL] G (Fault -> F Idle);

var error: bit := false;

start Idle { ref Fault: error = 1; }
state Fault {
    ref Fault: error = 1;   // ← залипание: сбой может длиться вечно
    ref Idle: error = 0;
}
```

```text
$ taktc verify fails.takt
СВОЙСТВО НАРУШЕНО: G (Fault -> F Idle)
  контрпример: Idle -> [ Fault ]*
  (абстракция управления: условия переходов не учитываются — контрпример может быть недостижим по данным)

Проверено свойств: 1; не держится/не проверено: 1
```

Контрпример — **лассо**: конечный префикс плюс цикл в скобках, повторяемый
бесконечно (`[ … ]*`). Читается как прогон автомата: `Idle`, затем `Fault`
навсегда. Это **какой-то** нарушающий прогон, не обязательно кратчайший:
префикс может оказаться длиннее необходимого — для доказательства нарушения
достаточно одного примера.

#### Контрпример: атом — не состояние

Свойства над данными в абстракции управления невыразимы. Верификатор не считает
их молча ложными, а **отказывается** проверять:

```lam: [LTL] G temp;      // temp — переменная, а не состояние
var temp: u8 := 0;
start Heating { ref Cooling; }
state Cooling { ref Heating; }
```

```text
$ taktc verify atom_not_state.takt
СВОЙСТВО НЕ ПРОВЕРЕНО: G temp
  атом(ы) temp — не имена состояний проверяемой модели.
  Атом обязан быть именем состояния: проверяются свойства управления (достижимость, порядок, живость).
  Вне охвата: свойства над данными (`G (temp <= 100)`) и состояния вложенных моделей — их формулы объявляйте внутри самой модели.
```

Та же диагностика — на опечатку в имени состояния (`F Dane` вместо `F Done`) и
на состояние **вложенной** модели: у вложенной модели свой граф, поэтому её
свойства объявляются внутри неё:

```lam
model Engine {: [LTL] F Stop;        // проверяется по состояниям Engine
    start Run { ref Stop; }
    state Stop;
}
start Main = Engine;
```

```text
$ taktc verify nested.takt
СВОЙСТВО ДЕРЖИТСЯ [модель Engine]: F Stop
```

#### Область формулы: где объявлена, о том и говорит

Формула, объявленная **в теле состояния**, — сокращение для
`G (Состояние -> φ)`: «всякий раз, когда автомат попадает в это состояние,
дальше держится φ». Формула уровня модели областью не связана и проверяется от
стартового состояния.

```lam
var error: bit := false;

start Idle {
    ref Fault: error = 1;
}

state Fault {: [LTL] F Idle;        // читается как G (Fault -> F Idle)

    ref Fault: error = 1;  // ← самопетля: залипание в сбое
    ref Idle:  error = 0;
}
```

```text
$ taktc verify state_scope_fails.takt
СВОЙСТВО НАРУШЕНО: G (Fault -> F Idle)
  контрпример: Idle -> [ Fault ]*
  (абстракция управления: условия переходов не учитываются — контрпример может быть недостижим по данным)
```

Печатается **проверенная** формула (`G (Fault -> F Idle)`), а не авторская
запись: вердикт обязан говорить о том вопросе, на который отвечал.

Убрав самопетлю `ref Fault` (пример `state_scope_holds.takt` — из `Fault`
единственный путь ведёт через `Recovery` обратно в `Idle`), получаем:

```text
$ taktc verify state_scope_holds.takt
СВОЙСТВО ДЕРЖИТСЯ: G (Fault -> F Idle)
```

Область — свойство **состояния**, а не текста: формула в именованном блоке
состояния (`enter`/`exit`/`always`) связывается тем же состоянием — блок
исполняется, лишь когда автомат в нём. Формула в теле функции области не
получает (функцию вправе позвать любое состояние) и проверяется от старта.

#### Область проверки: свой файл, а не чужая библиотека

Дерево модели содержит и **импортированные** модели. Проверять их заодно нельзя:
нарушенное свойство чужой библиотеки роняло бы сборку тому, кто её лишь
импортировал, — а чинить чужой `: [LTL]` он не вправе.

Поэтому `taktc verify` проверяет **модели своего файла**; пропущенное
перечисляется — молча сузить область значило бы выдать «все держатся» за
«проверено всё»:

```text
$ taktc verify main.takt
СВОЙСТВО ДЕРЖИТСЯ: F Done

Не проверено (вне области): 1 — модели из импортов: Badlib
  --scope all — проверить их тоже.

Проверено свойств: 1; все держатся
```

```sh
taktc verify main.takt               # по умолчанию: --scope file
taktc verify --scope all main.takt   # проверить и импортированные модели
```

Область считается **по происхождению**, а не по вложенности: `model`, объявленная
в самом файле, проверяется всегда — включая её вложенные модели. Отсекается лишь
то, что пришло через `import` (любой из трёх форм), причём **поддеревом целиком**:
вложенные модели чужого файла — тоже не ваши.

#### Как это работает и как отлаживать

Конвейер — стандартный автоматный подход: по **отрицанию** свойства строится
автомат Бюхи `A_¬φ` (его язык — нарушающие прогоны), берётся произведение
`K × A_¬φ`, и проверяется пустота языка (поиск достижимого принимающего цикла
вложенным DFS). Пусто ⟹ нарушить свойство нечем ⟹ оно держится. Непусто ⟹
найденный цикл и есть контрпример-лассо.

Флаг `--trace` печатает все три звена — это основной инструмент отладки, когда
вердикт кажется неожиданным:

```text
$ taktc verify --trace --property "F Done" unreachable.takt
=== Структура Крипке (абстракция управления) ===
  Done -> Done
  Wait -> Work
  Work (start) -> Wait
=== Формула F Done ; автомат строится по отрицанию !(F Done) — его язык суть нарушающие прогоны ===
=== Автомат Бюхи (GPVW) ===
Начальные состояния: {0}
Принимающие состояния: {0}
s0 : { !Done }
  переходы -> s0
=== Произведение K x A_!phi (2 состояний, 2 принимающих) ===
  (Work,q0) (нач., принимающее) -> (Wait,q0)
  (Wait,q0) (принимающее) -> (Work,q0)
СВОЙСТВО НАРУШЕНО: F Done
  контрпример: Work -> [ Wait -> Work ]*
```

Трасса сразу показывает причину: в структуре Крипке в `Done` не ведёт ни одно
ребро, поэтому цикл `Work → Wait → Work` живёт вечно, ни разу не попав в `Done`.

Проверка **всегда завершается**: структура Крипке конечна по построению (число
вершин = число состояний FSM). Вердикт детерминирован — тот же вход даёт тот же
ответ.

#### Ограничения (текущий срез)

- Свойства над данными (`G (temp <= 100)`) не проверяются — атом обязан быть
  именем состояния. Расширение (explicit-state или символьный MC) строится
  поверх готового конвейера.
- Условия переходов абстрагированы, поэтому возможны ложные срабатывания
  (контрпример недостижим по данным). Обратной ошибки — пропуска нарушения —
  абстракция не даёт.
- `--property` проверяется против **корневой** модели файла; свойства вложенных
  моделей объявляйте внутри них (`taktc verify` без флага проверит все).
- **Импортированные модели по умолчанию не проверяются** — см. «Область
  проверки» ниже; `--scope all` возвращает проверку всего дерева.
- **Очень большие модели** (тысячи состояний) могут исчерпать стек: обходы
  рекурсивны. Для типичных моделей (десятки состояний) запаса достаточно.

### Порты ввода-вывода

```lam
model Motor {
    out Enable: bit;   // запись
    out Speed:  u8;
    in  Sensor: bit;   // чтение
    in  Limit:  bit;
}
```

- **`out`-порт**: модель пишет в него; чтение — ошибка.
- **`in`-порт**: модель читает из него; запись — ошибка.

При кодогенерации создаются отдельные enum-типы и типизированные функции для in/out.

### Адресные литералы (MMIO)

Инициализатор **порта** — это его **адрес** (а не начальное значение): порт
отображается на аппаратный регистр. Форма `адрес:бит` задаёт позицию бита в
слове; голый адрес позицию бита не задаёт.

```lam
out LED : u8  := 0x00100000;      // порт LED по адресу 0x00100000
in  BTN : bit := 0x00200000:0;    // бит 0 слова по адресу 0x00200000
in  FLAG: bit := 0x00200000;      // адрес без указания бита
```

Проверка «значение типа `bit` — только 0 или 1» (`SE-035`) к инициализатору
**порта не применяется** — это адрес, а не значение; для обычных
`var`/`const` типа `bit` она сохраняется — контрпример `var f: bit := 5;` даёт
`SE-035`. Прежде голый адрес на `bit`-порту ошибочно отвергался этой проверкой
(тогда как `u8`-порт его принимал).

### Внешние функции (FFI)

```lam
extern fn hal_uart_send(data: u8);
extern fn hal_gpio_set(pin: u8, val: bit);
```

В сгенерированном C-коде они превращаются в прямые вызовы без обёрток.

### LSP-сервер

```sh
scripts/install.sh                                    # ставит и takt-lsp тоже
cargo build --release --features lsp --bin takt-lsp   # только сборка
takt-lsp --version                                    # версии сервера и языка
```

**Версия установленного сервера сверяется командой**. Редактор держит сервер
запущенным и обновляется независимо от дерева, поэтому устаревший `takt-lsp`
показывает диагностики, которых свежий компилятор уже не даёт — и выглядит это
как дефект языка. `takt-lsp --version` печатает версию инструмента и версию
языка; расхождение с `taktc --version` значит, что сервер надо переустановить
(`scripts/install.sh`).

Поддерживаемые возможности: диагностика, hover, автодополнение, Go to Declaration,
форматирование документа (`textDocument/formatting` — то же ядро, что у `taktc fmt`).

Настройка в Zed:

```json
{
  "lsp": {
    "takt-lsp": {
      "binary": {
        "path": "takt-lsp"
      },
      "initialization_options": {
        "searchPaths": ["lib", "../shared"]
      }
    }
  }
}
```

**Пути поиска импортов в редакторе**. Ключ `searchPaths` в
`initialization_options` — аналог `-I` у `taktc`: массив каталогов, где
`takt-lsp` ищет импортируемые файлы. Относительный путь разрешается от корня
рабочей области, абсолютный — как есть; порядок значим (одноимённый файл из
`searchPaths` перекрывает локальный — как у `-I`). Без ключа поведение прежнее:
ищется только каталог открытого документа.

### Онлайн-редактор в браузере

Модель на Takt пишут, проверяют и прогоняют в браузере — без установки
инструментов. Страница
держит модуль WebAssembly, собранный из **тех же** крейтов, что `taktc`,
`takt-lsp` и `takt-sim`: диагностика в браузере совпадает с диагностикой
компилятора, а вывод цели — с выводом `taktc` байт в байт (это проверяет проверка
`scripts/check-wasm.sh` — он сверяет два вывода).

```bash
scripts/build-web.sh                  # собрать статику (модуль + страница)
scripts/deploy-web.sh -d /srv/takt    # выложить на стенд
scripts/stand.sh up                   # поднять стенд (Docker: база + сервер)
scripts/stand.sh status               # проверить: сервис отвечает и видит базу
scripts/dump-web.sh                   # снять копию: база и исходники
```

**Поделиться работой можно двумя способами, и они не подменяют друг друга.**
Ссылка-**снимок** несёт исходник во фрагменте адреса: она открывается без
учётной записи и без сервера, живёт вечно и не портится удалением проекта.
Ссылка `/p/<идентификатор>` — **живая** страница проекта: следует за правками,
требует сервера.

**Проекты** нужны ровно для трёх вещей: сохранить работу, скопировать чужой
образец себе и получить право на чужой проект. Без входа страница работает как
прежде. Исходники лежат в файловой системе сервера
(`<владелец>/<проект>/<файлы>`), база ведёт сведения о проекте и состав файлов;
порождённый вывод целей не хранится нигде — он воспроизводим. Проект, к
которому не обращались 90 дней, сворачивается в архив, а первое же обращение
разворачивает его обратно.

**Границы браузера названы, а не скрыты:** `import "файл.takt";` там кончается
`SE-001` (файловой системы у страницы нет), прогон ограничен бюджетом тактов, а
инструменты целей (`cc`, `iec2c`, `verilator`) живут на машине — страница
показывает порождённый код, но чужим компилятором его не проверяет.

### Оснастка редакторов (IDE)

Подсветка и навигация для `.takt` доступны в нескольких средах:

| Среда | Пакет | Подсветка | Статус |
|-------|-------|-----------|--------|
| Zed | `extensions/zed-takt` | через `takt-lsp` (semantic tokens) | v0.1.1 |
| IntelliJ IDEA (и IDE на IntelliJ Platform) | `extensions/intellij-takt` | лексическая (офлайн, Community) + **семантическая** через LSP4IJ + `takt-lsp`; навигация к декларации и по `import`; **Rename** и **ссылка на файл `import`**; **Reformat Code** |   |
| Любой LSP-клиент | `takt-lsp` | диагностика, hover, автодополнение, semantic tokens, **переход к декларации и к определению (в т.ч. в импортированный файл)**, **поиск использований**, **переименование** | стабильно |

**F12 работает в любом клиенте**: сервер объявляет
и `declarationProvider`, и `definitionProvider`, а обслуживает их **один**
обработчик. В Takt объявление и определение — одно и то же (`var x := 0;` — и
то, и другое), поэтому отвечать на них по-разному не только незачем, но и
вредно; редакторы же расходятся в том, какой метод шлют по F12 (VS Code —
`definition`, Zed — `declaration`). Прежде объявлен был только `declaration`, и в
VS Code «Go to Definition» не работал вовсе.

**Поиск использований** (`textDocument/references`) находит
вхождения имени **в телах `enter`/`exit`/`always` и в телах функций** — там, где
семантическое дерево позиций не хранит, а значит, их не видел и переход к
декларации. Работает не текстовым поиском, а по областям видимости: одноимённая
переменная соседней модели в ответ не попадёт, и локальная `var x`, затеняющая
переменную модели, считается отдельным символом. Вхождения ищутся в открытом
документе — рабочая область сервером не индексируется.

**Переименование** (`textDocument/rename`, та же фича) работает по принципу
**полнота или отказ**: либо меняются все вхождения символа, либо сервер
отказывается — и отказ приходит на `prepareRename`, до ввода нового имени.
Отказ даётся, если файл не разбирается, если имя объявлено в другом файле, если
это имя модели (оно видно импортирующим файлам, а их сервер не индексирует), если
новое имя не идентификатор или ключевое слово, а также если сервер встретил в
файле место, которого не разобрал. Причина отказа приходит текстом. Правки не
затрагивают внешние артефакты, где те же имена тоже встречаются: карту адресов
(`--address-map`), `--define` и сценарии симулятора.

**Переход к декларации в `takt-lsp`**. Курсор на имени модели —
`start Main = Helper;` или `S(Helper)` — открывает **тот файл**, где модель
объявлена. Путь берётся из реестра файлов компилятора, а не угадывается по имени
модели, поэтому работает и алиас:

```lam
import "engine.takt" as Motor;   // имя `Motor` связано с файлом engine.takt

start Main = Motor;             // переход отсюда откроет engine.takt
```

Импорты разрешаются по **каталогу открытого документа** (неявный путь) **и по путям `searchPaths`** из
`initialization_options` (аналог `-I`): модель, чьи импорты
лежат в общей библиотеке вне её каталога, `takt-lsp` найдёт, если каталог
библиотеки указан в `searchPaths` — как `taktc -I lib` её собирает.

Плагин IntelliJ даёт автономную **лексическую** подсветку синтаксиса (ключевые
слова, операторы `:=`/`=`/`<=`, литералы, комментарии `//`/`///`/`/* */`) без
запуска LSP-сервера, плюс страницу настройки цветов, комментирование (Ctrl+/) и
подсветку парных скобок. Есть также **переход к декларации** (`Ctrl/⌘+Click`,
`Ctrl/⌘+B`) для `model`/`state`/`type`/`enum`/`cond`/`var`/`const`/`fn` и
импортированных имён, а также **переход по строке-пути `import`** к файлу `.takt`.

Поверх этого:

- **Семантическая подсветка**:
  через LSP4IJ + `takt-lsp` идентификаторы красятся **по смыслу** (функция, тип,
  вариант `enum`, состояние/модель, переменная — каждый своим цветом). Опциональна
  и деградируема: без LSP4IJ/сервера остаётся лексическая подсветка.
- **Reformat Code** (`Ctrl+Alt+L`):
  форматирует `.takt` тем же ядром печати, что и `taktc fmt` — результат байт-в-байт
  совпадает (через `textDocument/formatting` того же `takt-lsp`).
- **Rename и ссылка на `import`**:
  штатный **Rename** (`Shift+F6`) имён Takt (декларация + использования в файле) и
  настоящая `PsiReference` для строки-пути `import` — с **автообновлением пути**
  при переименовании/перемещении файла. Работают офлайн, без `takt-lsp`.

Сборка/установка — см.
[`extensions/intellij-takt/README.md`](extensions/intellij-takt/README.md).


### Раскладка тестовых целей

Интеграционные тесты сгруппированы по темам: каждая тема — **одна** цель
(`tests/<тема>/main.rs`), а каждый набор внутри неё остаётся **отдельным файлом
и модулем**. Так имя теста несёт префикс набора и остаётся различимым, а
запускается всё это одним бинарником вместо ста сорока семи.

| Крейт | Цель | Что внутри | Наборов |
|---|---|---|---|
| `takt-lang` | `semantic` | дерево, типы, диагностики, параметры, порты | 82 |
| `takt-lang` | `targets` | цели `c`, `c-hal`, `st`, `rust`, `sv`, `sv-mmio`, адреса | 110 |
| `takt-lang` | `syntax` | лексика, разбор, форматтер, канон стиля | 20 |
| `takt-lang` | `lsp` | языковой сервер и редакторский слой | 16 |
| `takt-lang` | `verify` | LTL и автоматы Бюхи | 6 |
| `takt-sim` | `conformance` | сверки эталона с целями | 112 |
| `takt-sim` | `sim` | остальные тесты симулятора | 26 |

```sh
cargo test --test targets                     # вся тема
cargo test --test targets c_stub_tests::      # один набор внутри темы
cargo test --test conformance conformance_sv  # отбор по подстроке
```

Причина группировки — замер: первый запуск свежесобранного тестового бинарника
стоит 0.60 с при загрузке процессора 2 % (проверка кода ядром, чтение с диска,
работа динамического загрузчика), повторный — 0.033 с. В проверке каждый бинарник
запускается впервые, поэтому цена платилась на каждом прогоне.

### Покрытие тестами

Покрытие измеряется **по требованию**, а не на каждом прогоне:

```sh
scripts/coverage.sh          # сводка по крейтам
scripts/coverage.sh --html   # HTML-отчёт в target/llvm-cov/html
```

Это **не проверка**: скрипт не вызывается из `precheck.sh`, порога нет. Сборка с
инструментацией не переиспользует обычные артефакты и стоит минут, а сам процент
ничего не гарантирует — проект не раз ловил дефекты именно в **покрытом** коде
(цель `sv` компилировалась и считала не то; `c-hal` собиралась и молча теряла
биты). Ценность прогона — список мест, которых не касается ни один тест.

Нужен `cargo-llvm-cov`; без него скрипт печатает подсказку по установке и
завершается успешно.

### Бенчмарки производительности

Замеряются **функции** (разбор, семантика, конвейер до цели `c`, верификация,
индекс LSP, слой использований, форматтер, такт симулятора), а не время
процесса:

```sh
scripts/bench.sh                 # быстрый прогон
scripts/bench.sh --full          # полный прогон criterion
scripts/bench.sh --save NAME     # сохранить baseline
scripts/bench.sh --compare NAME  # сравнить с baseline
```

Это **не проверка**: порога нет, из `precheck.sh` бенчи не вызываются — время на
общей машине шумит, и порог давал бы ложные срабатывания. Ценность замера — не
проценты, а видимая смена **класса** сложности: линейный рост, ставший
квадратичным, — то, что уже дважды чинили (обходы по числу состояний и потолок
вершин верификации).

### Стратегия тестирования

- `.takt`-файлы в `tests/data/valid/` — должны компилироваться без ошибок.
- `.takt`-файлы в `tests/data/invalid/` — должны производить ожидаемую диагностику.

### Виды тестов

| Вид               | Что проверяется                       |
|-------------------|---------------------------------------|
| Лексические       | Корректное разбиение на токены        |
| Синтаксические    | Построение AST из допустимых программ |
| Семантические     | Разрешение имён, типы, ошибки         |
| Кодогенерация     | Валидный C-код на выходе              |
| Эталонные примеры | Полный прогон из `examples/`          |

#### Проверка трейлеров коммита

`scripts/check-commit-trailers.sh` (шаг `precheck.sh`) запрещает трейлер
`Co-Authored-By:` в сообщениях коммитов — в любом написании. Авторство выражает
поле `Author`, принадлежность работы — трейлер `Feature: NNNN`; третья запись об
авторстве не уточняет ни того, ни другого и появляется от настроек инструмента,
а не от решения автора.

> Проверка обходит **всю историю ветки**, а не последний коммит: правило имеет смысл
> только как свойство истории. Падение — списком коммитов.
>
> Чистка прошлого — переписывание истории (`git filter-repo`), и она меняет
> **все** хеши: теги переносятся вместе с коммитами, а `push --force`
> согласуется отдельно.

#### Снятие замера расхождения

Когда нужно выяснить, расходятся ли эталон и цели на какой-то записи, замер
снимается одной командой:

```bash
scripts/probe.sh -n 3 model.takt
```

Она прогоняет **эталон и все восемь целей** и приводит ответы в одну таблицу.
Кроме того, она проверяет **саму пробу** на ловушки, каждая из которых уже
приводила к неверному выводу: объявление, которое не используется (штатный
фильтр выбрасывает его из вывода целей — замер показывает «расхождения нет»);
имя файла, совпадающее с объявленным типом (корневая модель берёт имя из имени
файла, и появляется посторонняя коллизия); отказ **общей** диагностикой, который
приходит раньше цели и потому её поведения не измеряет.

Последним разделом проба печатает **вердикт инструментов целей**:
порождённый код прогоняется теми же командами и флагами, что и проверки
предкоммита — `cc -Wall -Wextra -Werror`, `iec2c` (и сборка порождённого им C),
`rustc`/`clippy-driver -D warnings`, `verilator --lint-only -Wall` и
`yosys synth`:

```text
ИНСТРУМЕНТЫ ЦЕЛЕЙ (те же команды и флаги, что у гейтов предкоммита)
  c         cc принял
  st        iec2c ОТВЕРГ:
             …: error: Number of subscripts/indexes does not match …
  rust      rustc принял · clippy принял
  sv        verilator принял · yosys синтезировал
```

> Нулевой код возврата `taktc` **не означает**, что вывод валиден: файл
> принимает или отвергает **чужой** инструмент. Отсутствующий арбитр
> (`iec2c`, `verilator`, `yosys` — внешние) печатается словом «пропуск» и
> никогда не выглядит как «принял».

> **Скрипт не судит** — он приводит ответы в таблицу, сравнивает их человек.
> Автоматическая сверка значений — это потактовые сверки
> (`takt-sim/tests/conformance/`), и подменять их скриптом нельзя.
>
> Чек-лист того, что машине недоступно (контрольный вход, скобки в спорных
> приоритетах, одна причина за раз, датирование замера), — свод свода
> [`docs/RULE.md`](docs/RULE.md).

#### Проверка старых имён

`scripts/check-legacy-names.sh` (шаг `precheck.sh`) запрещает в **рабочих**
файлах имена, упразднённые переименованиями проекта: прежние названия самого
языка, компилятора и языкового сервера, прежние расширения исходников и пути
упразднённых крейтов. Падает **списком** мест с номерами строк. Исключения заданы
**префиксами путей** — `docs/`, `CHANGES.md`, `CLAUDE.md`, `AGENTS.md`,
`FEATURES.md`, `.claude/` и проверки, описывающие сам переезд: там старое имя есть
свидетельство, а не ошибка. Ратчета исключений нет и не нужно: префикс не
устаревает. Контроль `scripts/test-legacy-names.sh` мутацией доказывает, что
ловится каждый из шаблонов — и что имя, пришедшее им на смену, проверка принимает.

> **Повод не косметический.** Замер нашёл 36 мест, и одно из них было дефектом
> документации: команда настройки графики в `examples/graphics-configs/README.md`
> была неверна и по именам, и по флагам — не исполнялась вовсе. Сама проверка на
> первом прогоне добавил ещё 8 мест: ссылки на пути, устаревшие дважды (ренейм
> крейтов и перенос тестовых целей).
>
> **Перечень запрещённых имён README не повторяет** — он живёт **в
> заголовке проверки**, и второй список неизбежно разошёлся бы с первым. Коротко:
> под надзором и **порождаемый** код — хелперы фиксированной точки
> переименованы вместе с языком, прежний префикс ловится в любом регистре,
> включая снапшоты `examples/generated/`. Вне надзора остались служебные
> идентификаторы самих инструментов.
>
> Побочно это доказано на самом README: первая редакция раздела перечисляла
> запрещённые имена буквально — и проверка её отверг, назвав три строки.

### Сборка из исходников

**Требования:** Rust 1.75+, LALRPOP (генерируется автоматически через `build.rs`).

```sh
git clone https://github.com/Pastor/Takt.git
cd Takt
scripts/install.sh            # релизная сборка + установка в ~/.local/bin
```

Скрипт собирает **три** инструмента — компилятор `taktc`, симулятор `takt-sim`
и языковой сервер `takt-lsp` — и кладёт их в `bin` префикса.

| Флаг | Что делает |
|---|---|
| `--prefix DIR` | префикс установки (по умолчанию `~/.local`; та же переменная — `TAKT_PREFIX`) |
| `--no-lsp` | не собирать языковой сервер |
| `--build-only` | только собрать, не устанавливать |
| `--check` | проверить, что установлено, и выйти |
| `--dry-run` | показать, что было бы сделано |

Скрипт собирает в **свой** каталог `target/install`, а не в общий `target`:
накопленный рабочий каталог сборки способен растянуть минутную сборку на часы
(замер   — cargo обходит
его перед каждой единицей компиляции). Переопределяется через
`CARGO_TARGET_DIR`.

Отдельные инструменты собираются и обычным cargo:

```sh
cargo build --release --bin taktc
cargo build --release --bin takt-sim
cargo build --release --features lsp --bin takt-lsp
```

**Модуль для браузера.** Крейт `takt-wasm` собирает компилятор, слой LSP и
эталон в один модуль WebAssembly — тот же вывод, что у `taktc` и `takt-sim`,
но без файловой системы:

```bash
cargo build -p takt-wasm --profile wasm --target wasm32-unknown-unknown
```

Модуль общается плоским C-ABI через один буфер: страница кладёт туда JSON
запроса и зовёт операцию, операция кладёт JSON ответа туда же. Сверку вывода
модуля с инструментами гоняет `scripts/check-wasm.sh` (нужен `node`).

**Страница редактора.** `web/static` — онлайн-редактор Takt: подсветка,
диагностики, вкладки восьми целей и прогон, всё в браузере через модуль
`takt-wasm`. Сборка статики и локальный запуск:

```bash
scripts/build-web.sh
```

Собранное ложится в `web/dist` (каталог производный, в дерево не коммитится);
открыть можно любым статическим сервером, например
`python3 -m http.server 8731 --directory web/dist`. Зависимостей у страницы
нет: ни npm, ни бандлера — только модули браузера.

Раскладка собранного подчинена правилу «содержимое задаёт адрес, адрес задаёт
срок»: `index.html` и `version.json` лежат в корне и кешу не отдаются, страница
целиком — в `b/<отпечаток>/` (неизменна), модуль — в `wasm/<версия>/` с описью
`manifest.json` и контрольной суммой. Рядом с текстовыми файлами сборка кладёт
`.gz` (и `.br`, если есть `brotli`), чтобы стенд ничего не считал на лету.

**Сервер проектов.** `web/server` — отдельный workspace на `axum` и
PostgreSQL: учётные записи, вход, хранилище исходников и раздача собранной
статики. Знания о языке в нём нет ни строки — компилирует и исполняет модель
браузер. Проверки без базы идут всегда, проверки хранилища и HTTP — там, где
база есть:

```bash
TAKT_WEB_TEST_DB=postgresql://пользователь@127.0.0.1:5432/база scripts/check-web-server.sh
```

Первый администратор и сброс пароля — командами `takt-web-server admin` и
`takt-web-server passwd`: почта не хранится, восстановления по письму нет.

**Обход хранилища — `takt-web-server sweep`** (он же идёт по времени внутри
сервера, `TAKT_WEB_SWEEP_HOURS`). Проходов два, и предметы у них разные:
проекты, к которым не обращались дольше срока (`TAKT_WEB_RETENTION_DAYS`, по
умолчанию 90 дней), **сворачиваются** в архив рядом с каталогом, а
**осиротевшие каталоги** — те, чья строка исчезла мимо ручки, — убираются с
диска. Осиротевшее подметается не раньше чем через час после последней правки:
между записью файла и закрытием транзакции каталог существует без строки, и
подметание в этот миг унесло бы исходник у автора.

Витрина открытых проектов доступна без входа и листается **курсором**: страница
показывает первые двадцать записей и кнопку «Ещё» — по смещению вставленный
соседом проект сдвигал бы выдачу, и читатель видел бы запись дважды либо не
видел вовсе.

Страница набрана одним шрифтом — моноширинным Fira Code, тем же, что и
документ `book/` (решение заказчика 2026-09-05; прежде интерфейс набирался
чертёжным по ГОСТ 2.304-81). Файл лежит в `web/static/font/` вместе с текстом
лицензии.
Оформление описано книгой контролов `web/design/BOOK.md` и показано витриной
`web/design/controls.html` (она стоит на живом `web/static/app.css`, третьей
копии правды нет). Правила книги — цвет только из палитры, отклик формулой,
пара из реестра, кегль и высота из шкал — контролирует `scripts/check-design.py`;
витрину открывают тем же сервером из каталога `web`.

**Симулятор без графики.** Визуализация прогона (GIF, SVG, раскладка графа) —
фича `graphics` крейта `takt-sim`, включённая по умолчанию. Библиотеку можно
собрать без неё — там, где нет ни растеризатора, ни файловой системы:

```sh
cargo build -p takt-sim --no-default-features --lib
```

Без фичи остаются разбор сценариев, прогон модели и трасса (`takt_sim::trace`),
а запрос кадров отвергается с названной причиной. Бинарник `takt-sim` графику
**требует**: он умеет писать GIF и SVG, и без них половина его ключей не имела
бы смысла.

**Каталог сборки у всех потребителей общий — `target/precheck`** (, файл `.cargo/config.toml`).
Так весь кэш попадает под самоочистку предкоммита: за отдельным каталогом не
следил никто, и он вырастал незаметно (замер-18 — **47.7 ГиБ и
198 621 файл**, из-за чего полный прогон деградировал; на чистом дереве он
занимает 152 с).

**Цена настройки:** cargo берёт блокировку на каталог сборки, поэтому
параллельные сборки **ждут друг друга** — во время предкоммита диагностика
редактора замирает и наоборот. Нужна независимая сборка прямо сейчас — задайте
свой каталог:

```sh
CARGO_TARGET_DIR=target/scratch cargo build
```

#### Необязательные зависимости (проверка порождённого кода)

Нужны только для проверки того, что компилятор породил **валидный** код целевого
языка. Сборка и тесты `taktc` без них проходят полностью.

| Инструмент | Зачем | Что проверяет |
|---|---|---|
| `cmake` + `ninja` + C-компилятор | проверка цели `c` (`scripts/precheck.sh`) | порождённый C компилируется |
| **MatIEC `iec2c`** | проверка цели `st`  | порождённый Structured Text компилируется |

**MatIEC** — открытый транспилятор ST → ANSI C; пакетом дистрибутивов **не
поставляется**. Ставить руками не нужно: `precheck.sh` сам проверяет наличие и
при отсутствии собирает из исходников. Тем же скриптом можно вызвать отдельно:

```sh
scripts/ensure-iec2c.sh          # → ~/.local/bin/iec2c (≈15 с; повторный вызов мгновенный)
IEC2C_SKIP=1 scripts/ensure-iec2c.sh   # отключить (оффлайн/CI)
```

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `IEC2C_PREFIX` | `~/.local` | Куда ставить (`$PREFIX/bin/iec2c`) |
| `IEC2C_SRC` | `~/.cache/matiec` | Куда клонировать исходники |
| `IEC2C_SKIP` | — | `1` — пропустить проверку целиком |

Ручной прогон (`-I` обязателен — без библиотеки `ieclib.txt` инструмент падает
на любом входе):

```sh
~/.local/bin/iec2c -I ~/.local/share/matiec/lib -T /tmp/out файл.st   # код 0 = ST валиден
```

**macOS:** системный `bison` — версии 2.3, а `configure` требует ≥ 2.4
(`Wrong bison version: 2.3 < 2.4`). Нужен `brew install bison`; скрипт сам
подхватывает `/opt/homebrew/opt/bison/bin`, а при слишком старом bison мягко
пропускает сборку, не роняя предкоммит. На `ubuntu-latest` bison 3.x —
препятствия нет.

`make install` MatIEC ставит **только бинарники**: библиотеку стандартных
функций (`lib/`) скрипт копирует сам в `$PREFIX/share/matiec/lib`.

Проверка ST **подключён и зелён**: цель `st` дозрела (тела `FUNCTION_BLOCK`
эмитятся), и `iec2c` принимает **весь** корпус `examples/` (8/8 валидны).

#### Гигиена каталога сборки: предкоммит не должен идти дольше минут

`cargo` **не удаляет** артефакты прошлых сборок: каждая сборка с другим набором
флагов, версией крейта или составом модулей оставляет в `target/debug/deps/`
новый набор файлов со своим хешем. За месяцы работы каталог разрастается до
десятков гигабайт и сотен тысяч файлов, и тогда **каждый** вызов `cargo` начинает
упираться в файловую систему, а не в вычисления.

Замер на рабочей машине (2026-08-04) — как выглядит запущенный случай:

| Показатель | Значение |
|---|---|
| `target/` | **86 ГБ**, 460 458 файлов |
| артефактов одного крейта `takt_lang` в `deps/` | **105 680** |
| диск | заполнен на **92 %** |
| предкоммит | **25–30 минут**, `cargo` при этом с **0 % CPU** |

После `cargo clean` на том же дереве и той же машине:

| Показатель | Значение |
|---|---|
| диск | заполнен на **73 %** (освободилось 91 ГиБ) |
| полная пересборка `taktc` с нуля | **19 секунд** |
| предкоммит целиком | **4 мин 50 с**, код возврата 0 |

Нулевая загрузка процессора при десятках минут ожидания — верный признак того,
что дело не в объёме работы, а в состоянии каталога (на APFS деградация записи
заметна уже около 90 % заполнения).

**Норма для этого проекта измерена** фичей: `cargo test` — 95–127 с
(84 % времени прогона), проверка тестбенчей `sv` — 8.8 %, все документные проверки
вместе — около двух секунд. Если предкоммит идёт дольше нескольких минут, ищите
причину **в окружении**, а не в составе проверок: делить прогон на компоненты
уже пробовали, и замер показал, что экономить нечего.

Профилактика — чистить артефакты, которых не касались несколько дней:

```sh
cargo install cargo-sweep
cargo sweep --time 3          # снести всё, что старше трёх дней
```

Если каталог уже запущен, `sweep` спасает лишь частично (свежие артефакты он не
трогает, а при активной работе их накапливаются десятки тысяч за день) — тогда
нужна полная очистка:

```sh
cargo clean
```

Она безопасна: `target/` — кэш, восстанавливается сборкой, и цена восстановления
(десятки секунд) несопоставима с потерями на раздутом каталоге.

Признаки, при которых стоит проверить `target/` **раньше**, чем искать дефект
в коде: прогон внезапно стал в разы дольше при тех же проверках; `cargo` висит с
нулевой загрузкой процессора; свободного места на диске меньше 15 %.

### Непрерывная интеграция

CI (`.github/workflows/ci.yml`) прогоняет **весь** `scripts/precheck.sh` под
строгим режимом (`PRECHECK_STRICT=1`) — **единый источник истины проверок**: логики
проверок в самом workflow нет, он лишь ставит инструменты (cmake/ninja/verilator/
yosys/bison/flex + сборка `iec2c`) и делает один вызов скрипта. Под строгим
режимом отсутствие любого инструмента — **ошибка** (а не мягкий пропуск: иначе
пропущенный проверка зелёный и неотличим от пройденного), а формат **проверяется**
(`cargo +nightly fmt --check`). Локально без флага поведение прежнее: мягкие
пропуски, `fmt` применяется. Так `main` защищён тем же барьером, что и коммит
разработчика — все семь целей и инфраструктурные проверки (воспроизводимость,
float→q, канон формата, ссылки) проверяются вживую.

## 10. Расширение и версии

### Версия

**Версия языка: 0.18.0** (крейт `takt-lang`). Документ актуален для ветки `v2`.
Список изменений — в файле [`CHANGES.md`](CHANGES.md).

> **Место Takt среди родственных языков** — отчёт
> [`docs/DIFF.md`](docs/DIFF.md): сравнение с 26 языками и инструментами
> (синхронные языки Esterel/Lustre-SCADE/Céu, автоматные DSL SCXML/XState/
> StateSmith/Stateflow, промышленные стандарты IEC 61131-3 и IEC 61499, языки
> верификации SPIN/nuXmv/UPPAAL/TLA+/P, языки описания аппаратуры
> SystemVerilog/Chisel/SpinalHDL/Amaranth), сводные таблицы, разбор индекса TIOBE
> и выводы о нише, пользователях и пробелах языка. Каждый язык описан по единому
> набору из 17 полей, и на **всех** языках решён один и тот же пример
> («проблесковый маячок») — синтаксис сопоставляется построчно. Отдельно
> разобраны **модель времени** (механизм и пример у каждого языка, сводная
> таблица) с предложением **вариантов её введения в Takt** (раздел 11.6) и
> **работа с моделями как сущностями** — порты, композиция моделей, взаимодействие
> между ними (таблицы 10.8–10.9, вывод — раздел 11.7). Дата среза данных —
> 2026-07-27.

> Версия языка живёт единственным источником истины в коде —
> `takt_lang::LANGUAGE_VERSION` (`takt-lang/src/version.rs`); строка выше
> обязана ей соответствовать, что стережёт проверка
> `scripts/check-language-version.sh` в `precheck.sh` (рассинхрон валит
> предкоммит). Сверяются **три** источника: константа, строка выше и живой
> контекст `CLAUDE.md`. Версия языка **накапливается** по циклам, а
> не растёт с каждой фичей.
>
> Подъём версии помечается **аннотированным** тегом `v<версия>` — и на том самом
> коммите, который меняет номер: только так по истории видно, где проходит
> граница версии. Это стережёт `scripts/check-version-tag.sh` в `precheck.sh`: у закоммиченной версии обязан быть такой тег, достижимый из
> `HEAD`. Повод измерен — из восьми версий тегов не имели две, причём последний
> пропуск был сделан накануне заведения проверки.
>
> **Проверка молчит, пока подъём не закоммичен** (версия в рабочем дереве
> отличается от версии в `HEAD`): тег ставится **на** коммит, а предкоммит идёт
> **до** коммита — иначе проверка мешала бы ровно тем фичам, которые правило
> исполняют верно. В этом случае он печатает пропуск и подсказывает команду.
>
> Живой контекст проверяется и шире: `scripts/check-claude-md.py` сверяет статусы
> упомянутых фич с реестром, пути к файлам — с деревом, версии крейтов — с
> манифестами и запрещает ссылки вида `файл.rs:NNN` (они гниют молча — строка
> остаётся, символ уезжает). `CLAUDE.md` читается в начале каждой сессии, и
> ложный факт в нём становится предпосылкой всей последующей работы.

> **0.3.0 → 0.4.0:**
> семантика `[bit;N]` уточнена — это **упакованный N-битный вектор** во всех целях
> и симуляторе (`[bit;8]` ≡ `u8`; N ≤ 64 — скаляр ширины `round_up(N)`; N > 64 —
> массив `uint64_t[⌈N/64⌉]`, впервые выразим `[bit;128]`), прежде трактовался
> пятью потребителями по-разному. Изменение **наблюдаемой семантики типа**, а не
> синтаксиса: цель C байт-в-байт неизменна на корпусе; rust/st/sv меняются лишь на
> `extend_complex`. `.takt`-исходники не правятся.

> **0.2.0 → 0.3.0:** отображение типов Takt в типы
> C приведено к явному и проверяемому виду. Меняется **наблюдаемая семантика
> порождаемого кода**, а не синтаксис языка: `float` → `double` (8 байт, было
> 4 — совпадение с точностью симулятора f64), `bit` → `uint8_t` (было `int` —
> 32 бита со знаком), `[T;N]` при `T` ≠ `bit` → настоящий массив `T name[N]`
> (было `uint{N}_t` — несуществующий тип). Правки `.takt`-исходников **не
> требуется** — изменение выражается в перегенерации C; автомиграция не нужна.
>
> Ужесточение: скалярный инициализатор массива → `CC-017` (прежде давал
> **невалидный C**, то есть ни одна работавшая программа не сломана). Широкий
> `[bit;N]` в 0.3.0 отвергался как `CC-014`, но с **0.4.0**  это
> упакованный вектор — `[bit;128]` → `uint64_t[2]`, диагностика `CC-014` выведена.
>
> **Версия 0.3.0 накапливает изменения**: перечисленное ниже внесено в **уже
> поднятую** версию, не поднимая её снова.
> **Вызов функции** из тела функции — композиция `f→g`
> внутри модели (аддитивно: ранее отвергавшиеся программы компилируются, смысл
> валидных не меняется); рекурсия запрещена диагностикой `SE-053`. См.
> «Функции».
> **Именованный инвариант** `invariant Имя = <Условие>;`
> (аддитивно: одно жёсткое ключевое слово, `assert` не вводится) + оживление
> Guard-формул в симуляторе (`SIM-025` вместо тихого пропуска). См. «Инварианты
> и assert».
> **Вход в стартовое состояние**: больше не расходует
> такт — тело исполняется на такте 1 на любой глубине, как в симуляторе. Ломающее
> изменение **наблюдаемой семантики такта** (не синтаксиса): порождённый C
> меняется, прошивки при пересборке стартуют на `depth` тактов раньше; `.takt` не
> правятся. См. «Семантика первого такта».

> **Аддитивное расширение в 0.3.0:** выражение адреса
> **вычисляется** — допустимы имена (`--define`, затем `const` модели) и
> целочисленная арифметика. Прежде принимались только литералы, а символьная и
> арифметическая формы **молча теряли адрес**. Совместимость полная: ни одна
> валидная программа не меняет смысла — валидными становятся те, что прежде
> отвергались. См. «Символьные адреса и `--define`».

> **Аддитивное расширение 0.1.0 → 0.2.0:** оператор задания адреса
> порта `address Имя = <адрес>;` (жёсткое ключевое слово `address`), внешняя
> `.ld`-подобная карта адресов (`--address-map`) и цель генерации `-t c-hal`
> (таблица адресов + принятый по умолчанию HAL). Совместимость полная — инлайн-адрес
> `in P: T := <addr>;` работает как прежде.

> **Слом совместимости 0.0.x → 0.1.0:** присваивание записывается
> `:=` (было `=`), сравнение на равенство — `=` (было `==`); оператор `==`
> выведен. Реляционный `<=` без изменений. Старые `.takt` переводятся
> отдельным инструментом переписывания дерева разбора.

### Композиция моделей

Takt поддерживает два вида сборки систем:

```lam
// Последовательная: Init → Startup (после завершения Init запускается Startup)
start Sequential = Init + Startup;

// Параллельная: Run и Halt работают одновременно
start Parallel = Run | Halt;

// Комбинированная
start System = (Init + Startup) + (Run | Halt);
```

### Формулы и ассемблерные вставки

Для встраивания платформо-зависимого кода или формальных спецификаций:

```lam
assembly "arm" {
    // платформо-зависимый код
}

formula "ltl" {
    always(active())
    eventually(done())
}
```

**LTL-аннотации** (`: [LTL] φ;`) — свойства линейной темпоральной логики прямо в
модели, состоянии или блоке кода. Операторы: `X` (next), `F` (eventually),
`G` (always), `U` (until), `R` (release), `!`, `&`, `|`, `->`. **Атом — голое
имя** (переменной, состояния или `cond`); вызовы функций в атоме не допускаются:

```lam
var a: u8 := 0;
var b: u8 := 0;
start c { : [LTL] G (a -> F b), X c; }   // атомы a, b — переменные; c — состояние
```

> **Статус.** LTL-формула **разбирается** на всех трёх уровнях
> (модель/состояние/блок) — прежде в блоке она молча терялась (0035).
> **Управляющие свойства проверяются** подкомандой
> [`taktc verify`](#верификация-модели-taktc-verify) (0049): атом = имя состояния.
> Свойства **над данными** (атом-переменная, как `a`/`b` в примере выше) пока не
> проверяются ничем — о чём сообщает предупреждение `SE-055` на каждую формулу
> при компиляции. Неизвестный атом (опечатка) даёт `SE-056`.

### Расширение языка

Добавить новую конструкцию в Takt:

1. Расширить грамматику в `takt-lang/src/grammar.lalrpop` и `lexer.rs`.
2. Добавить узел AST в `ast.rs`.
3. Реализовать семантический проход в `semantic/tree.rs`.
4. При необходимости — расширить кодогенератор в `generator/c/`.
5. Добавить тесты в `tests/data/valid/` и `tests/data/invalid/`.

Полная грамматика — в приложении документа
[«Грамматика»](book/src/appendix-grammar/index.typ); языковая фича обязана пройти
стадию «Документирование», а лексику приложения сверяет с кодом проверка
`scripts/check-book-keywords.py`.
