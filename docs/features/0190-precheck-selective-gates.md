## Краткое описание

`scripts/precheck.sh` — единственный вход всех проверок проекта (909 строк, ~20
проверок) и **единственный источник истины** для CI. Цена этого
устройства: прогон целиком идёт **порядка двадцати минут** и запускается ровно
так же, менялся ли весь конвейер семантики или одна строка документа. Правка,
затрагивающая один слой, ждёт verilator, yosys, `iec2c`, сборку Cargo и два
прогона генерации на детерминизм.

Требуется разложить предкоммит на **именованные компоненты** с возможностью
запустить подмножество, не теряя главного свойства: **полный прогон остаётся
умолчанием и обязателен перед коммитом**, а любое сужение — громкое.

> Фича заведена **по запросу заказчика 2026-07-31** в ходе работы над
> [пересмотр задания адресов и доступа к портам](0187-port-io-redesign.md): цикл «правка → проверка» стал заметно
> дороже самой правки.

## Что известно на входе

- **Проверки уже сгруппированы визуально, но не структурно.** В скрипте различимы
  блоки: документные проверки (`check-links.py`, глифы, `check-claude-md.py`,
  статусы фич), `fmt`/`check`/`clippy`, `cargo test --all-features`, формат
  примеров, генерация всех целей, проверка воспроизводимости (два прогона × цели),
  проверка `float`-профилей, цель `rust` (rustc + clippy + сборка Cargo + прогон
  моделей), цель `sv` (verilator + yosys + тестбенчи), `sv-mmio`, цель `c`
  (cmake + `cc -c` для `c-hal`), исполнение харнессов, проверка `iec2c`, проверка
  примеров `book/`. Каждый блок — линейный участок кода, разделяемый без
  переписывания логики.
- **Механизм выбора уже частично есть:** `PRECHECK_STRICT`  и
  `require_tool` дают единую точку «проверка выполняется / пропущен». Пропуск при
  этом **печатается** — тот же приём годится и для намеренного сужения.
- **Стоимость по стадиям не измерена.** Известно только суммарное время
  (порядка 20 минут на рабочей машине). Что в нём занимает `cargo test`, что —
  yosys, что — двойная генерация, **никто не мерил**; оптимизировать без замера
  значит гадать.
- **Кэша нет вовсе.** Каждый прогон повторяет всё, даже если ни один вход
  соответствующего проверки не изменился (например, `book/` не тронут, а проверка
  примеров документа отрабатывает 25 файлов).
- **Ровно этот класс боли фича закрывает осью 5.** Молчаливо суженное
  покрытие неотличимо от пройденного — проверка `c-hal` пропускал два примера из
  одиннадцати, и боль оси 1 прожила в корпусе незамеченной. Всякое ускорение
  через «не проверять» обязано быть **громким**, иначе фича воспроизведёт
  дефект, который 0187 устраняет.

## Направление решения (наметка, не решение)

Прорабатываются варианты по осям:

1. **Ось «состав»** — как назвать и выделить компоненты: по слою (документы /
   линты / тесты / кодоген / проверки целей), по цели генерации (`c`, `rust`, `sv`,
   `st`), по инструменту (быстрые без внешних зависимостей / медленные внешние).
2. **Ось «выбор»** — как запускать подмножество: флаги (`--only sv`,
   `--skip book`), отдельные скрипты-компоненты с тонким `precheck.sh` поверх,
   переменные окружения (как сегодняшний `PRECHECK_STRICT`).
3. **Ось «автоматика»** — выводить ли набор проверок из изменённых путей
   (`git diff --name-only`). Соблазнительно и опасно: правка `semantic/`
   затрагивает **все** цели, и наивное сопоставление «путь → проверка» дало бы
   зелёный прогон при непроверенном изменении.
4. **Ось «кэш»** — пропуск проверки, входы которого не изменились (отпечаток
   содержимого), вместо пропуска по требованию пользователя.
5. **Ось «параллельность»** — независимые проверки (verilator, yosys, `iec2c`,
   cmake) могут идти одновременно; выигрыш без потери покрытия, но вывод
   перестаёт быть линейным и диагностика усложняется.

**Инвариант, не подлежащий торгу:** в CI (`PRECHECK_STRICT=1`) выполняется
**весь** набор, никакого выбора и никакого кэша — иначе `precheck.sh` перестаёт
быть единым источником истины, ради которого он и заведён.

Первая работа стадии анализа — **замер по стадиям**. Без него неизвестно,
даст ли разделение выигрыш вообще: может оказаться, что 80 % времени съедают
две стадии (`cargo test --all-features` и сборка Cargo порождённого Rust), и
дешевле ускорить их, чем строить механизм выбора.

### Context

`scripts/precheck.sh` — единственный вход всех проверок (909 строк, ~30 стадий) и
единственный источник истины для CI. Заказчик поставил задачу разложить его на
компоненты с выборочным запуском: цикл «правка → проверка» стал дороже самой
правки.

Карточка фичи требовала начать с **замера**: «оптимизировать без замера значит
гадать». Замер выполнен 2026-08-01 инструментированной копией скрипта (таймер на
каждой стадии; копия — вне репозитория, рабочий скрипт не трогался).

#### Замер: где на самом деле время

Полный прогон на **тёплом** дереве (сборка уже выполнена), macOS arm64, 12 ядер:

| Стадия | Время | Доля |
|---|---|---|
| `cargo test --all-features -- --test-threads=1` | **218.7 с** | **84 %** |
| проверка тестбенчей `sv` (verilator `--binary`) | **23.0 с** | **8.8 %** |
| проверка воспроизводимости (2 прогона × цели) | 3.4 с | 1.3 % |
| `cargo build` (три вызова) | 2.7 с | 1.0 % |
| формат примеров (`fmt --check`) | 2.0 с | 0.8 % |
| ссылки Markdown | 1.5 с | 0.6 % |
| размер модулей | 1.5 с | 0.6 % |
| проверка `iec2c` | 1.4 с | 0.5 % |
| проверки `sv` / `rust` (линт, синтез, clippy) | 1.1 / 1.0 с | 0.8 % |
| **прочие 20 стадий** (все документные, все `check-*.sh`, генерация, `c-hal`, `sv-mmio`, `book/`) | **< 1 с каждая, ~2 с суммарно** | **~1 %** |
| **Итого** | **261 с (4.4 мин)** | |

**Две стадии — 93 % времени.** Это в точности сценарий, которого опасалась
карточка: «может оказаться, что 80 % времени съедают две стадии, и дешевле
ускорить их, чем строить механизм выбора».

#### Замер: цена параллельных тестов

| Прогон (то же дерево) | Время | Итог |
|---|---|---|
| `cargo test -- --test-threads=1` (контроль) | 146 с | зелёный |
| `cargo test` (параллельно, 12 ядер, `--no-fail-fast`) | **89 с** | **1 упавший тест из ~1400** |

Падает `st_tests::test_plain_st_target_ignores_addresses_and_emits_no_configuration`
с `Os { code: 22, InvalidInput }`. Причина — не параллельность сама по себе, а
то, что каталог вывода уникален **по фикстуре, а не по тесту**:

```rust
fn target_dir(name: &str) -> PathBuf {
    Path::new(env!("CARGO_TARGET_TMPDIR")).join(format!("st_{}", name))
}
```

Несколько тестов используют фикстуру `types_all`, и каждый начинает с
`remove_dir_all` **общего** каталога: один сносит его, пока другой пишет.
Комментарий рядом это признаёт («тесты гоняются в один поток, но общий каталог
всё равно связал бы их друг с другом») — уникальность по фикстуре рассчитана
именно на однопоточность.

**Гонок оказалось две, и вторую полный прогон не показал.** После починки
`target_dir` отдельный прогон набора `st_tests` уронил другой тест: помощник
`compile_st_source` строит каталог по **имени входного файла**, а его берут два
теста. То есть «зелёный полный прогон» тут ничего не доказывает — гонка
проявляется от расклада потоков. Отсюда протокол проверки: не один прогон, а
серия, и отдельно по наборам.

#### Оговорки к замеру (без них цифры врут)

1. **Дерево тёплое.** `cargo check`/`clippy`/`build` показывают доли секунды; на
   холодном они займут минуты. Заявленные в карточке «порядка двадцати минут» —
   это, вероятно, прогон с холодной сборкой, и его отдельно **не мерили**.
2. **Разброс.** Первый однопоточный прогон дал 462 с, повтор — 146 с; аномалия
   не воспроизвелась (почти наверняка конкуренция с фоновым процессом). Прежде
   чем цифра станет основанием решения, протокол требует повторов на незанятой
   машине.
3. **`cargo test` не «чистый Rust»**: внутри сверок работают `cc`, `verilator`,
   `iec2c`, то есть часть этих 218 с — внешние инструменты.

### Decision Drivers

1. **Полный прогон остаётся умолчанием и обязателен перед коммитом.** Всякое
   сужение — громкое; молчаливо суженное покрытие неотличимо от пройденного
   (урок оси 5 [пересмотр задания адресов и доступа к портам](0187-port-io-redesign.md)).
2. **В CI (`PRECHECK_STRICT=1`) — весь набор, без выбора и кэша**, иначе
   `precheck.sh` перестаёт быть единым источником истины.
3. **Выигрыш соразмерен цене.** Механизм, экономящий 2 % времени, не окупает ни
   строчки сложности.
4. **Зависимости стадий реальны:** всё после сборки `taktc` требует её, всё
   после генерации — её. Выбор, игнорирующий это, даст зелёный прогон на
   устаревшем выводе.

### Considered Options

#### Option A. Именованные компоненты + выборочный запуск (исходный замысел)

Разложить скрипт на компоненты (`docs`, `lint`, `test`, `targets:sv`, …), дать
`--only` / `--skip`.

**Pros:**
- прямо отвечает формулировке задачи;
- позволяет гонять один целевой проверка при правке одного генератора.

**Cons:**
- **экономия ≤ 7 %**, если не трогать тесты: все документные и быстрые проверки
  вместе стоят ~2 с из 261 с;
- требует явной модели зависимостей (иначе «только `sv`» проверит вчерашний
  вывод) — сложность растёт, выигрыш остаётся малым;
- заводит второй способ запускать проверки, который может разойтись с CI.

#### Option B. Параллельные тесты (снять `--test-threads=1`)

Развести каталоги тестов по тесту, а не по фикстуре, и убрать принудительную
однопоточность.

**Pros:**
- **146 → 89 с на стадии тестов** (−39 %), то есть ~22 % полного прогона;
- цена входа — правка одной функции в одном файле (подтверждено: падает ровно
  один тест);
- ускоряет и локальный прогон, и CI, не меняя состава проверок — **покрытие не
  сужается вовсе**, драйвер 1 не задет.

**Cons:**
- параллельность может вскрыть другие скрытые связи через общие пути (сегодня
  она ровно одна, но новые тесты обязаны писать в свой каталог);
- порядок вывода тестов перестаёт быть детерминированным.

#### Option C. Кэш по отпечатку входов

Пропускать проверка, входы которого не изменились (хеш каталога/файлов).

**Pros:**
- экономит без участия человека — нельзя «забыть включить проверка»;
- бьёт по дорогим стадиям: тестбенчи `sv` (23 с) при нетронутом `sv` — чистая
  экономия.

**Cons:**
- отпечаток обязан включать **все** входы (исходники компилятора → любая проверка
  целей), иначе кэш соврёт; ошибка здесь равна молчаливо пропущенному проверке;
- в CI кэш запрещён драйвером 2, то есть выигрыш только локальный.

#### Option D. Прогон тестовых наборов параллельно (`cargo nextest`)

`cargo` параллелит тесты **внутри** набора, но наборы гоняет последовательно;
`nextest` снимает это ограничение.

**Pros:**
- потенциально больше, чем B (у проекта ~45 наборов, многие мелкие);
- заодно даёт машиночитаемый отчёт.

**Cons:**
- внешняя зависимость в обязательном пути сборки — решение заказчика;
- требует установки в CI и на машинах разработчиков.

#### Option E. Ничего не делать

**Pros:** нулевая цена; 4.4 минуты на тёплом дереве терпимы.

**Cons:** не отвечает на запрос заказчика; холодный прогон не измерен и может
быть заметно хуже.

### Decision

**Решение заказчика 2026-08-01: принимается Option B** — параллельные тесты,
каталог теста уникален по тесту.

Обоснование: замер показал, что 84 % времени предкоммита — одна стадия
`cargo test`, и однопоточность держалась не на природе тестов, а на **двух
строках** в `st_tests`. Вариант даёт наибольший выигрыш на единицу сложности и
**не трогает состав проверок вовсе** — драйвер 1 (никакого молчаливого сужения)
не задет по построению.

Прочие варианты **не отвергнуты, а отложены**: A (компоненты) экономит ≤ 7 % и
после B станет ещё менее выгодным; C (кэш) и D (`nextest`) остаются кандидатами,
если после B время снова станет мешать. E (ничего не делать) снят выбором B.

### Consequences

#### Положительные

- **`cargo test`: 146 с → 95–127 с** (три параллельных прогона подряд, 12 ядер),
  то есть ~30 % самой дорогой стадии и ~20 % полного предкоммита.
- **Состав проверок неизменен** — ускорение получено без единого пропуска.
- **Устранён скрытый дефект тестов**: гонок оказалось две (каталог по фикстуре и
  каталог по имени входного файла), причём вторая проявилась только при
  отдельном прогоне набора — то есть жила бы дальше незамеченной.

#### Отрицательные / Action items

- Порядок вывода тестов больше не детерминирован — при разборе падения читать
  имя теста, а не позицию в выводе.
- **Новые тесты обязаны писать в свой каталог.** Правило записано в `CLAUDE.md`:
  покраснел параллельный прогон — чинить каталог теста, а не возвращать флаг.
- Холодный прогон по-прежнему не измерен; «двадцать минут» из карточки к нему и
  относятся. Отдельная работа, если заказчик сочтёт нужным.

#### Что остаётся верным независимо от выбора

- **разделение на компоненты само по себе задачу не решает**: 93 % времени лежит
  в двух стадиях, и ни одна из них выбором не убирается — обе обязательны;
- **любой выбранный путь не вправе сужать покрытие молча** (драйвер 1); это
  относится и к кэшу (C), где ошибка в наборе входов равносильна пропуску проверки;
- **однопоточность тестов — не свойство тестов, а следствие одного дефекта**
  (общий каталог на фикстуру), и он подлежит устранению независимо от выбранной
  оси.

#### Acceptance criteria

1. Полный прогон остаётся умолчанием; в `PRECHECK_STRICT=1` состав проверок не
   сужается ничем (ни выбором, ни кэшем).
2. Всякое сужение печатается в вывод — законный пропуск и пропуск-дефект
   различимы.
3. Заявленный выигрыш подтверждён замером **после** правки, тем же протоколом,
   что и до неё.

## Анализ

### Цель и контекст

Заказчик поставил задачу разложить `precheck.sh` на компоненты с выборочным
запуском: цикл «правка → проверка» стал дороже самой правки. Карточка требовала
начать с **замера** — и замер изменил постановку задачи.

[ADR](0190-precheck-selective-gates.md#архитектура-adr) принят 2026-08-01, вариант
**B**: параллельные тесты вместо механизма выбора. Основание — 84 % времени
предкоммита занимает одна стадия (`cargo test`), а все документные и быстрые
проверки вместе стоят около двух секунд, то есть делить было **нечего**.

Анализ переводит принятое решение в требования и критерии.

### Зависимости фичи

- **Зависит от:** нет.
- **Влияние на порядок разработки:** ничего не разблокирует и не блокирует.
  Затрагивает процесс (`precheck.sh`, `CLAUDE.md`), а не язык, поэтому идёт
  независимо от очереди языковых фич.
- **Смежно:** [cI прогоняет весь `precheck.sh` (живые проверки + check-links)](0090-ci-precheck.md) — предкоммит как единый
  источник истины проверок. Изменение наследуется CI автоматически: он вызывает
  тот же скрипт.

### Требования и проверяемые условия

- **R1. Состав проверок не сужается.** Ускорение получено без единого пропуска
  проверки: набор стадий до и после — тот же. Это главное требование; любой выигрыш
  за счёт «не проверять» противоречит уроку оси 5 [пересмотр задания адресов и доступа к портам](0187-port-io-redesign.md).
- **R2. Тесты идут параллельно и зелены.** `cargo test --all-features` без
  `--test-threads=1` завершается без провалов **в серии** прогонов, а не
  однократно: гонка проявляется от расклада потоков.
- **R3. Временный каталог теста уникален по тесту.** Ключ — имя потока (харнесс
  Rust называет поток именем теста); в однопоточном режиме поведение прежнее
  (ключ — фикстура).
- **R4. Правило зафиксировано для будущих тестов.** В живом контексте и рядом с
  командой в скрипте сказано: покраснел параллельный прогон — чинить каталог
  теста, а не возвращать флаг.
- **R5. CI не требует отдельной правки.** Он вызывает `precheck.sh`, значит
  наследует изменение; второго источника истины не появляется.
- **R6. Выигрыш измерен тем же протоколом, что и потеря.** Цифры «до» и «после»
  сняты одинаково, на одном дереве.

### Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | состав стадий предкоммита не изменился | дифф `precheck.sh`: правка — одна строка команды плюс комментарий |
| A2 | серия параллельных прогонов зелёная | `cargo test --all-features --no-fail-fast` ×3 |
| A3 | набор `st_tests` зелен при отдельном прогоне | `cargo test -p takt-lang --test st_tests` ×3 |
| A4 | каталог уникален по тесту | чтение `target_dir`/`compile_st_source`; однопоточный прогон остаётся зелёным |
| A5 | выигрыш подтверждён | замер до/после: 146 с против 95–127 с |
| A6 | предкоммит зелёный целиком | `./scripts/precheck.sh` |

### Декомпозиция разработки

| Задача | Содержание | Затрагивает |
|---|---|---|
| **0190-01** | каталог теста по тесту; снятие `--test-threads=1`; правило для будущих тестов | `takt-lang/tests/targets/st_tests.rs`, `scripts/precheck.sh`, `CLAUDE.md` |

Одна задача: замер показал, что остальные оси (компоненты, кэш, `nextest`) либо
не окупаются, либо требуют отдельного решения заказчика — они отложены ADR, а не
включены в объём.

### Особенности по обратной функциональности

Изменение **процессное**: язык, цели генерации и симулятор не затронуты. Команда
разработчика меняется (`cargo test` вместо `cargo test -- --test-threads=1`) —
старая форма продолжает работать, просто медленнее.

### Риски и зависимости

- **Риск: скрытые гонки за общие пути в других наборах.** Снижение — серия
  прогонов плюс отдельный прогон наборов. Полностью риск не снимается:
  отсутствие падений в серии не доказывает отсутствия гонки. Поэтому R4
  фиксирует, что делать при покраснении, — правило важнее разовой проверки.
  **Оправдался при разработке:** вторая гонка проявилась только на отдельном
  прогоне набора, полный прогон её не показал.
- **Риск: недетерминированный порядок вывода** затрудняет чтение логов. Принят:
  имя упавшего теста печатается всегда.
- **Риск: экономия окажется меньше на CI-машине** (меньше ядер). Не проверялся —
  CI недоступен (Actions заблокированы по биллингу); в худшем случае поведение
  вернётся к сегодняшнему, покрытие при этом не меняется.

## Разработка

### Задача

#### Что было

Предкоммит гонял `cargo test --all-features -- --test-threads=1`, а живой
контекст объяснял флаг так: «однопоточно — иначе гонки за общие файлы». Замер
стадии ([ADR](0190-precheck-selective-gates.md#архитектура-adr)) показал, что эта
стадия — **84 % времени** всего предкоммита, то есть флаг стоил дороже, чем всё
остальное вместе взятое.

Проверка того, чем именно держалась однопоточность, дала неожиданный ответ:
**двумя строками в одном файле**, а не природой тестов.

#### Что сделано

##### Каталог теста строится по тесту, а не по фикстуре

`takt-lang/tests/targets/st_tests.rs`, два помощника:

| Помощник | Ключ каталога был | Кто сталкивался |
|---|---|---|
| `target_dir` | имя фикстуры (`st_types_all`) | 3 теста на `types_all`, 2 на `enum_struct` |
| `compile_st_source` | имя входного файла | 2 теста на одном имени |

Оба начинают работу с `remove_dir_all`, поэтому параллельно один тест сносил
каталог, пока другой в него писал: `Os { code: 22, InvalidInput }` — и ошибка
приходила **как отказ компиляции ST**, то есть выглядела дефектом генератора, а
не гонкой теста.

Ключ уникальности — **имя потока**: тестовый харнесс Rust называет поток именем
теста. В однопоточном режиме имени нет (тест идёт в главном потоке), ключом
остаётся фикстура — там гонок и не бывает, поведение прежнее.

##### `--test-threads=1` снят

`scripts/precheck.sh` гоняет `cargo test --all-features`. Рядом — комментарий,
объясняющий, **чем** держалась однопоточность и что делать, если параллельный
прогон когда-нибудь покраснеет: чинить каталог теста, а не возвращать флаг.
Возврат спрятал бы гонку и вернул бы всю стоимость разом.

CI правок не потребовал: он вызывает тот же `precheck.sh`  и наследует
изменение автоматически — ровно ради этого единый вход и заведён.

##### Живой контекст обновлён

Раздел «Команды» больше не предписывает `--test-threads=1`; в «Технических
подводных камнях» появился пункт с ключом уникальности и правилом для новых
тестов.

#### Чем проверялось (и почему одного прогона мало)

**Вторую гонку полный прогон не показал.** После починки `target_dir`
полный `cargo test --all-features` был зелёным — а отдельный прогон набора
`st_tests` уронил другой тест (`test_st014_accepts_valid_names`). Гонка
проявляется от расклада потоков, поэтому «зелено с первого раза» здесь не
доказательство. Отсюда протокол: **серия** прогонов и отдельно по наборам.

| Проверка | Результат |
|---|---|
| `cargo test -p takt-lang --test st_tests` ×3 | 24 теста, зелёные все три раза |
| `cargo test --all-features --no-fail-fast` ×3 | 0 провалов; **127 / 102 / 95 с** |
| контроль: `-- --test-threads=1` | 146 с |
| `./scripts/precheck.sh` | зелёный |

**Выигрыш: ~30 % самой дорогой стадии** (146 с → ~100 с медианно), то есть около
20 % полного предкоммита. Состав проверок при этом **не изменился ни на одну** —
ускорение получено без единого пропуска, что и требовал драйвер 1 ADR.

#### Что не сделано (границы задачи)

- **Выборочный запуск компонентов (Option A) не делается** — замер показал
  экономию ≤ 7 %, и после этой задачи она станет ещё меньше. Вариант отложен, а
  не отвергнут.
- **Кэш по отпечатку входов (C) и `cargo nextest` (D)** — кандидаты на случай,
  если время снова станет мешать.
- **Холодный прогон не измерен.** Все цифры сняты на тёплом дереве; «двадцать
  минут» из карточки фичи относятся, по-видимому, именно к холодному, и это
  отдельная работа.
- **Гонки за общие пути вне `st_tests` не искались специально**: серия прогонов
  их не выявила, но отсутствие в серии — не доказательство отсутствия вообще.

## Тест-план

### Область и цель

Фича процессная: язык не меняется, поэтому проверяется не поведение программ, а
**свойства самой проверки** — что она не сузилась и что стала быстрее.

Три класса:

1. **Покрытие не изменилось** — состав стадий тот же (главное требование R1).
2. **Параллельность безопасна** — серия прогонов зелёная, включая отдельные
   наборы.
3. **Выигрыш измерен** — одинаковым протоколом до и после.

**Особенность этой фичи: однократный прогон ничего не доказывает.** Гонка
проявляется от расклада потоков — при разработке вторая гонка вскрылась только
на отдельном прогоне набора, тогда как полный прогон был зелёным. Поэтому все
проверки параллельности — **серийные**.
