## Архитектура (ADR)

- **Статус:** Accepted
- **Дата:** 2026-08-20
- **Фича:** [../features/0348-st-array-parameter.md](0348-st-array-parameter.md)

### Контекст

Замер-20: `first(arr)` при `fn first(a: [u8;2])` давал `iec2c` «Data
type incompatibility for value passed in position 1» — при **нулевом** коде
возврата `taktc`; эталон, `c`, `rust` и `sv` вход исполняли.

Пробы MatIEC (по одной причине за раз):

| Форма параметра | `iec2c` | `cc` на его выводе |
|---|---|---|
| `a : ARRAY [0..1] OF USINT` (аноним) | **отказ** | — |
| `a : U8Arr2` в `VAR_INPUT` | принимает | **не собирается**: «operand of type '__ARRAY_OF_USINT_2' where arithmetic or pointer type is required» |
| `a : U8Arr2` в `VAR_IN_OUT` | принимает | собирается, значение верное |

То есть форму выбрал **полный цикл** `iec2c` → `cc`: одна трансляция сказала бы,
что `VAR_INPUT` годится.

Кроме того, типы аргумента и параметра обязаны **совпадать**: анонимный
`ARRAY […]` против именованного MatIEC не принимает (проба).

### Решение

- Имя типа строится по **форме** массива — `TAKT_ARR_<размер>_<ЭЛЕМЕНТ>`
  (`st_type::array_form_name`), а не по владельцу: все переменные и параметры
  одной формы получают один тип. Этим он отличается от именованных типов фичи, где речь о **конкретной** переменной, разделяемой с под-моделью.
- Параметры-массивы объявляются в `VAR_IN_OUT`; аргументы вызова
  переупорядочиваются под секции (`reorder_by_sections`), потому что
  позиционный вызов IEC следует порядку **объявления**.
- Именованную форму получают **только** массивы, чья форма встречается в
  параметрах функций: список считается один раз и общий у продюсера типов и у
  каждого объявления (урок ADR).

### Границы

- **Массив по значению не передать:** `VAR_IN_OUT` — ссылка, и функция,
  меняющая параметр, изменит массив вызывающего. Сегодня язык такой записи не
  порождает (аргумент — переменная модели), но это названное свойство формы.
- **Литерал-агрегат аргументом** по-прежнему отвергается (`ST-017`).

### Отвергнутые варианты

1. **`VAR_INPUT` с именованным типом.** Принимается разбором и даёт невалидный
   C — худший исход: отказ приходит от `cc` на выводе `iec2c`.
2. **Имя типа по владельцу (как 0210).** Функция вызывается с разными
   массивами; тип обязан зависеть от формы, а не от места объявления.

### Последствия

- Вывод корпуса не изменился: массивов, передаваемых в функции, в `examples/`
  нет, а прочие остаются анонимными.

## Анализ

### Цель и контекст

Кандидат заведён замером фичи: там передача массива аргументом была одной
из причин, маскированных отказом семантики.

### Зависимости фичи

- **Зависит от:** 0210 (именованный тип массива для `VAR_IN_OUT`), 0346
  (индексация параметра — без неё функция не строилась). Закрыты.
- **Влияние на порядок разработки:** снимает кандидата.

### Требования и проверяемые условия

- **R1.** `iec2c` принимает вывод.
- **R2.** **C, порождённый `iec2c`, собирается** — без этого условия форма
  выбрана бы неверно.
- **R3.** Значения совпадают с эталоном.
- **R4.** Вывод корпуса не изменился.

### Разбор

#### Почему проверка идёт до `cc`

`VAR_INPUT` с массивом `iec2c` **разбирает**. Дефект виден только на следующем
шаге: порождённый C не компилируется. Правило для будущих проб цели `st`:
форма, принятая разбором, не считается годной, пока не собран вывод.

#### Почему имя типа по форме

Функция вызывается с разными массивами, поэтому тип обязан зависеть от формы
(размер и элемент), а не от владельца, как в 0210. Отсюда же ограничение:
именованными становятся **только** формы, встречающиеся в параметрах, — иначе
правка задела бы каждый массив вывода.

#### Порядок аргументов

Параметры-массивы уходят в другую секцию, а позиционный вызов IEC следует
порядку объявления. Без перестановки `at_index(arr, 1)` печатался как
`at_index(arr, 1)` при объявлении `(i, a)` — «Data type incompatibility …
position 1».

### Риски

- **Функция, меняющая параметр-массив.** `VAR_IN_OUT` — ссылка; поведение
  разошлось бы с эталоном. Сегодня язык такой записи не даёт — граница названа.

### Задача

#### Состав правки

#### Проверено

- `iec2c` принимает вывод; порождённый им C собирается и даёт `7 9 3` — как
  эталон.
- Вывод корпуса не изменился; `cargo test` зелёный.

### Почему тесты именно такие

`VAR_INPUT` с массивом `iec2c` **разбирает** — и порождает C, который не
компилируется. Поэтому контроль проверяет **полный цикл**: принятая разбором
форма не считается годной, пока не собран вывод.

Вход с параметрами обеих секций обязателен: перестановка аргументов видна
только на нём.

1. **Разбор — не доказательство.** Форма, принятая `iec2c`, дала невалидный C.

## Итог (что сделано)

**Массив передаётся именованной формой через `VAR_IN_OUT`.**

- **Форму выбрал полный цикл `iec2c` → `cc`, а не одна трансляция:**
  `VAR_INPUT` с массивом инструмент **разбирает**, но порождает C, который не
  компилируется («operand of type '__ARRAY_OF_USINT_2' where arithmetic or
  pointer type is required»). Правило для будущих проб цели `st`: форма,
  принятая разбором, не годна, пока не собран вывод.
- **Имя типа — по форме** (`TAKT_ARR_2_USINT`), а не по владельцу: функция
  вызывается с разными массивами. Этим он отличается от именованных типов 0210.
- **Именованными становятся только формы из параметров:** иначе правка задела
  бы каждый массив вывода.
- **Порядок аргументов следует секциям:** параметры-массивы объявлены в
  `VAR_IN_OUT`, а позиционный вызов IEC идёт по порядку объявления. Вход с
  параметрами обеих секций обязателен — перестановка видна только на нём.
- **`VAR_IN_OUT` — ссылка:** функция, меняющая параметр, изменила бы массив
  вызывающего. Сегодня язык такой записи не порождает; граница названа.
