## Краткое описание

Состояние может нести композицию (`= A | B`) **и** собственные рёбра. Правило
языка задано фичей [симулятор исполняет реализацию состояния с переходом next](0181-sim-state-implementation-tick.md): реализация
тикается до проверки переходов, и переход берётся по её завершении. Эталон это
исполняет, а все восемь целей печатали только `next`, теряя `ref`-рёбра.

> Фича заведена **по решению заказчика 2026-08-19** и взята **вне очереди**
> (правило 19 п. 4): расхождение молчаливое и даёт другой автомат в прошивке
> (`Tier 1`), тогда как соседние по очереди записи — честные отказы. Найдена
> контрольным входом при закрытии
> [проверку состояния под-модели переводят не все цели](0267-state-of-model-in-targets.md).

## Документирование (правило 24)

когда проверяются собственные рёбра, в каком порядке относительно `next` и что
происходит, если не сработало ни одно.

- **Related issues:** [Фича](0303-composition-state-conditional-edge.md); найдено контрольным входом при закрытии [проверку состояния под-модели переводят не все цели](0267-state-of-model-in-targets.md); правило «переход берётся по завершении реализации» — [симулятор исполняет реализацию состояния с переходом next](0181-sim-state-implementation-tick.md); порядок `ref` перед `next` — там же; безусловное ребро завершает цепочку — [цель c печатает лишний break после безусловного перехода](0213-c-redundant-break.md)

### Context

Состояние может нести **реализацию** — композицию моделей — и при этом иметь
собственные рёбра:

```takt
start Entry = Worker | Idler {
    ref Finish: flag = 3;      // собственное ребро состояния-композиции
}

state Finish;
```

Правило языка задано фичей [симулятор исполняет реализацию состояния с переходом next](0181-sim-state-implementation-tick.md):
реализация тикается **до** проверки переходов, и переход берётся **по её
завершении** — на том же такте. Эталон исполняет это буквально: после
завершения композиции он проверяет переходы состояния — сначала `ref`-рёбра в
порядке объявления, затем `next` (последним, «иначе безусловный `next` затенил
бы их все» — комментарий `build_transitions`).

**Замер-19 (`scripts/probe.sh`, правило 30) показал, что цели этого не
делают: они печатают только `next`, а собственные `ref`-рёбра теряют.**

| Вход | Эталон | Все восемь целей |
|---|---|---|
| `ref Finish: flag = 3;`, условие истинно в момент завершения | → `Finish` | → `END` |
| `ref Finish: flag = 99;`, условие ложно всегда | **остаётся** в `Entry` | → `END` |
| `next Finish;` (контроль) | → `Finish` | → `Finish` |

Порождённый C на первом входе:

```c
case PLAINCOND_ENTRY: {
    PlaincondWorker_tick(&model->entry.worker0, model);
    PlaincondIdler_tick(&model->entry.idler1, model);
    if (PlaincondWorker_is_done(…) && PlaincondIdler_is_done(…)) {
        model->state = PLAINCOND_END;   // ребро `ref Finish` не напечатано
        break;
    }
    break;
}
```

Состояние `Finish` в перечислении объявлено и **недостижимо**. Вывод валиден,
`cc -Wall -Wextra -Werror` молчит, `verilator` и `yosys` молчат, `iec2c`
принимает — **автомат другой, и об этом не говорит никто**. Это `Tier 1` по
шкале `FEATURES.md`.

**Расхождение двустороннее.** Мало того, что цели не идут в `Finish`, — они
уходят в `END` там, где эталон **ждёт** (второй вход): при ложном условии
композиция уже завершена, но переход не разрешён, и узел остаётся в состоянии.

**Контроль отделил форму от предмета.** Замер снят дважды: с формой
`S(Модель) = Состояние` и с обычным условием (`flag = 3`) — результат один и
тот же. То есть дело не в виде условия, а в том, что рёбра состояния-композиции
не печатает никто. Третий контроль (`next`) показывает, что механизм перехода у
целей есть — не хватает именно `ref`-рёбер.

### Decision Drivers

1. **Норма уже определена и записана** — правилом и порядком
   `build_transitions` эталона. Речь не о выборе семантики, а о том, что цели её
   не исполняют.
2. **Молчание — худшая часть дефекта.** Инструменты целевых языков этот класс не
   видят: вывод валиден при любом исходе.
3. **Механизм перехода в целях есть.** `next` печатается всеми; недостаёт
   печати `ref`-рёбер в той же ветви.
4. **Отказ вместо перевода был бы регрессом:** запись законна, эталон её
   исполняет, а корпус её не содержит — то есть запрет ударил бы по чужим
   моделям ради нашего удобства.

### Considered Options

#### Option A. Печатать `ref`-рёбра в ветви завершения композиции (норма эталона)

Внутри `if (композиция завершилась)` цель печатает сначала условные рёбра
состояния (в порядке объявления; безусловное завершает цепочку),
затем `next` либо `END`.

**Pros:**
- цели начинают исполнять уже записанное правило языка;
- механизм переиспользуется: печать рёбер у обычных состояний есть в каждой
  цели;
- расхождение снимается в **обе** стороны — и «не пошёл в `Finish`», и «ушёл в
  `END` вместо ожидания».

**Cons:**
- правка в четырёх целях; несогласованность видна только сверкой (вывод остаётся
  валидным).

#### Option B. Отвергать такую запись семантикой

**Pros:** одна проверка вместо четырёх правок.

**Cons:** запрещает законную и работающую в эталоне конструкцию; правило
прямо описывает её поведение. Это регресс языка ради удобства целей.

#### Option C. Оставить как есть, задокументировав различие

**Pros:** ноль правок.

**Cons:** документирует расхождение вместо его устранения — прошивка ведёт себя
не так, как отлаженная в симуляторе модель. Ровно тот класс, ради которого
заведены потактовые сверки.

### Decision

Принимается **Option A**.

Цели `c`, `st`, `rust`, `sv` (а с ними `c-hal`, `st-at`, `sv-mmio`) печатают
собственные рёбра состояния-композиции внутри ветви завершения — **перед**
переходом по `next`/`END`, в порядке объявления. Порядок и приоритет берутся у
эталона: `ref` вперёд, `next` последним.

Контроль — **потактовые сверки**, а не проверки: инструменты целевых языков принимают
и прежний, и новый вывод.

### Consequences

#### Положительные

- эталон и цели сходятся на записи, которую язык допускает с 0181;
- недостижимое состояние в перечислении перестаёт быть недостижимым;
- ожидание при ложном условии воспроизводится в прошивке.

#### Отрицательные / Action items

- вывод целей на таких входах меняется — но в `examples/` записи нет ни одной
  (проверено), поэтому снапшоты корпуса не двигаются;
- в документ (`book/`, раздел о композиции) добавляется описание перехода из
  состояния-композиции: когда проверяются рёбра и почему `next` идёт последним.

#### Acceptance criteria

1. Вход с истинным условием: эталон и цели `c`, `sv`, `rust`, `st` дают
   переход в `Finish` (потактовые сверки).
2. Вход с ложным условием: все они **остаются** в состоянии-композиции.
3. Контроль `next` — прежнее поведение сохранено.
4. Безусловное `ref`-ребро завершает цепочку: `next`/`END` после
   него не печатается.
5. Корпус и проверки целей не изменились; `./scripts/precheck.sh` зелёный.

## Анализ

### Цель и контекст

Свести цели с эталоном на записи `state S = A | B { ref T: условие; }`.

Замер-19: эталон исполняет собственные рёбра состояния после
завершения композиции — сначала `ref` в порядке объявления, затем `next`. Все восемь целей печатают **только** `next`, а рёбра теряют, —
вывод валиден, автомат другой, диагностики нет ни у кого.

Фича взята **вне очереди решением заказчика 2026-08-19** (правило 19 п. 4):
запись даёт `Tier 1`, тогда как соседние по очереди — честные отказы.

### Зависимости фичи (правило 17/19)

- **Зависит от:** нет. Правило языка задано закрытой фичей; правка живёт в
  четырёх генераторах и в общем слое карты (`semantic::minimap`).
- **Влияние на порядок разработки:** снимает кандидата, заведённого при
  закрытии 0267. Никого не блокирует.

### Требования и проверяемые условия

- **R1. Сработавшее ребро ведёт в своё состояние.** По завершении композиции
  цели проверяют `ref`-рёбра в порядке объявления и переходят в цель первого
  сработавшего.
- **R2. Несработавшее ребро не завершает автомат.** Если переходы у состояния
  есть, но ни один не сработал, автомат **остаётся** в состоянии; `END`
  подставляется только состоянию без переходов — как у эталона.
- **R3. `next` идёт последним.** Порядок «`ref`, затем `next`» сохранён:
  безусловный `next` не должен затенять рёбра.
- **R4. Безусловное `ref` завершает цепочку**: за ним не
  печатается ни `next`, ни `END`.
- **R5. Достижимость учитывается картой.** Состояние, достижимое из композиции
  по `ref`, попадает в карту целей — иначе цель о нём не знает вовсе.
- **R6. Прежнее поведение цело.** Корпус, снапшоты, проверки целей не меняются.

### Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | Переход по сработавшему ребру | потактовая сверка эталон ≡ C |
| A2 | Ожидание при несработавшем | потактовая сверка эталон ≡ C (контрольный вход) |
| A3 | Все четыре цели переводят | `scripts/probe.sh` + проверки целей |
| A4 | Карта видит достижимое состояние | вывод `rust` содержит вариант состояния |
| A5 | Регресс | `./scripts/precheck.sh`, снапшоты корпуса без изменений |

### Особенности по обратной функциональности

Правило 11. Меняется **вывод целей** на записях, которые прежде переводились
неверно: автомат приводится к эталону. Обратной совместимости это не нарушает —
прежнее поведение было дефектом, а не контрактом; в `examples/` таких записей
нет ни одной (проверено: снапшоты не изменились).

**Версия языка не меняется**: синтаксис и семантика прежние — цели начинают
исполнять уже записанное правило (0181).

### Правило 29: редакторский слой

Правок **не требует**: ни лексика, ни синтаксис, ни семантика не менялись.
Затронуты печатники четырёх целей и слой карты; LSP берёт диагностики из общей
точки и порождённый код не разбирает.

### Документирование (правило 24)

**Требуется:** раздел о композиции (`book/src/09-imports/`) должен сказать, что
у состояния-композиции могут быть собственные рёбра, когда они проверяются и в
каком порядке относительно `next`.

### Риски и зависимости

- **Риск: правка карты (`minimap`) заденет другие цели.** Она добавляет в обход
  достижимые по `ref` состояния — то есть карта может **вырасти**. Снижение:
  прогон всех проверок и сравнение снапшотов корпуса (не изменились).
- **Риск: `END` перестанет печататься там, где он нужен.** Условие сужено до
  «есть рёбра»; контрольный вход с ложным условием проверяет обе ветви.
- **Риск: расхождение между четырьмя целями.** Каждая правится отдельно, но
  сверка ведётся с одним эталоном; для `sv` и `rust` вывод дополнительно
  проверяется инструментов.

## Разработка

### Задача

#### Что было

У состояния с реализацией (`= A | B`) цели печатали **только** переход по
`next`/`END`; собственные `ref`-рёбра терялись. Эталон их исполняет (правило: по завершении реализации проверяются переходы состояния — `ref` в порядке
объявления, `next` последним).

Расхождение двустороннее: цели не шли в целевое состояние, **и** уходили в
`END` там, где эталон ждёт (условие ложно → переходов нет → узел остаётся).

#### Что сделано

**Общий слой.** `semantic::minimap::visit_state` в ветви `StateNode::Implement`
кладёт в обход не только `next`, но и цели `ref`-рёбер. Прежде состояние,
достижимое из композиции по ребру, в карту не попадало вовсе — цель `rust` о
нём не знала (его не было ни в перечислении состояний, ни в таблице).

**Цели.**

- `c` — `generate_extend_transition` печатает рёбра (`generate_state_transitions`)
  перед `next`/`END`; функция печати рёбер стала возвращать «было безусловное».
  Заодно снята **копия** этой логики в ветви одиночной модели
  (`StateExtend::Model`): она несла своё «next либо END» и теряла рёбра;
- `rust` — `emit_extend_transition` зовёт `emit_transitions` перед `next`/`END`;
- `st` — печать рёбер вынесена в новый модуль `st_edges.rs` (файл упирался в
  лимит размера, а звать её нужно из **двух** мест) и вызывается из
  `st_compose::emit_state_exit` — общей точки выхода параллельной композиции и
  последнего шага конкатенации;
- `sv` — `emit_parent_transition` зовёт `emit_transitions` (та стала
  `pub(crate)` и возвращает «было безусловное»).

Во всех четырёх целях `END` подставляется **только** состоянию без рёбер: у
эталона узел завершается при пустом списке переходов.

#### Проверки

```sh
cargo test --test conformance composition_edge
./scripts/precheck.sh
```

- потактовые сверки эталон ≡ C на двух входах (сработавшее и несработавшее
  ребро);
- `scripts/probe.sh` — все восемь целей переводят вход, трасса эталона
  прежняя;
- снапшоты `examples/generated` **не изменились**: записи такого вида в корпусе
  нет.

## Отчёт о тестировании

### Резюме

**Пройдено, фича готова к закрытию.** Молчаливое расхождение `Tier 1` снято:
