- **Статус:** **ГОТОВО** (закрыта 2026-07-27)

## Краткое описание

Определить **нормативно** семантику переполнения целых типов и привести к ней
все цели генерации. Сегодня семантика не определена: один и тот же счётчик даёт
разные результаты в разных целях, а порождённый Rust **падает**.

> Фича зарегистрирована из бэклога кандидатов (отобрана заказчиком 2026-07-27); далее проходит жизненный цикл по правилу 17.

## Что известно на входе

Живая проба (аудит 2026-07-27), модель `var t: u8 := 250; always { t := t + 1; }`
— типовая конструкция всех примеров книги (`beacon`, `traffic`, `watchdog`, `lift`):

- **симулятор** — `255 → 0` (wraparound, прогон `takt-sim`);
- **цель `c`** — `uint8_t`, wraparound;
- **цель `sv`** — `logic [7:0]`, wraparound;
- **цель `rust`** — печатает `self.t += 1` и **паникует**:
  `attempt to add with overflow` (проба: `rustc` + драйвер, паника на 6-м такте).
  В release-профиле — молча wraparound, то есть **поведение зависит от профиля
  сборки пользователя**, а в `no_std` паника означает останов системы;
- **цель `st`** — поведение **не проверялось**, проверить в объёме фичи.

Отдельный слой: у языка есть **знаковые** типы (`i8`/`i16`/`i32`,
`semantic/type_node.rs:95`), а знаковое переполнение в C — **UB**.

## Направление решения (наметка, не решение)

- Нормативное правило по образцу правила 3 [fixed-point Q(m.n) как тип языка](0061-fixed-point-type.md)
  (там wraparound для `q(m, n)` зафиксирован **явно**, чтобы автор не принял
  умолчание за обещание).
- Цель `rust`: `wrapping_add`/`wrapping_sub`/`wrapping_mul` в `rust_expr`.
- Цель `c`: для знаковых — `-fwrapv` в контракте сборки либо беззнаковая
  арифметика с приведением.
- Потактовые сверки переполнения во **всех** `conformance_*` (иначе повторится
  урок: «проверка доказывает компилируемость, но не верность»).

Окончательный выбор — за стадиями **архитектуры** (ADR) и **анализа**: раздел
выше фиксирует то, что уже проверено, а не предрешает реализацию.

- **Date:** 2026-07-27

### Context

Аудит 2026-07-27 показал живой пробой: типовой счётчик
`var t: u8 := 250; always { t := t + 1; }` — конструкция, которая есть в
**каждом** примере книги (`beacon`, `traffic`, `watchdog`, `lift`) — ведёт себя
в целях по-разному. Симулятор, `c` и `sv` считают дальше (`255 → 0`), а
порождённый **Rust паникует**: `attempt to add with overflow`. Хуже того, в
release-профиле тот же код молча оборачивается — то есть поведение прошивки
зависело от **профиля сборки пользователя**.

При этом правило у проекта **уже есть**, только не названо правилом языка. Анализ
[починка вычислителя выражений симулятора](0025-simulator-expression-eval.md#архитектура-adr) фиксирует принцип: «определённое в
C поведение — воспроизводим; неопределённое (UB) — не воспроизводим и не
паникуем, а диагностируем», и из него два следствия:

- **S1** — переполнение беззнакового: в C определено (обёртка mod 2ⁿ),
  симулятор её воспроизводит;
- **S2** — переполнение знакового: в C это **UB**, симулятор **диагностирует**
  (`SIM-003`).

То есть эталон определён, а расхождение целей с ним никем не проверялось: сверки
`conformance_*` переполнения не касались вовсе, поэтому дефект цели `rust` дожил
до аудита. Поведение цели `st` при переполнении не проверялось **никогда**.

### Decision Drivers

1. **Эталон уже есть** — задача не изобрести правило, а **возвести его в норму
   языка** и привести цели к нему.
2. **Прошивка не должна зависеть от профиля сборки.** Паника в debug и обёртка в
   release — это два разных изделия из одного исходника.
3. **Проверять, а не декларировать.** Урок: проверка доказывает, что вывод
   компилируется, но не что он верен; нужна потактовая сверка.
4. **Не расширять объём.** Знаковое переполнение — отдельная тема (в C это UB),
   и «чинить» его в целях означало бы изобретать семантику, которой у языка нет.

### Considered Options

#### Option A. Возвести S1/S2 в правило языка; цель `rust` привести к S1

Беззнаковое переполнение — нормативная обёртка `mod 2ⁿ`; цель `rust` печатает
`wrapping_add`/`wrapping_sub`/`wrapping_mul` для беззнаковых операндов.
Знаковое — ошибка программы (симулятор диагностирует, цели не обязаны совпадать).
Сверки переполнения добавляются во **все четыре** цели.

**Pros:**
- Совпадает с уже принятым эталоном (0025), ничего не переопределяет.
- Устраняет зависимость поведения от профиля сборки.
- Малый объём: печать трёх операций в одном печатнике плюс четыре сверки.
- Знаковый случай остаётся честно названным «ошибкой программы», а не
  замаскированным.

**Cons:**
- Порождённый Rust становится многословнее (`a.wrapping_add(b)` вместо `a + b`).
- Знаковое переполнение по-прежнему ведёт себя в целях по-разному (но теперь это
  **названо** и задокументировано).

#### Option B. Обёртка для **всех** целых в цели `rust` (и знаковых тоже)

**Pros:**
- Единообразие внутри цели `rust`; никакой зависимости от профиля.

**Cons:**
- **Молча** расходится с эталоном: симулятор на знаковом переполнении даёт
  `SIM-003`, а прошивка тихо продолжит с другим значением. Проект такие
  расхождения считает худшим исходом («один вход — четыре ответа, и три из них
  молча»).
- Отнимает у разработчика единственный бесплатный сигнал об ошибочной программе
  (паника debug-профиля).

#### Option C. Диагностировать переполнение во всех целях (проверки в времени выполнения)

**Pros:**
- Полное совпадение с эталоном, включая знаковый случай.

**Cons:**
- Цена в коде: проверка на каждой арифметической операции — недопустимо для
  прошивки МК и **невыразимо** в RTL (цель `sv`), где «сообщить об ошибке»
  некому.
- Меняет назначение целей: они порождают управляющую логику, а не отладочный
  время выполнения.

### Decision

Принимается **Option A**.

**Правило языка (нормативно):**

1. **Переполнение беззнакового целого — обёртка по модулю `2ⁿ`.** Одинаково у
   эталона-симулятора и у всех целей генерации; проверяется потактовыми сверками.
2. **Переполнение знакового целого — ошибка программы.** Симулятор
   диагностирует (`SIM-003`) и останавливает прогон; поведение порождённого кода
   в этом случае языком **не гарантируется** (в C это UB). Программа, полагающаяся
   на переход знакового через край, некорректна.

**Реализация:** цель `rust` печатает беззнаковую арифметику `+`, `−`, `*` как
`wrapping_add`/`wrapping_sub`/`wrapping_mul` (тип операнда определяется уже
существующим `expression_type`); свёртка в составное присваивание (`x += 1`) для
таких узлов отключена — она вернула бы панику. Знаковая арифметика печатается
как прежде: паника debug-профиля — полезный сигнал об ошибочной программе, а не
дефект.

### Consequences

#### Положительные

- Прошивка на Rust больше не зависит от профиля сборки в вопросе переполнения.
- Правило названо и **проверено исполнением** во всех четырёх целях
  (`conformance_{c,rust,sv,st}`), а не заявлено в документации.
- Поведение цели `st` при переполнении проверено **впервые**.
- Документация языка перестала утверждать неверное: прежняя формулировка
  «арифметика выполняется по модулю разрядности типа» распространяла обёртку и
  на знаковые типы, где её нет.

#### Отрицательные / Action items

- **Знаковое переполнение остаётся разноголосым** (симулятор — диагностика,
  C — UB, Rust — паника/обёртка по профилю, SV — обёртка). Это **названо**
  правилом («программа ошибочна»), но не устранено; полное устранение — Option C,
  отвергнутый по цене.
- **Порождённый Rust многословнее.** Цена принята: читаемость уступает
  предсказуемости.
- **Сверка ST идёт с поправкой на INIT-сдвиг** цели `st` (существующий долг
  контракта 0033, к переполнению отношения не имеющий) — по той же конвенции,
  что уже принята в Q-сверке.

#### Acceptance criteria

1. `wrapping_*` печатается для беззнаковой арифметики в цели `rust`; свёртка в
   `+=` для таких узлов не применяется.
2. Потактовая сверка переполнения проходит у **всех четырёх** целей.
3. Контроль взведён: откат правки генератора обязан красить сверку `rust`.
4. Правило записано в документ описания языка (раздел «Типы»), включая явное
   различие беззнакового и знакового случаев.
5. `./scripts/precheck.sh` зелёный; изменения в `examples/generated/rust`
   объяснимы (обёртка вместо `+`).

> Диаграмма по правилу 18 **не требуется**: синтаксис не меняется — нормируется
> семантика уже существующей арифметики.

## Анализ

### Цель и контекст

Возвести уже существующий эталон (S1/S2 анализа
[починка вычислителя выражений симулятора](0025-simulator-expression-eval.md#анализ)) в **правило языка**, привести к нему
цель `rust` и проверить исполнением все четыре цели. Решение — Option A
[ADR](0127-int-overflow-semantics.md#архитектура-adr).

### Зависимости фичи (правило 17/19)

- **Зависит от:** `нет`.
- **Влияние на порядок разработки:** **разблокирует
  [модель времени в языке: литерал длительности и частота такта](0134-language-time-model.md)** (модель времени): разрядность
  счётчика времени выбирает компилятор, и без определённой семантики
  переполнения выбор не обоснован.

### Что измерено до правки

| Цель | `u8`, `255 + 1` | `i8`, `127 + 1` |
|---|---|---|
| симулятор (эталон) | `0` — обёртка (S1) | **`SIM-003`**, прогон остановлен (S2) |
| `c` | `0` (тип `uint8_t`, обёртка определена C11 6.2.5p9) | **UB** (`int8_t`) |
| `rust` | **паника** `attempt to add with overflow` (debug) / `0` (release) | паника (debug) / обёртка (release) |
| `sv` | `0` (регистр `logic [7:0]`) | обёртка |
| `st` | **не проверялось никем** | не проверялось |

Ключевое: у цели `rust` результат зависел от **профиля сборки пользователя**, а
конструкция-источник (`always { t := t + 1; }`) есть в каждом примере книги.

### Требования и проверяемые условия

- **R1. Правило названо.** Беззнаковое — обёртка `mod 2ⁿ`; знаковое — ошибка
  программы. Записано в документ описания языка, а не только в анализ.
- **R2. Цель `rust` приведена к S1** — беззнаковая арифметика печатается
  обёрткой; результат не зависит от профиля сборки.
- **R3. Знаковый случай не «чинится» молча.** Обёртка для знаковых **не**
  печатается: тихое расхождение с эталоном (`SIM-003`) хуже паники.
- **R4. Проверка исполнением, а не декларацией.** Потактовая сверка переполнения
  во **всех четырёх** целях.
- **R5. Контроль взведён.** Откат правки генератора обязан красить сверку `rust`.
- **R6. Свёртка в `+=` не возвращает панику.** `x := x + 1` над беззнаковым не
  должен схлопываться в `x += 1`.

### Критерии приёмки и способ проверки

### Особенности по обратной функциональности

**Меняется вывод цели `rust`** для любой беззнаковой арифметики: `a + b` →
`a.wrapping_add(b)`. Это **исправление**, а не поломка: прежний вывод в
debug-профиле паниковал вместо счёта. Программы, полагавшиеся на панику как на
сигнал (её не было в контракте), не существуют по построению — контракт языка
такого не обещал.

Вывод целей `c`, `sv`, `st` **не меняется** (там правило выполнялось само).
Знаковая арифметика во всех целях печатается как прежде.

### Риски и зависимости

- **Риск: обёртка для знаковых «за компанию».** Снят решением R3 и явной
  проверкой: знаковый `+` печатается прежним оператором.
- **Риск: сверка проходит потому, что обе стороны стоят.** Снят пиннингом трасс
  (ожидаемая последовательность записана числом в каждом тесте) и проверкой
  взведённости (A7).
- **Риск: сверка `st` невозможна из-за сдвига тактов.** Реализовался частично:
  цель `st` тратит такт на вход в каждый уровень стартового состояния
  (существующий долг контракта 0033). Снят той же конвенцией, что уже принята в
  Q-сверке: сравнение с поправкой на сдвиг **плюс** отдельная проверка, что
  переход `255 → 0` в трассе присутствует.

## Разработка

### Задача

#### Что было

Правило существовало (S1/S2 анализа 0025), но не как правило **языка**, и цели к
нему не сверялись. Цель `rust` печатала `n += 1`, и на `255 + 1` прошивка
паниковала в debug-профиле, а в release молча оборачивалась — поведение зависело
от профиля сборки пользователя. Поведение цели `st` при переполнении не
проверялось никем.

#### Что сделано

1. **Цель `rust`** (`generator/rust/rust_expr.rs`): беззнаковая арифметика
   `+`, `−`, `*` печатается как `wrapping_add`/`wrapping_sub`/`wrapping_mul`.
   Знаковость определяется уже существующим `rust_fixed::expression_type`
   (используется и Q-путём). Свёртка в составное присваивание (`x += 1`) для
   таких узлов **отключена** — она вернула бы панику.
2. **Знаковая арифметика не тронута:** по правилу S2 такая программа ошибочна;
   паника debug-профиля — полезный сигнал, а не дефект.
3. **Фикстура** `takt-sim/tests/data/eval/conformance_overflow.takt`: счётчик
   `u8` от 253, обёртка случается **внутри** прогона (254 → 255 → 0 → 1 → 2 → 3).
4. **Потактовые сверки во всех четырёх целях:** `c`, `rust`, `sv`, `st`.
   Для `st` — впервые; сравнение с поправкой на INIT-сдвиг цели (существующий
   долг контракта 0033) плюс отдельная проверка, что переход `255 → 0` в трассе
   присутствует.
5. **Документация:** раздел «Типы» книги получил подраздел «Переполнение» с
   нормативной формулировкой и двумя примерами; в «Частые ошибки» добавлен
   `SIM-003`. Прежняя фраза «арифметика выполняется по модулю разрядности
   типа» **исправлена**: она распространяла обёртку и на знаковые типы, где её
   нет.

#### Вынужденные правки по ходу

- **`conformance_c_tests.rs` упёрся в лимит размера** (1002 строки при лимите
  1000). Тест переполнения вынесен в подмодуль
  `conformance_c_tests/overflow.rs`, подключён `#[path]` (корень тестового крейта
  ищет подмодули рядом с собой) — приём фичи.
- **Тест фичи** (`rust_emits_model_level_always_before_match`) пиннил
  строку `self.n += 1;`. Ожидание обновлено на
  `self.n = self.n.wrapping_add(1);` — сам смысл проверки (тело `always` стоит
  до диспетчеризации) не изменился.

#### Проверки

| Проверка | Результат |

## Тест-план

### Область и цель

Фича **языковая**: нормируется семантика арифметики, поэтому правило 16
применяется полностью — проверки, примеры и контрпримеры.

Центральный вопрос проверки: **одинаково ли считают эталон и все цели**. Поэтому
основной инструмент — потактовая сверка исполнением, а не чтение вывода: молча
неверная трансляция компилируется и проходит проверки.

### Проверки (условие → ожидаемый результат)

| # | Условие | Ожидаемый результат |
|---|---|---|
| A1 | вывод цели `rust` для `u8`-арифметики | `wrapping_add`/`wrapping_sub`/`wrapping_mul`, ни одного `+=` над беззнаковым |
| A2 | вывод цели `rust` для `i8`-арифметики | обычный `+` (обёртка не печатается) |
| A3 | трасса симулятора на фикстуре переполнения | `254, 255, 0, 1, 2, 3` — обёртка на третьем такте |
| A4 | сверка с целью `c` | трассы совпадают потактово |
| A5 | сверка с целью `rust` | трассы совпадают потактово |
| A6 | сверка с целью `sv` | трассы совпадают потактово |
| A7 | сверка с целью `st` | трассы совпадают с поправкой на INIT-сдвиг; в трассе присутствует переход `255 → 0` |
| A8 | взведённость контроля | откат правки генератора (`is_unsigned_int` → `false`) обязан красить A5 |

| A11 | `./scripts/precheck.sh` | `EXIT=0` |

### Примеры и контрпримеры (правило 16)

**Пример — определённое поведение (беззнаковое):**

```takt
var t: u8 := 254;
start Counting {
    always { t := t + 1; }   // 254 → 255 → 0 → 1 …
}
```

**Контрпример — ошибочная программа (знаковое):**

```takt
var s: i8 := 127;
start Counting {
    always { s := s + 1; }   // SIM-003: 128 не помещается в i8
}
```

Оба вошли в документацию (раздел «Типы» → «Переполнение»); упоминание `SIM-003` —
в блоке «Частые ошибки» того же раздела.

### Разбивка проверок по функциональности

- **Правило соблюдается всеми целями** — A3–A7 (главная группа).
- **Знаковый случай не «починен» молча** — A2, A9.
- **Контроль настоящий, а не удачливый** — A8.
- **Правило названо пользователю** — A10.
- **Контракт проекта** — A11.

### Тестовые данные и окружение

Фикстура — `takt-sim/tests/data/eval/conformance_overflow.takt` (общая для
сверок `c`, `sv`, `st`); сверка `rust` использует собственный исходник с
выходным портом, поскольку поля порождённой прошивки приватны и наблюдение идёт
через HAL. Инструменты: `cc`, `rustc`, `verilator`, MatIEC `iec2c`; при
отсутствии любого из них соответствующая сверка **мягко пропускается**, а трасса
симулятора остаётся пришпиленной числом — то есть тест не превращается в
пустышку.

**Ограничение сверки `st`:** цель тратит такт на вход в каждый уровень
стартового состояния (долг контракта 0033, к переполнению отношения не имеющий),
поэтому сравнение идёт с поправкой на сдвиг — по конвенции, уже принятой в
Q-сверке. Чтобы поправка не «съела» смысл, добавлено отдельное утверждение о
наличии перехода `255 → 0`.

### Результаты по функциональности

- **Правило соблюдается всеми целями** (A3–A7). Впервые проверено поведение цели
  `st`: `USINT` именно **оборачивается** (`255 → 0`), а не насыщается и не даёт
  отказ.
- **Знаковый случай не «починен» молча** (A2, A9): обёртка для знаковых не
  печатается, эталон по-прежнему диагностирует.
- **Контроль настоящий** (A8): временный откат `is_unsigned_int` на `false` уронил
  сверку `rust` с той самой паникой, ради которой фича заводилась. Проверка
  сделана вручную и **не** оставлена в коде — она мутирует генератор.

  утверждение** документации: прежняя фраза «арифметика выполняется по модулю
  разрядности типа» распространяла обёртку и на знаковые типы, где её нет.

### Влияние на порождённый корпус

Изменились два файла — `examples/generated/rust/comprehensive.rs` и
`stacker.rs`: беззнаковая арифметика печатается обёрткой
(`self.temperature -= 1;` → `self.temperature = self.temperature.wrapping_sub(1);`
и подобные). Вывод целей `c`, `st`, `sv`, `plantuml` **байт-в-байт неизменен** —
там правило выполнялось само.

### Вынужденные правки (не дефекты фичи)

1. **`conformance_c_tests.rs` упёрся в лимит размера** (1002 строки при лимите
   1000) — проверка сработал правильно. Тест переполнения вынесен в подмодуль
   `conformance_c_tests/overflow.rs` (`#[path]`, приём фичи), файл вернулся
   к 960 строкам.
2. **Тест фичи** пиннил строку `self.n += 1;` в порождённом Rust. Ожидание
   обновлено на `self.n = self.n.wrapping_add(1);`; смысл проверки (тело
   model-level `always` стоит **до** диспетчеризации) не изменился.

### Выводы и дальнейшие шаги

Фича закрывается со статусом **ГОТОВО**. Версия языка **не поднимается**: цикл
`0.6.0` открыт фичей, и по правилу 22 последующие фичи цикла вносят
изменения в него же.

**Открытые следствия (перенесены из ADR):**

1. **Знаковое переполнение остаётся разноголосым** между целями (симулятор —
   диагностика, C — UB, Rust — паника/обёртка по профилю, SV — обёртка). Это
   **названо** правилом «программа ошибочна», но не устранено: полное
   устранение (проверки в времени выполнения у всех целей) отвергнуто по цене и
   невыразимости в RTL.
2. **Закрытие 0127 разблокирует [модель времени в языке: литерал длительности и частота такта](0134-language-time-model.md)**
   (модель времени): разрядность счётчика времени выбирает компилятор, и теперь
   у этого выбора есть определённая семантика переполнения.

## Итог (что сделано)

- **Правило языка названо** (нормативно, в разделе «Типы» документа):
  переполнение **беззнакового** целого — обёртка по модулю `2ⁿ`; переполнение
  **знакового** — **ошибка программы** (симулятор даёт `SIM-003`, поведение
  порождённого кода языком не гарантируется — в C это UB). Эталон при этом не
  изобретался: правило существовало как S1/S2 анализа
  [починка вычислителя выражений симулятора](0025-simulator-expression-eval.md) и лишь возведено в норму.
- **Цель `rust` приведена к правилу:** беззнаковые `+`, `−`, `*` печатаются как
  `wrapping_add`/`wrapping_sub`/`wrapping_mul`; свёртка в `x += 1` для таких
  узлов отключена (она возвращала бы панику). Прежде прошивка **паниковала** в
  debug-профиле и молча оборачивалась в release — то есть поведение зависело от
  профиля сборки пользователя.
- **Знаковая арифметика намеренно не тронута:** обёртка для неё **не**
  печатается. Тихое расхождение с эталоном (который диагностирует) сочтено
  худшим исходом, чем паника debug-профиля, полезная как сигнал.
- **Проверено исполнением во всех четырёх целях** — потактовые сверки
  `conformance_{c,rust,sv,st}` на общей фикстуре. Для цели **`st` это первая в
  истории проверка поведения при переполнении**: `USINT` именно оборачивается.
- **Контроль взведён:** ручной откат правки генератора роняет сверку `rust` с той
  самой паникой, ради которой фича заводилась.
- **Исправлено неверное утверждение документации:** фраза «арифметика
  выполняется по модулю разрядности типа» распространяла обёртку и на знаковые
  типы, где её нет.
- Отчёт — вердикт **✅ ПРОЙДЕН** (11/11, `precheck.sh` `EXIT=0`, 2194 теста),
  [`0127-int-overflow-semantics.md#отчёт-о-тестировании`](0127-int-overflow-semantics.md#отчёт-о-тестировании).
- Версия языка **не поднималась**: цикл `0.6.0` открыт фичей (правило 22 —
  накопление). Порождённый корпус изменился в двух файлах цели `rust`
  (`comprehensive.rs`, `stacker.rs`); вывод остальных целей байт-в-байт прежний.
- **Остаточное следствие:** знаковое переполнение по-прежнему ведёт себя в
  целях по-разному. Это **названо** правилом («программа ошибочна»), но не
  устранено; устранение (проверки в времени выполнения) отвергнуто по цене и
  невыразимости в RTL.
- **Разблокирует [модель времени в языке: литерал длительности и частота такта](0134-language-time-model.md)** (модель времени):

  определённая семантика переполнения.
