нужна проверка совместимости с `org.jetbrains.intellij.platform` 2.1.0 и
платформой 2024.2; и **проверить исход нечем** — JDK 22+ на машине нет, то есть
«починка» осталась бы недоказанной.

### Context

Сборка плагина `extensions/intellij-takt` ограничивает **пусковой** JDK — тот, на
котором работает демон Gradle (не путать с JDK компиляции: его задаёт
`jvmToolchain(21)` и скачивает сам Gradle). Под слишком новым пусковым JDK
сборка падает сообщением, состоящим из одной строки — номера версии:

```
* What went wrong:
26.0.2
```

Фича поставила преflight-проверку, объясняющую отказ, и записала причину:
«таблица версий Java внутри `kotlin-gradle-plugin` 2.0.21 обрывается на
`JAVA_21`». Кандидат, из которого заведена фича, предложил лечение: поднять
Kotlin — «более свежий Kotlin ограничение снял бы вовсе». Не сделано было по
трём причинам: нужна сеть, нужна проверка совместимости с
`org.jetbrains.intellij.platform` 2.1.0, и **проверить исход нечем** — JDK
новее 21 на машине не было.

#### Что показала проба (замеры кандидата перепроверены)

Все три препятствия сегодня сняты, и главный замер оказался **неверным**.

**1. Сеть есть.** `repo1.maven.org` и `plugins.gradle.org` отвечают `200`.

**2. Проверить исход есть чем.** На машине стоит `openjdk 26.0.2` (Homebrew,
`/opt/homebrew/opt/openjdk`), то есть пусковой JDK заведомо новее границы.
Отказ воспроизведён на нём дословно (`* What went wrong: 26.0.2`).

**3. Причина названа неверно.** Стектрейс отказа (`--stacktrace`) указывает не на
`kotlin-gradle-plugin` проекта, а на **встроенный в Gradle** компилятор
Kotlin-скриптов, которым компилируется сам `build.gradle.kts`:

```
at org.jetbrains.kotlin.com.intellij.util.lang.JavaVersion.parse(JavaVersion.java:305)
at org.jetbrains.kotlin.cli.jvm.modules.JavaVersionUtilsKt.isAtLeastJava9(javaVersionUtils.kt:11)
...
at org.gradle.kotlin.dsl.support.KotlinCompilerKt.compileKotlinScriptToDirectory(KotlinCompiler.kt:149)
```

Класс — `com.intellij.util.lang.JavaVersion` внутри **Gradle 8.10.2**, а не
`commons-lang3 JavaVersion` внутри KGP. Отсюда следствие: версия
`kotlin("jvm")`, объявленная в `plugins {}`, к этому отказу отношения не имеет —
падение происходит **до** того, как она вообще применяется.

**4. Подъём одного Kotlin ограничения не снял бы.** Независимая проверка того же
вывода: таблица `commons-lang3 JavaVersion` внутри самих KGP-jar (`javap`):

| Kotlin | таблица доходит до |
|---|---|
| 2.0.21 (текущий) | `JAVA_21` |
| 2.1.21 | `JAVA_22` |
| 2.2.21 | `JAVA_22` |
| 2.4.10 (последний стабильный) | `JAVA_24` |

Даже новейший Kotlin не покрывает JDK 26 — то есть предложенное кандидатом
лечение не сработало бы и по своей же логике.

**5. Что снимает ограничение — подъём Gradle.** Проба на копии проекта
(guard снят, чтобы увидеть настоящий отказ):

| Связка | Пусковой JDK 26.0.2 |
|---|---|
| Gradle 8.10.2 + IPP 2.1.0 + Kotlin 2.0.21 (как есть) | `IllegalArgumentException: 26.0.2` при компиляции скрипта сборки |
| Gradle 9.3.0 + IPP 2.1.0 | скрипт компилируется; падает **плагин платформы**: `Adding a provider of configurations directly to the configuration container is not allowed` |
| Gradle 9.3.0 + IPP 2.18.1 + Kotlin 2.0.21 | `compileKotlin` **успешен** |
| Gradle 9.7.0 + IPP 2.18.1 + Kotlin 2.4.10 | сборка и тесты успешны (89/90; единственный провал — корпусный тест, которому нужен корень репозитория: проба живёт вне его) |

Та же связка под пусковым **JDK 17** — тоже 89/90. Конфигурационный кэш Gradle
работает (`Configuration cache entry stored`).

**6. Kotlin поднять всё же стоит — но по другой причине.** На Gradle 9.7 KGP
2.0.21 печатает `Declaring a Usage attribute with a legacy value has been
deprecated. This will fail with an error in Gradle 10` (значения
`java-api-jars`/`java-runtime-jars`). С Kotlin 2.4.10 эти предупреждения
исчезают. То есть подъём Kotlin — не лечение пускового JDK, а условие
работоспособности на следующем мажоре Gradle.

#### Побочная находка: форма списка IDE в верификаторе

В IPP 2.18.1 метода `ide("IC-2024.3")` больше нет; ближайшая замена —
`create(type, version)`. Но записи трёх версий **схлопываются**: в 2.1.0 плагин
заводил отдельную конфигурацию на каждую IDE
(`intellijPluginVerifierIdesDependency_IC_2024.3`, `…_IC_2025.1`, `…_IC_2025.2`),
а в 2.18.1 конфигурация одна, и обычный резолв Gradle сводит три версии к
старшей (`idea:ideaIC:2024.3 -> 2025.2`). README плагина ровно об этом и
предупреждал — «форма `ide(type, version)` для одного типа схлопнулась бы в одну
проверку». Проверить, теряется ли покрытие на самом деле, можно только прогоном
`verifyPlugin` (решение заказчика 2026-08-17: прогнать).

### Decision Drivers

1. **Лечение обязано соответствовать причине.** Кандидат называл Kotlin;
   измерение называет Gradle. Подъём не той зависимости оставил бы отказ на
   месте — и был бы объявлен «починкой».
2. **Исход должен быть доказан прогоном.** JDK 26 на машине есть, значит
   отговорка 0159 («проверить нечем») больше не действует.
3. **Не потерять то, что работало.** Пусковой JDK 17 обязан работать
   по-прежнему: на него настроен скрипт установки и им пользуются.
4. **Границы guard — замер, а не догадка.** Комментарий 0159 прямо требует:
   «подняли Kotlin — перезамерьте границы».

### Considered Options

#### Option A. Поднять только `kotlin("jvm")` (буквально по кандидату)

**Pros:**
- Минимальная правка одной строки.

**Cons:**
- **Не решает задачу — доказано дважды:** отказ приходит из embedded-компилятора
  Gradle до применения KGP, а таблица версий даже у Kotlin 2.4.10 обрывается на
  `JAVA_24` при пусковом JDK 26.

#### Option B. Поднять сборочную связку: Gradle + плагин платформы + Kotlin

**Pros:**
- Снимает ограничение по факту: связка Gradle 9.7.0 + IPP 2.18.1 + Kotlin 2.4.10
  собирает и прогоняет тесты под пусковым JDK 26 **и** 17.
- Снимает deprecation-предупреждения, обещающие отказ на Gradle 10.
- Плагин платформы 2.1.0 → 2.18.1 закрывает семнадцать минорных версий
  отставания.

**Cons:**
- Правка API: `ide("IC-…")` → другая форма, и её поведение требует проверки
  прогоном `verifyPlugin`.
- Подъём трёх компонентов сразу: если что-то сломается позже, виновника придётся
  искать перебором.

#### Option C. Оставить как есть, ограничившись guard'ом 0159

**Pros:**
- Ноль работы; отказ объяснён преflight-проверкой.

**Cons:**
- Ограничение остаётся, а машина разработчика уже несёт JDK 26: сборка требует
  держать рядом старый JDK и помнить про `JAVA_HOME`.
- Отставание сборочной связки растёт: Gradle 10 сломает KGP 2.0.21 обещанным
  отказом.

### Decision

Принимается **Option B**: подъём **Gradle 8.10.2 → 9.7.0**,
**`org.jetbrains.intellij.platform` 2.1.0 → 2.18.1**, **Kotlin 2.0.21 → 2.4.10**;
`platformVersion` (2024.2.5) и `sinceBuild` (242) **не трогаются** — совместимость
плагина с IDE предметом фичи не является.

Границы преflight-проверки перезамеряются: измеренного «плохого» пускового JDK
больше нет (17 и 26 проверены прогоном), поэтому жёсткий `error` снимается, а
предупреждение о непроверенных версиях остаётся — ровно по логике самого 0159
(«запрещать неизмеренное — та же догадка, только с другим знаком»).

Заголовок фичи говорит о Kotlin — он остаётся как есть (номер фичи привязан к
названию), но предмет уточнён этим ADR: Kotlin входит в объём, однако
ограничение снимает **Gradle**.

### Consequences

#### Положительные

- Сборка плагина идёт на любом пусковом JDK из измеренного диапазона 17…26;
  держать рядом старый JDK не нужно.
- Сборочная связка перестаёт отставать на семнадцать минорных версий плагина
  платформы и на мажор Gradle.
- Скрипт установки (`install-rustrover-plugin.sh`/`.ps1`) больше не обязан
  искать JDK 17 — правка документируется вместе со связкой.

#### Отрицательные / Action items

- **Форма списка IDE верификатора меняется**, и её эквивалентность старой
  доказывается прогоном `verifyPlugin` (стадия 6). Схлопывание к одной версии —
  регресс покрытия, и если новая форма его даёт, список задаётся иначе.
- Плагин по-прежнему собирается **только локально** (`./gradlew --offline test`)
  и в `precheck.sh`/CI не входит — фича этого не меняет (правило 29: контроль
  `TaktKeywordSyncTest` существует, но машина его не запускает).
- Числа guard'а и README снова устареют при следующем подъёме — это свойство
  измеренной границы, и текст обязан говорить, **что** измерено, а не «работает».

#### Acceptance criteria

1. `./gradlew test` зелёный под пусковым JDK **26** и под **17** (все тесты, в
   том числе `TaktPsiCorpusTest`, который требует корня репозитория).
2. `./gradlew buildPlugin` даёт zip; `verifyPlugin` отрабатывает и его вывод
   показывает, сколько IDE проверено (три — покрытие сохранено).
3. Deprecation-предупреждений вида «legacy Usage attribute» в сборке нет.
4. Преflight-проверка в `build.gradle.kts` перезамерена: числа соответствуют
   пробам, жёсткого отказа на неизмеренной версии нет.
5. README плагина, скрипты установки и живой контекст (`CLAUDE.md`) не обещают
   снятого ограничения.

## Анализ

### Цель и контекст

Снять ограничение на **пусковой** JDK сборки плагина `extensions/intellij-takt`.
ADR установил пробой, что ограничение задаёт **версия Gradle** (её встроенный
компилятор Kotlin-скриптов), а не `kotlin("jvm")`, как предполагал кандидат.
Поэтому объём — подъём сборочной связки: Gradle 8.10.2 → 9.7.0,
`org.jetbrains.intellij.platform` 2.1.0 → 2.18.1, Kotlin 2.0.21 → 2.4.10.

Язык Takt, компилятор, симулятор и порождаемый код фичей **не затрагиваются**:
правки идут в подпроекте сборки плагина IDE, его документации и скриптах
установки.

### Зависимости фичи (правило 17/19)

- **Зависит от:** нет. Фича (преflight-проверка пускового JDK) закрыта; её
  артефакты — контекст, а не блокер. Фича (PSI-плагин) и 0038 (LSP4IJ)
  закрыты и версии платформы не меняют.
- **Влияние на порядок разработки:** никого не разблокирует. Косвенно облегчает
  будущие работы по плагину (0221 — символ инварианта в панели структуры):
  сборка перестаёт требовать отдельного старого JDK.

### Требования и проверяемые условия

- **R1. Сборка идёт под новым пусковым JDK.** `./gradlew test` зелёный под
  пусковым JDK 26.0.2 без выставления `JAVA_HOME` на старый JDK.
- **R2. Старый пусковой JDK не потерян.** Тот же прогон зелёный под JDK 17 —
  на него настроен скрипт установки, и им пользуются.
- **R3. Все тесты плагина проходят.** 90 тестов, включая `TaktPsiCorpusTest`
  (round-trip по корпусу `.takt`) и `TaktKeywordSyncTest` (сверка ключевых слов
  с лексером) — контроля, ради которых плагин и собирается локально.
- **R4. Покрытие верификатора не потеряно.** `verifyPlugin` проверяет **три**
  сборки IDE (IC-2024.3, IC-2025.1, IC-2025.2), а не одну: в IPP 2.18.1 форма
  `ide("IC-…")` изъята, а замена может схлопнуть версии (ADR, побочная находка).
- **R5. Deprecation-предупреждений нет.** В сборке не остаётся предупреждений
  «legacy Usage attribute … will fail with an error in Gradle 10» (их даёт
  Kotlin 2.0.21 на Gradle 9).
- **R6. Границы преflight-проверки перезамерены.** Числа в `build.gradle.kts`
  соответствуют пробам (17 ✅, 26 ✅), жёсткого `error` на неизмеренной версии
  нет — по логике самого 0159.
- **R7. Документация не обещает снятого ограничения.** README плагина, оба
  скрипта установки (`.sh`/`.ps1`) и живой контекст `CLAUDE.md` не утверждают,
  что пусковой JDK обязан быть не новее 21.
- **R8. Артефакт плагина собирается.** `./gradlew buildPlugin` даёт zip.

### Особенности по обратной функциональности (правило 11)

- **Пользовательская совместимость плагина не меняется:** `platformType`,
  `platformVersion` (2024.2.5), `pluginSinceBuild` (242) и открытый
  `pluginUntilBuild` остаются прежними. Плагин ставится в тот же круг IDE.
- **Совместимость сборки расширяется, а не сужается:** пусковой JDK 17
  продолжает работать (R2), добавляется 26. Нижняя граница задаётся Gradle 9
  (JDK 17+) и совпадает с прежней практикой скрипта установки.
- **Слом для тех, кто собирал под JDK < 17,** теоретически возможен, но такой
  сборки не было: `jvmToolchain(21)` и платформа 2024.2 требуют 17+ и до фичи.
- Версия языка не поднимается (правило 22): язык не изменён.

### Редакторский слой (правило 29)

Фича **сама** живёт в редакторском слое, но **язык не меняет**: лексика,
синтаксис и семантика прежние, новых токенов и форм объявления нет. Правок в
`takt-lang/src/lsp/` не требуется. В плагине правится **только сборка** —
исходники (`src/`), списки ключевых слов и PSI не трогаются, что и подтверждает
неизменный набор из 90 тестов (R3).

### Документирование (правило 24)

**Не требуется.** Документ `book/` описывает язык; сборка плагина IDE в него не
входит (правило 15 — инструментарий описывает README). Правится README
подпроекта плагина и раздел живого контекста `CLAUDE.md`.

### Риски и зависимости

- **Риск: подъём трёх компонентов сразу.** Если сборка сломается позже, виновника
  придётся искать перебором. Снижение: в ADR зафиксирована таблица пошаговых
  проб (какая связка что даёт), то есть перебор уже проделан и записан.
- **Риск: потеря покрытия `verifyPlugin`** (главный, R4). Проверяется настоящим
  прогоном — решение заказчика 2026-08-17. Схлопывание к одной IDE считается
  провалом критерия, а не «мелочью формы».
- **Риск: неизмеренный пусковой JDK 27+.** Остаётся, и guard об этом
  предупреждает; жёстко запрещать неизмеренное фича не будет (логика 0159).
- **Проверки у плагина нет:** `precheck.sh` и CI его не собирают (правило 29,
  «машина контроля не запускает»). Фича этого не меняет — прогон остаётся
  ручным, поэтому его результаты фиксируются в отчёте (стадия 6).

## Разработка

### Задача

#### Что было

Сборка плагина падала под пусковым JDK новее 21 сообщением из одного номера
версии (`* What went wrong: 26.0.2`). Преflight-проверка фичи объясняла
отказ таблицей версий в `kotlin-gradle-plugin` 2.0.21 и требовала запускать
Gradle под старым JDK. ADR показал пробой, что причина названа неверно:
падает **встроенный в Gradle** компилятор Kotlin-скриптов, а подъём одного
Kotlin JDK 26 не покрыл бы вовсе (таблица даже у 2.4.10 обрывается на 24).

#### Что сделано

**1. Сборочная связка поднята** (`extensions/intellij-takt`):

| Компонент | Было | Стало |
|---|---|---|
| Gradle (wrapper) | 8.10.2 | **9.7.0** |
| `org.jetbrains.intellij.platform` | 2.1.0 | **2.18.1** |
| Kotlin (`kotlin("jvm")`) | 2.0.21 | **2.4.10** |

`platformVersion` (2024.2.5), `platformType` (IC), `pluginSinceBuild` (242) и
открытый `pluginUntilBuild` **не тронуты** — круг совместимых IDE прежний.
Wrapper обновлён задачей `./gradlew wrapper --gradle-version 9.7.0`, поэтому
`gradlew`/`gradlew.bat` переписаны самим Gradle (у `.bat` вернулись CRLF).

**2. Форма списка IDE верификатора заменена вынужденно.** В 2.18.1 метода
`ide("IC-2024.3")` нет; `create(type, version)` заводит одну конфигурацию на все
версии, и резолв Gradle сводит их к старшей (`idea:ideaIC:2024.3 -> 2025.2`).
Работает форма с одним провайдером:

```kotlin
ides {
    create(providers.provider { listOf("IC-2024.3", "IC-2025.1", "IC-2025.2") })
}
```

Прогон `verifyPlugin` подтверждает: **три** верификации, все `Compatible`.

**3. Преflight-проверка перезамерена.** Жёсткий `error` снят — измеренной
«плохой» версии больше нет (17 и 26 проверены прогоном); осталось
предупреждение о непроверенных 27+, называющее лечение (поднять Gradle).
Комментарий переписан: он больше не винит Kotlin, а приводит стектрейс с
`org.gradle.kotlin.dsl.support.KotlinCompiler`.

**4. Скрипт установки перестал искать именно JDK 17**
(`extensions/install-rustrover-plugin.sh`). Теперь он следит за **диапазоном**
`JDK_MIN=17`…`JDK_MAX=26`: текущий JDK не трогается, если годится; иначе ищется
подходящий; не нашли — предупреждение, а не отказ. Границы вынесены в
переменные, чтобы проза сообщений и проверка брались из одного значения.
PowerShell-версия (`.ps1`) JDK не выбирает вовсе — правок не требует.

**5. Документация приведена в соответствие:** README плагина (требования,
раздел `verifyPlugin`, описание скрипта) и живой контекст `CLAUDE.md`.

**Попутно** (найдено при правке, не предмет фичи): в `README.md` и `CLAUDE.md`
каталог плагина назывался `extensions/intellij-lam` — имя, отменённое
переименованием Lam → Takt. Три вхождения исправлены.

Обратная функциональность (правило 11): исходники плагина, язык, компилятор и
симулятор не менялись; версия языка не поднимается.

#### Проверки

```sh
cd extensions/intellij-takt
JAVA_HOME=/opt/homebrew/opt/openjdk/libexec/openjdk.jdk/Contents/Home ./gradlew --warning-mode all test
JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew --rerun-tasks test
./gradlew buildPlugin
./gradlew verifyPlugin
sh -n ../install-rustrover-plugin.sh
cd ../.. && ./scripts/precheck.sh
```

Результаты — в отчёте [0224-intellij-kotlin-upgrade.md#отчёт-о-тестировании](0224-intellij-kotlin-upgrade.md#отчёт-о-тестировании).

### Выводы и дальнейшие шаги

1. **Гипотеза кандидата была неверна, и это доказано дважды.** Ограничение
   задавал не `kotlin("jvm")`, а **Gradle** — его встроенный компилятор
   Kotlin-скриптов, падавший до применения KGP (T12); подъём одного Kotlin не
   покрыл бы JDK 26 и по своей же логике (T13). Лечение — подъём связки:
   Gradle 8.10.2 → 9.7.0, плагин платформы 2.1.0 → 2.18.1, Kotlin 2.0.21 →
   2.4.10.
2. **Вывод `dependencies` оказался ложным сигналом.** Он показывал схлопывание
   трёх версий IDE к старшей (`idea:ideaIC:2024.3 -> 2025.2`), и по нему форма
   выглядела сломанной; настоящий прогон `verifyPlugin` показал три
   верификации. Урок прежний: свойство доказывает исполнение, а не отчёт о
   конфигурации.
3. **Kotlin всё же поднят — но по другой причине:** на Gradle 9 KGP 2.0.21
   печатает предупреждения «legacy Usage attribute … will fail with an error in
   Gradle 10» (T5).
4. **Остаётся неизмеренным пусковой JDK 27+** — такого на машине нет. Сборка о
   нём предупреждает и называет лечение; запрещать неизмеренное фича не стала
   (логика 0159).
5. **Проверки у плагина по-прежнему нет:** `precheck.sh` и CI его не собирают
   (правило 29). Прогоны ручные, их результаты — в этой таблице.
6. Попутно исправлено устаревшее имя каталога `extensions/intellij-lam`
   (переименование Lam → Takt) в `README.md` (2 вхождения) и
   `CLAUDE.md` (1).

## Итог (что сделано)

Ограничение на **пусковой** JDK сборки плагина снято: сборка и все 90 тестов

**`org.jetbrains.intellij.platform` 2.1.0 → 2.18.1**, **Kotlin 2.0.21 → 2.4.10**
(последний — ради предупреждений «legacy Usage attribute», обещающих отказ на
Gradle 10).

Побочно: форма списка IDE верификатора заменена вынужденно (`ide("IC-…")` в
