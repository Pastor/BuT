# Фича: Комментарии в порождённом коде: шапка и комментарии автора

- **Номер:** 0535
- **Статус:** ГОТОВО
- **Зависит от:** [язык сообщений компилятора и симулятора (i18n)](0532-i18n-diagnostics.md) — решением заказчика
  2026-09-06 комментарии вывода подчинены ключу `--lang`, то есть их тексты
  живут в каталоге сообщений. Достаточно задачи `0532-01` (носитель, формат,

## Краткое описание

Порождённый код несёт комментарии, адресованные **разработчику компилятора**, а
не читателю вывода: номера фич (`(фича 0059)`), ссылки на решения проекта
(`контракт ADR 0033`), путь проверки (`проверяется гейтом (scripts/precheck.sh)`),
служебные маркеры `// NOTICE:` и пустые строки комментария. Заказчик (2026-09-06)
просит их исключить.

> Фича зарегистрирована по запросу заказчика; далее проходит жизненный цикл по
> правилу 17.

## Документирование (правило 24)

**Язык не меняется**: предмет — текст комментариев в выводе, а не синтаксис,
семантика или поведение. Ключа сборки не появляется, поэтому проверка
[ключи сборки описаны в документе](0527-book-build-flags.md) не затрагивается. Документ правится в двух
местах: раздел «Инструментарий» получает фразу о том, что вывод несёт шапку и
комментарии автора модели, а снимки порождённого кода в `book/` пересобираются
проверкой [снимки порождённого кода в book/ никем не сверяются](0274-book-generated-snapshots-gate.md).

### Context

#### Замер (правило 30, дата 2026-09-06)

Корпус `examples/*.takt` собран **всеми восемью целями** в чистый каталог
(`taktc compile -t <цель>`), затем посчитаны строки. 90 файлов, 16 571 строка,
1 991 строка комментария (12 % вывода).

| Цель | строк | комментариев | ссылок на процесс | `NOTICE:` | пустых комментариев |
|---|---|---|---|---|---|
| `c` | 3325 | 494 | 0 | 87 | 0 |
| `c-hal` | 3047 | 439 | 0 | 73 | 0 |
| `st` | 2121 | 55 | 0 | 0 | 0 |
| `st-at` | 1869 | 47 | 0 | 0 | 0 |
| `rust` | 3634 | 762 | 61 | 0 | 108 |
| `sv` | 1085 | 92 | 13 | 0 | 4 |
| `sv-mmio` | 1235 | 102 | 16 | 0 | 4 |
| `plantuml` | 255 | 0 | 0 | 0 | 0 |
| **итого** | **16 571** | **1 991** | **90** | **160** | **116** |

Предмет поручения делится на **три класса**, и они разной природы.

**Класс 1 — адрес решения вместо смысла (90 строк).** Вхождения: `ADR NNNN` — 70,
`scripts/precheck.sh` — 11, `фича NNNN` — 9. Примеры из вывода:

```rust
    /// Общие с под-моделями переменные (фича 0059).
    /// Блоки `enter` здесь не исполняются: по контракту ADR 0033 вход
// проверяется гейтом (scripts/precheck.sh).
```

```systemverilog
    input  logic [10:0] reg_addr,   // регистровый интерфейс цели sv-mmio (фича 0062): адрес
    // состояние живёт в ветви сброса (контракт ADR 0033).
```

**Это не косметика.** У читателя вывода нет ни карточек фич, ни `docs/`, ни
`precheck.sh`: ссылка выглядит указанием на документ, который он обязан найти, —
и не находит. Половина таких комментариев при этом теряет и смысл: «по контракту
ADR вход в стартовое состояние не расходует такт» **объясняет** правило, а
« » после осмысленной фразы не добавляет ничего.

**Класс 2 — служебный маркер `NOTICE:` (160 строк, только цели `c` и `c-hal`).**

```c
// NOTICE: Определение переменных модели
// NOTICE: Определение extend
/// NOTICE: Функции портов ввода вывода
```

Слово не значит ничего: это не предупреждение, не `TODO` и не соглашение языка C.
Оно осталось от ранней разработки и печатается 160 раз.

**Класс 3 — пустой комментарий (116 строк, `rust` и `sv`).** Строки `///` и `//`
без текста. У `rust` пустой `///` — это **пустая doc-строка**: `cargo doc` строит
по ней пустой абзац.

#### Почему это дефект проекта, а не вкусовщина

Правило «в артефакте для пользователя нет процесса разработки» в проекте **уже
действует** — просто не распространено на вывод генераторов:

- правило 24: документ `book/` содержит только язык, «без деталей реализации,
  номеров фич и процесса»;
- [старое имя языка в порождаемом коде (lam_q_*, LAM_Q_*)](0253-legacy-names-in-generated-code.md): порождаемый код отдельно
  внесён под проверка запрещённых имён — то есть вывод уже признан артефактом, за
  чистоту которого отвечает машина;
- [заглушка, обещающая задачу, ловится проверкой](0332-stub-task-promise.md): обещание задачи в **тексте
  диагностики** признано дефектом по той же причине — «номера фич не место в
  тексте, который читает автор модели».

Вывод целей — тот же читаемый человеком артефакт, и исключения для него нет.

#### Что убирать не следует

Замер показывает, что полезного в комментариях больше, чем лишнего: из 1 991
строки под три класса подпадают 366 (18 %). Остальное — это

- **шапка файла**: «Порождено компилятором Takt (taktc) — цель: Rust (профиль
  no_std)», «Не редактировать вручную: файл перезаписывается при каждой
  генерации» (11 файлов). Она отвечает на первый вопрос читателя — «откуда это и
  можно ли править»;
- **doc-строки публичного API** цели `rust`: `/// Один такт автомата.`,
  `/// Завершён ли автомат модели.`, `/// Порт ввода-вывода модели. Реализация —
  за трейтом [`Hal`]` (33 вхождения каждой). Их читает тот, кто встраивает
  порождённый модуль, и `cargo doc` строит по ним справку;
- **пояснения семантики**, за которыми стоит правило языка: «вход в стартовое
  состояние такта не расходует», «сброс доходит до вложенных моделей через
  `init`». Эти фразы полезны — лишним в них является **только** адрес решения.

### Decision Drivers

- **D1. Читатель вывода — не разработчик компилятора.** Комментарий обязан
  объяснять код, а не называть место, где принято решение.
- **D2. Полезное не терять.** Шапка и doc-строки API — часть контракта вывода;
  вычистить их заодно значило бы ухудшить встраивание.
- **D3. Возврат класса ловит машина.** Правка текстов без контроля протухает:
  новый печатник напишет `(фича NNNN)` снова, и никто этого не заметит —
  инструменты целей комментарии не проверяют вовсе.
- **D4. Снимки — это дифф.** `examples/generated/` и снимки `book/` хранятся в
  дереве: правка комментариев даёт большой, но **однократный**
  и осмысленный дифф.
- **D5. Новый ключ сборки — новая ось.** Ключ обязан быть назван в `book/`, учтён в матрице сценариев сборки, в таблице применимости к
  целям (`compile_cli::target_flags`) и в веб-интерфейсе (0531, задача 09m).
  Цена ключа — не одна ветка `if`.

### Considered Options

#### Option A. Прополка на месте + проверка-контроль

Пройти по печатникам восьми целей и убрать три класса: адрес решения (текст
переписывается так, чтобы объяснял суть, а не ссылался), маркер `NOTICE:`, пустой
комментарий. Проверка `scripts/check-generated-comments.py` собирает корпус всеми
целями и падает **списком**: строка, файл, класс.

- **Плюсы:** дефект уходит целиком и не возвращается; объём вывода почти не
  меняется (комментарии остаются, но осмысленные); ни одной новой оси сборки.
- **Минусы:** тому, кому комментарии не нужны вовсе, выбора не даёт.
- **Объём:** ~366 строк вывода, ~50 мест печати в `generator/`; пересбор снимков
  `examples/generated/` и `book/`.

#### Option B. Ключ сборки `--comments=<full|api|none>`

Объём комментариев выбирает автор: `full` — как сейчас, `api` — шапка и
doc-строки публичного API, `none` — только шапка «порождено».

- **Плюсы:** выбор у автора; `none` даёт минимальный файл для встраивания в
  чужое дерево.
- **Минусы:** **сам по себе поручение не выполняет** — при `full` внутренности
  остаются на месте, а умолчание менять придётся всё равно. Плюс полная цена
  D5: ось матрицы 0466, упоминание в `book/`, таблица применимости, вкладка веба.
- **Объём:** ключ, три ветви у восьми печатников, проверки — заметно больше A.

#### Option C. A, затем B отдельной задачей

Сначала прополка со контролем (A), потом — ключ (B) поверх вычищенного вывода.

- **Плюсы:** поручение закрывается первой же задачей, а выбор объёма появляется,
  если он действительно нужен; вторая задача дешевле, чем B с нуля, — она делит
  уже готовое на «шапка / API / прочее».
- **Минусы:** дороже A на цену второй задачи.

#### Option E. Генератор не сочиняет: шапка на латинице + перенос авторских комментариев

**Вариант заказчика (2026-09-06).** В выводе остаются ровно две вещи:

1. **Шапка файла** — на латинице: предупреждение, что файл порождён, версия
   компилятора и, при необходимости, версия генератора. **Дат нет** (дата в
   порождаемом файле делает вывод невоспроизводимым — вопреки проверке).
2. **Комментарии автора модели** — те, которыми помечены элементы и строки
   `.takt`, перенесённые **как есть** в то же логическое место вывода.

Всё остальное — «отсебятина» генератора — не печатается: ни `NOTICE:`, ни адреса
решений, ни пояснения семантики, придуманные компилятором.

**Что для этого уже есть.** Механизм привязки комментария к узлу написан и
работает: лексер складывает комментарии в отдельный `Vec<Comment>`, каждый несёт
`Location::Source(файл, начало, конец)`, а `format::comments`
сшивает их с узлами по смещениям и различает **ведущий** (на своих строках перед
узлом) и **хвостовой** (на той же строке). Форматтер хранит текст **сырым** и
печатает дословно. Переносу нужен тот же носитель, а не новый.

**Замер опоры и цены (2026-09-06).**

| Предмет | Факт |
|---|---|
| комментариев в корпусе `examples/*.takt` | 561 строка в 11 файлах из 11 |
| из них с кириллицей | 489 |
| многострочных `/* */` в корпусе | 0 |
| шапка «порождено» сегодня | есть у `st`, `st-at`, `rust`, `sv`, `sv-mmio`; **нет** у `c` (22 файла), `c-hal` (18) и `plantuml` (11) |
| версия компилятора в выводе | отсутствует у всех восьми целей |
| дата в выводе | отсутствует — менять нечего |
| позиция у операторов семантики (`StatementNode`) | **2 варианта из 15**: `Expression` и `Variable`; `Block`, `If`, `Loop`, `For`, `Return`, `Match`, `Formula`, `Assembly` и прочие её не несут |

**Главная цена — позиции.** Генераторы печатают из **семантических** узлов, а
комментарий привязан к узлу **АСД**: сшить их можно только через позицию, а её
несут 2 варианта оператора из 15. Это тот самый долг, который снимали [сокращение долга позиций — с девяти записей до трёх](0470-position-debt-reduction.md) и
[позиция у темпоральной формулы и заголовка цикла](0471-ast-position-for-formula-and-loop.md); там же снят и замер способа:
считать надо **шаги, на которых сведение теряется**, а не вхождения — оценка «по
вхождениям» оказалась завышена вдесятеро.

**Найден класс невалидного вывода — прогоном по корпусу, а не рассуждением.**
В `examples/stacker.takt:203` авторский комментарий содержит `*)`:

```takt
// Управляет целевыми координатами (cmd_target_*) по трём осям.
```

В ST комментарий записывается `(* … *)` и **не вкладывается**: перенесённый «как
есть», он закроется на `cmd_target_*)`, а хвост `по трём осям.` уедет в код —
`iec2c` отвергнет файл при нулевом коде возврата `taktc`. То же у `c` с `/* */`.
Значит «как есть» невозможно буквально: перенос обязан **приводить форму** к
комментарию цели (у `st` — `(*`/`*)`, у `plantuml` — `'`, у прочих — `//`) и
обезвреживать закрывающую последовательность. Правило принадлежит одному
носителю, а не каждой цели порознь.

**Узел исходника не всегда даёт одно место вывода.** Подстановка функции
([инлайнинг функций: эвристика по размеру и атрибуты inline/noinline](0444-function-inlining.md)), разворот цикла у `sv`
([цель `sv` разворачивает `for` со статическими границами](0321-sv-for-unroll.md)), разворот среза и агрегата
([срез в аргументе вызова не переводит ни одна цель](0400-slice-in-call-argument.md), [раскрытие вложенного агрегата — общий носитель](0366-nested-aggregate-carrier.md)),
специализация параметров ([параметризация моделей (ключевое слово `parameter`)](0185-model-parameters.md)) и уплощение
композиции у `sv` размножают один узел в несколько мест — или не дают ни одного
(неиспользуемая функция не печатается, [цель st печатает неиспользуемую функцию](0445-st-unused-function.md)).
Правило «куда девать комментарий размноженного узла» обязано быть названным, а
не выведенным из порядка обхода.

**Версия компилятора в шапке ссорится со снимками.** Версия крейта
`takt-lang` — `0.59.0`, то есть поднималась 59 раз, практически каждой фичей.
Снимки `examples/generated/` (90 файлов) и снимки `book/` хранятся в дереве и
сверяются проверками и [снимки порождённого кода в book/ никем не сверяются](0274-book-generated-snapshots-gate.md): версия в
шапке означала бы пересборку всех снимков при **каждом** подъёме версии крейта.
Ответов три, и это вопрос к заказчику:

- **версия языка** (`LANGUAGE_VERSION`, сейчас `0.18.0`) — меняется редко и по
  правилу 22, а читателю вывода отвечает на осмысленный вопрос «на каком Takt
  это написано»;
- **версия компилятора** (`CARGO_PKG_VERSION`) — точнее для отчёта о дефекте, но
  снимки придётся пересобирать шагом предкоммита автоматически;
- **обе**, с нормализацией версии в проверке снимков.

- **Плюсы:** снимает **источник** проблемы, а не следствие — генератор перестаёт
  сочинять текст, и классу «отсебятины» неоткуда взяться снова; вывод несёт
  смысл, вложенный автором модели, то есть комментарий объясняет **эту** модель,
  а не устройство компилятора; шапка появляется там, где её сегодня нет (51
  файл).
- **Минусы:** дороже A — требует позиций у операторов (долг 0470/0471), носителя
  приведения формы и названного правила для размноженных узлов; теряются
  doc-строки публичного API `rust` (`cargo doc` порождённого модуля станет
  пустым) и пояснения контракта такта — если заказчик не выделит их отдельно.
- **Объём:** больше A примерно вдвое; разбивается на задачи (шапка → позиции →
  носитель переноса → приведение формы → проверка).

#### Option D. Убрать из вывода все комментарии, кроме шапки

- **Плюсы:** самое дешёвое и однозначное правило; спорить о «полезности»
  комментария не приходится.
- **Минусы:** нарушает D2 — теряются doc-строки трейта `Hal` и модели у цели
  `rust` (33 вхождения), то есть справка встраиваемого модуля становится пустой;
  теряются и пояснения семантики, за которыми стоят правила языка (контракт
  такта, порядок сброса). Читатель прошивки лишается ровно тех фраз, которые
  писались для него.

### Decision

**Option E — вариант заказчика (2026-09-06)**, он же целевое устройство:
генератор комментарии **не сочиняет**; в выводе остаются шапка на латинице (с
версией, без дат) и перенесённые комментарии автора модели. Ключ `--comments`
не заводится (Option B и C отклонены): поручение звучало «исключить ненужные», а
не «дать управление объёмом», а цена ключа по D5 оправдана только спросом,
которого никто не заявлял.

**Option A не отменяется, а становится первой ступенью E.** Перенос авторских
комментариев сам по себе не убирает 366 строк, уже напечатанных генератором:
это разные работы — «перестать сочинять» и «убрать сочинённое». Порядок обратный
тому, что кажется: сперва прополка (вывод становится чистым и проверяемым
проверкой), затем перенос (вывод наполняется авторским смыслом). Иначе первая же
задача даёт вывод, где авторский комментарий соседствует с `// NOTICE:`.

Option D отклонён: он теряет doc-строки публичного API `rust` (33 вхождения
каждой из трёх), а по варианту E их судьбу решает отдельный вопрос, а не
умолчание.

#### Развилки внутри E, решённые заказчиком 2026-09-06

1. **Версия в шапке — версия языка** (`takt_lang::LANGUAGE_VERSION`, сейчас
   `0.18.0`), не версия крейта. Снимки `examples/generated/` и `book/` тем самым
   не пересобираются при подъёме версии компилятора (59 подъёмов на сегодня), а
   читателю вывода отвечают на осмысленный вопрос — на каком Takt написан
   исходник. Версия генератора печатается **при необходимости** — то есть только
   если у цели появится своё несовместимое изменение формы вывода; сегодня такой
   нужды нет, и поле не заводится (запись без нужды — та же отсебятина).
2. **doc-строки публичного API `rust` тоже убираются.** Генератор не сочиняет
   **ничего**: ни `/// Один такт автомата.`, ни `/// Порт ввода-вывода модели.`
   Следствие принято: `cargo doc` порождённого модуля станет пустым.
   Риск сборки **снят замером** (2026-09-06): ни `#![deny(missing_docs)]`, ни
   `missing_docs` в флагах проверки цели `rust` нет — порождённый модуль объявляет
   только `#![forbid(unsafe_code)]`, и удаление doc-строк его не ломает.
3. **Комментарий размноженного узла повторяется в каждом месте.** Комментарий
   объясняет код, а код после подстановки функции (0444), разворота цикла у `sv`
   (0321) и специализации (0185) стоит в нескольких местах — значит объяснение
   нужно в каждом. Цена названа: развёрнутый цикл на 64 итерации даёт 64
   копии комментария, и это ожидаемое поведение, а не дефект.

#### Второе решение: язык комментариев — по ключу `--lang`

**Комментарии вывода подчиняются выбору языка** (решение заказчика 2026-09-06):
их тексты переезжают в каталог сообщений [язык сообщений компилятора и симулятора (i18n)](0532-i18n-diagnostics.md)
наравне с диагностиками, и `taktc compile --lang en` печатает английские
комментарии. Сегодня они русские во всех восьми целях безусловно.

Следствие, которое нельзя пропустить: **снимки становятся зависимы от языка
прогона**. `examples/generated/` и снимки `book/`  хранятся в
дереве; чтобы они не поехали, проверки обязаны собирать их при умолчании (`ru`),
а не наследовать `TAKT_LANG` машины. Носитель 0532 системную локаль не читает
(решение заказчика 2026-09-06), так что достаточно **не задавать** переменную в
проверках — но это надо проверить прогоном, а не предположить.

Второе следствие: прополка и перевод — **одна** работа, а не две. Текст,
переписанный на месте и лишь потом унесённый в каталог, пришлось бы трогать
дважды; поэтому вычищенная фраза сразу становится ключом каталога с парой
`ru`/`en`.

### Consequences

- **Ключа сборки не появляется** — ни новой оси в матрице 0466, ни записи в
  `book/` по проверке, ни поля во вкладке веба (0531, задача 09m).
- **Каталог сообщений растёт** на комментарии вывода: ключи в своём
  пространстве (`gen.*`), чтобы отличать их от диагностик. Проверка паритета
  (`check-messages.py`) судит их наравне с прочими.
- **Снимки пересобираются один раз**: `examples/generated/` и `book/` дают
  большой дифф, состоящий **только** из комментариев. Основание сверки —
  детерминированность генерации (0048).
- **Появляется проверка** `scripts/check-generated-comments.py` со своим контролем
  (правило: у каждого проверки — контроль, и он идёт первым).
- **Язык вывода целей становится наблюдаемым**: `--lang en` меняет комментарии,
  но не код. Это надо назвать в `book/` там, где описан ключ `--lang` (фича заводит абзац; здесь он дополняется одной фразой).

#### Acceptance criteria

1. **Ничего сочинённого.** В выводе всех восьми целей на корпусе `examples/`
   нет ни `фича NNNN`, ни `ADR NNNN`, ни пути `scripts/`, ни слова `NOTICE`, ни
   пустой строки комментария, ни пояснений, которых нет в исходнике.
2. **Шапка есть у каждого файла каждой цели** — на латинице, с предупреждением
   о порождённости и версией языка, **без даты**. Сегодня шапки нет у 51 файла
   (`c`, `c-hal`, `plantuml`), и это проверяется положительным контролем.
3. **Комментарий автора доезжает.** Модель с ведущим и хвостовым комментарием у
   объявления, состояния, перехода и оператора даёт вывод, где оба стоят в
   логически том же месте — у всех целей, печатающих комментарии.
4. **Перенос не ломает вывод.** Комментарий, содержащий закрывающую
   последовательность цели (`*)` для `st`, `*/` для `c`), обезврежен, и
   инструменты целей принимают файл. Контроль — вход из корпуса
   (`examples/stacker.takt:203`), на котором класс и найден.
5. **Размноженный узел несёт комментарий в каждом месте** — проверяется на
   развороте цикла `sv` и на подстановке функции.
6. **Проверка падает списком** и проверен снятием: с возвращённым сочинённым
   комментарием краснеет, на вычищенном дереве зелёный.
7. **Поведение не меняется**: потактовые сверки и проверки целей зелёные; снимки
   `examples/generated/` и `book/` пересобраны и отличаются **только**
   комментариями.

### Риски и зависимости

- **Позиции — главная цена** (задача 03). Замер предупреждает: оценка «по
  вхождениям» завышает объём вдесятеро, считать надо шаги потери сведения.
- **Кириллица авторского комментария в выводе цели.** 489 комментариев корпуса
  русские; `iec2c`, `cc` и `verilator` на UTF-8 в комментариях замером **не
  проверялись** — проба обязана быть первым шагом задачи 04, а не допущением.
- **Проверка запрещённых имён** ([старое имя языка в порождаемом коде (lam_q_*, LAM_Q_*)](0253-legacy-names-in-generated-code.md))
  судит порождаемый код: авторский комментарий со старым именем языка пролезет в
  вывод и покраснит проверка на входе, за который автор модели не отвечает. Правило
  поведения назвать в задаче 04.
- **`plantuml`** комментариев не печатает вовсе (0 строк): перенос к нему
  применим лишь частично — диаграмма не текст программы. Границу назвать.

## Разработка

### Задача — прополка сочинённого и проверка

Предмет — первая ступень варианта E: вывод перестаёт рассказывать о внутреннем
устройстве компилятора. Перенос авторских комментариев в задачу не входит
(задачи `03`…`05`), шапка перерабатывается задачей `02`.

#### Что сделано

**Убрано из печатников восьми целей** — три класса замера плюс doc-строки
публичного API `rust` (решение заказчика 2026-09-06):

- адреса решений проекта: `(фича NNNN)`, `контракт ADR NNNN`, «проверяется (`scripts/precheck.sh`)»;
- служебный маркер `// NOTICE:` у целей `c` и `c-hal`;
- пустые строки комментария `///` и `//`;
- сочинённые пояснения: `/* Model … */`, `/* Forward declarations */`, подписи
  секций, хвостовые комментарии у служебных портов `sv`
  (`// служебный порт цели sv: …`) и регистрового интерфейса `sv-mmio`.

**Оставлено:** шапка «Порождено компилятором Takt (taktc) — цель: …» и
предупреждение «Не редактировать вручную». Предупреждение пришлось
**возвращать**: первый проход снял его вместе с прочим, потому что оператор
печати не содержал слова-признака шапки. Замечено чтением диффа снимков — тестам
и проверкам целей его пропажа невидима.

**Проверка** `scripts/check-generated-comments.py` (`G1`…`G4`) и контроль
`scripts/test-check-generated-comments.sh` (`C1`…`C6`), оба в предкоммите,
контроль первым. Проверка судит **собранный корпус**, а не исходники генераторов:
печать идёт из десятков мест, включая шаблоны строк (`c_hal.rs` печатает
комментарии внутри raw-литерала функции HAL), и греп по `src/` пропустил бы
половину. Контроль мутирует **компилятор**, а не файл: между `taktc` и проверкой
встаёт обёртка, дописывающая в вывод строку нужного класса, — иначе проба не
проверяла бы то, ради чего проверка заведён.

#### Замер (2026-09-06)

| Цель | строк было → стало | комментариев было → стало |
|---|---|---|
| `c` | 3325 → 3024 | 494 → 0 |
| `c-hal` | 3047 → 2772 | 439 → 0 |
| `st` | 2121 → 2110 | 55 → 4 (шапка) |
| `st-at` | 1869 → 1858 | 47 → 4 (шапка) |
| `rust` | 3634 → 2961 | 762 → 1 (шапка) |
| `sv` | 1085 → 997 | 92 → 2 (шапка) |
| `sv-mmio` | 1235 → 1137 | 102 → 2 (шапка) |
| `plantuml` | 255 → 255 | 0 → 0 |

Адресов решений, маркеров `NOTICE` и пустых комментариев в выводе — **ноль**
(было 90, 160 и 116).

#### Что нашла прополка

Три находки, и все три — не то, что ожидалось.

1. **Открывающая `(*` шапки ST была вырезана** автоматической правкой: оператор
   печатал только скобку, слова-признака в нём нет. Вывод стал невалидным ST при
   нулевом коде возврата — ровно тот класс, ради которого в проекте держат
   арбитра. Поймано **чтением вывода**, а не тестом: `iec2c` в этот момент не
   гонялся. Скобка возвращена.
2. **Тест `imported_enum_reaches_generated_output` был ложно-зелёным.** Он искал
   `Mode` в заголовке — и находил подстроку в сочинённом комментарии
   `/* Model App */`. Импортированное перечисление доезжает до вывода **всегда**,
   но в `.c` и константами (`ENUM_APP_MODE_AUTO`), а не типом в `.h`.
   Тест переписан на обещание.
3. **Тест `test_header_has_forward_declarations` проверял подпись секции**, а не
   секцию: `header.contains("/* Forward declarations */")`. Сами опережающие
   объявления он проверяет строкой ниже — проверка комментария снята.

Обе находки одного рода: **комментарий использовался как признак**. Пока он
печатался, тест зеленел, ничего не доказывая. Это довод в пользу проверки, а не
только правки текстов.

#### Проверки

- проверка `check-generated-comments.py`: 90 файлов корпуса, сочинённого нет, шапок 39;
- контроль: 6 проб, включая положительный контроль (`C5` — нетронутый вывод
  принимается) и контроль шапки (`C6`);
- тесты крейтов и проверки целей (`cc`, `iec2c`, `verilator`, `yosys`) — в
  предкоммите;
- снимки `examples/generated/` и `book/**/generated/` пересобраны; дифф состоит
  **только** из удалённых комментариев.

#### Что осталось за границей задачи

- Шапка у целей `c`, `c-hal` (40 файлов) и `plantuml` (11) по-прежнему
  отсутствует, версии языка в ней нет — задача `0535-02`.
- Комментарии автора модели в вывод не переносятся — задачи `0535-03`…`0535-05`.
- Тексты шапки живут литералами: в каталог сообщений  они переезжают
  вместе с задачей `02`, когда шапка получит окончательную форму.

### Задача — шапка одним носителем

Предмет — вторая половина требования заказчика: в самом верху каждого файла
предупреждение о порождённости, **на латинице**, с версией и **без дат**.

#### Что сделано

**Носитель** `generator/header.rs`: `file_header(target, style)` отдаёт три
строки — чем порождено и подо что, что файл не правят руками, версия языка.
Обрамление накладывает `CommentStyle` (`//` у C, Rust и SV; `(* … *)` у ST;
`'` у PlantUML): текст один, форма принадлежит целевому языку. Прежде шапку
печатали четыре места своими литералами, а три цели не печатали её вовсе.

**Шапка появилась там, где её не было** — у `c` (22 файла), `c-hal` (18) и
`plantuml` (11), то есть у 51 файла из 90. У `c` она стоит **до** feature-теста
`_POSIX_C_SOURCE` и до include guard: комментарий на них не влияет, а требование
«в самом верху» выполняется буквально.

**Профиль сборки — часть имени цели**: `C` против `C (HAL profile)`,
`Structured Text (IEC 61131-3)` против `… , AT profile`,
`SystemVerilog (IEEE 1800)` против `… , MMIO register file`. Шапка отвечает на
вопрос «чем это собрано», и без профиля ответ был бы неполным.

**Версия — языка** (`LANGUAGE_VERSION`, сейчас `0.18.0`), не компилятора; даты
нет. Оба решения записаны заказчиком 2026-09-06 и обоснованы в ADR.

#### Границы, названные явно

- **Шапка не переводится** ключом `--lang`, в отличие от будущих
  авторских комментариев: заказчик назвал латиницу её свойством. Порождённый
  файл читают рядом с чужими библиотеками, и техническая преамбула не должна
  зависеть от того, каким ключом запустили компилятор.
- **Версия генератора не печатается.** Требование заказчика допускало её «при
  необходимости»; необходимости нет — своей несовместимой формы вывода у целей
  сегодня не бывает, а запись без нужды была бы той же отсебятиной.
- **У `plantuml` шапка стоит после `@startuml`**, а не перед. PlantUML читает
  только то, что лежит между `@startuml` и `@enduml`; шапка снаружи не была бы
  частью диаграммы, и читатель, скопировавший блок, потерял бы предупреждение.
  Выбор сделан по правилу языка, **а не прогоном**: арбитра `plantuml` в
  проекте нет — проверка цели проверяет генерацию, но не рендер. Это названная
  граница, а не пропущенная проверка.

#### Проверки

- модульные тесты носителя (5): состав строк, отсутствие даты, латиница во
  **всех** трёх формах, обрамление по цели, отсутствие `*)` внутри блока IEC;
- проверка `check-generated-comments.py` дополнен: `G5` — шапка обязана быть в
  **каждом** файле (прежнее «хотя бы один» пропустило бы цель, потерявшую её
  целиком), `G6` — даты в шапке нет, `G7` — шапка на латинице;
- контроль дополнен пробами `C7` (дата) и `C8` (кириллица) — обе проверены
  снятием;
- снимки `examples/generated/` и `book/**/generated/` пересобраны.

### Задача — позиция у семантических операторов

Предмет — опора для переноса: комментарий автора привязан к смещению в
исходнике, а генераторы печатают из семантических узлов. Пока у оператора не
было координаты, сшивать было нечего.

#### Замер (правило 30, дата 2026-09-06)

Пересъём подтвердил оценку анализа: позицию несли **2 варианта
`StatementNode` из 15** — `Expression` (0264) и `Variable` (0386), плюс `For`
(0471). В АСД позиция есть **у всех**: она отбрасывалась в точке понижения
(`ast::Statement::If(_, …)` — координата уходила в `_`).

Цена, снятая прогоном, а не оценкой: одно поле у `If` дало **38** ошибок
компиляции, из них 28 — сопоставления, дополняемые `..` механически, и 10 —
места построения, где позицию надо назвать осознанно. Это и есть «шаги, на
которых сведение теряется» (способ 0471): построений по всем вариантам
оказалось около сорока, тогда как упоминаний — свыше четырёхсот.

#### Что сделано

Позицию получили `If`, `Loop`, `Match`, `Assembly` (поле `loc`) и `Return`,
`Continue`, `Break` (кортежное поле). Источник — узел АСД в точке понижения;
синтетические узлы (guard границ 0433, подстановка раннего возврата 0446)
получают `Location::Codegen`, а обёртка вокруг авторского оператора берёт
координату **у него**.

Носитель `semantic::statement_loc`: метод `StatementNode::loc()` и **ручной**
`PartialEq`.

#### Что нашёл прогон

**Позиция вошла в равенство и расщепила узлы.** `PartialEq` у `StatementNode`
выводился производно, и как только координата появилась у `Continue`/`Break`,
тест `continue_break_resolve` покраснел: узлы, отличавшиеся **только**
позицией, перестали быть равными. Это ровно класс — прецедент уже был в
`MatchArmNode`, где равенство написано руками именно поэтому. Теперь так же у
операторов, и на это заведён тест с положительным контролем.

Класс дорог тем, что тест поймал его случайно: сравнение операторов живёт в
подстановке функций (0444) и в свёртке, и расхождение пришло бы не отказом, а
**другим выводом**.

#### Границы

- `Block`, `InlineFormula` и `Formula` координаты не хранят: у блока её роль
  играет позиция первого элемента (так `loc()` и отвечает), у формул — позиция
  вместилища. Поле стоило бы правки всех сопоставлений, а переносить
  комментарий перед ними незачем — он привязан к оператору внутри тела.

#### Проверки

- 4 теста носителя: позиция не расщепляет одинаковые операторы (все семь форм),
  разные операторы остаются разными (контроль), позиция доезжает, блок отвечает
  позицией первого элемента;
- вывод восьми целей на корпусе — **байт в байт** прежний: позиция появилась в
  дереве, но печатники её пока не читают (это задача `0535-04`);
- проверка размера модуля: `semantic/mod.rs` **ужат** с 1235 до 1011 строк —
  тесты вынесены в `semantic/tests.rs` (приём фич и 0225), реестр долга
  уменьшен.

### Задача — перенос комментариев автора

Предмет — носитель переноса: сшивка комментария с узлом по смещению, приведение
формы к комментарию цели и обезвреживание закрывающей последовательности.

#### Замер первым шагом (правило 30, дата 2026-09-06)

**Риск «кириллица в выводе» снят прогоном, а не допущением.** Все арбитры
принимают UTF-8 в комментариях: `cc -std=c11 -Wall -Wextra -Werror -pedantic`,
`iec2c`, `verilator --lint-only -Wall`, `yosys`, `rustc -D warnings`.

**Где стоят комментарии корпуса** (469 в 11 файлах) — замер решил, куда
вкладывать силы:

| Перед чем | Сколько |
|---|---|
| `model` | 103 |
| порты (`in`/`out`) | 80 |
| типы (`struct`/`enum`) | 67 |
| состояния (`state`/`start`) | 63 |
| переменные (`var`/`const`) | 52 |
| функции (`fn`/`extern`) | 37 |
| `import` | 32 |
| внутри тел (`always`, `cond`) | 15 |

**Внутри тел операторов лежат лишь 6 комментариев из 469.** Перенос,
сделанный только по телам, дал бы на корпусе три строки — то есть почти
ничего. Это и решило состав задачи: места объявлений важнее мест операторов.

#### Что сделано

**Носитель** `generator::comments`: `SourceComments` (исходник + позиции),
`leading` и `trailing`, `emit_around` (обрамление оператора), `defuse`.
Классификация «ведущий / хвостовой» взята у форматтера (0024-02) — вторая
разошлась бы с первой молча.

**Канал доставки**: комментарии собирает конвейер (единственный, кто видит и
текст, и разбор) и кладёт в `GenerateOptions::comments`; потребитель без
исходника получает `None` и работает как прежде.

**Места у цели `c`**: операторы тела (ведущие и хвостовой), объявления
структур, переменных модели, функций и **самой модели**.

**Форма принадлежит цели, текст — автору**: авторские маркеры снимаются, текст
обрамляется комментарием целевого языка, закрывающая последовательность
обезвреживается (`*)` → `* )` у ST, `*/` → `* /` у C).

#### Что нашёл прогон

1. **Позиция объявления указывает на имя, а не на начало строки.** У `struct St`
   координата — на `St`, и поиск назад упирался в слово `struct`: комментарий
   перед структурой не переносился вовсе, хотя перед оператором — переносился.
   Отсчёт исправлен на начало строки.
2. **Хвостовой комментарий соседа чуть не стал ведущим.** После правки (1)
   между `// счётчик` предыдущей строки и началом следующей — только перевод
   строки, и наивный поиск подхватил бы его: комментарий уехал бы к чужому
   коду. Теперь ведущим считается только тот, что **начинается на своей
   строке**; на это заведён тест.
3. **Две потактовые сверки стали ложно-красными.** Фикстура
   `conformance_fixed_cast_literal` объясняет словами, что «`floor(...)`
   компилируется и считает верно», — и это пояснение доехало до вывода, а
   проверка искала подстроку `floor(` во всём тексте. То же у
   `conformance_fixed_place` с литералом `2.0`. Проверки смотрят на код,
   комментарии отбрасываются. Класс тот же, что у двух ложно-зелёных тестов
   задачи `01`, только знак обратный: **тест проверял текст, а не предмет**.
4. **Позиция чужого файла роняла `taktc` паникой.** У импортированного
   объявления координата указывает в текст другого файла; приложенная к своему
   исходнику, она попадала внутрь многобайтового символа —
   `is not a char boundary`. Поймано прогоном на
   `book/src/09-imports/examples/pid_loop.takt`. Кириллица в исходниках
   проекта повсеместна, так что случай не экзотический, а обычный. Носитель
   теперь знает **свой** номер файла и на чужие позиции отвечает «переносить
   нечего»; вторая линия обороны — срез через `get`, а не индексированием.
5. **Проверка судил авторские тексты.** В примерах корпуса авторы пишут «фича», и такой комментарий, доехав до вывода, покраснил `G1` — хотя
   генератор ни при чём. Проверка научен отличать авторское от сочинённого по
   исходнику; на само различение заведена проба `C9`, иначе оно осталось бы
   непроверенным.

#### Границы (названы, а не забыты)

- **Перенос сделан у цели `c`.** Остальные семь целей — задача `0535-05`:
  устройство доказано на всех видах мест, распространение механическое.
- **Константы перечислений комментария не получают**: у цели `c` они
  печатаются отсортированным списком `#define`, и комментарий, привязанный к
  одному варианту, встал бы в произвольное место.
- **`import` (32 комментария) в вывод не переносится**: импорт — не элемент
  вывода, переносить его комментарий некуда.

### Задача — остальные цели и закрытие

Предмет — распространить перенос на цели, оставшиеся за границей задачи 04.

#### Что сделано

**Носитель стал потоковым** (`comments::activate` / `reset`) — приём и причина
те же, что у позиции оператора (`generator::site`): печатники
операторов принимают три разных контекста (`ModelNode` у `st`, `Scope` у `sv` и
`rust`, карту у `c`), и протаскивание носителя через все сигнатуры стоило бы
правки десятков функций ради данных, нужных в двух местах на цель. Цель `c`
переведена на него же — способ доступа один.

Сброс стоит **на всех путях выхода**, включая отказ: иначе следующая
генерация в том же потоке взяла бы комментарии чужого исходника.

**Места**: тела операторов и объявления моделей — у `st`, `st-at`, `rust`, `sv`,
`sv-mmio`; объявления типов — у всех трёх. Форма принадлежит цели: `(* … *)` у
ST, `//` у прочих.

#### Замер переноса (2026-09-06, корпус `examples/`)

| Цель | Перенесено авторских строк |
|---|---|
| `c` | 132 |
| `c-hal` | 112 |
| `st` | 102 |
| `rust` | 102 |
| `st-at` | 88 |
| `sv`, `sv-mmio` | по 16 |
| `plantuml` | 0 (граница) |

У `sv` меньше по устройству: цель уплощает композицию, и отдельных объявлений
под-моделей у неё нет.

**Обезвреживание проверено на живом входе**: `examples/stacker.takt:203` несёт
`(cmd_target_*)`, в выводе ST стоит `(cmd_target_* )`, и `iec2c` файл
принимает. Без обезвреживания комментарий закрылся бы досрочно, а хвост строки
уехал бы в код.

#### Что нашёл прогон

**Ещё два теста стали ложно-красными** — и это уже третий случай одного класса
за фичу. `test_ports_without_at_in_plain_st` проверяет «цель `st` адрес не
эмитит» поиском подстроки `AT %`, а фикстура **объясняет словами**: «Цель
`st-at`: `VAR_GLOBAL … AT %IX256.0`». Пояснение доехало до вывода, и тест
покраснел. То же у `test_st_array_variable_is_emitted_as_real_array` с
`uint4_t`.

Вывод общий и стоит записи: **проверка на отсутствие конструкции в выводе
обязана смотреть на код, а не на текст**. Пока комментариев в выводе не было,
разница ничего не стоила; с переносом она стала обязательной. За фичу этот
класс всплыл трижды — дважды ложно-зелёным (задача 01) и трижды ложно-красным
(задачи 04 и 05).

**Хвостовой комментарий у ST ломал вывод.** Блочная форма IEC многострочна, и
её первая строка — голое `(*`. Приклеенная к строке кода, она открывала
комментарий и не закрывала его:

```text
t := t + 1; (*
IF t = 3 THEN
```

`iec2c` отвечал «invalid statement in ST statement» — то есть **невалидный
вывод при нулевом коде возврата `taktc`**, ровно тот класс, ради которого в
проекте держат арбитра. Поймано проверкой цели. Хвостовой комментарий печатается
однострочной формой (`CommentStyle::wrap_inline`), на класс заведён тест.

**Сравнение двух выводов сломалось законно.** Тесты «`--float-embedded` даёт тот
же ST/Rust, что явный `q(8,8)`» сравнивают вывод **двух разных фикстур**, а у
них законно разные комментарии. Предмет проверки — совпадение кода; сравнение
переведено на общий помощник `target_code::code_only`.

Помощник заведён один на все наборы сверок: класс всплыл в семи тестах, и
семь копий фильтра разошлись бы молча.

#### Границы

- **`plantuml` комментарии не получает** — и это решение, а не пропуск:
  PlantUML комментарии не рисует, диаграмма их не показывает, переносить текст
  туда некуда. Цель и раньше не печатала ни одного комментария.
- **Константы перечислений** у `c` по-прежнему без комментариев (печатаются
  отсортированным списком `#define`).
- **Порты и состояния** комментария не получают ни у одной цели: у первых в
  выводе — перечислители, собираемые из разных моделей, у вторых — ветви
  `case`, и место комментария там неоднозначно. Названо как остаток, а не
  сделано молча.

## Итог (что сделано)

Порождённый код перестал рассказывать о внутреннем устройстве компилятора и
начал нести то, что вложил автор модели.

**Было** (замер-06): 1 991 строка комментария в выводе восьми целей, из
них 366 — адреса решений проекта (`ADR 0033`, `фича 0059`, `scripts/precheck.sh`),
служебные маркеры `NOTICE:` и пустые строки комментария. Шапки не было у 51
файла из 90, версии — ни у одной цели. Комментарии автора модели в вывод не
попадали вовсе.

**Стало**: сочинённого генератором текста ноль; шапка — у каждого файла
(латиница, версия языка, без дат, профиль сборки в имени цели); комментарии
автора доезжают у семи целей из восьми (`c` — 132 строки на корпусе, `c-hal` —
112, `st` — 102, `rust` — 102, `st-at` — 88, `sv` и `sv-mmio` — по 16).

**Контроля**: `check-generated-comments.py` (`G1`…`G7`) со контролем на девять
проб, включая положительный контроль и различение авторского текста;
`target_code::code_only` — один фильтр на все сверки.

**Чего фича стоила сверх плана.** Прогон нашёл десять классов, и три из них —
невалидный вывод либо падение инструмента:

1. открывающая `(*` шапки ST, вырезанная автоправкой;
2. хвостовой комментарий блочной формы, оставлявший в строке кода голое `(*`;
3. позиция чужого файла, ронявшая `taktc` паникой на многобайтовом символе.

Остальные семь — тесты, проверявшие **текст, а не предмет**: два ложно-зелёных
(находили подстроку в комментарии, который сами и породили) и пять
ложно-красных (искали отсутствие конструкции вместе с пояснением фикстуры).

Вывод, который стоит помнить: **пока комментариев в выводе не было, разница
между «нет конструкции в коде» и «нет подстроки в файле» ничего не стоила**. С
переносом она стала обязательной — и обнаружилась разом в семи местах.
