## Краткое описание

**Ширина выведенного типа берётся у операнда, поэтому `const K := 1 << 8;`
даёт ноль.** Замер при закрытии
[три константных вычислителя компилятора живут порознь](0208-const-evaluators-unification.md) (2026-08-16): тип
выводится от левого операнда (`1` → `[bit;8]`), а нормирование
[отрицание ~0 для беззнакового типа: два правила языка столкнулись](0207-bitwise-not-unsigned-literal.md) заворачивает
вычисленные 256 в ноль. Прежде это была ошибка `SE-089`. Поведение следует
из двух принятых правил и в теле такое же (`u: u8` → `u := 1 << 8;` даёт 0),
но для **объявления без явного типа** неочевидно: автор не выбирал ширину, её
выбрал литерал. Смежно с кандидатом о `wider_type(Integer, Array)`. Кандидат:
либо выводить ширину по **результату** вычисления, либо предупреждать, когда
нормирование меняет вычисленное значение.

> Фича заведена **из бэклога кандидатов пакетным переводом** (решение заказчика
> 2026-08-18: «перевести всех кандидатов в фичи без проработки, решить, делать
> или нет, позже»). Стадии 2 и 3 **не пройдены**: приоритет, зависимости и
> объём не оценивались. Далее — жизненный цикл по правилу 17.

### Context

Инициализатор объявления сворачивается в литерал (0192), а вычисленное значение
**нормируется по типу объявления** (0207): беззнаковое переполнение — обёртка
`mod 2ⁿ`, как в теле состояния. Оба правила верны и согласованы между девятью
потребителями.

Но тип **выводится до свёртки** (порядок 0192: разрешить → вывести типы →
свернуть), а вывод берёт тип у **операндов**. Отсюда: `const K := 1 + 255;`
получает `[bit;8]` от левого литерала, и нормирование заворачивает вычисленные
`256` в **ноль**.

**Замер-19** (`scripts/probe.sh`, проба признана годной):

| Запись | Значение | Почему |
|---|---|---|
| `1 << 8` | **0** | ширина от `1` — 8 бит |
| `1 + 255` | **0** | то же |
| `255 + 1` | **0** | порядок операндов не спасает |
| `2 * 128` | **0** | не только сложение |
| `200 + 200` | **144** | `400 mod 256` |
| `300 - 44` | 256 | ширина от `300` — 16 бит |
| `1000 + 1` | 1001 | то же |

**Кандидат винил сдвиг — дело в любой арифметике.** Строки `300 - 44` и
`1000 + 1` показывают причину: там ширины хватало **случайно**, потому что
левый операнд сам по себе не влезал в восемь бит.

**Расхождения между потребителями нет:** значение сворачивается в семантике,
и все девять дают одно и то же. Это `Tier 2` по шкале проекта — «молча неверное
значение при согласии инструментов»: инструменты не противоречат друг другу,
они одинаково неправы относительно написанного.

**Прежде это была ошибка `SE-089`.** Фича сменила отказ на нормирование
— верно для **явного** типа (там ширину выбрал автор) и неожиданно для
**выведенного** (там её выбрал операнд).

### Decision Drivers

1. **Автор не выбирал ширину.** Если тип не написан, единственное, что автор
   выразил, — это выражение; подгонять его результат под ширину случайного
   операнда значит отвечать не на то, что спросили.
2. **Явный тип трогать нельзя.** `var u: u8 := 200 + 100;` = `44` — принятое
   решение, согласованное с телом состояния.
3. **Молчание хуже отказа.** До 0207 здесь была диагностика; теперь ни
   диагностики, ни верного значения.
4. **Граница правил должна быть узкой.** Соседние правила (нормирование
   0207, вывод из сигнатуры функции Ce6) верны и обязаны остаться нетронутыми.

### Considered Options

#### Option A. Оставить как есть

**Pros:** ноль правок; поведение согласовано и выводимо из двух правил.

**Cons:** `const K := 1 + 255;` даёт ноль, и об этом не говорит никто.
«Выводимо из правил» — не то же, что «ожидаемо для автора».

#### Option B. Предупреждение, когда нормирование меняет значение

**Pros:** не меняет поведения.

**Cons:** значение остаётся неверным. Предупреждение уместно там, где поведение
**нормировано** (`SE-090`), а здесь нормировать нечего — верный ответ известен.

#### Option C. Вернуть `SE-089` для выведенного типа

**Pros:** громко.

**Cons:** отвергает запись, у которой есть очевидный верный смысл. И
противоречит 0207, снявшей этот отказ.

#### Option D. Ширина выведенного типа — по результату вычисления

**Pros:**
- `const K := 1 + 255;` даёт `256` — то, что написано.
- Явный тип, вывод из сигнатуры и правило не затронуты.
- Ничего не добавляется в язык: меняется только выбор ширины там, где её никто
  не выбирал.

**Cons:** правка стоит **в свёртке**, то есть после вывода типов — приходится
запоминать, был ли тип объявлен. Требует трёх границ (см. ниже), и каждая из
них — потенциальный перебор.

### Decision

Принимается **Option D**.

1. Имена, у которых тип **не объявлен**, снимаются **до** вывода типов (после
   него `Inference` заменён, и отличить «автор выбрал ширину» от «её выбрал
   операнд» уже нечем).
2. После свёртки, если такое объявление получило литерал, **превышающий верхнюю
   границу** выведенного типа, тип переопределяется по результату
   (`infer_int_type`) — тем же носителем, каким выбирается тип литерала.
3. Границы берутся у **единственного** носителя
   (`validate::literal_range::type_range`): своя копия разошлась бы с `SE-089`.

**Три границы, и каждая поймана чужим тестом, а не чтением:**

- **явный тип не трогать** — иначе ломается правило;
- **тип из сигнатуры функции не трогать** — первая редакция переопределяла тип
  **всегда**, и `fn get32() -> [bit;32]` с `var val := get32();` дал `[bit;8]`,
  потому что вычислитель сворачивает вызов в `0` (упал тест Ce6);
- **отрицательное не расширять** — вторая редакция смотрела и на нижнюю
  границу, и `var u := ~0;` перестал давать `255` (упал тест нормирования 0207).

### Consequences

#### Положительные

- Объявление без типа даёт то значение, которое написано.
- Диагностики не добавилось, язык не сузился: изменился только выбор ширины.
- Правило и вывод Ce6 остались нетронутыми — доказано их же тестами.

#### Отрицательные / Action items

- **Наблюдаемое поведение меняется**: `const K := 1 + 255;` было `0`, стало
  `256`. Прежнее значение было дефектом, а не контрактом.
- Правка живёт в свёртке и опирается на множество «имена без объявленного
  типа». Новый путь, добавляющий объявления **после** вывода типов, обойдёт её
  молча — граница названа в коде.

#### Acceptance criteria

1. `1 + 255`, `255 + 1`, `2 * 128`, `1 << 8` дают `256`; `200 + 200` — `400`
   (A1).
2. `300 - 44` и `250` не изменились (A2, контроль).
3. `var u: u8 := 200 + 100;` = `44` (A3).
4. `var u := ~0;` = `255` (A4).
5. `var val := get32();` сохраняет `[bit;32]` (A5).
6. `./scripts/precheck.sh` зелён (A6).

## Разработка

### Задача

#### Что было

Тип объявления выводится **до** свёртки (порядок 0192), и вывод берёт его у
операндов. `const K := 1 + 255;` получал `[bit;8]`, нормирование 0207
заворачивало `256` в ноль — молча и одинаково у всех девяти потребителей.

#### Что сделано

**1. Имена без объявленного типа снимаются до вывода типов**
(`prepare_variables`): после него `Inference` заменён выведенным типом, и
отличить «автор выбрал ширину» от «её выбрал операнд» уже нечем.

**2. После свёртки тип переопределяется по результату** — но только когда
литерал **превышает верхнюю границу** выведенного типа. Ширина берётся тем же
`infer_int_type`, которым выбирается тип литерала; границы — у единственного
носителя `validate::literal_range::type_range` (своя копия разошлась бы с
`SE-089`).

**3. Три границы, и каждую поймал чужой тест, а не чтение кода:**

| Граница | Что ломала правка | Кто поймал |
|---|---|---|
| явный тип не трогать | — (заложено сразу) | контроль T6 |
| тип из сигнатуры функции не трогать | `fn get32() -> [bit;32]` + `var val := get32();` давал `[bit;8]`: вычислитель сворачивает вызов в `0`, а первая редакция переопределяла тип **всегда** | `semantic_tests::part4::ce6_array32_return_type_inferred` |
| отрицательное не расширять | `var u := ~0;` перестал давать `255`: вторая редакция смотрела и на **нижнюю** границу, а это домен правила | `computed_initializer_norm_tests::inferred_bit_vector_is_unsigned_too` |

Обе неудачные редакции выглядели верными при чтении. Это ровно тот довод, по
которому в проекте заведены сверки значений: правку сужают **контроля**, а не
рассуждение.

**4. Документ.** Языковой раздел «Типы», подраздел «Вывод типов»: правило
записано с примером и контрпримером (явный тип по-прежнему заворачивает).

## Тест-план

### Область и цель

Фича **меняет язык** (наблюдаемое значение), поэтому правило 16 применяется:

- **Пример:** `const STEP := 1 + 255;` — даёт `256`, ширина по результату;
- **Контрпример:** `var u: u8 := 200 + 100;` — даёт `44`, потому что ширину
  выбрал автор.

Оба вошли в языковой раздел «Типы», подраздел «Вывод типов».

**Половина проверок — границы, а не предмет.** У этой правки две неудачные
редакции были пойманы **чужими** контролем (вывод Ce6 и нормирование 0207);
проверки T6–T8 закрепляют их рядом с правилом, чтобы граница была видна вместе
с ним.

**Контроль «не изменилось» обязателен** (T5): без него нельзя отличить
«починили ширину» от «поменяли вывод типов вообще».

### Выводы и дальнейшие шаги

1. **Кандидат винил сдвиг — замер показал любую арифметику.** `2 * 128` и
   `200 + 200` дают тот же дефект, а `300 - 44` работал **случайно**: там левый
   операнд сам не влезал в восемь бит. Правка, сделанная по букве кандидата
   (только `<<`), закрыла бы восьмую часть класса.
2. **Правка сужалась дважды, и оба раза её сузили чужие контроля.** Первая
   редакция переопределяла тип всегда и сломала вывод Ce6 из сигнатуры функции;
   вторая смотрела и на нижнюю границу и сломала `~0`. Обе
   выглядели верными при чтении — это прямой довод в пользу сверок значений.
3. **Расхождения между потребителями не было и нет:** значение сворачивается в
   семантике, все девять согласны. `Tier 2` подтверждён в своём смысле —
   инструменты не противоречат друг другу, они были одинаково неправы.
4. **Исправлений не требуется.** Дефектов, заводящих `docs/fixes/0285-YY-*`,
   не найдено.
5. **Кандидатов не заведено.** Соседний класс уже описан фичей
   [wider_type(Integer, Array) берёт тип литерала и даёт ложную SE-089](0287-wider-type-array-literal.md) (правило `wider_type`
   побеждает объявленный тип источника); замер подтвердил, что фичи не
   пересекаются — 0285 правит выбор ширины после свёртки, 0287 само правило.

## Итог (что сделано)

Ширина **выведенного** типа берётся у результата вычисления, а не у операндов.
`const K := 1 + 255;` даёт `256`; `const WIDE := 200 + 200;` — `400`. Явный тип,
вывод из сигнатуры функции и нормирование (0207) не тронуты.

**Кандидат винил сдвиг — замер показал любую арифметику.** `2 * 128`,
`128 * 2`, `1 + 255`, `255 + 1` давали ноль, `200 + 200` — `144`. А `300 - 44`
и `1000 + 1` работали **случайно**: там левый операнд сам не влезал в восемь
бит. Правка по букве кандидата (только `<<`) закрыла бы восьмую часть класса.

**Расхождения между потребителями не было:** значение сворачивается в
семантике, и все девять давали один и тот же неверный ответ. `Tier 2`
подтверждён в собственном смысле — «молча неверное значение при согласии
инструментов».

**Правка сужалась дважды, и оба раза её сузили чужие контроля.** Первая
редакция переопределяла тип **всегда** и сломала вывод Ce6: `fn get32() ->
[bit;32]` с `var val := get32();` дал `[bit;8]`, потому что вычислитель
сворачивает вызов в `0`. Вторая смотрела и на **нижнюю** границу и сломала
`var u := ~0;` (перестал давать `255` — а это домен правила). Обе редакции
выглядели верными при чтении.

Отсюда три границы, каждая закреплена контролем: явный тип не трогать, тип из
сигнатуры не трогать, отрицательное не расширять. Границы типа берутся у
**единственного** носителя `validate::literal_range::type_range` — своя копия
разошлась бы с `SE-089`.

Версия крейта `takt-lang`: `0.43.0` → `0.44.0`. Версия языка **не растёт**:
цикл `0.10.0` открыт фичей (правило 22, накопление).
