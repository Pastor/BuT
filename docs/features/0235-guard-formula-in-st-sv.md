# Фича: Цели st и sv теряют охранную формулу

- **Номер:** 0235
- **Статус:** ГОТОВО

## Краткое описание

Охранная формула (`: [Guard] c;`, `invariant`) **не доезжает** до целей `st` и
`sv`: их вывод не содержит проверки вовсе — ни при опечатке, ни при верном имени.
Автор, собирающий ПЛК или FPGA, получает прошивку **без** объявленного им
средства безопасности, и никто об этом не говорит.

> Фича зарегистрирована **из находки фичи** (запрос заказчика 2026-08-15);
> далее проходит жизненный цикл по своду.

## Что известно на входе

**Класс:** генерация (Tier 1 — молчаливая потеря средства безопасности).

Замер пробоя [validate не обходит формулы: неизвестное имя в Guard молчит](0203-validate-formulas-traversal.md) (2026-08-15) на одной
модели с одной формулой:

| Цель | `: [Guard] level < 3;` |
|---|---|
| `c` | `assert(main->level < 3);` |
| `rust` | `assert!(shared.level < 3);` |
| `st` | **формулы нет в выводе** |
| `sv` | **формулы нет в выводе** |
| симулятор | `SIM-025` при нарушении |

Молчание того же класса, что закрывала 0203: **потребители расходятся**, и
двое из пяти делают не то, что написал автор. Решение о форме (эмиссия проверки
против явного отказа `ST-…`/`SV-…`) принимает стадия архитектуры: у IEC 61131-3
нет `assert`, а в синтезируемом SV проверка живёт в `assert property` вне
синтезируемого подмножества — «просто напечатать» может оказаться невозможно, и
тогда честный ответ — **отказ с причиной**, а не тишина.

## Архитектура (ADR)

- **Status:** Accepted (Option C с уточнением заказчика: `st` предупреждает, а не отказывает; 2026-08-15)
- **Date:** 2026-08-15
- **Authors:** Архитектор
- **Related issues:** [Фича](0235-guard-formula-in-st-sv.md); находка [фичи](0203-validate-formulas-traversal.md) (validate не обходил формулы); смежно с [ADR](0044-sim-assert-invariant.md#архитектура-adr) (`invariant` как сахар над `cond` + `Formula::Guard`), [ADR](0041-st-backend.md#архитектура-adr) (генератор ST), [ADR](0045-sv-backend.md#архитектура-adr) (генератор SV)

### Context

Охранная формула — средство **безопасности**: `: [Guard] level < 3;` и
`invariant Safe = level < 3;` объявляют условие, которое обязано держаться.
[validate не обходит формулы: неизвестное имя в Guard молчит](0203-validate-formulas-traversal.md) закрыла молчание в
семантике: опечатка в имени внутри формулы стала ошибкой компиляции. Но она же
назвала границу, оставленную вне объёма: **цели `st` и `sv` не печатают
проверку вовсе — и при верном имени тоже**.

Автор, собирающий ПЛК или FPGA, получает прошивку **без** объявленного им
средства безопасности. Компилятор при этом рапортует об успехе.

#### Пробой (2026-08-15)

Вход — одна модель, одна формула:

```takt
var level: u8 := 0;
invariant Safe = level < 3;
start Run { : [Guard] level < 3; always { level := level + 1; } ref Run; }
```

| Цель | Что в выводе |
|---|---|
| `c` | `assert(model->level < 3);` |
| `rust` | `assert!(self.level < 3, "нарушен инвариант 'Safe'");` |
| `st` | **ничего** |
| `sv` | **ничего** |
| симулятор | `SIM-025` при нарушении |

#### Возможна ли трансляция вообще — измерено, а не предположено

**Цель `sv`.** Immediate assertion внутри `always_ff`:

| Форма | verilator `--lint-only -Wall` | yosys `synth` |
|---|---|---|
| `assert (level < 3);` | **принял** (код 0) | **принял** (код 0) |
| `assert (level < 3) else $error("…");` | принял (код 0) | **ОТВЕРГ**: `syntax error, unexpected TOK_ELSE` |

Статистика синтеза для принятой формы: 29 ячеек, из них **`$check` — одна**,
логика прежняя (8 `$_DFF_PN0_` и комбинационная обвязка). То есть проверка
попадает в вывод как **формальное свойство** и синтезируемую логику не трогает.

Отсюда следствие: **текст сообщения (имя инварианта) в цель `sv` перенести
нельзя** — форма с `else $error(…)` валит yosys. Цель `rust` имя печатает, цель
`c` игнорирует, цель `sv` не сможет по устройству инструмента.

**Цель `st`.** В IEC 61131-3 конструкции `assert` **нет вовсе**. Проба
ближайшего аналога — булев флаг нарушения:

```st
IF NOT (level < 3) THEN guard_violated := TRUE; END_IF;
```

`iec2c` принимает (код 0). То есть техническая возможность есть, но она
**вводит в язык новую сущность**: переменную, которой никто не читает, и
семантику «нарушение зафиксировано, выполнение продолжается».

#### Замер корпуса: цена отказа цели `st` — ноль правок

| Где | Файлов с `invariant` / `: [Guard]` |
|---|---|
| **`examples/`** (корпус проверок `st`/`sv`) | **0** |
| `book/src/*/examples/` | 2 (`airlock`, `lift`) — проверка компилирует их целью **`c`** |
| `takt-sim/tests/data/` (фикстуры эталона) | 5 |
| `takt-lang/tests/data/formula0203/` | фикстуры 0203, целями не собираются |

То есть главный минус вариантов с отказом (**«ломает корпус»**) на замере
**отсутствует**: ни один пример, который проверка транслирует целью `st`, формул не
содержит. Обратная сторона того же факта: **корпус этот класс не покрывает
вовсе** — потому потеря и дожила незамеченной, и любое решение обязано прийти
со своей фикстурой.

#### Дополнительная находка: в цели `sv` инфраструктура уже заведена

`SvMap` хранит поле `guard_enable` («эмитить ли guard-проверки — флаг
`--guard-disable` наоборот») и отдаёт его геттером `guard_enable()`. **Ни один
печатник цели `sv` этот геттер не вызывает.** То есть заготовка под проверки
существует с самого генератора, а самих проверок нет — тот же класс, что 0194
(«механизм на месте, поле не наполнено») и 0232 («проверка считалась и
выбрасывалась»).

### Decision Drivers

1. **Молчаливая потеря средства безопасности недопустима.** Это тот же класс,
   ради которого заведена 0203: автор написал охрану, её нет, и никто не сказал.
2. **Возможности целей различны, и это не вкусовщина.** В SV средство штатное и
   принимается обоими инструментами проверки; в IEC 61131-3 его нет.
3. **Кодогенератор не вправе вводить семантику, которой нет в языке.** Флаг
   `guard_violated` в ST — новая наблюдаемая сущность: кто её читает, что
   означает её значение между сканами, попадает ли она в интерфейс
   `FUNCTION_BLOCK`. Такие решения принимает язык, а не генератор.
4. **Отказ — законный ответ.** У проекта есть прецедент: `SV-003` на `float`,
   `ST-011` на агрегатную инициализацию, `RS-011` на поля структур. Отказ с
   причиной честнее молчания и дешевле неверной семантики.
5. **Уже заведённый флаг `--guard-disable` обязан работать одинаково** во всех
   целях, которые проверки печатают.

### Considered Options

#### Option A. Обе цели печатают проверку

`sv` → `assert (expr);`; `st` → булев флаг нарушения плюс присваивание.

**Pros:**
- Ни одна цель не теряет объявленное средство безопасности.
- Для `sv` цена нулевая: синтезируемая логика не меняется.

**Cons:**
- В ST вводится **новая сущность языка** через генератор: переменная-флаг, которую
  никто не читает, и молчаливое продолжение работы после нарушения. Симулятор в
  той же ситуации **останавливается** (`SIM-025`) — то есть цель `st` получила бы
  семантику, отличную от эталона, и это расхождение пришлось бы описывать.
- Флаг попадает в состав `FUNCTION_BLOCK`, то есть в наблюдаемый интерфейс.

#### Option B. Обе цели отказывают с диагностикой

`ST-…` и `SV-…`: «охранная формула целью не транслируется».

**Pros:**
- Молчание исчезает; поведение целей единообразно.
- Не вводит семантики, которой нет в языке.

**Cons:**
- Для `sv` это **отказ там, где средство есть и работает**: обе пробы приняли
  `assert`. Отказывать при наличии штатного механизма — терять даром.
- Программы корпуса, содержащие `invariant`, перестанут собираться этими целями
  (совместимость; объём правки корпуса надо мерить).

#### Option C. `sv` печатает, `st` отказывает

Разные ответы, потому что возможности целей различны: в SV — `assert (expr);`
(без `else`, по пробе); в ST — диагностика `ST-…` с названной причиной («в IEC
61131-3 конструкции assert нет; выразить проверку без введения новой сущности
невозможно»).

**Pros:**
- Каждая цель делает **максимум возможного**, и ни одна не молчит.
- Ничего не выдумывается: SV получает штатное средство, ST — честный отказ.
- Мёртвый `guard_enable` в `SvMap` оживает, флаг `--guard-disable` начинает
  работать и там.

**Cons:**
- Ответы целей различаются — это надо назвать в документе, иначе следующий
  читатель сочтёт расхождением.
- Отказ `st` ломает сборку программ с `invariant` этой целью (нужен замер
  корпуса).

#### Option D. `sv` печатает; `st` печатает флаг только по явному запросу CLI

Как C, но у `st` появляется опция `--st-guard-flag`, включающая эмиссию флага.

**Pros:**
- Автор ПЛК получает выбор.

**Cons:**
- Флаг CLI, меняющий **семантику** вывода, — прямое нарушение принципа 0042
  («CLI не должен менять логику автомата»); единственное узаконенное исключение
  (0096) документировано и сверяется трассами.
- Умножает состояния: два вывода `st` вместо одного, оба надо сверять.

### Decision

Принимается **Option C с уточнением заказчика** (2026-08-15): цель `sv`
**печатает** проверку, цель `st` **предупреждает**, а не отказывает.

- **Цель `sv`:** `assert (<условие>);` внутри тактового блока. Форма
  подтверждена обеими пробами; **без `else $error(…)`** — эта форма валит
  yosys (`syntax error, unexpected TOK_ELSE`), то есть имя инварианта в цель
  `sv` перенести нельзя по устройству инструмента, а не по забывчивости.
  Проверка уважает `--guard-disable` через уже существующее поле
  `SvMap::guard_enable`, которое до сих пор не читал никто.
- **Цель `st`:** новый код **`ST-022`** — предупреждение «охранная формула не
  транслируется: в IEC 61131-3 конструкции `assert` нет». **Вывод остаётся**:
  модель по-прежнему собирается для ПЛК, автор лишь узнаёт, что охрана в
  прошивку не попала. Канал доставки у цели `st` уже есть (`report`,
  `emit_functions` → `warnings`).

Почему предупреждение, а не отказ (уточнение заказчика): отказ лишил бы автора
рабочей трансляции ПЛК из-за конструкции, которая для этой цели лишь
**неприменима**, а не ошибочна. Предупреждение снимает молчание — то есть
решает предмет фичи — и не отнимает возможности собрать модель.

Почему **не** булев флаг нарушения в ST (Option A): он ввёл бы в язык
сущность, которой в нём нет, и семантику «нарушено, но работаем дальше»,
расходящуюся с эталоном (`SIM-025` останавливает прогон). Такое решение
принимает язык, а не генератор.

### Consequences

#### Положительные

- Охранная формула перестаёт молча исчезать: в SV она попадает в вывод, в ST
  автор узнаёт о невозможности **до** прошивки ПЛК.
- Поле `guard_enable` в `SvMap` перестаёт быть мёртвым, а `--guard-disable`
  начинает работать в трёх целях из четырёх.

#### Отрицательные / Action items

- **Совместимость цели `st` Не нарушается** (уточнение заказчика: предупреждение
  вместо отказа): программы с `invariant`/`: [Guard]` по-прежнему собираются, к
  выводу лишь добавляется `ST-022`. Замер корпуса это подтверждает избыточно —
  в `examples/` таких программ ноль.
- **Предупреждение печатается из библиотеки** (`eprintln!` в `report`) — общий
  дефект доставки, названный ещё ADR и заведённый фичей
  [предупреждения генераторов возвращаются вызывающему, а не печатаются из библиотеки](0168-generator-warnings-return.md) (`СОЗДАНА`). `ST-022`
  наследует его вместе с образцом; чинить здесь нельзя — фича превратилась бы в
  рефакторинг доставки.
- **Сверка поведения:** проверка в SV не должна менять трассу
  (`conformance_sv_tests`), иначе «добавили безопасность — сломали поведение».
- **Форма без `else` фиксируется проверкой:** попытка добавить сообщение через
  `else $error(…)` уронит yosys, и об этом обязан знать следующий.
- Смежное, вне объёма: цель `c` игнорирует имя инварианта, `rust` печатает —
  расхождение существовало до фичи и остаётся.

#### Acceptance criteria

1. Охранная формула не исчезает молча ни в одной цели.
2. Цель `sv` печатает проверку, и вывод принимается **обоими** инструментами
   проверки (verilator и yosys).
3. Синтезируемая логика цели `sv` не изменилась (сверка трасс зелёная).
4. Флаг `--guard-disable` подавляет проверки и в цели `sv`.
5. Цель `st` выдаёт **предупреждение `ST-022`** и **продолжает** трансляцию;
   это закреплено тестом и названо в документе.
6. Замер корпуса выполнен: известно, какие примеры задеты.
7. `./scripts/precheck.sh` зелёный.

## Анализ

### Цель и контекст

ADR принял Option C с уточнением заказчика: цель `sv` **печатает** проверку,
цель `st` **предупреждает** (`ST-022`) и продолжает трансляцию. Анализ отвечает
на четыре вопроса: **куда** в выводе `sv` встаёт `assert`, **откуда** цель
берёт формулы, **где** цель `st` выдаёт предупреждение и **чем** доказать, что
поведение не поехало.

### Зависимости фичи

- **Зависит от:** нет незакрытых. Смежные закрыты:
  [юнит-конструкции языка для симуляции (assert/invariant)](0044-sim-assert-invariant.md) (десахаризация `invariant`),
  [validate не обходит формулы: неизвестное имя в Guard молчит](0203-validate-formulas-traversal.md) (обход формул в
  `validate`, откуда взялась находка), [генератор генерации в SystemVerilog](0045-sv-backend.md)
  (генератор SV), [генератор генерации в Structured Text (IEC 61131-3)](0041-st-backend.md) (генератор ST),
  [предупреждение о делителе (`SV-009`) в цели `sv`](0064-sv-divider-warning.md) (канал предупреждений `sv`).
- **Смежная незакрытая:** [предупреждения генераторов возвращаются вызывающему, а не печатаются из библиотеки](0168-generator-warnings-return.md)
  (`СОЗДАНА`) — предупреждения генераторов печатаются `eprintln!` из библиотеки.
  `ST-022` наследует этот дефект вместе с образцом; **чинить его здесь нельзя**,
  иначе фича превращается в рефакторинг доставки.

### Требования и проверяемые условия

#### R1. Источник формул — общий обход, второго списка мест не заводить

[validate не обходит формулы: неизвестное имя в Guard молчит](0203-validate-formulas-traversal.md) свела места
объявления формул в **один** сбор — `semantic/formula/sites.rs`
(`model_formula_sites`, шесть мест, листья `Ltl`/`Guard`). Цели обязаны брать
формулы **оттуда же**, а не обходить дерево заново.

Цели `c` и `rust` сегодня печатают формулы **по своему обходу** (тела блоков,
`generate_formula_check` / `emit_guard`). Это существующее устройство, и фича
его не переписывает: она добавляет **новых** потребителей. Но если новый обход
понадобится — он берётся из общего сбора.

**Условие:** ни `sv`, ни `st` не заводят собственного перечня мест объявления
формулы.

#### R2. Форма проверки в SV задана пробой, а не вкусом

`assert (<условие>);` — **без** `else $error(…)`:

| Форма | verilator | yosys |
|---|---|---|
| `assert (expr);` | принял | **принял** |
| `assert (expr) else $error("…");` | принял | **ОТВЕРГ** (`TOK_ELSE`) |

Отсюда: **имя инварианта в цель `sv` не переносится**. Цель `rust` его
печатает, `c` игнорирует, `sv` не может — и это свойство инструмента, а не
недоделка. Условие обязано быть записано там, где следующий его увидит.

#### R3. Место вставки в SV — тактовый блок, и оно не меняет логику

Проба: 29 ячеек, из них `$check` — одна, остальные (8 `$_DFF_PN0_` и
комбинационная обвязка) те же, что без `assert`. То есть проверка попадает в
формальный слой и синтезируемую логику не трогает.

**Условие:** сверка `conformance_sv_tests` остаётся зелёной — трасса не
меняется. Если изменится, значит проверка встала не туда.

#### R4. `--guard-disable` обязан работать и в `sv`

Поле `SvMap::guard_enable` существует с самого генератора, геттер есть, **читателя
нет**. Фича делает поле живым.

**Условие:** при `--guard-disable` вывод `sv` не содержит `assert`, при
умолчании — содержит. Оба состояния проверяются тестом.

#### R5. Предупреждение цели `st` — новый код `ST-022`, трансляция продолжается

Занятые коды кончаются на `ST-021`. Текст обязан называть **причину**
(в IEC 61131-3 конструкции `assert` нет) — иначе автор решит, что это дефект
компилятора.

**Условие:** цель `st` возвращает вывод (`Ok`), а не ошибку; предупреждение
выдаётся **на каждую** охранную формулу, иначе вторая потеряется молча.

#### R6. Что остаётся вне объёма — названо

| Наблюдение | Решение |
|---|---|
| предупреждения генераторов печатаются `eprintln!` из библиотеки | дефект доставки, [предупреждения генераторов возвращаются вызывающему, а не печатаются из библиотеки](0168-generator-warnings-return.md) |
| `c` игнорирует имя инварианта, `rust` печатает | расхождение старше фичи; не трогаем |
| `Formula::LTL` в целях не эмитится | предмет 0035/0049, не этой фичи |

#### R7. Корпус класс не покрывает — фикстура обязательна

Замер: в `examples/` **ноль** программ с формулами. Значит проверки `st`/`sv`
этот класс не увидят никогда, и доказательство обязано прийти **фикстурой**
теста, а не корпусом. Это ровно та причина, по которой потеря дожила
незамеченной.

## Разработка

### Задача

#### Что было

Цель `sv` не печатала охранную формулу **вовсе** — ни при опечатке, ни при
верном имени (находка [validate не обходит формулы: неизвестное имя в Guard молчит](0203-validate-formulas-traversal.md)).
Автор, собирающий FPGA, получал прошивку **без** объявленного им средства
безопасности, а компилятор рапортовал об успехе.

При этом поле `SvMap::guard_enable` («эмитить ли guard-проверки — флаг
`--guard-disable` наоборот») существовало **с самого генератора** вместе с
геттером, и **ни один печатник его не читал**: заготовка без потребителя, тот же
класс, что 0194 и 0232.

#### Что сделано

**Эмиссия охранных формул в `sv_blocks.rs`** (не в `sv_fsm.rs`: тот — 998 строк
при пределе 1000): `emit_state_guards` / `emit_model_guards`, обе через общий
`emit_guard`.

- **Форма выбрана пробой, а не вкусом:** `assert (<условие>);`. Проба
  2026-08-15: `assert (…) else $error("…");` **verilator принимает**, а **yosys
  отвергает** (`syntax error, unexpected TOK_ELSE`). Поэтому имя инварианта
  (0044) в цель `sv` **не переносится** — это свойство синтезатора, а не
  недоделка; цель `rust` его печатает, `c` игнорирует.
- **Место — там же, где у цели `c`:** формулы модели перед `unique case`,
  формулы состояния первыми в его ветви. Проверка стоит **до** присваиваний, а
  умолчание `name_next = name` уже выполнено — значит условие читает значения на
  начало такта, как `assert` в начале `_tick` цели `c`.
- **Синтез не задет:** проба показала 29 ячеек, из них `$check` — одна, логика
  прежняя (8 `$_DFF_PN0_`).
- **`guard_enable` ожил:** `--guard-disable` подавляет проверки и в цели `sv`.

Функциональности: **цель `sv`** — да; **прочие цели, симулятор, семантика** —
н/п (не тронуты).

### Задача

#### Что было

Цель `st` теряла охранную формулу так же молча, как `sv`. Но в отличие от SV, в
IEC 61131-3 конструкции `assert` **нет вовсе**: проба показала, что выразить
проверку можно лишь булевым флагом нарушения (`iec2c` его принимает), а это
ввело бы в вывод переменную, которой нет в модели, и семантику «нарушено, но
работаем дальше» — расходящуюся с эталоном, где `SIM-025` останавливает прогон.

#### Что сделано

**Предупреждение `ST-022`** (решение заказчика 2026-08-15: предупреждение, а не
отказ — отказ лишил бы автора рабочей прошивки ПЛК из-за конструкции, которая
для этой цели лишь **неприменима**):

- выдаётся **на каждую** охранную формулу, с позицией самой формулы;
- текст называет **причину** («в IEC 61131-3 конструкции assert не существует»)
  и то, где охрана остаётся действующей (симулятор, цели `c`/`rust`/`sv`);
- **трансляция продолжается**: файл ST порождается, код возврата 0.

**Формулы берутся из общего сбора мест** (`semantic/formula/sites.rs`), а не из собственного обхода: второй список мест разъехался бы с первым
при появлении нового места объявления формулы (R1 анализа).

Предупреждение печатается `eprintln!` **из библиотеки** — общий дефект
доставки, названный ещё ADR и заведённый фичей
[предупреждения генераторов возвращаются вызывающему, а не печатаются из библиотеки](0168-generator-warnings-return.md); `ST-022` наследует его
вместе с образцом, чинить здесь нельзя.

### Что нашлось сверх ожиданий

**1. Пробой отменил «очевидную» форму.** Первое, что напрашивалось для SV, —
`assert (условие) else $error("нарушен инвариант 'Safe'");`, по образцу цели
`rust`. **verilator её принимает**, а **yosys отвергает** синтаксически
(`unexpected TOK_ELSE`). То есть форма прошла бы локальную проверку и уронила
проверка. Отсюда правило, записанное в коде: имя инварианта в цель `sv` не
переносится — это свойство синтезатора, а не недоделка.

**2. Инфраструктура для проверок в `sv` существовала с самого генератора.** Поле
`SvMap::guard_enable` и его геттер были на месте, **читателя не было ни одного**:
заготовка без потребителя. Тот же класс, что 0194 («механизм на месте, поле не
наполнено») и 0232 («проверка считалась и выбрасывалась»). Фича сделала поле
живым, а `--guard-disable` — работающим и в этой цели.

**3. Корпус класс не покрывает вовсе.** В `examples/` — **ноль** программ с
`invariant`/`: [Guard]`. Именно поэтому потеря дожила незамеченной: проверки `st` и
`sv` гоняют корпус, а в корпусе этого нет. Все доказательства фичи — на
фикстурах.

**4. Синтез не дорожает.** Проба: 29 ячеек, из них `$check` — одна; логика
прежняя (8 `$_DFF_PN0_`). Проверка попадает в формальный слой, а не в схему.

### Замечания к следующим фичам

- **Предупреждение печатается из библиотеки** (`eprintln!`) и не глушится
  `--quiet` — общий дефект доставки, названный ещё ADR; [предупреждения генераторов возвращаются вызывающему, а не печатаются из библиотеки](0168-generator-warnings-return.md) (`СОЗДАНА`).
- **Таблица кодов приложения отстаёт на пять кодов** (`ST-017`…`ST-021` в коде
  есть, в таблице нет) — записано кандидатом в `FEATURES.md`.
- **Цели расходятся в мелочи:** `rust` печатает имя инварианта, `c` его
  игнорирует, `sv` не может. Расхождение старше фичи и в объём не входило.

## Итог (что сделано)

**Охранная формула больше не исчезает молча ни в одной цели.**

- **Цель `sv` печатает** `assert (условие);` — форма подтверждена пробой: её
  принимают **оба** инструмента проверки, тогда как вариант с сообщением
  (`else $error(…)`) verilator принимает, а **yosys отвергает**. Отсюда правило:
  имя инварианта в эту цель не переносится. Синтез не дорожает (проверка уходит
  в ячейку `$check`).
- **Цель `st` предупреждает** `ST-022` и **продолжает** трансляцию (решение
  заказчика): в IEC 61131-3 конструкции `assert` нет, а придумывать ей замену
  генератор не вправе.
- **Ожил флаг `--guard-disable`** в цели `sv`: поле `SvMap::guard_enable` было
  заведено с самого генератора, но не читал его никто.
- **Корпус класс не покрывает** (в `examples/` формул ноль) — доказательства
  на фикстурах: [`guard_targets_tests.rs`](../../takt-lang/tests/targets/guard_targets_tests.rs),
  6 тестов, обе мутации краснеют.
