# Фича: Артефакт фичи — один файл

- **Номер:** 0402
- **Статус:** ГОТОВО
- **Зависит от:** нет
- **Tier:** proc — процесс: раскладка артефактов и проверки
- **Класс:** прочее
- **Связанные issue (анализ):** решение заказчика 2026-08-22

## Стадии жизненного цикла (правило 17)

Все стадии — **разделы этой карточки** (правило 32): «Архитектура (ADR)»,
«Анализ», «Разработка», «Тест-план», «Отчёт о тестировании», «Итог». Раздел
заводится в момент прохождения стадии, а не заранее. Отдельным артефактом
остаются только исправления — [`docs/fixes/`](../fixes/README.md) (при
необходимости `0402-YY-*`).

## Краткое описание

Шесть артефактов на фичу (карточка, ADR, анализ, разработка, тест-план, отчёт)
сведены в **один** — карточку `docs/features/XXXX-*.md`, где каждая стадия
стала разделом. Отдельным артефактом остались только исправления
(`docs/fixes/`). Порядок прохождения стадий и статусы не изменились.

Замер-22 перед работой: **2018** файлов стадий на **401** фичу при
**пяти** реестрах, которые приходилось держать согласованными.

> Фича зарегистрирована по запросу заказчика («ADR, Анализ, Разработка, Фича,
> Тестирование и Отчёт должны находиться в одном файле… Fixes остаются
> отдельным артефактом»).

## Документирование (правило 24)

**Не требуется** — язык не затрагивается вовсе: предмет фичи целиком
процессный (раскладка артефактов, правила свода и проверки). В `book/` детали
процесса не попадают по тому же правилу 24.

## Архитектура (ADR)

- **Status:** Accepted — решение заказчика 2026-08-22
- **Date:** 2026-08-22
- **Authors:** Архитектор + Аналитик

### Context

Жизненный цикл фичи (правило 17) заводил **шесть** артефактов: карточку, ADR,
анализ, задачи разработки, тест-план и отчёт — каждый своим файлом в своей
папке, каждая папка со своим реестром `README.md`.

Замер-22 перед работой:

| Папка | Файлов |
|---|---|
| `docs/features/` | 402 |
| `docs/adr/` | 361 |
| `docs/analyze/` | 376 |
| `docs/development/` | 614 |
| `docs/tests/` | 335 |
| `docs/reports/` | 332 |
| `docs/fixes/` | 49 |

Итого **2018** файлов стадий на 401 фичу; ссылок на них — в 444 файлах
репозитория. Цена такой раскладки уже была измерена дважды:

- проверка `check-registries.py` (0164) заведён потому, что **42** артефакта не
  значились в реестрах своих папок;
- проверка `check-registry-verdicts.py` (0218) — потому, что **79** записей
  утверждали «тестирование не проводилось» там, где оно проведено.

Оба проверки лечили следствие одной причины: пять реестров, которые надо держать
согласованными руками.

### Decision Drivers

1. **История одной фичи читается по шести файлам** — переход между ними
   стоит внимания и ломает чтение.
2. **Реестры расходятся с диском** — это уже случалось и потребовало проверки.
3. **Порядок стадий ценен и должен сохраниться** — он и есть процесс.
4. **Исправление живёт своей жизнью:** заводится после закрытия фичи, часто
   ссылается на несколько фич сразу.

### Considered Options

#### Option A. Оставить шесть артефактов

**Cons:** сохраняет обе измеренные болезни (рассинхрон реестров, чтение по
шести файлам).

#### Option B. Один файл на фичу, стадии — разделы

**Pros:** один реестр; история фичи читается подряд; порядок стадий виден по
оглавлению карточки; проверки упрощаются (две папки вместо семи).
**Cons:** карточка растёт (у крупных фич — сотни строк); миграция затрагивает
2018 файлов и 444 файла со ссылками.

#### Option C. Один файл, но и исправления внутрь

**Cons:** исправление заводится после закрытия фичи и часто относится к нескольким —
приклеивание к одной карточке прячет работу.

### Decision

Принимается **Option B**: артефакт фичи — один файл; исправления остаются отдельными
(правило 32).

### Consequences

- Каталогов стадий больше нет; реестр один — `docs/features/README.md`, он же
  несёт колонку «Вердикт тестирования» (правило 21).
- Ссылка на чужую стадию ведёт на карточку с якорем раздела.
- Проверки `check-registries.py`, `check-registry-verdicts.py`,
  `check-feature-status.py` и контроля генератора переведены на новую раскладку.

#### Acceptance criteria

1. Каталоги `docs/adr`, `docs/analyze`, `docs/development`, `docs/tests`,
   `docs/reports` отсутствуют; их содержимое — в карточках.
2. Битых ссылок нет (правило 14).
3. Генератор создаёт **одну** карточку; `--stage` файлов не заводит (кроме
   `fixes`).
4. Все проверки предкоммита зелёные.

### Найденные дефекты

Исправлений не потребовалось. По ходу работы вскрылись и устранены три
«побочных» места:

1. **Якорь в пути.** Скрипт переписывания добавил якорь раздела и в
   **shell-пути** (`test-legacy-names.sh`, `test-new-feature.sh`), где путь
   проверяется `-f`. Якорь снят: в скриптах путь без якоря.
2. **Проверка статусов читал последнюю колонку** — а последней стала «Вердикт».
   Переведён на третью ячейку; самопроверка проверки обновлена вместе с ним.
3. **Архив инструмента** `docs/development/0021-03-tool/` — не Markdown-стадия;
   перенесён в `docs/features/0021-03-tool/`, ссылки поправлены.

### Выводы и дальнейшие шаги

**1. Миграция механическая, но контроля пришлось править вместе с ней.** Три
проверки читали старую раскладку, и два из них — **через самопроверку**: их
ловушки были написаны в старом формате строк реестра. Проверка, чья самопроверка
не обновлена вместе с ним, ловит собственную заготовку, а не дефект.

**2. Ссылки — самая объёмная часть.** 408 файлов; после переписывания проверка 14
нашёл 2019 битых (реестры удаляемых папок) — их сняло удаление каталогов, а
остаток (44) правился точечно.

**3. Порядок стадий сохранён** — это было условием заказчика: разделы карточки
идут в том же порядке, что стадии правила 17, и заводятся по мере работы.

**Вердикт: ГОТОВО.**
