# Фича: Цель `rust`: печать операндов степени не проходит её же проверка

- **Номер:** 0415
- **Статус:** ГОТОВО
- **Зависит от:** нет
- **Tier:** 2
- **Класс:** генерация
- **Связанные issue (анализ):** кандидат блока 2 `FEATURES.md` (найден контрольным входом 0407)

## Стадии жизненного цикла

Все стадии — разделы этой карточки.

## Краткое описание

Цель `rust` печатала `({base}).wrapping_pow(({exp}) as u32)` безусловно. Оба
операнда при этом печатались неверно: у литеральной базы в Rust нет типа
(`E0689`), а приведение показателя чаще всего избыточно
(`clippy::unnecessary_cast`). Из четырёх форм записи проверка цели проходила
**одна**, и всё — при нулевом коде возврата `taktc`.

## Документирование

Не требуется: язык не меняется — предмет в печати одной цели.

## Архитектура (ADR)

- **Status:** Accepted
- **Date:** 2026-08-23
- **Authors:** архитектор, разработчик

### Context

**Замер-23** (`scripts/probe.sh`, прогон `rustc` и `clippy -D warnings`
теми же флагами, что в проверке предкоммита):

| Форма | Ответ инструмента |
|---|---|
| `v := 2 ** 8` | `rustc`: **`E0689`** — метод на неоднозначном типе `{integer}` |
| `v := b ** 8` при `b: u32` | `clippy::unnecessary_cast` — `(8) as u32` |
| `v := b ** n` при `n: u32` | `clippy::unnecessary_cast` — `u32` → `u32` |
| `v := b ** k` при `k: u8` | **принят** — приведение здесь обязательно |

Эталон исполняет все четыре, `c`/`c-hal`/`st`/`st-at`/`plantuml` переводят, их
инструменты принимают.

**Запись кандидата замером опровергнута дважды.** Он утверждал, что (1) `sv`
отвечает `SV-008` — на деле `sv` и `sv-mmio` степень переводят (0329) и оба
инструмента вывод принимают; (2) «база-переменная компилируется» — она даёт
отказ `clippy`, просто от другого линта. Класс оказался шире названного: не
одна форма из четырёх, а **три**.

Проверка цели этого не видел **по устройству**: он гоняет корпус, а степени в
`examples/` нет ни одной — та же слепота, что стоила дефектов и 0407.

### Decision Drivers

- Отказ приходит от **чужого инструмента** при нулевом коде возврата — класс: цель рапортует об успехе, файл не собирается.
- Правило обязано действовать не только в позиции «степень прямо в приёмнике»:
  `v := (2 ** 3) + x;` — обычная запись.
- Печать арифметики вокруг степени менять нельзя: она идёт **обёрткой**
  (`wrapping_add`).

### Considered Options

1. **Суффикс типа приёмника у базы + приведение показателя по нужде**
   (принято). Тип берётся там, где он известен, — в `rust_coerce`.
2. **Разворот степени в умножения** (как у `sv`). Отвергнут: `2 * 2 * 2` в
   debug **паникует** на переполнении, а `wrapping_pow` обёртывает — правка
   меняла бы семантику там, где сегодня она верна.
3. **Вычислять литеральную степень в цели.** Отвергнут: результат надо
   нормировать по типу приёмника, а в теле нормирования нет (правило
   действует в объявлении) — значение молча разошлось бы с эталоном.
4. **Приведение базы `2 as u32`.** Отвергнут замером: это
   `clippy::unnecessary_cast` — обмен одного отказа проверки на другой.

### Decision

Принят вариант 1.

- `rust_shift::power` принимает тип приёмника: `power_base` приписывает
  литеральной базе **суффикс** (`2u32`), `power_exponent` печатает `as u32`
  **по нужде** (литерал и `u32` идут без него — классы и 0361).
- Тип приёмника доезжает **полем контекста** `Scope::power_target`, а не
  собственным печатником арифметики: образец — `return_type`.
- База-литерал в позиции без известного приёмника — отказ **`RS-011`** с
  названной причиной (`E0689`): громкий отказ дешевле молчания.

### Consequences

- Вывод корпуса **не изменился** (степеней в `examples/` нет) — проверено.
- Названная граница: степень с литеральной базой в аргументе встроенной
  функции отвергается; вынесено кандидатом.

#### Acceptance criteria

Все четыре формы принимаются `rustc` и `clippy -D warnings`; значения
совпадают с эталоном потактово.

## Анализ

### Цель и контекст

Снять расхождение «цель рапортует об успехе — её же проверка вывод отвергает» во
всех формах записи степени.

### Замер

Таблица — в разделе Context. Контрольный вход (`b ** k` при `k: u8`) снят
отдельно и **опроверг** ожидание «приведение всегда лишнее».

### Зависимости фичи

Опирается на носители 0326/0334 (`shift_width::type_of`, `literal`) и на
`rust_coerce` (0335/0336/0360).

### Требования и проверяемые условия

- База-литерал получает тип приёмника суффиксом.
- Приведение показателя печатается по нужде, но **сохраняется** для иного типа.
- Приёмник доезжает до степени сквозь арифметику.
- Позиция без приёмника — отказ с причиной, а не невалидный вывод.

### Критерии приёмки и способ проверки

Эмиссионные тесты + прогон настоящего `clippy -D warnings` + потактовая сверка
с эталоном.

### Редакторский слой

Не затронут: узлов АСД и лексики фича не меняет.

### Особенности по обратной функциональности

Вывод корпуса не изменился; ветвь охраняется признаком «в выражении есть
степень», поэтому прочие записи печатаются прежним путём.

### Риски и зависимости

Поле `power_target` — подсказка о приёмнике; забыв её выставить в новой
позиции приёмника, получишь прежний отказ `RS-011`, а не невалидный вывод.
Ошибка в безопасную сторону.

## Разработка

### Задача

#### Что было

`power` печатал оба операнда безусловно; предикат свёртки `x := x + 1`
(`compound_assign`) печатал левый операнд через `?`, поэтому отказ степени
приходил **до** того, как приёмник вступал в дело.

#### Что сделано

- `generator/rust/rust_shift.rs` — `power(base, exp, scope, target)`,
  `power_base`, `power_exponent`.
- `generator/rust/rust_expr.rs` — поле `Scope::power_target` и метод
  `with_power_target`; ветвь `Power` берёт подсказку.
- `generator/rust/rust_coerce.rs` — охраняемая ветвь `contains_power` ставит
  подсказку и печатает выражение **обычным** путём.
- `compound_assign` — печать операнда в предикате перестала пробрасывать
  ошибку: это **вопрос**, а не вывод. Глотание ограничено одним сравнением;
  печать значения ошибку по-прежнему пробрасывает, иначе повторился бы класс (печатник, теряющий оператор молча).

#### Проверки

Пять проб через `probe.sh`, эмиссионные тесты, `clippy`, потактовая сверка,
две мутации.

## Итог (что сделано)

Цель `rust` печатала операнды степени безусловно, и её собственный проверка
отвергал **три формы записи из четырёх** при нулевом коде возврата `taktc`.
Теперь тип приёмника доезжает до степени полем контекста (`Scope::power_target`,
образец `return_type` фичи), база-литерал получает **суффикс**, а
приведение показателя печатается **по нужде**.

**Запись кандидата опровергнута дважды**: `sv` степень
переводит, а база-переменная тоже давала отказ — просто от другого линта.

**Класс оказался трёхслойным:** починка базы обнажила избыточное приведение
показателя, а та — отказ из предиката свёртки `x := x + 1`, печатавшего
операнд **до** приёмника.

**Разворот в умножения отвергнут замером семантики:** `2 * 2 * 2` в debug
паникует на переполнении, тогда как `wrapping_pow` обёртывает.

Контроля: эмиссия + настоящий `clippy -D warnings` + потактовая сверка; обе
мутации проверены.
