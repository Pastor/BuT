# Фича: Цель `c`: сдвиг на переменную величину не насыщается

- **Номер:** 0416
- **Статус:** ГОТОВО
- **Зависит от:** нет
- **Tier:** 1
- **Класс:** генерация
- **Связанные issue (анализ):** кандидат блока 2 `FEATURES.md` (граница фичи)

## Стадии жизненного цикла

Все стадии — разделы этой карточки.

## Краткое описание

Правило насыщения сдвига действовало только для **литеральной** величины
(0326 у `rust`, 0392 у `c`). У цели `c` переменная величина оставалась голым
`v >> n`, то есть UB при `n ≥ ширины`, — и прошивка молча считала другое, чем
эталон и три остальные цели.

## Документирование

Не требуется: правило языка задано ранее (0326/0392), меняется только его
исполнение одной целью.

## Архитектура (ADR)

- **Status:** Accepted

### Context

**Замер-23** — прогон порождённой прошивки (`u32`, значение
`0xFFFFFFFF`, величина растёт 16 → 32 → 48):

| Такт | эталон | прошивка `c` |
|---|---|---|
| `n = 16` | 65535 | 65535 |
| `n = 32` | **0** | **4294967295** |
| `n = 48` | **0** | **65535** (сдвиг по модулю 32) |

Результат одинаков на `-O0` и `-O2`; `cc -Wall -Wextra -Werror` **молчит**;
код возврата `taktc` — ноль. Формы остальных целей проверены: `rust` печатает
`checked_shr(...).unwrap_or(0)`, `st` — `SHR`, `sv` — `>>`; все три дают ответ
эталона. Расходилась **одна** цель со всеми.

Запись кандидата называла класс «тише литерального, потому что `cc` молчит».
Замер уточнил: молчание инструментов делает его **дороже** — это Tier 1
(инструменты противоречат друг другу молча), а не Tier 2.

**Граница замера названа честно:** значения `st` и `sv` прогоном не
снимались — их поведение выведено из напечатанной формы (`SHR` и `>>`
определены стандартами при любой величине). Расхождение доказано для пары
«эталон ↔ `c`», и правится именно она.

### Decision Drivers

- Класс невидим инструментам: вердикт даёт только прогон значений.
- Операнд в языке Takt бывает **с эффектом** (вызов функции пишет в переменные
  модели) — печатать его дважды нельзя.
- Вывод корпуса меняться не должен.

### Considered Options

1. **Тернарный оператор на месте** — `(n >= 32 ? 0 : (v >> n))`. Отвергнут:
   печатает величину дважды. Тот же довод, по которому `rust` выражает
   знаковый сдвиг через `min`, а не `unwrap_or` (0334).
2. **Маскирование величины** — `v >> (n & 31)`. Отвергнут: это не насыщение, а
   другое правило; `n = 32` дало бы `v`, а не 0.
3. **Хелперы `takt_shl`/`takt_shr_u`/`takt_shr_i`** (принято). Операнды
   печатаются по разу, эмиссия — по факту вызова, как у `takt_ipow` (0328) и
   Q-хелперов (0061).

### Decision

Принят вариант 3.

- Порог — ширина **продвинутого** типа (`max(32, W)`, C11 6.5.7p3), тот же, что
  у литеральной величины (0392).
- Знак при насыщении знакового вправо берётся **сравнением** (`v < 0 ? -1 : 0`),
  а не сдвигом на `w − 1`: `>>` отрицательного в C implementation-defined (тот
  же довод, что у floor-хелпера 0061).
- Счёт идёт в `uint64_t`: это снимает и второй UB — переполнение `int` при
  левом сдвиге узкого типа (`narrow << 31`).

### Consequences

- Вывод корпуса **не изменился**: сдвигов на переменную величину в `examples/`
  нет (та же слепота проверки, что у 0392).
- Узкие типы теперь тоже идут через хелпер. Это не избыточность, а починка:
  см. «Найденные дефекты».

#### Acceptance criteria

Потактовые значения эталона и прошивки совпадают на всех трёх формах (вправо
беззнаковый, вправо знаковый, влево); литеральная величина печатается прежним
путём.

### Найденные дефекты

**Ожидание контрольного теста было опровергнуто замером.** Первая редакция
требовала, чтобы узкий тип (`u8`) печатался обычным сдвигом — «продвижение до
`int` спасает». Прогон показал, что спасает оно лишь до 31 включительно:
`narrow << 31` переполняет `int` (UB). Хелпер, считающий в `uint64_t`, для
узких типов **необходим**, и контрольный тест переписан на настоящую границу —
литеральную величину.

**Граница 0392 была закреплена тестом** (`variable_shift_amount_is_left_alone`): он утверждал «переменная величина печатается как прежде» — и
покраснел, как и должен. Утверждение снято вместе с границей, тест переписан на
новое поведение и на контроль «операнды печатаются по одному разу».

### Выводы и дальнейшие шаги

Кандидат снят.

## Итог (что сделано)

Цель `c` печатала сдвиг на переменную величину голым оператором, то есть UB при
`n ≥ ширины`: прогон дал **4294967295** и **65535** там, где эталон, `rust`,
`st` и `sv` дают 0, — при молчащем `cc -Werror` и нулевом коде возврата
`taktc`. Насыщение считает хелпер (`takt_shl`, `takt_shr_u`, `takt_shr_i`),
эмитируемый по факту вызова.

**Тернарный оператор на месте отвергнут:** он печатает величину дважды, а
операнд в Takt бывает с эффектом (довод 0334).

**Знак берётся сравнением, а не сдвигом на `w − 1`:** `>>` отрицательного в
C implementation-defined (довод 0061).

**Контрольный тест был неверен и исправлен замером** — узкие типы тоже
нуждаются в хелпере: продвижение до `int` не спасает от переполнения при левом
сдвиге.

Контроль — потактовая сверка с прогоном `cc` флагами проверки; мутация проверена.
