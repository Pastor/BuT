# Фича: Цель `c` — указатель на состояние в вызове из условия

- **Номер:** 0502
- **Статус:** ГОТОВО
- **Зависит от:** нет
- **Tier:** 2
- **Класс:** генерация
- **Связанные issue (анализ):** кандидат `FEATURES.md` «вызов функции из условия ребра передаёт лишний аргумент» (2026-09-02)

## Стадии жизненного цикла (правило 17)

Все стадии — **разделы этой карточки** (правило 32). Отдельным артефактом
остаются только исправления — [`docs/fixes/`](../fixes/README.md).

## Краткое описание

Указатель на состояние передаётся вызову **по нужде** — тем же признаком, по
которому он попал (или не попал) в сигнатуру функции (0396, 0419, 0449). Признак
спрашивает печатник **выражений**, а печатник **условий** передаёт указатель
безусловно: функция, не касающаяся состояния, объявляется без него, а из условия
ребра зовётся с ним. `cc` отвечает «too many arguments to function call» при
**нулевом** коде возврата `taktc`.

> Фича зарегистрирована из бэклога кандидатов; далее проходит жизненный цикл по
> правилу 17.

## Документирование (правило 24)

**Не требуется.** Язык не меняется: та же запись в теле блока переводится верно
и сегодня, а речь о форме порождённого C. Диагностик не заводится.

## Архитектура (ADR)

- **Status:** Accepted
- **Date:** 2026-09-02
- **Authors:** архитектор, разработчик

### Context

Замер-02 (`scripts/probe.sh`). Вход простейший: `fn twice(v: u8) -> u8
{ return v + v; }` при `ref Hot: twice(ticks) > 3;`.

| Потребитель | Ответ |
|---|---|
| эталон, `st`, `st-at`, `rust`, `sv`, `sv-mmio`, `plantuml` | исполняют / переводят, инструменты принимают |
| `c`, `c-hal` | `cc`: «too many arguments to function call, expected single argument 'v', have 2 arguments» |

Порождённое: объявление `static uint8_t M_twice(uint8_t v);`, вызов
`M_twice(model, model->ticks)`.

Контроль (отделяет класс от соседей):

- тот же вызов в **теле** блока печатается верно — печатник выражений
  спрашивает признак (0396);
- функция, которая **читает** переменную модели, из условия зовётся верно:
  указатель есть и в сигнатуре, и в вызове.

То есть расходятся два печатника, а не правило.

### Decision Drivers

- Признак нужды считается один раз на функцию (`c_needs::needs_state`, 0419);
  второго знания заводить нельзя — разъехавшись, они дают невалидный C.
- Ошибка громкая (`cc` отказывает), но код возврата `taktc` нулевой — то есть
  для инструмента это молчание.

### Considered Options

1. **Спросить общий признак в печатнике условий** (принято). Одна строка знания
   переносится туда, где её не хватало; вторая копия правила не появляется.
2. **Печатать указатель всегда, а в сигнатуре — тоже всегда.** Отвергнуто:
   возврат к состоянию до 0396, лишний параметр гасится заглушкой `(void)`, и
   вывод, который читают люди, становится шумнее.
3. **Отказ цели на вызов из условия.** Отвергнуто: запись законна, семь
   потребителей её переводят, а эталон исполняет.

### Decision

Печатник условий цели `c` спрашивает тот же `c_needs::needs_state`, что и
печатник выражений, и передаёт указатель только по нужде.

### Consequences

- Вызов функции из условия ребра, `cond`-условия и охранной формулы даёт
  валидный C.
- Снимков `examples/generated/` правка не меняет: в корпусе такой формы нет —
  ровно поэтому проверка цели класса и не видел.

#### Acceptance criteria

1. Проба: `cc` принимает вывод `c` и `c-hal`.
2. Контроль: функция, читающая состояние, по-прежнему получает указатель — в
   обоих печатниках.
3. Потактовая сверка эталон ↔ `c` (значение, вычисленное функцией из условия).
4. `./scripts/precheck.sh` зелёный.

## Анализ

### Цель и контекст

Печатников вызова у цели `c` **два**: `c_expr/call.rs` (выражения) и
`c_expr/condition.rs` (условия). Первый с 0396 спрашивает
`c_needs::needs_state`, второй печатает `first_arg` безусловно.

### Замер (правило 30, 2026-09-02)

Таблица — в разделе «Архитектура (ADR) → Context». Соседние формы, измеренные
попутно и в объём **не** входящие:

- **функция, читающая состояние, из условия** — печатается верно (контроль);
- **именованное условие с вызовом функции** (`cond warm = hot() > 3;`) —
  непригодно у всех: эталон отвечает `SIM-016`, цели отказывают пятью разными
  кодами. Причина глубже печати: условия разрешаются раньше функций (стадии 3 и
  5), и вызов в `cond` остаётся неразрешённым. Заведено кандидатом.

### Требования и проверяемые условия

| № | Требование |
|---|---|
| Т1 | Вызов из условия передаёт указатель только по нужде |
| Т2 | Признак — общий носитель `c_needs::needs_state`, второго знания нет |
| Т3 | Функция, читающая состояние, указатель получает (контроль) |
| Т4 | Снимки `examples/generated/` не меняются |

### Критерии приёмки и способ проверки

Критерии — в ADR. Способ: `scripts/probe.sh`, прогон `cc` флагами проверки,
потактовая сверка, `precheck.sh`.

### Редакторский слой (правило 29)

**Не требуется:** ни лексика, ни синтаксис, ни диагностики не затронуты.

### Особенности по обратной функциональности

Обратная совместимость полная: правка снимает лишний аргумент там, где вывод и
так не собирался.

### Риски и зависимости

- **Риск:** признак у двух печатников разойдётся снова. Снимается тем, что
  знание одно (`c_needs::needs_state`), и контроль проверяет **обе** позиции.

## Разработка

### Задача: признак спрашивается в печатнике условий

`takt-lang/src/generator/c/c_expr/condition.rs`, ветвь
`ConditionNode::Function`: владелец функции берётся у `Local { upper }`, и
указатель печатается по ответу `c_needs::needs_state` — того же носителя, каким
живёт печатник выражений и сама сигнатура. Владельца нет — прежнее поведение
(судить не о чем).

### Задача: место обращения попадает в сплошной перебор

`takt-lang/tests/targets/matrix_probes.rs`: заведён вид обращения
`Touch::FnCallOnEdge` — чистая функция, вызываемая из условия ребра. Перебор
«вид обращения × форма реализации» (0449) этого места не знал, оттого и не
поймал класс; ожидание вида — «указателя нет» — снято прогоном.

Контроля формы и прогон `cc` дописаны в набор той же темы —
`c_param_on_demand_tests.rs`: признак один, и его проверки живут
вместе.

### Задача: ось матрицы вынесена в свой модуль

Новый вид обращения перевёл `matrix_probes.rs` за предел размера (1011 строк
при ~1000). Ось «форма объявления» (`Kind` и его методы) вынесена в
`matrix_kind.rs` — граница по ответственности: там знание о том, как выглядят
объявление, чтение и запись каждой формы, здесь — сборка исходника пробы.
Набор LSP берёт генератор по пути (`#[path]`), поэтому получил и второй модуль.

## Тест-план

| Проверка | Ожидание |
|---|---|
| вызов чистой функции из условия | `M_twice(model->ticks)` — без указателя |
| контроль: функция читает переменную модели | `M_accumulated(model)` — с указателем |
| `cc` флагами проверки на выводе | принимает |
| под-модель: чистая и читающая корень функции в условиях | `Worker_pure_twice(model->step)` и `Worker_read_shared(main)` |
| сплошной перебор `root_pointer_matrix` с новым видом | признак точен, вывод собирается |
| формы сборки `--fsm=table`, `--inline=auto` | `cc` принимает |
| размер модулей после правки | предел ~1000 строк не превышен |

## Отчёт о тестировании (правило 20)

### Резюме

`./scripts/precheck.sh` — зелёный. Пробы `scripts/probe.sh`: восемь целей
переводят, инструменты проверки принимают. Снимки `examples/generated/` не
изменились — в корпусе такой формы нет, что и объясняет молчание проверки.

### Фактические результаты по проверкам

Все проверки пройдены. Мутационная проверка — обе мутации пойманы:

| Мутация | Ответ набора |
|---|---|
| указатель передаётся всегда (прежнее поведение) | три теста темы **и** сплошной перебор `root_pointer_matrix` |
| указатель не передаётся никогда | контроль «функция читает состояние» и прогон `cc` |

Вторая мутация показывает, зачем контроль: без него правка читалась бы как
«в условиях не передавать никогда», и класс просто поменял бы знак.

### Найденные дефекты

Прогон вскрыл соседний класс, в объём не входящий (заведён кандидатом):
**именованное условие с вызовом функции** (`cond warm = hot() > 3;`) непригодно
у всех потребителей — эталон отвечает `SIM-016`, цели отказывают пятью разными
кодами. Причина глубже печати: условия разрешаются на стадии 3, функции — на
стадии 5, и вызов в `cond` остаётся неразрешённым.

### Выводы и дальнейшие шаги

Перебор 0449 получил недостающее место обращения — следующий такой промах он
поймает сам.

## Итог (что сделано)

Печатник условий цели `c` спрашивает тот же признак нужды, что и печатник
выражений: указатель на состояние передаётся вызову только тогда, когда он есть
в сигнатуре. Прежде функция без обращения к состоянию объявлялась без него, а
из условия ребра звалась с ним — `cc` отвечал «too many arguments» при нулевом
коде возврата `taktc`.

Место обращения заведено в сплошной перебор признака (0449), где его не было.
