## Краткое описание

Фича [тело `always` на уровне модели не эмитится в C](0083-model-always-block-c.md) установила: тело `always` на уровне
модели исполняется **каждый такт** — в эталоне и во всех целях. У модели, чьё
состояние есть композиция, эталон его **не исполняет вовсе**, а цель `c`
исполняет. Расхождение молчаливое: обе стороны работают и рапортуют успех.

> Фича зарегистрирована из бэклога кандидатов (решение заказчика 2026-08-02:
> Tier-1 находки переводятся в фичи вперёд Tier 2); далее проходит жизненный
> цикл по правилу 17.

## Что известно на входе

Перепроверено пробой 2026-08-02, находка жива. Вход:
`var probe: u8 := 0; model Tuner { … } always { probe := probe + 1; } start Main = Tuner | Tuner;`

| Сторона | Результат |
|---|---|
| эталон | `probe = 0` на всех тактах |
| цель `c` | `model->probe = model->probe + 1;` в теле такта |

- То же с **именованной** моделью-композицией (`start Main = Tuner \| Tuner;`
  внутри `model Root2 { … always { … } }`).
- У модели со **своими** состояниями (`always { … } start S { … }`) блок
  исполняется верно — то есть дефект в ветви, где такт модели уходит в
  композицию, и тело модели-владельца до исполнения не доезжает.
- Корпус класс **не покрывает**: `always` на уровне модели есть только у
  моделей со своими состояниями.
- Урок исправления: тела корпуса идемпотентны (`x := <выражение>`), и на
  них лишнее либо пропущенное исполнение **неразличимо**. Контроль обязан стоять
  на **накапливающем** теле (`probe := probe + 1`).

### Context

Фича [тело `always` на уровне модели не эмитится в C](0083-model-always-block-c.md) установила контракт: тело
`always` **вне состояния** исполняется **каждый такт до диспетчеризации
состояния** — в эталоне и во всех целях. У модели, чьё состояние есть
**композиция**, эталон его не исполняет вовсе.

Проба воспроизведена заново 2026-08-03 (не по записи в карточке):

```takt
var probe: u8 := 0;
out p: u8;
model Tuner { start Count { ref Count; } }
always { probe := probe + 1; p := probe; }
start Main = Tuner | Tuner;
```

| Сторона | Наблюдаемое |
|---|---|
| эталон (`takt-sim`) | `probe = 0` на **всех** тактах |
| цель `c` | `main->probe = main->probe + 1;` в теле такта |
| цель `rust` | `self.probe = self.probe.wrapping_add(1);` |
| цель `sv` | `anon_probe_next = (anon_probe_next + 1);` |
| цель `st` | `probe := probe + 1;` |

**Расходится эталон против всех четырёх целей**, а не цель против эталона.
Направление правки этим и определено: чинится `takt-sim`, контракт 0083 не
пересматривается.

Контрпример (контроль направления): у модели со **своими** состояниями тот же
блок исполняется верно — `probe = 1, 2, 3`. То есть дефект в ветви, где такт
модели уходит в композицию.

#### Где теряется

`build_impl` (`takt-sim/src/unit/builder.rs`) делегирует в `build_extend` в
**двух** случаях: модель с единственным состоянием-реализацией без переходов
(`start Main = A | B`) и модель без своих состояний (`model M = A | B`).
`build_extend` собирает `UnitKind::Parallel`/`Sequential` из ветвей, и
`executions` у них наполняется **только** слиянием из юнитов-ветвей
(`Unit::add`/`union`) — блоки модели-**владельца** туда не попадают.

При этом механизм исполнения **уже есть и работает**: `tick_body` зовёт
`self.execution("always")` до диспетчеризации формы, а `Unit::execution` читает
поле `executions` и у `Parallel`, и у `Sequential`. То есть поле объявлено,
читается — и никогда не наполняется.

### Decision Drivers

1. **Контракт 0083 уже принят и соблюдается четырьмя целями.** Пересматривать
   его ради эталона значило бы менять поведение четырёх генераторов из-за одного
   потребителя.
2. **Ровно одно исполнение за такт.** Соседний исправление снимал **двойное**
   исполнение (`Unit::execution` спускался в дочерние юниты). Починка обязана
   дать одно — и это доказывается **значением**, а не наличием кода.
3. **Порядок: до ветвей.** Контракт 0083 — «до диспетчеризации состояния»;
   у композиции диспетчеризация есть тик ветвей.
4. **Контекст записи должен быть тем же, что видят ветви.** Иначе запись уйдёт в
   другой экземпляр `ModelNodeContext`, и `probe` останется нулём — «починка»,
   которая молча не работает.

### Considered Options

#### Option A. Наполнить `executions` композиции блоками владельца при построении

Механизм исполнения не трогаем: поле уже читается `Unit::execution`, вызов уже
стоит в `tick_body` до диспетчеризации. Блоки владельца компилируются с тем
**общим контекстом**, который `build_extend` строит для ветвей.

**Pros:**
- минимальная правка: наполняется существующее поле, новых путей исполнения нет;
- «ровно одно исполнение» — **по построению**: блок попадает в один юнит,
  корневой композитный, а в детей не спускается (инвариант цел);
- порядок «до ветвей» получается даром — `tick_body` зовёт `execution("always")`
  раньше `tick_parallel`/`tick_sequential`;
- симметрия с `build_node`, который наполняет `executions` ровно так же
  (из `model.named_blocks`).

**Cons:**
- контекст надо провести до места компиляции блоков (сегодня `build_extend`
  строит его внутри и наружу не отдаёт) — правка сигнатуры или порядка вызовов;
- у формы «модель без своих состояний» контекст создаётся из **первой ветви**;
  совпадение владельца и контекста надо проверить значением, а не рассуждением
  (драйвер 4).

#### Option B. Строить композицию как `Node` с состоянием-реализацией

Не делегировать в `build_extend`, а строить обычный `Node` с единственным
состоянием, чья реализация — композиция (механизм `state_impls`, заведённый
фичей).

**Pros:**
- один вид узла на «модель со своим телом», без особого случая;
- `executions`, `guards`, `every` и прочее наполняются существующим `build_node`
  — тело владельца перестаёт быть исключением не только для `always`.

**Cons:**
- **меняет форму дерева** для всей композиции верхнего уровня: `Unit::variable`,
  трасса состояний (`[Count, Count]`), `state_io`, viewport и сверки завязаны на
  нынешнюю форму. Риск не в объёме правки, а в **молчаливых** сдвигах;
- исправление и фича недавно правили именно этот стык — перестройка сразу
  после них вероятнее вернёт закрытый дефект, чем найдёт новый;
- цена несоразмерна поводу: теряется одно поле, а перестраивается ветвь целиком.

#### Option C. Спускать блоки владельца в дочерние юниты

**Pros:**
- не требует ничего проводить: дети уже исполняют свои `executions`.

**Cons:**
- это **буквально дефект**: N ветвей → N исполнений за такт. На
  идемпотентном теле (`x := выражение`) разница неразличима, на накапливающем
  (`probe := probe + 1`) — молча неверный результат. Отвергается сразу.

### Decision

Принимается **Option A** — наполнить `executions` композиции блоками
модели-владельца при построении. Рекомендация архитектора и решение заказчика
(2026-08-03) совпали.

Обоснование: правка чинит ровно то, что сломано (незаполненное поле), не трогая
ни контракт 0083, ни форму дерева симуляции, и даёт «ровно одно исполнение»
**по построению**, а не проверкой — блок попадает в один юнит и в детей не
спускается, то есть инвариант исправления цел.

Option B (строить композицию как `Node`) отвергнут **по цене риска, а не по
существу**: он снял бы класс целиком, но перестраивает стык, правленный фичей и исправлением совсем недавно, а трасса, `state_io`, viewport и сверки
завязаны на нынешнюю форму дерева — сдвиги там молчаливые. Если единообразие
понадобится, это отдельная фича со своим ADR, а не попутная правка.

### Consequences

#### Положительные

- эталон перестаёт расходиться с четырьмя целями на конструкции, которую все
  четыре переводят одинаково;
- поле `executions` у `Parallel`/`Sequential` перестаёт быть мёртвым — сейчас оно
  объявлено и читается, но никогда не наполняется.

#### Отрицательные / Action items

- **A1.** Контроль обязан стоять на **накапливающем** теле (`probe := probe + 1`):
  на идемпотентном (`x := выражение`) ни пропуск, ни двойное исполнение
  неразличимы — урок исправления, из-за которого дефект и дожил.
- **A2.** Проверить **обе** формы: анонимный корень (`start Main = A | B` в
  файле) и именованная модель-композиция. Они идут разными ветвями `build_impl`.
- **A3.** Проверить **обе** композиции — `|` и `+`: у них разные ветви такта
  (`tick_parallel` / `tick_sequential`), а вызов `execution("always")` общий.
- **A4.** Доказать «ровно одно исполнение» **значением**: после N тактов
  `probe = N`, не `2N`.
- **A5.** Корпус этот класс не покрывает (`always` уровня модели есть только у
  моделей со своими состояниями) — контроль обязан быть фикстурным, и его
  ценность подтверждается мутацией.
- **A6.** Model-level `enter`/`exit`/`every` у композиции остаются
  **нереализованными** — как и у обычной модели (0083 реализовала только
  `always`). Объём не расширяем; если поведение отличается от модели со своими
  состояниями, это фиксируется кандидатом, а не чинится молча.

#### Acceptance criteria

1. На пробе из раздела Context эталон даёт `probe = 1, 2, 3, …` — как все цели.
2. То же для именованной модели-композиции и для последовательной композиции `+`.
3. Исполнение **ровно одно** за такт: после N тактов `probe = N`.
4. Значенческая сверка sim ≡ `c` на накапливающем теле; мутация (убрать
   наполнение) её **роняет**.
5. Модель со своими состояниями и корпус не задеты: предкоммит зелёный, дифф
   `examples/generated/` пуст.

## Анализ

### Цель и контекст

ADR принял **Option A** (рекомендация архитектора и решение заказчика совпали):
наполнить `executions` узла композиции блоками модели-владельца при построении.
Механизм исполнения менять не нужно — он уже есть: `tick_body` зовёт
`self.execution("always")` до диспетчеризации формы, а `Unit::execution` читает
поле `executions` и у `Parallel`, и у `Sequential`. Поле объявлено, читается — и
никогда не наполняется.

### Зависимости фичи (правило 17/19)

**Нет.** Контракт 0083 принят и не меняется; механизм 0181 не трогается.

### Места правки

| # | Что | Файл | Замечание |
|---|---|---|---|
| М1 | контекст владельца строится **один раз** и отдаётся обоим потребителям | `takt-sim/src/unit/builder.rs::build_impl` | тем же способом, что в `build_node`: `new_with_parent` при наличии `shared_parent`, иначе `new` |
| М2 | компиляция `named_blocks` владельца | там же | тем же кодом, что в `build_node` (0083) — **вынести** в общую функцию, а не скопировать |
| М3 | укладка в `executions` результата | там же | у `Parallel`/`Sequential`; поле уже есть |

**М2 — вынос, а не копия.** Наполнение `executions` из `model.named_blocks`
написано в `build_node`. Вторая копия разъедется при первой правке —
тот же класс, что «арифметика в одном месте» (0042) и «ключ строится одной
функцией» (0084/0193).

### Ограничения, которые определяют форму решения

- **О1. Одна ячейка значений.** Тело владельца и ветви обязаны писать в **один**
  контекст. Сегодня контекст ветвей строит `shared_context` — из «родительской
  модели первой ветви», а не из владельца. Совпадение проверяется **значением**
  (`probe` растёт), а не рассуждением: разойдясь, «починка» молча не сработает.
- **О2. Ровно одно исполнение.** Блок кладётся в **один** юнит — корневой
  композитный, — и в детей не спускается (`Unit::execution` в дочерние юниты не
  ходит, инвариант исправления). Проверяется значением: после N тактов
  `probe = N`, не `2N`.
- **О3. Порядок соблюдается даром.** `tick_body` зовёт `execution("always")`
  **до** `tick_parallel`/`tick_sequential` — контракт 0083 «до диспетчеризации
  состояния» выполняется без правки такта.
- **О4. Достижима из текста только одна из двух делегирующих ветвей.** Проба
  2026-08-03: форма «модель без своих состояний» (`model M = A | B { … }`)
  ломается **раньше и целиком** — эталон даёт пустую трассу `[—]` и мгновенное
  завершение, цель `c` отвергает `CC-005`. Правка делается симметрично в обеих
  ветвях (она дешёвая), но **проверить значением** можно только первую; вторая
  честно отмечается непроверенной, а её собственный дефект — кандидатом.
- **О5. Корпус класс не покрывает** (`always` уровня модели есть только у
  моделей со своими состояниями), поэтому контроль обязан быть фикстурным и
  подтверждаться мутацией — иначе он не доказывает ничего.

### Особенности по обратной совместимости (правило 11)

- **Язык не меняется**, вывод генераторов не меняется — правка целиком в
  `takt-sim`.
- **Поведение эталона меняется** на конструкции, где он расходился со всеми
  целями: это и есть предмет фичи. Сценарий, полагавшийся на «тело не
  исполняется», сломался бы — таких в корпусе нет (О5).
- Контекст ветвей может измениться (М1): если владелец и «родитель первой
  ветви» — разные модели, ветви получат контекст владельца. В корпусе они
  совпадают (проверяется прогоном сверок и предкоммитом); расхождение, если
  всплывёт, — сигнал, а не шум.

### Документирование (правило 24)

**Не требуется.** Правило «model-level `always` исполняется каждый такт» уже
описано (0083) и не меняется — фича приводит эталон в соответствие с ним.
Уточнения формулировки для композиции не потребовалось: контракт сформулирован
про модель, а композиция — её состояние.

### Риски

## Разработка

### Задача

#### Что было

`build_impl` делегировал прямо в `build_extend` в **обеих** ветвях — у модели с
единственным состоянием-реализацией (`start Main = A | B`) и у модели без своих
состояний. `build_extend` собирает `Parallel`/`Sequential` из ветвей, и поле
`executions` наполнялось **только** слиянием из юнитов-ветвей: блоки
модели-владельца туда не попадали.

Механизм исполнения при этом был на месте и работал: `tick_body` зовёт
`self.execution("always")` **до** диспетчеризации формы, а `Unit::execution`
читает `executions` и у `Parallel`, и у `Sequential`. Поле объявлено, читается —
и никогда не наполнялось.

#### Что сделано

**Вынос (М2).** Компиляция `named_blocks` вынесена из `build_node` в новый
модуль `takt-sim/src/unit/blocks.rs` (`model_level_executions`). Вынос, а не
копия: правило нужно **двум** строителям, а вторая копия разъехалась бы при
первой правке — тот же класс, что «арифметика в одном месте» (0042) и «ключ
строится одной функцией» (0084, 0193). Отдельный модуль ещё и держит
`builder.rs` в пределах лимита размера.

**Узел-композиция (М1, М3).** Заведена `build_composition`: строит контекст
владельца **один раз** (тем же способом, что `build_node` — `new_with_parent`
при наличии общего родителя, иначе `new`) и отдаёт его **обоим** потребителям —
ветвям как общий родитель, телу владельца как приёмник значений. Затем блоки
владельца дописываются в `executions` результата.

**Один контекст — не деталь, а условие работоспособности** (О1 анализа): будь
их два, запись ушла бы в другой экземпляр `ModelNodeContext`, и наблюдаемая не
изменилась бы — «починка», которая молча не работает.

**Ровно одно исполнение — по построению** (О2): блок кладётся в **этот** юнит
и в дочерние не спускается. `Unit::execution` в детей не ходит намеренно —
иначе тело исполнилось бы по разу на ветвь (дефект-близнец с
противоположным знаком).

**Ветвь `Node`/`None`** результата обрабатывается явно и **ничего не делает**:
композиция из одной ветви сворачивается в `Node` самой ветви, и её `executions`
принадлежат чужой модели — дописывать туда тело владельца значило бы исполнить
его в чужом контексте. Язык такого входа не порождает (`|`/`+` требуют двух
операндов); ветвь существует для полноты разбора.

### Задача

#### Что было

Контрольных тестов у класса не было: корпус его не покрывает — `always` уровня модели есть
только у моделей со **своими** состояниями. Хуже, что покрытие такого рода легко
сделать бесполезным: на идемпотентном теле (`n := выражение`), которым полон
корпус, **ни пропуск, ни двойное исполнение неразличимы**. Именно поэтому исправление (тело исполнялось по разу на ветвь) дожил незамеченным при зелёных
тестах.

#### Что сделано

**Значенческие тесты** — `takt-sim/tests/sim/composition_model_always_tests.rs`
(4 теста, тело **накапливающее**: `n := n + 1`):

|---|---|
| `anonymous_root_parallel_runs_body_once_per_tick` | анонимный корень `\|` — `1, 2, 3, 4` |
| `named_composition_model_runs_body_once_per_tick` | именованная модель — вторая делегирующая ветвь `build_impl` |
| `sequential_composition_runs_body_once_per_tick` | композиция `+` — ветвь `tick_sequential` |
| `model_with_own_states_is_unchanged` | контрпример: направление правки (чинили ветвь композиции, а не `always` вообще) |

Тест на `+` заведён **отдельно**, а не «то же самое»: у `|` и `+` разные
ветви такта, а вызов `execution("always")` общий — совпадение надо доказать.

**Потактовая сверка с целью `c`** —
`takt-sim/tests/conformance_c_tests/composition_always.rs` на фикстуре

Контрпример при этом остаётся **зелёным** — как и задумано: он контролирует

### Выводы и дальнейшие шаги

**1. Механизм исполнения был на месте — не хватало только данных.** `tick_body`
звал `execution("always")` для любого вида юнита, а `Unit::execution` читал
`executions` и у `Parallel`, и у `Sequential`. Поле было объявлено, читалось — и
никогда не наполнялось. Это объясняет, почему дефект пережил и фичу, и исправление: код, который «должен был бы» выглядеть отсутствующим, присутствовал.

**2. Мутация подтвердила ценность контрольных тестов и их адресность.** Снятие наполнения
роняет три теста композиции и сверку с `c` (`0, 0, 0, 0` вместо `1, 2, 3, 4`), а
контрпример «модель со своими состояниями» остаётся **зелёным** — то есть тесты
меряют именно ту ветвь, которую чинили, а не поведение `always` вообще.

**3. Предкоммит поймал битую ссылку в моём же ADR.** Первый прогон вернул код
**1**: ссылка на `ADR 0083` вела на `0083-model-always-block-c.md`, тогда как
файл называется `0083-model-always-block.md` (суффикс `-c` есть у карточки
фичи, но не у ADR). Фоновое уведомление о завершении показало «exit code 0» —
это код конвейера `tee`, а не скрипта; вердикт брался из строки лога, а не из
уведомления. Урок: код возврата длинного прогона проверять в логе.

**4. Одна из двух делегирующих ветвей значением не проверена — и это сказано
прямо.** Форма «модель без своих состояний» (`model M = A | B { … }`) ломается
раньше и целиком: эталон даёт пустую трассу `[—]` и мгновенное завершение, цель
`c` отвергает вход `CC-005`. Правка сделана симметрично в обеих ветвях (она
дешёвая), но контроля у второй нет — её собственный дефект вынесен кандидатом, а
не выдан за покрытый.

**5. Объём не расширялся; действие A6 ADR выполнено замером, а не рассуждением.**
Пробы 2026-08-03:

- **`enter` уровня модели** не исполняется **ни** у обычной модели, **ни** у
  композиции — обе дают `n = 0` там, где тело присваивает `100`. То есть
  поведение одинаково, и композиция не отстаёт от обычной модели;
- **`every` уровня модели** грамматикой **не принимается вовсе** (`SY-002`) — ни
  в модели, ни в корне, — то есть сравнивать нечего.

Ни то, ни другое не регресс и не пробел фичи: 0083 реализовала только `always`.
Расхождения между композицией и обычной моделью, ради которого A6 требовал
завести кандидата, **не обнаружено**.

**Исправления (`docs/fixes/`) не требуются:** находок внутри разработки не было.

## Итог (что сделано)

Эталон исполняет тело `always` модели-владельца, чьё состояние есть композиция,
— **ровно раз за такт**, как и все четыре цели:

| Форма | Было | Стало |
|---|---|---|
| `start Main = A \| B` | `n = 0` на всех тактах | `1, 2, 3, 4` |
| именованная модель-композиция | `0` | `1, 2, 3` |
| `start Main = A + B` | `0` | `1, 2, 3, 4` |

Принят Option A (ADR; рекомендация архитектора и решение заказчика совпали):
наполнить `executions` узла композиции блоками владельца при построении.
Механизм исполнения менять не пришлось — он **был на месте**: `tick_body`
звал `execution("always")` для любого вида юнита, а `Unit::execution` читал поле
и у `Parallel`, и у `Sequential`. Поле было объявлено, читалось — и никогда не
наполнялось; этим и объясняется, почему дефект пережил фичу и исправление.

Компиляция `named_blocks` **вынесена** в `takt-sim/src/unit/blocks.rs` и теперь
одна на обоих строителей: копия правила разъехалась бы при первой правке.
Контекст владельца строится **один раз** и отдаётся и ветвям, и телу — иначе
запись ушла бы в другой экземпляр `ModelNodeContext`, и починка молча не
сработала бы.

«Ровно одно исполнение» получено **по построению** (блок кладётся в один юнит
и в детей не спускается) и доказано **значением**: рост на единицу, а не на
двойку — иначе вернулся бы дефект-близнец исправления. Контроля стоят на
**накапливающем** теле; на идемпотентном оба дефекта неразличимы.

Отвергнут Option B (строить композицию как `Node`): он снял бы класс целиком,
но перестраивает стык, правленный фичей совсем недавно, а трасса,
`state_io` и viewport завязаны на нынешнюю форму дерева.

Детали: [ADR](0194-sim-composition-model-always.md#архитектура-adr),
[анализ](0194-sim-composition-model-always.md#анализ),

## Направление решения (наметка, не решение)

- Правка эталона (`takt-sim`), а не целей: контракт 0083 уже принят, и цель `c`
  ему следует.
- Осторожно с направлением ошибки: соседний исправление

  надо доказать значением, а не фактом наличия кода.
- Контроль — значенческая сверка sim ≡ `c` на накапливающем теле, по образцу

## Документирование (правило 24)

**Не требуется.** Правило «model-level `always` исполняется каждый такт» уже
описано и не меняется — фича приводит эталон в соответствие с ним. Если анализ
покажет, что для композиции правило требует **уточнения** формулировки, раздел
о композиции придётся освежить; решение принимается на стадии анализа.
