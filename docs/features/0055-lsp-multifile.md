- **Номер:** 0055
- **Статус:** ГОТОВО

  `0054` (общий слой печати позиции — `ГОТОВО`). Обе закрыты → фича **не

- **Связанные issue (анализ):** новая фича (из блока «Кандидаты в фичи»

- **Приоритет / Tier:** Tier 2 — в редакторе `import` **всегда** был ошибкой.

## Краткое описание

В редакторе `import "lib.lam";` **всегда** давал ошибку «файл не найден»:
`collect_diagnostics` звала `construct_model(&ast, None, &[])` — с пустыми путями
поиска. А диагностика из импортированного файла подсвечивалась в **текущем**
документе по чужому смещению, потому что `grammar_diagnostic_to_lsp` отбрасывала
`file_no`.

Зонд по ходу вскрыл, что корень глубже: **`lamc` тоже не искал импорт рядом с
импортирующим файлом** — только по явному `-I`, даже при запуске из его каталога.

> Фича зарегистрирована из блока «Кандидаты в фичи» `FEATURES.md` (по запросу
> заказчика 2026-07-16); проходит жизненный цикл по правилу 17.

### Context

`lam-lsp` однофайлов, и это видно пользователю двумя способами:

1. **`import` в редакторе — всегда ошибка.** `collect_diagnostics` (`lsp.rs:157`)
   звала `construct_model(&ast, None, &[])` — с **пустыми** путями поиска.
   `read_import_file` перебирает только `search_paths`, поэтому кандидатов нет
   вовсе → `SE-013` «файл не найден».
2. **Чужая ошибка подсвечивается не там.** `grammar_diagnostic_to_lsp`
   (`lsp.rs:224`) отбрасывала `file_no` (`Location::Source(_, start, end)`) и
   мапила смещение в текст **текущего** документа.

**Зонд вскрыл, что корень глубже.** `lamc` **тоже** не ищет импорт рядом с
импортирующим файлом:

```text
$ lamc compile -t c main53.lam -o o.c        # badsem.lam лежит рядом
main53.lam:1:1: Ошибка компиляции [SE-013]: Файл импорта не найден:
«badsem.lam». Пути поиска: (пути не заданы)
```

Даже запуск из каталога файла не помогает: путей нет — значит, кандидатов нет.
То есть `import` непригоден без `-I`, и это расходится с интуицией
(`#include "x.h"`, Python, JS ищут рядом с импортирующим файлом).

Отсюда развилка, которую аналитик решать не вправе: если научить искать рядом
**только LSP**, редактор станет зелёным там, где сборка красная. Это ровно тот
класс дефекта, который проект лечит (0028-01 — расхождение веток печати; 0054 —
расхождение форматов). Решение заказчика (2026-07-16): **каталог файла —
неявный путь в ядре**.

### Decision Drivers

1. **Редактор и компилятор обязаны видеть одно.** Расхождение — доказанный класс
   дефекта в этом проекте.
2. **Обратная совместимость** (правило 11): существующие сборки с `-I` не должны
   менять поведение.
3. **Не врать координатами.** Ошибка чужого файла не имеет позиции в открытом
   документе; подставлять чужое смещение — ложь.
4. **Не молчать.** Скрыть чужую ошибку — оставить автора без объяснения, почему
   модель не собирается.

### Considered Options

#### Каталог импортирующего файла: где искать

##### Option A. Неявный путь в ядре, **в конце** списка (принято)

**Pros:**
- Правка **строго аддитивна**: `-I` перебирается первым, значит там, где импорт
  разрешался раньше, найдётся **тот же** файл. Меняется только случай ошибки.
- Редактор и компилятор согласованы по построению.

**Cons:**
- Файл рядом с моделью **шадоуится** одноимённым файлом из `-I`. Интуиция
  «сначала моё» нарушена.

##### Option B. Неявный путь в ядре, **в начале** списка

**Pros:**
- Совпадает с интуицией `#include "x.h"`.

**Cons:**
- **Ломает** совместимость: проект с `-I lib`, где рядом с моделью лежит
  одноимённый файл, начнёт брать **другой** файл — молча сменив смысл сборки.
  Правило 11 требует обоснования; обоснования нет — выгода стилистическая.

##### Option C. Только в LSP

**Cons:**
- Редактор зелёный, сборка красная. Отвергнут заказчиком и драйвером 1.

#### Чужая диагностика: как показать

##### Option D. На строке `import` + текст «в файле X:строка:колонка» (принято)

**Pros:**
- Подсветка — там, где причина **видна в этом файле**: на самом `import`.
- Текст называет настоящее место, поэтому автор знает, куда идти.
- Не врёт координатами (драйвер 3) и не молчит (драйвер 4).

**Cons:**
- Ошибка не появляется в самом `lib.lam`, пока он не открыт.

##### Option E. Публиковать в URI чужого файла

**Pros:**
- Ошибка видна в `lib.lam`.

**Cons:**
- Нужно снимать устаревшие диагностики чужих URI (иначе они «залипнут» после
  правки) — заметно больше работы и состояния. Отвергнут заказчиком.

##### Option F. Не показывать вовсе

**Cons:**
- Автор не узнает, почему модель не собирается. Нарушает драйвер 4.

### Decision

Приняты **Option A** (аддитивный неявный путь в ядре) и **Option D** (якорь на
`import` + текст с настоящим местом).

**Якорь берётся из заметки, а не угадывается.** Проход 0 ставит ошибке из чужого
файла заметку «`X` импортирован в `Y`» с позицией `import` — на **каждом** уровне
всплытия. У цепочки `top → mid → deep` таких заметок две, и ровно одна имеет
`file_no == 0`, то есть лежит в открытом документе. Альтернатива — искать в АСД
`import` по имени файла — работает лишь для прямых импортов и врёт на вложенных.

Заметки полезны и `lamc`: он печатает цепочку импорта, как `rustc`.

### Consequences

#### Положительные

- `import` работает в редакторе и в `lamc` без настройки.
- Чужая ошибка видна, названа и привязана к месту, которое автор может править.
- `lamc` печатает цепочку импорта.

#### Отрицательные / Action items

- **A1.** Файл рядом с моделью шадоуится одноимённым из `-I` (цена
  аддитивности). Если понадобится «сначала моё» — это смена контракта, отдельная
  фича с обоснованием по правилу 11.
- **A2.** `goto_declaration` по-прежнему **угадывает** файл по имени модели
  (`to_snake_case` + перебор путей), хотя реестр даёт точный путь. Вне объёма:
  трогает другой сценарий (переход), а не диагностику. Кандидат.
- **A3.** LSP не читает `initializationOptions`, поэтому аналог `-I` в редакторе
  задать нельзя: работает только каталог документа. Кандидат.
- **A4.** Схемы кроме `file:` (например, `untitled:`) путей не имеют — импорт для
  них не разрешится. Это честнее, чем угадывать каталог.

#### Acceptance criteria

1. `import` рядом с документом разрешается в редакторе и в `lamc` без `-I`.
2. Сборка с `-I` находит **тот же** файл, что и раньше.
3. Ошибка чужого файла привязана к строке `import` и называет `в файле
   X:строка:колонка`.
4. Своя ошибка показывается на своём месте.
5. `lamc` печатает цепочку импорта заметками.
6. Регрессий нет: `precheck.sh` зелёный; версия языка не меняется.

## Анализ

### Цель и контекст

Сделать `import` работающим в редакторе и показать чужую диагностику так, чтобы
она не врала координатами. Кандидат вскрыт отчётом 0053.

### Зависимости (правило 17)

| Фича | Статус | Почему зависимость |
|---|---|---|
| 0053 | `ГОТОВО` | `FileTable`, настоящий `file_no`, `Diagnostic::file`, `construct_model_with_files` |
| 0054 | `ГОТОВО` | общий слой печати позиции (`position_prefix`) — им формируется текст «в файле X:стр:кол» |

Обе закрыты → фича **не блокируется**.

### Меняет ли фича язык (правило 22)

**Нет.** Грамматика и АСД не трогаются. Но **меняется разрешение импорта**
(каталог импортирующего файла — неявный путь): это семантика **инструмента**, а
не языка. Версия языка (0.3.0) не растёт; вывод генераторов на корпусе неизменен.

### Обратная совместимость (правило 11)

**Сохранена намеренной ценой.** Неявный путь добавляется **в конец** списка:

| Случай | Было | Стало |
|---|---|---|
| `-I` находит файл | найден файл из `-I` | **тот же** файл |
| `-I` не задан, файл рядом | `SE-013` | найден |
| Файл есть и рядом, и в `-I` | из `-I` | **из `-I`** (не изменилось) |

Строго аддитивно: меняется только исход, который раньше был ошибкой. Цена —
шадоуинг локального файла одноимённым из `-I` (ADR, A1).

## Разработка

### Задача

#### Что было

Импорт искался **только** по явным `-I`. Файл рядом с импортирующим не
находился — даже при запуске компилятора из его каталога:

```text
$ lamc compile -t c main53.lam -o o.c        # badsem.lam лежит рядом
main53.lam:1:1: [SE-013] Файл импорта не найден: «badsem.lam».
Пути поиска: (пути не заданы)
```

То есть `import` был непригоден без настройки — и это, а не «однофайловость LSP»,
оказалось корнем: редактор просто наследовал поведение ядра, вызывая
`construct_model(&ast, None, &[])`.

#### Что сделано

> **Готово.**

1. **`search_paths_with_importer_dir`** — каталог импортирующего файла
   добавляется к путям поиска. Импортирующий = вершина `import_stack`, а если
   стек пуст (импорт из корня) — корень из реестра (`FileTable`).
   Реестр-однодневка корня не знает → неявного пути нет, поведение прежнее.

2. **Путь добавляется В конец** — правка строго аддитивна (правило 11): `-I`
   перебирается первым, поэтому там, где импорт разрешался раньше, найдётся
   **тот же** файл. Поставь каталог первым — и проект с `-I lib`, где рядом с
   моделью лежит одноимённый файл, начал бы брать другой файл, молча сменив
   смысл сборки.

3. **`note_imported_here`** — ошибка из чужого файла получает заметку
   «`X` импортирован в `Y`» с позицией `import`, на **каждом** уровне всплытия.

#### Зачем заметки

Две причины, и обе нужны:

- **`lamc`** печатает цепочку импорта:

  ```text
  deep.lam:2:18: Ошибка компиляции [SE-002]: Ссылка 'Missing' не найдена
    примечание: 'deep.lam' импортирован в 'mid.lam'
    примечание: 'mid.lam' импортирован в 'top.lam'
  ```

- **LSP** по заметке находит место в **открытом** документе: у цепочки
  `top → mid → deep` ровно одна заметка имеет `file_no == 0`.

**Сообщение обязано быть самодостаточным.** Первая редакция писала
«импортировано здесь: deep.lam», рассчитывая на позицию заметки. Но `lamc`
печатает **только текст** заметки — и пользователь видел два бесполезных
примечания без координат. Заметка называет оба файла именно поэтому.

### Задача

#### Что было

- `collect_diagnostics(source)` (`lsp.rs:157`) звала `construct_model(&ast, None,
  &[])` — с пустыми путями поиска: `import` в редакторе **всегда** был ошибкой.
- `grammar_diagnostic_to_lsp` (`lsp.rs:224`) отбрасывала `file_no`
  (`Location::Source(_, start, end)`) и мапила смещение в текст **текущего**
  документа — подсветка ложилась не туда.

#### Что сделано

> **Готово.**

1. **`collect_diagnostics_at(path, source, search_paths)`** — знает путь
   документа, поэтому каталог документа работает как неявный путь поиска ([многофайловость LSP — импорты и позиции диагностик](0055-lsp-multifile.md#разработка)). `collect_diagnostics(source)`
   осталась обёрткой (`path = ""` → неявного пути нет) — прежние вызовы и тесты
   не тронуты.

2. **`diagnostic_to_lsp`** различает свой файл и чужой по `file_no`:
   - `file_no == 0` → как прежде, на своём месте;
   - иначе → якорь на строке `import` (заметка с `file_no == 0`), текст —
     `в файле lib.lam:2:18: …` (позицию строит общий слой
     `grammar::diagnostics::position_prefix`).

3. **`lam_lsp.rs`**: `uri_to_path` + `percent_decode` — путь документа из URI
   (`file://…`). Обрабатывается только схема `file:`: у прочих (`untitled:`)
   пути нет, и угадывать каталог честнее не пытаться.

#### Ловушка стадии

Тесты LSP живут под `#[cfg(feature = "lsp")]`, и **обычная `cargo build` их не
видит**: первая редакция добавила тесты без проверки — сборка проходила, а
`precheck.sh` (`--all-features --all-targets`) падал с `cannot find lsp in
grammar`. Та же ловушка, что в фиче 0053 с литералами `Diagnostic` под `lsp`.

## Тест-план

### Область и цель

Проверяется **что увидит автор в редакторе** (разрешился ли импорт, где легла
подсветка, что сказано в тексте) и **что не изменилось у компилятора** (сборки с
`-I` находят те же файлы).

**Ключевой принцип плана.** Фича добавляет неявный путь поиска — то есть трогает
разрешение импорта у **всех** инструментов. Поэтому каждая проверка «стало
работать» обязана иметь пару «прежнее поведение сохранено»: аддитивность —
обещание фичи (правило 11), а не побочность.

### Проверки (условие → ожидаемый результат)

| # | Проверка | Предусловие | Ожидаемый результат | Ссылка на R/A |
|---|---|---|---|---|
| T1 | Импорт разрешается в редакторе | `uses_ok.lam` (импорт рядом) | нет «файл не найден» | R1, R5 / A1 |
| T2 | **Пара к T1:** сборка с `-I` не изменилась | корпус `examples/` | снапшоты и проверка детерминизма зелены | R2 / A2 |
| T3 | `lamc` без `-I` находит импорт рядом | проба: `main53.lam` | ошибка — семантическая, а не `SE-013` | R1 / A1 |

**Зонд вскрыл, что кандидат винил не тот слой.** Кандидат назывался «LSP

тоже** не ищет импорт рядом с импортирующим файлом — только по явному `-I`, даже

только LSP, редактор стал бы зелёным там, где сборка красная: тот самый класс
дефекта, который проект уже лечил (0028-01 — расхождение веток печати; 0054 —
расхождение форматов). Решением заказчика неявный путь заведён **в ядре**, и
редактор с компилятором согласованы по построению.

### Решения заказчика (2026-07-16)

Проработка вскрыла две развилки, которые аналитик решать не вправе:

1. **Откуда LSP берёт пути поиска** → «каталог файла — неявный путь **в ядре**».
   Вариант «только в LSP» отвергнут: он создал бы расхождение редактора и сборки.
2. **Как показывать чужую диагностику** → «на строке `import` + текст
   `в файле X:стр:кол`». Вариант «публиковать в URI чужого файла» отвергнут:
   требует снятия устаревших диагностик чужих URI — заметно больше состояния.

### Обратная совместимость (правило 11)

Неявный путь добавляется **в конец** списка, поэтому правка **строго аддитивна**:
где импорт разрешался раньше, найдётся тот же файл; меняется только исход,
который прежде был ошибкой. Цена — файл рядом с моделью шадоуится одноимённым из
`-I` (ADR, A1). Обратный порядок («сначала моё») выглядит интуитивнее, но
молча сменил бы смысл существующих сборок, а выгода стилистическая.

### Ловушки, найденные на стадии

1. **Заметка была бесполезна в `lamc`.** Первая редакция писала «импортировано
   здесь: deep.lam», рассчитывая на позицию заметки. Но `lamc` печатает **только
   текст** заметки — пользователь видел два примечания без координат. Проба это
   показала сразу; сообщение стало самодостаточным («`X` импортирован в `Y`»).
   Тесты бы не поймали: они смотрят на LSP, где используется позиция, а не текст.
2. **Тесты LSP под `#[cfg(feature = "lsp")]` обычная сборка не видит.** Первая
   редакция добавила их без проверки: `cargo build` проходил, `precheck.sh`
   (`--all-features --all-targets`) падал. Та же ловушка, что в 0053 с литералами
   `Diagnostic` под `lsp` — второй раз подряд, и оба раза поймал предкоммит.

Фича **закрыта** 2026-07-16. Отчёт —
[`0055-lsp-multifile.md#отчёт-о-тестировании`](0055-lsp-multifile.md#отчёт-о-тестировании).

**Ядро.** Каталог **импортирующего** файла стал неявным путём поиска — общим для
`lamc` и LSP (решение заказчика). Поэтому редактор и компилятор согласованы **по
построению**, а не по договорённости. Путь добавляется **в конец** списка: правка
строго аддитивна (правило 11) — где импорт разрешался раньше, найдётся тот же
файл; меняется только случай, где раньше была ошибка.

**Цепочка импорта.** Ошибка из чужого файла получает заметку «`X` импортирован в
`Y`» на **каждом** уровне всплытия (`tree.rs::note_imported_here`). Она нужна
дважды: `lamc` печатает читаемую цепочку, а LSP по ней находит место **в открытом
документе** — собственные координаты ошибки указывают в текст, которого здесь нет.

**LSP.** `collect_diagnostics_at(path, source, search_paths)` знает путь
документа; чужая диагностика привязывается к строке `import` и в тексте называет
настоящее место — `в файле lib.lam:2:18: …`. Своя ошибка показывается на своём
месте, как прежде.

**Версия языка не менялась** (0.3.0), вывод генераторов неизменен.
