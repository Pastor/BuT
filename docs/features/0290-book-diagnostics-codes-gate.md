## Краткое описание

**Приложение «Ошибки» отстаёт от реестра диагностик на 19 кодов.** Замер
уточнён при закрытии [печатник цели c печатает пустоту на неразрешённом условии](0236-c-unresolved-condition-refusal.md)
(2026-08-16): в `docs/diagnostics/README.md` 211 кодов, в
`book/src/appendix-errors/` — 193; отсутствуют **19**, и это не только `ST`,
как считалось при находке 0235: `CC` — 4 (`CC-009`, `CC-014`, `CC-020`,
`CC-021`), `SE` — 4, `ST` — 4, `SV` — 3, `LE` — 2, `RS` — 2. То есть по
таблице документа код не найти. Машина этого не ловит: проверка сверяет
исходник с **реестром**, а `check-book-keywords.py` — **лексику**, а не
перечень диагностик. Списков кодов в проекте **три**: реестр (под проверкой),
приложение документа и таблица `README.md` — расходятся два последних.
Кандидат: сверять коды документа с реестром проверкой, как ключевые слова.

> Фича заведена **из бэклога кандидатов пакетным переводом** (решение заказчика
> 2026-08-18: «перевести всех кандидатов в фичи без проработки, решить, делать
> или нет, позже»). Стадии 2 и 3 **не пройдены**: приоритет, зависимости и
> объём не оценивались. Далее — жизненный цикл по правилу 17.

## Что известно на входе

Всё, что проверено, — в разделе выше: это **дословный текст кандидата** со
своим замером и ссылками на фичу, при закрытии которой он был вынесен. Ничего
сверх этого не проверялось.

Замер снят на дату, указанную в тексте. Прежде чем брать фичу в работу,
**перепроверь** его: условие карточки перепроверяется, а не наследуется — урок
[остаточные старые имена языка в данных и комментариях](0161-fixture-comments-rename.md), где обоснование отказа держало
работу отложенной два месяца и оказалось неверным уже в момент отказа.

## Направление решения (наметка, не решение)

Наметка — в тексте кандидата выше (там, где он её содержит). Решение о том,
**делать ли фичу вообще**, отложено заказчиком и принимается до стадии 2.

### Context

Списки кодов диагностик в проекте **два**: реестр
[`docs/diagnostics/README.md`](../diagnostics/README.md) (под проверкой
`scripts/check-diagnostic-codes.sh` — сверяется с исходниками в обе стороны) и
приложение документа `book/src/appendix-errors/index.typ` — справочник, который
читает **автор программы**, увидевший код в выводе инструмента. Второй список
наполняется руками и контроля не имеет вовсе.

**Замер-20** (перепроверка замера кандидата, снятого 2026-08-16 при
закрытии [печатник цели c печатает пустоту на неразрешённом условии](0236-c-unresolved-condition-refusal.md)):

| Список | Кодов |
|---|---|
| реестр (строки таблиц) | 264 |
| приложение (сводная таблица) | 247 |

- **Нет в приложении — 18 кодов:** `CC-014`, `CC-020`, `CC-021`, `LE-010`,
  `LE-011`, `RS-023`, `RS-024`, `SE-076`, `SE-081`, `SE-082`, `ST-017`,
  `ST-018`, `ST-019`, `ST-021`, `SV-015`, `SV-016`, `SV-017`, `SV-019`.
  Из них четыре — `RETIRED` (`CC-014`, `CC-020`, `RS-023`, `SE-082`), то есть
  выведенные; **четырнадцать эмитируются инструментом сегодня**, и найти их по
  справочнику нельзя.
- **Есть в приложении, нет в реестре — 1 код:** `SE-066` («Периодическое
  действие `every` пока не реализовано»). Он **выведен** задачей, когда
  `every` научились все цели, — и с тех пор справочник обещает диагностику,
  которой инструмент не выдаёт **никогда**. Это ложь автору, а не пробел.

Уточнения к тексту кандидата (замер-16 наследовать нельзя, правило 30):

- расхождение не «19 кодов», а **18 + 1 в обратную сторону**: обратное
  направление кандидат не называл вовсе, а оно дороже — пробел заставляет
  искать, ложь заставляет верить;
- **третьего расходящегося списка нет.** Кандидат называл «таблицу
  `README.md`»; замер: README упоминает 119 кодов по ходу изложения, и **все**
  они есть в реестре. Списком кодов README не является и сверки не требует.

Машина класс не видит: `check-diagnostic-codes.sh` сверяет реестр с
**исходниками**, `check-book-keywords.py` — **лексику** (ключевые слова и
пунктуацию), `check-book-glyphs.py` — символы. Перечень диагностик документа не
проверяет никто.

### Decision Drivers

1. **Справочник, отставший от инструмента, хуже отсутствующего**: по коду из
   вывода автор идёт в приложение, и там либо пусто, либо неправда.
2. **Два списка одного набора расходятся молча**;
   единственное лекарство, доказавшее себя в проекте, — машинная сверка.
3. **Правило простое контролируется дешевле правила с исключениями**: всякое
   исключение («этот код документу не нужен») — место, где сверка молча
   выключается.

### Considered Options

#### Option A. Сверять только эмитируемые коды (`RETIRED`/`RESERVED` — исключение)

**Pros:** документ не пополняется тем, чего инструмент не выдаёт.
**Cons:** три `RETIRED`-кода уже описаны в приложении с пометкой «(снят)» —
значит правило нарушается в самом документе; исключение придётся контролировать
отдельно («если код снят, но описан — не ругаться»), а номера не
переиспользуются, и встретить старый код в чужом выводе автор может.

#### Option B. Тождественность множеств: коды приложения = коды реестра

Приложение обязано перечислять **каждый** код реестра; выведенный —
с пометкой «(снят)», как уже сделано для `SE-091`, `SE-093`, `ST-005`. Код,
которого в реестре нет, в приложении **запрещён**.

**Pros:**
- Правило без исключений: проверка — сравнение двух множеств, дырок нет.
- Ловит **оба** направления, в том числе найденную ложь (`SE-066`).
- Продолжает уже принятое в документе решение (снятые коды описываются).

**Cons:** приложение пополняется четырьмя записями о выведенных кодах.
Цена — четыре строки таблицы.

#### Option C. Порождать приложение из реестра скриптом

**Pros:** расхождение невозможно по построению.
**Cons:** тексты реестра писаны для разработчика инструмента (со ссылками на
фичи и файлы исходников) — правило 24 прямо запрещает такое в документе;
порождение вернуло бы номера фич в `book/`. Ручной текст приложения —
осознанный, он адресован автору программы.

### Decision

Принимается **Option B**.

1. Проверка `scripts/check-book-diagnostics.py` (шаг предкоммита) сверяет коды
   сводной таблицы приложения с таблицами реестра **в обе стороны** и падает
   **списком**: «нет в приложении» и «нет в реестре» — раздельно.
2. Самопроверка `scripts/test-book-diagnostics.sh` (шаг предкоммита) доказывает
   мутацией на **копии** дерева, что проверка ловит обе стороны и принимает
   согласованное состояние (образец 0255: четыре условия проверки прожили без
   самопроверки, и дырявым оказалось непробованное).
3. Расхождение устраняется: 18 кодов добавляются в приложение (четыре
   выведенных — с пометкой «(снят)»), запись `SE-066` из приложения
   **удаляется**.

Разбор с примерами (вторая часть приложения) остаётся **подмножеством** сводной
таблицы и сверке не подлежит: он раскрывает основные ошибки, а не все.

### Consequences

#### Положительные

- По любому коду из вывода инструмента справочник даёт ответ.
- Ложное обещание `SE-066` снято.
- Следующий новый код обязан попасть в документ — иначе предкоммит красный.

#### Отрицательные / Action items

- Заводя код, автор правит **три** места: исходник, реестр, приложение. Это
  цена справочника, написанного для человека (Option C отвергнут).
- Проверка сверяет **наличие кода**, а не верность его описания: текст остаётся на
  человеке (правило 4), как и у `check-claude-md.py`.

#### Acceptance criteria

1. Проверка падает, когда код есть в реестре и нет в приложении.
2. Проверка падает, когда код есть в приложении и нет в реестре.
3. **Контроль:** на согласованном дереве проверка молчит и даёт код 0.
4. Самопроверка проверки — шаг предкоммита, гоняется на копии дерева.
5. Приложение и реестр согласованы; `SE-066` в документе нет.
6. `./scripts/precheck.sh` — код 0.

## Анализ

### Цель и контекст

Сделать так, чтобы справочник кодов в документе не мог отстать от реестра
молча. ADR принял Option B: множества кодов приложения и реестра **тождественны**,
сверяет их проверка предкоммита со своей самопроверкой.

### Замер (снят 2026-08-20, правило 30)

Замер кандидата (2026-08-16) **перепроверен и уточнён** — наследовать его
нельзя.

Как снят:

```sh
grep -oE '^\| `[A-Z]{2,4}-[0-9]{3}`' docs/diagnostics/README.md \
  | grep -oE '[A-Z]{2,4}-[0-9]{3}' | sort -u          # 264 кода
grep -oE '\b[A-Z]{2,4}-[0-9]{3}\b' book/src/appendix-errors/index.typ \
  | sort -u                                            # 247 кодов
```

Коды берутся **из строк таблиц** реестра, а не грепом по всему файлу:
проза реестра называет `CC-009` и `SE-024` в объяснении про пропуски номеров,
и наивный греп добавил бы к расхождению два несуществующих кода. Первая
редакция замера на этом и споткнулась — счёт вышел 20 вместо 18.

**Итог замера:**

| Направление | Кодов | Состав |
|---|---|---|
| в реестре, нет в приложении | 18 | `CC-014`, `CC-020`, `CC-021`, `LE-010`, `LE-011`, `RS-023`, `RS-024`, `SE-076`, `SE-081`, `SE-082`, `ST-017`, `ST-018`, `ST-019`, `ST-021`, `SV-015`, `SV-016`, `SV-017`, `SV-019` |
| в приложении, нет в реестре | 1 | `SE-066` |

- Из 18 недостающих **четырнадцать эмитируются сегодня**; четыре — `RETIRED`
  (`CC-014`, `CC-020`, `RS-023`, `SE-082`).
- `SE-066` («периодическое действие `every` пока не реализовано») **выведен**
  задачей: `every` переводят все цели. Справочник обещает диагностику,
  которой не существует — это ложь, а не пробел, и кандидат её не называл.
- **Контроль замера:** три `RETIRED`-кода (`SE-091`, `SE-093`, `ST-005`) в

  описывать выведенные коды, и тождественность множеств (Option B) его

**Третий список кандидата не подтвердился.** README упоминает 119 кодов по
ходу изложения; сверка `comm` с реестром даёт пустое множество расхождений.
Списком кодов README не является — сверять нечего.

- **R6.** Документ собирается (`make -C book build`), символы новых записей

Язык не затронут; версия языка прежняя (`0.10.0`).

**Не требуется.** Лексика, синтаксис и семантика языка не менялись: правится

### Документирование (правило 24)

**Требуется — и составляет предмет фичи.** Затронуто приложение «Ошибки и
предупреждения» (`book/src/appendix-errors/index.typ`), раздел «Сводная таблица

`SE-066`. Правило 25 соблюдено: полнота справки живёт в приложении, основной
текст не дублирует.

Тексты берутся **не из реестра дословно**: реестр писан для разработчика
инструмента и содержит номера фич и пути к исходникам, а правило 24 запрещает
им попадать в документ. Каждая запись переписывается для автора программы —
что случилось и что делать.

### Риски и зависимости

- **Риск: проверка сверяет наличие, а не верность описания.** **Снижение:** граница
  названа в ADR и здесь; верность текста — на человеке (правило 4), как у
  `check-claude-md.py`.
- **Риск: ложное срабатывание на прозе.** Проза реестра называет коды в
  объяснениях (см. замер). **Снижение:** проверка читает **строки таблиц** реестра
  (`| \`XX-NNN\` |`) и **строки сводной таблицы** приложения, а не любой текст;
  контроль гоняет проверка на копии настоящего дерева, поэтому ложное срабатывание
  видно сразу.
- **Риск: расхождение вернётся через разбор ошибок** (вторая часть приложения).
  **Снижение:** разбор — подмножество сводной таблицы и сверке не подлежит;
  код, описанный в разборе, обязан быть в таблице, и это следует из R2.

## Разработка

### Задача

#### Что сделано

**`scripts/check-book-diagnostics.py`** — сверка множеств кодов в обе стороны:

- со стороны реестра читаются **строки таблиц** `docs/diagnostics/README.md`
  (`| \`XX-NNN\` | … |`), а не весь текст: проза реестра называет `CC-009` и
  `SE-024` в объяснении про пропуски номеров, и наивный греп добавил бы к
  расхождению два несуществующих кода;
- со стороны документа читается **только сводная таблица** приложения — участок
  между `== Сводная таблица кодов` и `== Подробный разбор`: вторая часть
  приложения раскрывает основные ошибки, а не все, и сверять её нельзя;
- падение — **списком**, раздельно по направлениям: «нет в приложении» лечится
  дописыванием записи, «нет в реестре» — удалением обещания (или возвратом кода
  в реестр). Одно сообщение на оба класса заставило бы разбираться заново;
- **пустое множество — ошибка**: и отсутствие строк таблиц реестра, и
  отсутствие раздела сводной таблицы валят проверка с объяснением. Иначе смена
  разметки молча превратила бы сверку в проверку пустоты (урок исправления);
- корень дерева переопределяется `BD_ROOT` — этого требует контроль, гоняющий
  проверка на копии.

**`scripts/test-book-diagnostics.sh`** — контроль проверки, пять проверок на копии
дерева: контроль (согласованное принимается), пропавший код, лишний код,
документ без сводной таблицы, реестр без таблиц. Первая проверка обязательна:
без неё «проверка падает» означало бы лишь, что он падает всегда.

**`scripts/precheck.sh`** — оба шага в блоке документных проверок (там же, где
глифы 0146 и лексика 0160), самопроверка **первой**.

#### Проверка

```sh
python3 scripts/check-book-diagnostics.py   # код 0, «264 кодов сверены»
sh scripts/test-book-diagnostics.sh         # 5/5
```

#### Границы

Проверка сверяет **наличие** кода, а не верность его описания: текст справочника
остаётся на человеке (правило 4), как и у `check-claude-md.py`.

### Задача

#### Что сделано

Сводная таблица приложения «Ошибки и предупреждения»
(`book/src/appendix-errors/index.typ`) приведена в соответствие с реестром.

## Тест-план

Проверка `scripts/check-book-diagnostics.py` и согласованность приложения

примеров и контрпримеров на языке (правило 16) фича не требует: предметом
является **документ и его контроль**.

### Мутационные проверки (доказательство небутафорности)

- **М1.** Удалить из проверки сравнение `registry - appendix` → П2 обязана
  провалиться. Проверяет, что направление «нет в приложении» действительно

- **М2.** Удалить сравнение `appendix - registry` → П3 обязана провалиться.

Верность **текста** записи проверка не проверяет — только наличие кода. Разбор

### Что нашёл прогон (сверх текста кандидата)

1. **Расхождение больше заявленного: 32 кода, а не 19.** Греп по всему файлу
   приложения показывал 18 отсутствующих, но четырнадцать кодов (`SE-075`,
   `SE-077`…`SE-080`, `SE-083`…`SE-089`, `ST-020`, `SV-018`) имели **разбор**,
   не значась в **сводной таблице**. Вход в справочник — таблица, и по ней их
   было не найти.
2. **Обратное направление, которого кандидат не называл.** `SE-066`
   («периодическое действие `every` пока не реализовано») выведен задачей — справочник обещал диагностику, которой инструмент не выдаёт
   никогда. Это ложь, а не пробел, и она дороже.
3. **Третий список кандидата не подтвердился.** README упоминает 119 кодов, и
   **все** они есть в реестре; списком кодов README не является. Запись
   кандидата в этой части была неверна.
4. **Ловушка замера.** Наивный греп по реестру ловит `CC-009` и `SE-024` из
   прозы про пропуски номеров — коды, которых не существует. Проверка читает
   строки таблиц; первая редакция замера дала 20 вместо 18 именно поэтому.
