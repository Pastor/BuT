### 0. Контекст проекта (прочитать первым)

- **Что за проект.** Lam (Language of Automata Models) — DSL для конечных автоматов (FSM),
  компилируется в C. Workspace из двух крейтов: `grammar` (компилятор, ~30 тыс. строк) и
  `simulation` (симулятор + GIF-рендер, ~7 тыс. строк). Бинарники: `lamc` (компилятор),
  `lam-lsp` (LSP). Исходники FSM — `.lam`.
- **Ключевые файлы** перечислены в `CLAUDE.md` (раздел «Key files») — свериться перед правками.
- **Команды сборки/тестов** (из `CLAUDE.md`):
  ```sh
  cargo build --bin lamc
  cargo test -- --test-threads=1                    # тесты ОДНОПОТОЧНО (гонки в общих файлах)
  cargo test --features lsp -- --test-threads=1     # + LSP-тесты
  cargo test <name> -- --test-threads=1             # один тест
  ./scripts/precheck.sh                                      # fmt + check + clippy + test + сборка примеров
  ```
- **Правила разработки** (из `CLAUDE.md`, обязательны):
  - **Язык:** русский в комментариях, docstring, commit-сообщениях, `CHANGES.md`.
  - **TDD:** сначала падающий тест, потом минимальный код, потом рефактор.
  - **Размер патча:** логически сгруппированные изменения, **≤300 строк на патч**;
    файл патча `changes/Changes-XX[-PYY].patch`.
  - **Changelog:** дописывать в начало `CHANGES.md` (формат Keep a Changelog).
  - `./scripts/precheck.sh` **обязателен** перед коммитом.
  - После каждой задачи — однострочная запись в `STATUS.md`; в начале сессии — читать `STATUS.md`.
  - При написании тестов — **сначала зонд для захвата реальных значений**, потом assertions;
    не угадывать ожидаемые строки/адреса.

#### Инварианты — не ломать

1. **Условия рёбер `ref` не разрешаются.** `ref Next: expr;` хранится как
   `Condition::Unresolved(ast::Condition)`. **Не добавлять** проход
   `resolve_state_references`. Тест `syntax_simple` это охраняет. См. `CLAUDE.md`.
2. **`grammar/src/semantic/reference.rs` ≠ запрещённый проход.** Существующий `reference.rs`
   определяет структуру данных `ReferenceNode<StateNode>` (данные о ссылках на состояния) и
   используется в `semantic/mod.rs`. Это **не** `resolve_state_references` из предупреждения №1.
   Не удалять и не путать.
3. **Семантика `=` vs `==`:** `=` в выражениях → `Expression::Assign`; `==` в выражениях →
   `Expression::Equal`; `=` в условиях (`cond`/`ref`) → `Condition::Equal`.

#### P01 — `&String` → `&str` в `const_expr_string`
- **Требование CODE.md** (§Аргументы и типы): «принимай заимствованные срезовые типы:
  `&str` вместо `&String`».
- **Где:** `grammar/src/generator/c/c_decl.rs:15`
  ```rust
  fn const_expr_string(expr: &ExpressionNode, name: &String) -> Result<String, Diagnostic>
  ```
  Вызовы: `c_decl.rs:31` (`const_expr_string(v, name)`), `c_decl.rs:77` (`const_expr_string(expr, &name)`).
- **Изменение:** сигнатура → `name: &str`. В вызове на строке 77 `&name` заменить: если `name`
  уже `String`, передавать `&name` (авто-дереф в `&str` сработает) или `name.as_str()`; на
  строке 31 `name` уже `&str` после правки — передавать как есть.
- **Тесты:** отдельного unit-теста нет; покрывается компиляцией + существующими тестами
  генерации C (`grammar/tests/semantic_tests.rs`, C-генератор). Проверка:
  `cargo test -- --test-threads=1` + `./scripts/precheck.sh` (собирает примеры).
- **Риск:** минимальный.

#### P03 — `-> &String` → `-> &str` в `Comment::value`
- **Требование** (§Аргументы и типы): возвращать срез вместо `&String`.
- **Где:** `grammar/src/parser/ast.rs:68`
  ```rust
  pub const fn value(&self) -> &String { match self { Self::Line(_, s) | ... => s } }
  ```
- **Нюанс:** `pub const fn` со срезом `&str` — ок для `const fn` (возврат `&str` из `&String`
  требует `s.as_str()`, но `as_str` **не** `const` во всех версиях → возможно придётся снять
  `const`). **Действие:** сначала попробовать `s` с типом `-> &str` через coercion внутри
  `const fn`; если компилятор ругается на не-const операцию — снять `const`, оставив `#[inline]`.
  Зафиксировать реальное поведение компилятора, не угадывать.
- **Совместимость:** публичный API. Найти всех потребителей: `grep -rn '\.value()' grammar/src
  --include='*.rs'` и убедиться, что `&str` их устраивает (обычно да: `&String` и так дерефается).
- **Тесты:** ast/parser-тесты. `cargo test -- --test-threads=1`.
- **Риск:** низкий (может затронуть `const`-контексты — проверить).

#### P04 — `#[non_exhaustive]` на публичных растущих enum/struct
- **Требование** (§Расширяемость и API): «помечай публичные `enum`/`struct`
  `#[non_exhaustive]`, если планируешь добавлять варианты/поля без слома совместимости».
- **Где (кандидаты, растущие по своей природе):**
  - `grammar/src/diagnostics.rs:35` `Level`, `:66` `ErrorType`, `:365` `Location`
  - `grammar/src/generator/mod.rs:13` `Language` (сейчас `C`, `PlantUML` — целевые языки будут
    добавляться)
  - `grammar/src/parser/ast.rs`: `Type:136`, `StateElement:310`, `Expression:532`,
    `Statement:964`, `ModelElement:250` (расширяемые узлы AST)
  - `grammar/src/semantic/type_node.rs:495` `TypeNode`
- **Важное ограничение:** `#[non_exhaustive]` **запрещает** внешнее конструирование литералом и
  требует `_` в `match` вне крейта. **Внутри** крейта конструирование и исчерпывающий `match`
  остаются рабочими. Т.к. это библиотека (`grammar`) с внешними потребителями (`simulation`,
  бинарники) — **проверить**, что `simulation` не строит эти enum литералом и не делает
  исчерпывающий `match` без `_`. Начать с **безопасного подмножества**: `Language`, `Level`,
  `ErrorType` (наименее конструируются вовне). AST-узлы — только если `simulation`/`lamc` их не
  строят напрямую (проверить grep'ом).
- **Действие по каждому типу:**
  1. `grep -rn '<TypeName>::<Variant> *{' simulation/src grammar/src/bin` — есть ли внешнее
     конструирование/исчерпывающий match.
  2. Если нет — добавить `#[non_exhaustive]`.
  3. Прогнать `cargo test --features lsp -- --test-threads=1`.
- **Тесты:** компиляция всего workspace = основная проверка. Доп. тестов не требуется.
- **Риск:** средний (может потребовать `_ =>` в match вне крейта — тогда либо добавить `_`,
  либо отказаться от `non_exhaustive` для этого типа). Документировать решение в `CHANGES.md`.
- **Разбить на 2 патча:** P04a (diagnostics + generator::Language), P04b (AST/TypeNode) —
  чтобы уложиться в ≤300 строк и изолировать риск.

#### P05 — Убрать «bool trap» в `Generator::generate`
- **Требование** (§Диспетчеризация; §Расширяемость — приватные поля/осознанный API): булев
  флаг `guard_enable` на границе публичного API нечитаем на месте вызова; несколько позиционных
  аргументов — кандидат на структуру опций.
- **Где:** `grammar/src/generator/mod.rs:22` (trait `Generator::generate(&self, model, output_path,
  guard_enable: bool)`), реализации в `generator/c/mod.rs`, `generator/plantuml/mod.rs`, диспетчер
  `generate()` в `mod.rs:34`, вызовы в `grammar/src/bin/lamc.rs:309`, `grammar/src/lib.rs`.
- **Изменение (осознанно, KISS):** ввести
  ```rust
  #[non_exhaustive]
  #[derive(Debug, Clone)]
  pub struct GenerateOptions {
      pub guard_enable: bool,
      // задел под будущие опции (без преждевременного раздувания — только реальные)
  }
  impl Default for GenerateOptions { fn default() -> Self { Self { guard_enable: true } } }
  ```
  и заменить хвостовой `guard_enable: bool` на `options: &GenerateOptions` в trait, реализациях,
  диспетчере и вызовах. Значение по умолчанию — `guard_enable: true` (как сейчас в
  `lamc.rs:161`).
- **Альтернатива (проще):** ввести `enum GuardMode { Enabled, Disabled }` вместо структуры.
  **Рекомендация:** структура `GenerateOptions` (расширяемость по CODE.md), но если реальных
  будущих опций нет — YAGNI требует `enum GuardMode`. **Решение принять при реализации**, исходя
  из наличия других флагов в `lamc.rs` (проверить `parse_compile_args`).
- **Тесты:** существующие тесты генерации C/PlantUML; обновить их вызовы. `cargo test --
  --test-threads=1`.
- **Риск:** средний (широкая правка вызовов, но механическая).

  **захватить зондом** (напечатать `Default::default()` и сверить), не угадывать.

#### P08 — Точечный аудит `.clone()` (антипаттерн «clone ради borrow checker»)
- **Требование** (§Владение — не клонировать ради «успокоения» borrow checker; сначала
  пересмотреть заимствования).
- **Контекст:** 937 `.clone()` всего. **Большинство легитимны** (клонирование `Rc`,
  дешёвых `Copy`-подобных, необходимых владеемых значений AST). **Массовая замена запрещена** —
  только адресный разбор горячих точек:
  - `grammar/src/semantic/tree.rs` (132), `validate.rs` (83), `generator/c/c_expr.rs` (74),
    `semantic/condition.rs` (68), `semantic/minimap.rs` (61).
- **Метод (итеративно, по одному файлу за патч):**
  1. Для файла: `grep -n '\.clone()' <file>`.
  2. Для каждого клона задать вопрос: клонируется ли `Rc`/`Copy` (оставить; для `Rc` —
     предпочесть `Rc::clone(&x)` для явности, см. ниже) или **владеемые данные ради обхода
     borrow checker** (кандидат на устранение через переработку заимствований / `&`-ссылку /
     возврат ссылки).
  3. Только доказанные случаи «clone-ради-borrow-checker» переписывать; каждое изменение
     проверять `cargo test -- --test-threads=1`.
- **Побочно:** из 937 клонов только 51 — явные `Rc::clone`. Где `x.clone()` клонирует `Rc<...>`,
  заменять на `Rc::clone(&x)` (читаемость: явно видно, что это дешёвое клонирование счётчика, а
  не глубокое). Это отдельный проход, **низкий приоритет**, только в затрагиваемых P08-файлах —
  не делать массовую замену по всему проекту в одном патче.
- **Тесты:** регресс существующими тестами. Никаких изменений поведения — только владение.
- **Риск:** средний по трудозатратам, низкий по регрессу (тесты плотные, ~1400).
- **Замечание:** это открытая, итеративная задача. Зафиксировать в `STATUS.md`, сколько файлов
  разобрано. Не обязана быть «завершена» — цель снизить долю необоснованных клонов, а не число до нуля.

#### P09 — Возврат аргумента при `Err` в потребляющих API
- **Требование** (§Аргументы и типы): «при ошибке в методе, потребляющем аргумент по значению,
  возвращай его обратно (в `Err`)».
- **Где:** `simulation/src/unit/builder.rs:241` `pub fn build(model: Rc<RefCell<ModelNode>>) ->
  Result<Unit, Diagnostic>` — потребляет `model` по значению.
- **Нюанс:** `model` здесь — `Rc`, потребитель может дёшево клонировать `Rc` до вызова, поэтому
  строгой необходимости нет. **Действие:** оценить реальную пользу. Вариант A (по букве CODE.md):
  `Result<Unit, (Rc<RefCell<ModelNode>>, Diagnostic)>`. Вариант B (прагматично): оставить как есть,
  т.к. `Rc` дешёв — задокументировать решение. **Рекомендация:** применять паттерн только там, где
  аргумент **владеемый и дорогой** (`String`/`Vec`/большие структуры), а не `Rc`. Прогнать
  `grep -rn 'fn .*(self' grammar/src simulation/src` и `grep -rn 'mut .*: String)\|: Vec<' ...`
  для поиска потребляющих `self`/владеемый аргумент методов, которые в ветке `Err` теряют его.
- **Тесты:** обновить вызовы `build` (если меняется сигнатура), добавить тест, что при ошибке
  возвращается исходный `model`.
- **Риск:** низкий. Возможен вывод «изменения не требуются» — тогда зафиксировать в `STATUS.md`.

#### P10 — Шире применять `mem::take` / `mem::replace`
- **Требование** (§Владение): при смене варианта `enum` с переносом владения использовать
  `mem::take`/`mem::replace` вместо клонирования.
- **Контекст:** сейчас 4 применения. Кандидаты — места в семантических проходах, где вариант
  enum-узла (`StateNode`, `TypeNode`, `Expression`) заменяется, а поле предварительно клонируется.
- **Метод:** искать паттерн «клон поля → построение нового варианта → присваивание»:
  `grep -n 'clone()' grammar/src/semantic/tree.rs` в связке с переприсваиванием `*node =` / `= X::New`.
  Заменять на `std::mem::take(&mut field)` (если тип `Default`) или `mem::replace(&mut field, ...)`.
- **Тесты:** регресс. Изменение только владения.
- **Риск:** низкий-средний. Итеративная, необязательная к «нулю» задача.

#### P11 — `String::with_capacity` в горячих путях генератора
- **Требование** (§Строки): «для конкатенации в горячем пути заранее резервируй ёмкость».
- **Где:** генератор C — самые интенсивные по строкам файлы (`format!`: `c_expr.rs` 83,

- **Тесты:** вывод генератора **не должен измениться** — сверять существующими snapshot/интеграционными
  тестами C-генерации.
- **Риск:** низкий. Необязательная.

#### P12 — Ревизия doc-комментариев и doctest'ов

#### P13 — Аудит `new()` / `Default`
- **Требование** (§Конструирование): предоставлять `new()`; реализовывать `Default`

#### P05 — устранение «bool trap» в API генератора

**Проблема.** Хвостовой булев флаг `guard_enable: bool` на границе публичного API
нечитаем на месте вызова: `compile_to_c(file, src, out, &[], true)`, а тесты
буквально передавали `true`/`false` без пояснения.

**Решение.** Введён тип опций `generator::GenerateOptions` (реэкспорт
`grammar::GenerateOptions`):

```rust
#[derive(Debug, Clone)]
#[non_exhaustive]
pub struct GenerateOptions { pub guard_enable: bool }
impl GenerateOptions { pub fn new(guard_enable: bool) -> Self { … } }
impl Default for GenerateOptions { fn default() -> Self { Self { guard_enable: true } } }
```

Демонстрирует сразу три практики CODE.md: **options-struct вместо bool-trap**,
`#[non_exhaustive]` (расширяемость, правило 11) и `Default` + `new()`.

**Проведено через:**
- трейт `generator::Generator::generate(&self, model, output_path, &GenerateOptions)`
  и диспетчер `generator::generate(...)` (`generator/mod.rs`);
- реализации C (`generator/c/mod.rs`, `options.guard_enable` → `CMap::new`) и
  PlantUML (`generator/plantuml/mod.rs`, `_options` — guard игнорируется);
- публичную функцию `compile_to_c(..., options: &GenerateOptions)` (`lib.rs`),
  `compile_to_plantuml` внутри передаёт `&GenerateOptions::default()`;
- вызов в `bin/lamc.rs`: `&grammar::GenerateOptions::new(options.guard_enable)`;
- все тестовые вызовы (`grammar/tests/codegen_tests.rs`, unit- и doc-тесты `lib.rs`)
  → `&GenerateOptions::default()`.

**Совместимость (правило 11).** Публичная сигнатура `compile_to_c` изменена
(последний аргумент `bool` → `&GenerateOptions`) — осознанный слом ради читаемости
и расширяемости; проект на активной ветке `v2` до стабилизации API.

#### P11 — ёмкость строк в горячем пути

**Сделано.** `Printer::calculate_padding` (`generator/indent.rs`) строил строку
отступа посимвольным `push` в двойном цикле на каждом `up()`/`down()`. Длина
известна точно (`indent × indent_size`), поэтому заменено на `" ".repeat(n)` —
одна аллокация нужной ёмкости и более идиоматичный код (CODE.md §Функциональный
стиль).

**Осознанно пропущено.** Верхнеуровневые буферы сборки файла
(`c_header.rs`, `c_source.rs`: `let mut header/source = String::new()`) —
ёмкость зависит от размера модели и не оценивается надёжно; резервирование
константы было бы гаданием. Мелкие per-expression буферы (`rhs_str`, `lhs_str`,
`buf` в `c_expr.rs`) — не горячие. Микрооптимизация здесь противоречит KISS
(как и предупреждает план). Итог: точечное улучшение только там, где ёмкость
точная и путь действительно горячий.

#### P04b — `#[non_exhaustive]` на ядре AST/семантики

Добавлено к публичным расширяемым enum, растущим с каждой новой языковой
конструкцией: `parser::ast::{Type, ModelElement, StateElement, Expression,
Statement}` и `semantic::type_node::TypeNode`.

**Почему безопасно.**
- Enum-level `#[non_exhaustive]` **не запрещает** внешним крейтам конструировать
  известные варианты (`TypeNode::Bit`, `TypeNode::Integer { … }` в
  `grammar/tests/*` продолжают работать) — ограничивается лишь исчерпывающий
  внешний `match`.
- Исчерпывающих внешних `match` по этим типам в проекте нет (проверено grep'ом:
  `grammar/tests`, `grammar/src/bin`, `simulation/src`); `simulation` эти типы не
  матчит. Сборка `--all-targets --all-features` — без ошибок.
- **Внутрикрейтовая** исчерпывающая проверка (генераторы, семантические проходы)
  `#[non_exhaustive]` **не затрагивает** — компилятор по-прежнему укажет все места
  при добавлении варианта (рабочий процесс из `CLAUDE.md` сохранён). Профит для
  внешнего API (правило 11) без потери безопасности внутри.

`*Config` имеют рукописный (нетривиальный) `Default`; `SimulationRunner`,
`SemanticIndex`, `GenerateOptions` — `new()`.

Оставшиеся без `Default`/`new()` (`CompileOptions` — результат парсинга с полной

#### P09 — возврат аргумента при `Err`: изменений не требуется

Требование CODE.md (возвращать потреблённый по значению аргумент в `Err`)
применимо к **дорогим владеемым** аргументам, когда у вызывающего есть сценарий
повторной попытки/восстановления. В проекте таких API нет:

- `simulation::unit::builder::build(model: Rc<RefCell<ModelNode>>)` — принимает
  `Rc`; вызывающий при желании клонирует счётчик (`Rc::clone`) до вызова —
  возвращать его в `Err` бессмысленно.
- `save(self)`/`save_output(self)` (`gif.rs`, `svg.rs`, `runner.rs`) — терминальные
  финализаторы (запись файла в конце): после них объект не переиспользуется, а
  сигнатура `Result<(), (Self, String)>` усложнила бы обычный путь без реальной
  пользы (нет вызывающего, который бы повторял запись тем же объектом).

Добавлять возврат `self` «на всякий случай» — нарушение YAGNI. **Вывод: изменений
не требуется**; при появлении API с дорогим владеемым аргументом и сценарием
повтора паттерн применить.

#### P08 — аудит `.clone()` (первый проход: клоны Rc-хэндлов)

Из ~937 `.clone()` большинство легитимны (клонирование владеемых данных при
конверсии заимствованного AST в семантические узлы, ключи `HashMap` и т.п.).
Первый проход нацелен на **клоны Rc-хэндлов** — самый ясный и безопасный класс
по CODE.md («явно показывать дешёвое клонирование счётчика через `Rc::clone`»)
и на устранение лишних клонов Rc.

| Файл:строка | Было | Стало | Эффект |
|-------------|------|-------|--------|
| `semantic/tree.rs` (×6: 302, 317, 360, 371, 524, 573) | `model_node.clone()` | `Rc::clone(&model_node)` | явное дешёвое клонирование Rc (единый стиль с уже имевшимися `Rc::clone`) |
| `semantic/mod.rs:128` | `parent.clone().map(\|p\| Rc::downgrade(&p))` | `parent.as_ref().map(Rc::downgrade)` | **клон Rc устранён** (downgrade берёт `&Rc`) |
| `semantic/mod.rs:147` | `if let Some(parent) = parent.clone()` | `if let Some(parent) = &parent` | **клон Option<Rc> устранён** (нужна лишь ссылка) |
| `semantic/mod.rs:151` | `.insert(name, model.clone())` | `.insert(name, Rc::clone(&model))` | явное клонирование Rc |

Итог: 2 клона Rc устранены полностью, 7 приведены к явному `Rc::clone`.
Поведение не изменилось (Rc-клон и устранённый клон эквивалентны по результату).

**Не трогалось (осознанно).** Клоны владеемых данных (`def.value.clone()`,
`def.statement.clone()`, `field.ty.clone()`, клоны `String`-ключей и AST-узлов) —
это создание владеемого значения из **заимствованного** AST, а не «успокоение
borrow checker». Их устранение потребовало бы смены владения в AST/семантике и
несёт риск без выигрыша.

#### P10 — `mem::take`/`mem::replace`

`std::mem::take` уже применён в проходах разрешения (`semantic/tree.rs:773–809`):
`formulas`, `named_blocks`, `states`, `functions` забираются из
`model.borrow_mut()` без клонирования перед обработкой — это основной сценарий,
где паттерн уместен.

Дополнительный поиск «клон поля → построение нового варианта enum → присваивание»
в горячих файлах **safe-кандидатов не выявил**: оставшиеся клоны — это конверсия
заимствованного AST во владеемые семантические узлы (не перенос владения между
вариантами одного enum), где `mem::take` неприменим. **Вывод: расширять
применение без риска негде; существующее покрытие адекватно.**

#### Проверка

- `cargo build --all-targets --all-features` — без ошибок.
- `cargo test --features lsp -- --test-threads=1` — все наборы зелёные, падений нет.
- Изменения касаются только владения Rc-хэндлами; поведение не изменилось.

#### Осталось (итеративно, вне рамок фичи)

Полный проход по ~929 оставшимся `.clone()` не выполнялся: они преимущественно
легитимны. При появлении конкретных горячих путей с профилированием — точечно
пересматривать заимствования. Это **не** молчаливое ограничение: класс Rc-клонов
в семантике покрыт; остальное — владеемые данные без явной проблемы.
