## Краткое описание

Примеры документа описания языка не проверяются **ничем**: 18 файлов
`book/src/**/examples/*.takt` включаются в PDF, но ни один не подаётся ни
`taktc`, ни `takt-sim`. Правило 27(д) требует проверять пример **компиляцией И
симуляцией** — требование без машины, поэтому и не исполняется.

> Фича зарегистрирована из бэклога кандидатов (отобрана заказчиком 2026-07-27); далее проходит жизненный цикл по правилу 17.

## Что известно на входе

- В книге **18** файлов `book/src/**/examples/*.takt`, включаемых через
  `{{#include}}`.
- Слова `book` нет ни в `scripts/precheck.sh`, ни в `.github/workflows/ci.yml`.
- Прямое следствие уже зафиксировано отдельным кандидатом: seed-пример
  `01-overview/examples/blinker.takt` **не компилируется** (`start state Off` —
  недопустимая форма; отсутствует верхнеуровневый вход).

## Направление решения (наметка, не решение)

- Проверка в `precheck.sh`: `taktc compile` по всем примерам книги;
  `takt-sim` — там, где раздел заявляет сценарий поведения.
- Починить то, что проверка найдёт (как минимум `blinker.takt`).
- Проверка обязан отличать пример-иллюстрацию (намеренно неполный фрагмент) от
  цельной модели — иначе он заблокирует нормальные разделы; способ отметки
  фрагментов определяет анализ.

Окончательный выбор — за стадиями **архитектуры** (ADR) и **анализа**: раздел
выше фиксирует то, что уже проверено, а не предрешает реализацию.

- **Status:** Accepted

### Context

Правило 27(д) свода требует: пример раздела `book/` обязан **компилироваться и
быть проверен симуляцией** на осмысленное поведение. Машины под этим требованием
не было — слова `book` не встречалось ни в `scripts/precheck.sh`, ни в
`.github/workflows/ci.yml`. Примеры (18 файлов) включаются в PDF директивой
`{{#include}}`, а PDF локально не собирают, поэтому ошибка в примере не
проявлялась вовсе.

Цена бездоказательности известна поимённо: seed-пример
`01-overview/examples/blinker.takt` — **первый код, который видит читатель** —
не компилировался (недопустимая форма `start state Off` и отсутствие
верхнеуровневого входа). Дефект был найден при наполнении другого раздела, занесён
в кандидаты и дожил до аудита.

Обследование при проработке: из 18 примеров **16 компилируются**, 1 сломан
(`blinker`), 1 (`09-imports/examples/thermostat.takt`) не компилируется
**по построению** — это библиотечная модель, которую импортирует `room.takt`, и
собственного входа у неё нет.

### Decision Drivers

1. **Правило без машины — не правило.** Прецедент в проекте прямой: правило
   размера модуля работало только после появления `check-module-size.sh`.
2. **Библиотечный файл — не сломанный.** Проверка обязан отличать «пример не
   компилируется» от «пример не предназначен для отдельной компиляции», иначе он
   потребует ломать структуру раздела про импорты.
3. **Список исключений протухает.** Любой ручной перечень «эти не проверять»
   расходится с деревом файлов — тот же класс, что реестр карточек без проверки.
4. **Симуляция ловит другой класс.** «Компилируется, но падает на первом такте» —
   отдельный дефект; компиляция его не видит.

### Considered Options

#### Option A. Компиляция + симуляция; библиотечные выводятся автоматически

Каждый пример компилируется целью `c`; затем прогоняется `takt-sim -n 10` и
обязан завершиться без ошибки вычисления. Файл считается **библиотечным**, если
его имя встречается в `from "…"` другого примера; такой файл отдельно не
проверяется — его проверяет импортёр.

**Pros:**
- Закрывает оба класса дефектов (не компилируется; падает в симуляции).
- Признак «библиотечный» **выводится из содержимого**, а не поддерживается
  руками — исключения не протухают.
- Дёшево: два вызова уже собранных бинарников на файл.

**Cons:**
- Не проверяет, что пример делает **то, что обещает текст раздела**: прогон без
  входных сценариев доказывает лишь отсутствие отказа.

#### Option B. Полные поведенческие контракты (как `examples_scenario_tests`)

Для каждого примера — цепочка состояний, бюджет тактов и требование завершения.

**Pros:**
- Проверяет смысл, а не только отсутствие отказа.

**Cons:**
- Объём: 17 контрактов, каждый со своим сценарием входов; примеры разделов
  намеренно минимальны и часто **не завершаются** (маячок мигает вечно) — под них
  пришлось бы вводить отдельный вид контракта.
- Ставит документацию в зависимость от тестовой инфраструктуры симулятора:
  правка примера потребует правки контракта, и авторы разделов начнут избегать
  правок.

#### Option C. Только компиляция

**Pros:**
- Ещё дешевле.

**Cons:**
- Не исполняет вторую половину правила 27(д). Пример, падающий на первом такте
  (например переполнением знакового — `SIM-003`), прошёл бы проверка.

### Decision

Принимается **Option A**.

Option B отвергнут по соотношению цены и выигрыша: он проверяет смысл, но платит
за это связыванием документации с тестовой инфраструктурой, а осмысленность
примера сегодня обеспечивается ревью раздела (правило 27) и разбором в тексте.
Option C отвергнут: он оставляет невыполненной половину правила, ради которой
фича и заводится.

**Параметры решения:** цель компиляции — `c` (самая строгая по покрытию
конструкций из дешёвых); бюджет симуляции — 10 тактов (достаточно, чтобы
исполнились `enter`/`always` и хотя бы один переход); признак библиотечного файла
— вхождение его имени в `from "…"` любого примера книги.

### Consequences

#### Положительные

- Правило 27(д) стало проверяемым: пример, который не компилируется или падает
  в симуляции, валит предкоммит и CI (проверка живёт в `precheck.sh`, а CI зовёт его
  целиком — единый источник истины, контракт фичи).
- Починен seed-пример раздела «Обзор»; заодно текст раздела приведён в
  соответствие с поведением модели.
- Взведённость проверена **двумя** ловушками: сломанный синтаксис и корректно
  компилирующийся пример с ошибкой вычисления в симуляции.

#### Отрицательные / Action items

- **Проверка не проверяет осмысленность.** Прогон без сценария входов доказывает
  отсутствие отказа, но не то, что модель делает обещанное текстом. Ответственность
  за это остаётся на ревью раздела (правило 27). Кандидат на будущее: сценарии
  входов для примеров, где поведение существенно.
- **Формат примеров не проверяется** (`taktc fmt --check` к ним не применяется):
  примеры содержат выравнивание и маркеры-выноски `(1)`, `(2)`, которые
  канонический форматтер переставит. Сознательное исключение.
- **Бюджет 10 тактов — эвристика.** Пример, у которого отказ наступает позже,
  проверка не поймает.

#### Acceptance criteria

1. Проверка в `precheck.sh` проверяет каждый пример `book/src/**/examples/*.takt`.
2. Библиотечные файлы определяются автоматически и не проверяются отдельно.
3. Сломанный пример валит проверка; пример с ошибкой вычисления в симуляции валит
   проверка (проверено ловушками).
4. `blinker.takt` компилируется и симулируется; текст раздела соответствует его
   поведению.
5. `./scripts/precheck.sh` зелёный.

> Диаграмма по правилу 18 **не требуется**: язык не меняется — заводится проверка.

### Требования и проверяемые условия

- **R1. Проверяются все примеры** `book/src/**/examples/*.takt`, а не выбранные
  вручную.
- **R2. Библиотечный файл не считается сломанным.** Признак выводится из
  содержимого (кто-то импортирует его по имени), а не задаётся списком.
- **R3. Две проверки, а не одна:** компиляция и прогон в симуляторе.
- **R4. Проверка взведён.** Обе ловушки (не компилируется; падает в симуляции)
  обязаны валить проверка — проверено экспериментом, а не рассуждением.
- **R5. Единый источник истины.** Проверка живёт в `precheck.sh`; CI получает его
  автоматически (контракт фичи), собственной реализации не заводится.
- **R6. Найденное чинится.** Сломанный пример исправляется в объёме этой фичи;
  текст раздела приводится в соответствие с поведением модели.

### Особенности по обратной функциональности

Язык, инструменты и порождаемый код **не затрагиваются**: фича добавляет
проверку и правит один пример документа. Обратная совместимость неприменима.

Ужесточение процесса: **новый пример, не проходящий проверка, теперь валит
предкоммит**. Это и есть цель; для примеров-фрагментов, не предназначенных для
отдельной компиляции, штатный путь — сделать файл библиотечным (импортируемым),
как `thermostat.takt`.

### Риски и зависимости

- **Риск: проверка заблокирует раздел с намеренно неполным фрагментом.** Снижается
  правилом R2 (импортируемые файлы не проверяются отдельно) и тем, что фрагменты
  в тексте разделов пишутся **инлайн**, а не файлами: файл в `examples/`
  включается директивой `{{#include}}` целиком и обязан быть цельной моделью.
- **Риск: ложное чувство защищённости.** Проверка доказывает отсутствие отказа, но не
  осмысленность (ADR, отвергнутый Option B). Ограничение названо в ADR и в
  тест-плане, чтобы никто не принял зелёный проверка за проверку смысла.
- **Риск: бюджет 10 тактов мал.** Принят как эвристика; отказ, наступающий
  позже, проверка не поймает.

#### Что было

18 файлов `book/src/**/examples/*.takt` включаются в документ директивой

## Тест-план

### Область и цель

Фича **инфраструктурная плюс правка документации**: заводится проверка и чинится
один пример. Язык не меняется, поэтому правило 16 применяется в части «примеры и
контрпримеры» — но не к языку, а **к самому проверке**: проверяется, что он ловит
ровно то, ради чего заведён.

Ключевой риск области — «зелёный проверка, который ничего не проверяет». Поэтому
центральные проверки — **ловушки**: намеренно испорченный пример обязан валить
предкоммит.

### Проверки (условие → ожидаемый результат)

| # | Условие | Ожидаемый результат |
|---|---|---|
| A1 | прогон проверки на текущем дереве | все примеры проверены; итог «17 проверено, 1 библиотечных» |
| A2 | файл, импортируемый другим примером | помечен библиотечным, отдельно не компилируется |
| A3 | **ловушка 1:** пример с недопустимым синтаксисом (`start state Off`) | «не компилируется», предкоммит провален |
| A4 | **ловушка 2:** пример компилируется, но падает в симуляции (знаковое переполнение) | «симуляция отказала», предкоммит провален |
| A5 | `blinker.takt` после починки | компилируется целью `c` |
| A6 | `blinker.takt` под сценарием кнопки | `btn = 1` → состояние `On`, `led = 1`; `btn = 0` → `Off`, `led = 0` |
| A7 | текст раздела «Обзор» | описывает то поведение, которое даёт модель |
| A8 | проверка в составе полного предкоммита | секция присутствует в выводе, `EXIT=0` |
| A9 | CI | отдельной реализации проверки не заведено (CI зовёт `precheck.sh` целиком) |

### Примеры и контрпримеры (правило 16)

**Пример — то, что проверка обязан пропускать:**

```takt
model Lamp {
    in btn: bit;
    out led: bit;
    start Off { enter { led := 0; } ref On: btn = 1; }
    state On  { enter { led := 1; } ref Off: btn = 0; }
}
start Main = Lamp;
```

**Контрпример 1 — не компилируется** (недопустимая форма и нет входа):

```takt
model Broken {
    start state Off { }
}
```

**Контрпример 2 — компилируется, но падает на такте** (правило переполнения):

```takt
var s: i8 := 127;
start S { always { s := s + 1; } ref S: s = 100; }   // SIM-003
```

### Найденный дефект документа

**Д1. Seed-пример раздела «Обзор» не компилировался и не соответствовал тексту.**

- `start state Off` — недопустимая форма (`SY-002`); отсутствовал верхнеуровневый
  вход, из-за чего модель давала `SE-011`.
- **Сверх того**: оба перехода проверяли `btn = 1`, то есть модель
  перещёлкивалась **каждый такт** при нажатой кнопке, хотя текст обещал
  переключение «по нажатию».

Исправлено: форма приведена к `start Off` + `start Main = Lamp;`; переходы —
`Off → On` по `btn = 1`, `On → Off` по `btn = 0` (лампа горит, пока кнопка
нажата). Текст раздела приведён в соответствие. Поведение проверено симуляцией со
сценарием входов.

**Открытые ограничения (из ADR):**

1. **Проверка не проверяет осмысленность** — прогон без сценария входов доказывает
   отсутствие отказа, но не то, что модель делает обещанное текстом. Полные
   поведенческие контракты (Option B) отвергнуты по цене; ответственность

2. **Формат примеров не проверяется** (`fmt --check` к ним не применяется):

   переставит. Сознательное исключение.
