## Краткое описание

Довести конвейер верификации до рабочего: проверять LTL-свойства модели (`: [LTL]
φ;`) методом model checking. Затравка (`verification/`) даёт **два звена** — тип
`Ltl` и построение автомата Бюхи `build_buchi` (GPVW). Отсутствует **середина**:
структура Крипке из `ModelNode`, произведение с автоматом `¬φ`, проверка пустоты
(достижимый принимающий цикл), контрпример-лассо и подкоманда `lamc verify`.

По решению заказчика (2026-07-16) принята **абстракция управляющего графа**: атом
LTL — **имя состояния** FSM («автомат сейчас в состоянии S»); структура Крипке —
граф переходов автомата (состояния + рёбра `ref`), данные абстрагированы.
Проверяемы порядок состояний, достижимость, живость (`G(Fault -> F Idle)`);
свойства над данными (`G(temp <= 100)`) — вне охвата, будущее расширение.

> Фича зарегистрирована из блока «Кандидаты в фичи» `FEATURES.md` (по запросу
> заказчика 2026-07-16); проходит жизненный цикл по своду.

**Побочный результат — дефект затравки.** Задача вскрыла зондом, что
`build_buchi`  принимал **любой** бесконечный прогон: автомат `F p`
принимал слово, где `p` не наступает. Без исправления первый же вердикт
`lamc verify` был бы ложным на классе свойств живости. Правка — [вырожденное условие принятия автомата Бюхи (GPVW)](../fixes/0010-01-buchi-acceptance.md). Дефект прожил в зелёном CI с
[верификация свойств (LTL и автоматы Бюхи)](0010-verification-ltl.md), потому что у затравки не было потребителя, а её тесты проверяли структуру
автомата, а не принимаемый язык.

**Отступление от ADR (обосновано):** `SE-055` не снят для проверяемых формул, а
**переформулирован** (текст указывает на `lamc verify`). Причина: потребитель
появился у отдельной подкоманды, а `lamc compile` LTL по-прежнему не проверяет;
снятие вернуло бы класс дефекта, закрытый фичей (формула молча ничего не
делает). Детали — [верификация модели (Model Checking) на основе LTL](0049-model-checking-ltl.md#разработка).

### Найдено ревью и исправлено (до отчёта)

- **Недо-аппроксимация Крипке — `Holds` был неверен.** Самопетля ставилась
  только состоянию **без рёбер**. Но такт, в котором ни один guard не сработал,
  состояния не меняет (эталон — порождённый C: `if (cond) {…break;} break;`),
  поэтому состояние, все выходы которого условны, вправе стоять на месте вечно.
  Этот прогон в Крипке отсутствовал → множество прогонов было **меньше**
  реального → `F Done` на `start A { ref Done: x = 1; }` объявлялось
  **доказанным**, хотя автомат вправе никогда не уйти из `A`. Сломана была
  ровно главная гарантия фичи. Исправлено: самопетля ставится, если нет
  **безусловного** `ref` (`kripke.rs::may_stutter`); `next` состояния-реализации
  безусловным выходом не считается (вложенная модель может не завершиться).
  Закреплено юнит-тестами против эталона C.
- **`--property` со своей `;` молча усекался** до первой формулы
  (`-p "F Done; : [LTL] G Idle"` → «проверено: F Done»). Теперь отказ: строка
  обязана разбираться ровно в одну формулу.
- **Повторный `--property`** молча затирал первый — теперь отказ.

### Decision Drivers

1. **Профильная цель.** Формальная проверка свойств автоматной
   модели — не украшение, а прямое назначение DSL промышленных систем.
2. **Переиспользовать затравку, не переписывать.** `build_buchi` тотальна и
   протестирована; решение обязано опереться на неё, а не строить второй автомат.
3. **Конечность и разрешимость.** Структура Крипке обязана быть конечной, иначе
   проверка не завершается. Абстракция выбирается так, чтобы гарантировать
   конечность by construction.
4. **Соразмерность объёма.** Полный explicit-state (control × data) даёт взрыв
   пространства (u8 = 256 значений/переменную); символьный MC — отдельный крупный
   проект. Первый рабочий срез обязан быть цельным и завершаемым.
5. **Честная граница.** Что **не** проверяется — сообщается явно (наследие 0035:
   ни один путь LTL не молчит).

### Considered Options

Развилка — **семантика атома + структура Крипке** (вынесена заказчику).

#### Option A (принимается). Управляющий граф: атом = состояние FSM

Атом `S` истинен в состоянии Крипке `k` ⟺ `k` — состояние с именем `S`. Структура
Крипке = граф переходов автомата: вершины — состояния FSM, рёбра — `ref`-переходы
(гарантии абстрагированы: любой guarded-`ref` считается **возможным**
недетерминированным переходом). Данные (`var`/порты) в разметку не входят.

**Pros:**
- **Конечна и разрешима by construction**: |Крипке| = число состояний FSM.
- Ложится на природу Lam (это и есть FSM); граф переходов уже обходится
  (`c_model.rs:430`) — образец переиспользуется.
- Проверяемы содержательные свойства управления: достижимость, порядок состояний
  (`G(Fault -> F Idle)`), живость, отсутствие тупиков.
- Затравка `build_buchi` используется как есть; атом-предикат тривиален (сравнение
  имени состояния).
- Соразмерна первому срезу; расширение на данные — отдельная фича поверх.

**Cons:**
- Свойства над **данными** (`G(temp <= 100)`) невыразимы — атом-переменная/`cond`
  не проверяется. Сообщается явно (диагностика: «атом — имя состояния; условие/
  переменная в этой абстракции не поддержаны»).
- Абстракция гарантий (guarded-`ref` → возможный) даёт **over-approximation**:
  контрпример может быть недостижим по данным (ложное срабатывание). Осознанный
  размен; фиксируется в документации и контрпримере пометкой «абстракция
  управления».

#### Option B. Явное состояние (control × data) через симулятор

Атом = состояние или `cond`/переменная, вычисляемые конкретно; Крипке = достижимые
пары (состояние × оценка данных), перечисляемые прогоном симулятора.

**Pros:**
- Точность по данным: `G(temp <= 100)` проверяемо; контрпримеры реальны.

**Cons:**
- **Взрыв пространства состояний** (256^n): без предела/оптимизации не
  завершается на реальных моделях.
- Втягивает крейт `simulation` как генератор состояний — межкрейтная зависимость и
  крупный объём, несоразмерный первому срезу (драйвер 4).
- Требует решить, как атом-`cond` вычисляется символически/конкретно.

#### Option C. Bounded Model Checking (разворот на k шагов)

Развернуть модель на `k` тактов, искать контрпример длины ≤ k.

**Pros:**
- Дёшево находит короткие контрпримеры с данными.

**Cons:**
- **Не доказывает** свойство (только опровергает до глубины k) — для верификации
  «свойство держится всегда» непригодно.
- **Не использует затравку** `build_buchi` — другой алгоритм (обычно SAT), то есть
  выбросить готовое звено и построить новое.

### Decision

Принимается **Option A** — решение заказчика от 2026-07-16.

Обоснование. A — единственная опция, которая (1) конечна и разрешима без предела,
(2) переиспользует затравку `build_buchi` целиком, (3) ложится на природу Lam как
FSM и на уже существующий обход графа переходов, (4) соразмерна первому рабочему
срезу. B точнее по данным, но взрывается и втягивает симулятор; C не доказывает
свойство и игнорирует затравку. Ограничение A (данные вне охвата) **честно
сообщается** (наследие 0035) и снимается отдельной фичей-расширением (explicit-
state или символьный MC), которая строится поверх готового конвейера A.

**Конвейер (стандартный автоматный подход):** для свойства `φ` строится автомат
`A_¬φ = build_buchi(Not(φ))`; синхронное произведение `K × A_¬φ`; проверка
пустоты языка произведения (достижимый принимающий цикл). Пусто ⟹ `φ` держится;
непусто ⟹ найден контрпример-лассо, нарушающий `φ`.

### Consequences

#### Положительные

- `: [LTL] φ;` впервые **проверяется**: `lamc verify` даёт вердикт держится/нарушено
  с контрпримером. Профильная возможность DSL реализована.
- Затравка `verification/` входит в продуктовый контур (сейчас — только ради
  собственных тестов).
- Класс дефекта «LTL — терминальная аннотация» закрыт для управляющих свойств;
  SE-055 (0035) для проверяемых формул снимается (появляется потребитель).
- Конечный, завершающийся, детерминированный алгоритм — воспроизводимый вердикт.

#### Отрицательные / Action items

- **A1.** Явная разметка алфавита: извлечь литералы (`Atom`/`Not(Atom)`) из
  состояний `BuchiAutomaton` (сейчас неявны в `states[i].old`) для согласования в
  произведении.
- **A2.** Терминальные/тупиковые состояния FSM: добавить самопетлю (stutter),
  иначе конечные прогоны не дают бесконечных слов, которых требует семантика Бюхи.
- **A3.** Свойства над данными невыразимы — **явная диагностика** при атоме, не
  являющемся именем состояния (в выбранной абстракции), плюс раздел README.
- **A4.** Over-approximation: контрпример может быть недостижим по данным —
  пометить в выводе «абстракция управления» (честность результата).
- **A5.** Версия языка **не растёт**: синтаксис не меняется, `lamc verify` —
  аддитивная оснастка (прецедент `lamc fmt`). Атом получает
  **операционный** смысл (имя состояния), но принимаемое множество программ то же.
- **A6.** `parse_ltl` (`ltl.rs`) остаётся тестовым (паникует, атом = 1 символ) —
  продуктовый путь идёт через `ltl_ast_to_semantic`; не трогается.
- **A7.** Кандидаты-расширения (вносит координатор): (1) верификация
  свойств над данными (explicit-state/символьный MC); (2) `X`-оператор и точная
  трактовка stutter на терминальных; (3) контрпример как трасса симулятора.

#### Acceptance criteria

1. `lamc verify <file.lam>` проверяет все `: [LTL] φ;` модели: для держащегося
   свойства — «держится», для нарушенного — «нарушено» + контрпример-лассо.
2. Управляющее свойство `G(Fault -> F Idle)` на модели, где `Fault` не всегда
   ведёт к `Idle`, **опровергается** с контрпримером; на модели, где ведёт —
   **подтверждается**.
3. Достижимость: `F Done` истинно ⟺ состояние `Done` достижимо из старта.
4. Атом, не являющийся именем состояния (переменная/`cond`), даёт **явную
   диагностику** «в абстракции управления не поддержан» (не молча false).
5. Проверка **завершается** на всех примерах `examples/` (конечность Крипке).
6. Вердикт **детерминирован** (проверка — тот же вход даёт тот же вывод).
7. `build_buchi(Not(φ))` и произведение согласуются: известные теоремы
   (`F p` на модели без `p`; `G p` на модели с `!p`) дают ожидаемый вердикт
   (юнит-тесты на малых Крипке).
8. `./scripts/precheck.sh` зелёный; версия языка не изменена.

## Анализ

### Цель и контекст

Довести конвейер верификации до рабочего: `lamc verify` проверяет LTL-свойства
(`: [LTL] φ;`) методом model checking. Затравка `verification/`  даёт
`Ltl`, `to_nnf`, `build_buchi` (GPVW); отсутствует середина — структура Крипке,
произведение, проверка пустоты, контрпример, CLI (картирование кода 2026-07-16,
пути в [ADR](0049-model-checking-ltl.md#архитектура-adr)).

По решению заказчика (2026-07-16, [ADR](0049-model-checking-ltl.md#архитектура-adr),
Option A) — **абстракция управляющего графа**: атом = имя состояния FSM, Крипке =
граф переходов автомата, данные абстрагированы. Конвейер: `A_¬φ =
build_buchi(Not(φ))` → произведение `K × A_¬φ` → проверка пустоты (достижимый
принимающий цикл) → вердикт + контрпример-лассо.

Анализ **не переоткрывает** решение ADR, но фиксирует уточнения, снятые чтением
кода:

1. **Разметка автомата Бюхи неявна.** `BuchiAutomaton.transitions` — рёбра
   `usize→usize` без пометки; литералы (`Atom`/`Not(Atom)`) лежат в
   `states[i]` (`buchi.rs:74`, `:90-96`). Для произведения их **извлекают** из
   состояния-множества, а не из ребра.
2. **Терминальные состояния FSM обрывают прогон.** Семантика Бюхи требует
   бесконечных слов; тупиковое/`End`-состояние (`get_end_states`, `mod.rs:201`)
   получает **самопетлю** (stutter), иначе у него нет исходящих рёбер и лассо не
   строится.
3. **`build_buchi` вызывается впервые из продуктового пути** — сейчас 0 вызовов
   вне юнит-тестов (`grep`). Отрицание — `Ltl::Not(Rc::new(φ))` (или `to_nnf`
   уже разворачивает `Not`).

### Требования и проверяемые условия

- **R1. Структура Крипке из `ModelNode`.** Конечный граф: вершины — состояния
  FSM (`states`), рёбра — `ref`-переходы (`references()`); терминальные/тупиковые
  вершины получают самопетлю (R2-инвариант бесконечности). Стартовая вершина —
  `get_start_state()`.
- **R2. Оценка атома.** `Ltl::Atom(name)` истинен в вершине `k` ⟺ `k` — состояние
  с именем `name`. Прочие атомы (не имена состояний) → диагностика (R7), не
  молчаливый false.
- **R3. Отрицание и автомат свойства.** `A_¬φ = build_buchi(Not(φ))` —
  переиспользование затравки без правок `buchi.rs`.
- **R4. Синхронное произведение.** Состояние произведения — пара `(k, q)`; переход
  `(k,q)→(k',q')` ⟺ `k→k'` в Крипке, `q→q'` в автомате, и **литералы** состояния
  `q'` согласованы с разметкой `k'` (атом `S` ∈ q ⟹ `k'=S`; `!S` ∈ q ⟹ `k'≠S`).
  Принимающие пары — где `q` принимающее.
- **R5. Проверка пустоты.** Достижимый из начальной пары **принимающий цикл**
  (nested-DFS или SCC Тарьяна). Есть цикл ⟹ язык непуст ⟹ `φ` нарушено.
- **R6. Контрпример-лассо.** При нарушении — путь «префикс до цикла + цикл» в
  терминах состояний FSM; помечен «абстракция управления» (over-approximation,
  ADR A4).
- **R7. Честная граница.** Атом, не являющийся именем состояния, даёт явную
  диагностику «в абстракции управления не поддержан; поддержаны имена состояний»
  (наследие 0035: ни один путь не молчит).
- **R8. CLI `lamc verify`.** Подкоманда: `lamc verify <file> [-I …] [--property
  "φ"]`. Без `--property` проверяет все `: [LTL]` формулы модели. Код возврата: 0
  — все держатся, ≠0 — есть нарушение.
- **R9. Детерминизм и завершаемость.** Вердикт воспроизводим;
  проверка завершается на всех `examples/` (конечность Крипке).
- **R10. Версия языка не растёт.** Синтаксис не тронут; `lamc verify` —
  аддитивная оснастка (прецедент `lamc fmt`). Вывод целей `c`/`plantuml`/`st` не
  меняется.
- **R11. `verification/` — публичный вход.** Новый модуль (`kripke`, `product`,
  `check`) и публичная функция `verify_model(model, φ) -> Verdict` — по образцу
  `ltl_warnings`.

### Задача

#### Что было

*Проверено картированием кода 2026-07-16.* Готовой структуры Крипке нет; есть
сырьё — граф FSM:

- `StateNode` (`semantic/mod.rs:1023`): варианты `Simple`/`Implement` с

- `ReferenceNode` (`mod.rs:1455`): `{ name: String (цель), cond: ConditionNode,

- Образец обхода — `generator/c/c_model.rs:430` `generate_state_transitions`.

#### Что сделано

> **Готово.** Реализовано по ADR (Option A — управляющий граф, атом =
> состояние).

1. Новый модуль `grammar/src/verification/kripke.rs`:
   ```rust
   pub struct Kripke {
       pub states: Vec<String>,                 // имена состояний (детерминированный порядок)
       pub initial: usize,                      // индекс стартового
       pub transitions: BTreeMap<usize, BTreeSet<usize>>,
   }
   pub fn build_kripke(model: &ModelNode) -> Option<Kripke>;
   ```
   **Отличие от плана:** возвращается `Option`, а не `Kripke`. Модель без
   стартового состояния графа не задаёт, а молчаливый вердикт «держится» на
   пустом графе был бы ложью. `None` поднимается до
   `Verdict::NoStartState` (0049-03). Через `construct_model` такая модель не
   проходит (SE-011 — «должно быть только одно начальное состояние»), поэтому
   ветка защитная; юнит-тест собирает узел вручную.
2. Вершины = состояния FSM (ключи `states: BTreeMap` — алфавитный порядок). Рёбра — цели `ref` **и** `next` состояния-реализации. **Гарантии рёбер
   абстрагированы** (guarded-`ref` → возможный переход; `cond` игнорируется).
3. **Самопетля** (R2/A2) ставится вершине, в которой автомат **может
   задержаться** (`may_stutter`): у неё нет ни одного **безусловного** `ref`.
   Не только тупику!

   Эталон — порождённый C (`c_model.rs::generate_state_transitions`):

   ```c
   case S: {
       if (cond) { model->state = NEXT; break; }
       break;                 // ← ни один guard не сработал: состояние прежнее
   }
   ```

   **Первая редакция ставила самопетлю только вершине без рёбер — и это
   ломало главную гарантию фичи** (найдено ревью до сдачи). Состояние, все
   выходы которого условны, теряло реальный прогон «стоим на месте вечно»;
   Крипке становилась **недо**-аппроксимацией, и `F Done` на
   `start A { ref Done: x = 1; } state Done;` объявлялось **доказанным**, хотя
   автомат вправе никогда не уйти из `A`. Ошибаться дозволено лишь в сторону
   **лишних** прогонов: они дают ложные срабатывания, а не пропущенные
   нарушения. `next` состояния-**реализации** безусловным выходом не считается —
   он ждёт конца вложенной модели, а она может не закончиться никогда
   (`next` состояния *без* реализации `tree.rs` уже превратил в безусловный
   `ref`, поэтому он засчитывается).
4. Оценка атома (R2/R7): `atom_holds(k, name) = states[k] == name`; список
   неподдержанных атомов — `Kripke::unknown_atoms` (потребитель — 0049-03).
5. `Kripke::trace()` — дамп графа для отладки (`lamc verify --trace`).

**Переиспользование вместо копирования.** Обход рёбер взят не из образца
`c_model.rs:430`, а вынесен в общий помощник: `validate.rs::get_reachable_targets`
(анализ достижимости SE-046) стал `pub(crate) reachable_targets` и служит
единым источником истины о рёбрах графа FSM. Расхождение «что считается
переходом» между SE-046 и верификатором теперь невозможно by construction.

1. **Разметка автомата** (A1). `state_literals(&BuchiAutomaton, q) ->
   (BTreeSet<String> pos, BTreeSet<String> neg)` — требуемые истинными и ложными
   атомы состояния `q`. Нелитеральные формулы `states[q]` игнорируются: это
   темпоральные обязательства, а не ограничения на букву (за них отвечает
   условие принятия).
2. **Синхронное произведение** `verification/product.rs`:
   `product(&Kripke, &BuchiAutomaton) -> Product`, состояние — пара `(k, q)`.
   Переход `(k,q)→(k',q')` ⟺ `k→k'`, `q→q'` и `(k',q')` согласована. Начальные —
   согласованные `(initial_k, q0)`. Принимающие — где `q ∈ accepting`.
   Строится **обходом от начальных**: недостижимые пары в произведение не
   попадают. Согласованность пары с двумя `pos`-атомами ложна автоматически —
   вершина Крипке несёт ровно одно имя (так `A & B` даёт пустой продукт).
3. **Проверка пустоты** `verification/check.rs` — классический **nested-DFS**
   (Courcoubetis—Vardi—Wolper—Yannakakis): внешний DFS в постпорядке запускает
   из принимающего состояния внутренний, тот ищет путь обратно в него же.
   Возвращает `Option<Lasso>`.
4. **Контрпример-лассо** (R6): `Lasso { prefix, cycle }` в индексах
   произведения + проекция на имена состояний (`Lasso::state_names`).
   Форматирование трассы и пометка «абстракция управления» — на стороне
   потребителя (0049-03/0049-04), чтобы форматтер был один.
5. `Product::trace()` — дамп произведения для отладки (`--trace`).

##### Вскрыт дефект затравки: исправление

План задачи опирался на `build_buchi` как на готовое звено. **Зонд** (Крипке из
одной вершины `q` с самопетлёй, автомат `F p`) показал: автомат **принимал**
слово `q^ω`, где `p` не наступает никогда. Причина — в `expand` формулы клались в
`Old` только в ветке литералов, из-за чего условие прогресса `Until` вырождалось
в тождественную истину и принимающим становился **любой** бесконечный прогон.

Последствие для 0049 (не наступило — найдено до сдачи): ложные вердикты
«нарушено» на всех свойствах, отрицание которых содержит `Until`, — то есть на
`G (Fault -> F Idle)`, самом ценном классе. Правка — в
[исправлении](../fixes/0010-01-buchi-acceptance.md).

Урок зафиксирован в тест-плане: тесты `buchi.rs` проверяли **структуру**
(«states не пусто»), а не язык, — потому дефект и прожил в зелёном CI до первого
потребителя.

#### Проверки

Юнит-тесты `verification/{product,check}.rs::tests` (11, зелёные):

### Задача

#### Что было

ADR определил **атом** (имя состояния) и **абстракцию** (управляющий граф),
но не определил **область** формулы: место объявления `: [LTL] φ;` на проверку
не влияло. Формула состояния проверялась от **стартового** состояния — так же,
как формула уровня модели.

Это отвечало на вопрос, которого автор не задавал:

```lam
start Idle { ref Fault; }
state Fault {: [LTL] F Idle;    // намерение: «из Fault мы вернёмся в Idle»
    ref Fault;         // ← залипание в сбое
    ref Idle;
}
```

`F Idle` от старта **тривиально истинно**: старт и есть `Idle`. Вердикт —
«держится», хотя автомат вправе залипнуть в `Fault` навсегда. Формула, ради
которой пользователь и брал верификатор, молча не проверяла ничего.

Найдено ревью стадии тестирования (открытый вопрос 1 карточки фичи); поскольку
семантика была не определена ADR, а не сломана реализацией, вынесено решением
заказчика (2026-07-16) — выбран **вариант «б»**.

#### Что сделано

> **Готово.** Фича возвращена в `РАЗРАБОТКА` на одну задачу, затем — отчёт.

1. **Область стала данными о формуле.** `semantic/ltl_check.rs`: сборщик
   `model_ltl_formulas` возвращает `Vec<LtlSite>` вместо `Vec<(Ltl, Location)>`;
   `LtlSite { formula, loc, state: Option<String> }`. Поле `state` — имя
   состояния, в теле которого формула объявлена (`None` — уровень модели).
   Сборщик остаётся **единым источником истины** о том, где лежат формулы
   (паритет уровней — наследие 0035-01).

2. **Десахаризация — у потребителя, а не у сборщика.** `lib.rs::scoped_formula`
   разворачивает формулу состояния `S` в `G (S -> φ)`. Делать это в сборщике
   было **нельзя**: его второй потребитель — диагностики (SE-055/SE-056), а им
   нужна **авторская** формула. Иначе SE-056 ругался бы на атом `Fault`,
   которого автор не писал, — предупреждение указывало бы на наше же добавление.

3. **Область — свойство состояния, а не текста.** Формулы в именованных блоках
   состояния (`enter`/`exit`/`always`) получают ту же область: блок исполняется,
   лишь когда автомат в состоянии. Формулы в телах функций области **не**
   получают — функцию вправе позвать любое состояние, поэтому её область —
   модель.

4. **Пользователь видит проверенную формулу.** `PropertyResult::formula` несёт
   десахаризованную формулу, поэтому `lamc verify` печатает
   `СВОЙСТВО НАРУШЕНО: G (Fault -> F Idle)`, а не авторское `F Idle`. Печатать
   авторскую запись значило бы соврать об области: пользователь искал бы
   недостижимость `Idle` от старта.

#### Почему вариант «б», а не «а»/«в»

- **(а) оставить как есть** — сохраняет класс дефекта «формула молча не
  проверяет то, о чём написана»: ровно то, что фича закрывала для разбора,
  а 0049 — для проверки.
- **(в) отказывать** — ломает паритет уровней 0035-01 (формулы разбираются на
  всех трёх уровнях специально) и запрещает естественную запись без замены.

#### Проверка

Фикстуры-пара, `grammar/tests/data/verify/`:

| Фикстура | Формула (авторская → проверенная) | Вердикт |
|---|---|---|
| `state_scope_holds.lam` | `F Idle` в `Fault` → `G (Fault -> F Idle)` | держится |
| `state_scope_fails.lam` | то же; отличие — самопетля `ref Fault` | нарушено, `Idle -> [ Fault ]*` |

Тесты — `grammar/tests/verify_tests.rs` (5 шт., на **вердикт**, а не на форму
дерева формулы — капкан 0025).

**Мутационная проба** (метод T41): десахаризация отключена (`match None::<String>`)
→ краснеют **3** теста из 5. Не краснеет `state_scope_holds` — и это правильно:
на модели, где свойство держится, обе семантики дают «держится», отличить их
может только контрпример. Именно поэтому контролем работает **парная** фикстура,
а не одиночный пример.

## Тест-план

### Область и цель

Проверяется **вердикт**, который увидит пользователь: держится / нарушено (с
контрпримером) / не проверено. Покрываются требования R1–R11 и критерии
приёмки A1–A10 анализа.

**Ключевой принцип плана (капкан 0025, риск Р7 анализа).** Тесты пишутся на
**принимаемый язык и вердикт**, а не на структуру автомата («states не пусто»,
«есть принимающие состояния»). Именно тесты-на-структуру позволили дефекту
[вырожденное условие принятия автомата Бюхи (GPVW)](../fixes/0010-01-buchi-acceptance.md) (вырожденное условие принятия:
`build_buchi(F p)` принимал слово, где `p` не наступает) прожить в зелёном CI до
появления первого потребителя. Ни одна проверка ниже не считается пройденной,
если она подтверждает форму, а не поведение.

Из области **исключено** (ADR, осознанные границы): свойства над данными;
точность контрпримера по данным (over-approximation); минимальность
контрпримера.

## Отчёт о тестировании

### Резюме

**Пройдено. Фича готова к закрытию (`ГОТОВО`).**

`lamc verify` даёт вердикт по LTL-свойствам управления: держится (доказательство
на всех прогонах абстракции) / нарушено (контрпример-лассо) / не проверено
(честный отказ на атоме-не-состоянии). Все 47 проверок тест-плана (T1–T47)
пройдены; `./scripts/precheck.sh` зелёный целиком; `cargo test --
--test-threads=1` — **1618 тестов** в 19 наборах, из них 53 по этой фиче.

Версия языка **не менялась** (0.3.0): фича не трогает грамматику — `lamc verify`
читает те же `: [LTL] φ;`, что 0035 уже разбирал. Вывод генераторов
`c`/`c-hal`/`st`/`st-at`/`plantuml`/`rust`/`sv` не изменился.

**Главный результат стадии — не «зелёные тесты», а два вскрытых дефекта**, оба в
том, ради чего фича существует (в вердикте), и оба найдены **не** прогоном
тестов:

1. **Дефект затравки 0010** ([исправление](../fixes/0010-01-buchi-acceptance.md)):
   `build_buchi(F p)` принимал слово, где `p` не наступает. Прожил в зелёном CI с
   фичи, потому что тесты `buchi.rs` проверяли **структуру** автомата, а не
   принимаемый **язык**, и потребителя у затравки не было. Без исправления первый же
   вердикт `lamc verify` был бы ложным на всём классе свойств живости.
2. **Недо-аппроксимация Крипке** (ревью стадии разработки): самопетля ставилась
   только состоянию без рёбер, поэтому прогон «ни один guard не сработал, стоим
   вечно» в модели отсутствовал → `F Done` на `start A { ref Done: x = 1; }`
   объявлялось **доказанным**. Ломалась ровно главная гарантия фичи —
   надёжность `Holds`.

Оба подтверждают принцип плана: **тесты на вердикт, а не на форму**. Тест-план
это закрепил (T12/T13 — известные теоремы, T40 — независимый оракул, T41/T47 —
мутационные пробы, доказывающие, что тесты **умеют краснеть**).

#### Что показали мутационные пробы (T41, T47)

Проба — единственный способ отличить «тест зелёный, потому что кода нет дефекта»
от «тест зелёный всегда». Обе пробы временные, откачены после замера.

- **T41.** Возврат дефекта (`old.insert(η)` убран из ветки `Until`):
  `verify_tests.rs` краснеет — 4 теста, включая оракул T40. Тесты `buchi.rs`
  (10 шт., на структуру) остаются **зелёными**. Это и есть измеренная причина,
  по которой дефект прожил с фичи: набор, проверяющий форму, дефект
  принятия не видит в принципе.
- **T47.** Отключение десахаризации области (`scoped_formula` → `match
  None::<String>`): краснеют **3 теста из 5**. Не краснеет `state_scope_holds` —
  и это правильный результат, а не пробел: на модели, где свойство держится, обе
  семантики дают `Holds`, отличить их может только **контрпример**. Отсюда
  вывод, зафиксированный в 0049-06: контролем работает **парная** фикстура
  (пример + контрпример), одиночный пример контролем быть не может.

### Решения заказчика по открытым вопросам стадии (2026-07-16)

Три вопроса карточки фичи — неопределённости семантики, которых ADR не касался
(не дефекты реализации). Вынесены заказчику, решения приняты:

1. **Область формулы состояния** — вариант **«б»**: `: [LTL] φ;` в теле
   состояния `S` = сокращение для `G (S -> φ)`. **Потребовало доработки**: фича
   возвращена в `РАЗРАБОТКА` на задачу
   [верификация модели (Model Checking) на основе LTL](0049-model-checking-ltl.md#разработка), затем — этот отчёт.
   Обоснование выбора: вариант «а» (оставить) сохранял класс дефекта «формула
   молча не проверяет то, о чём написана» — на модели со стартом `Idle`
   формула `F Idle` в состоянии `Fault` держалась **тривиально**, пропуская
   вечное залипание в сбое.
2. **Импортированные модели** — вариант **«а»**: проверяются все модели файла,
   включая пришедшие через `import`; поведение задокументировано в README
   (раздел «Ограничения»). Сужение области — кандидат в фичи (`--scope`).
3. **Глубина рекурсии** — вариант **«а»**: обходы остаются рекурсивными (замер:
   3000 состояний — норма, 20000 — падение); для типичных моделей запаса
   достаточно. Ограничение задокументировано; итеративный обход — кандидат в
   фичи.

### Выводы и дальнейшие шаги

**Вердикт: готово.** Фича закрывается (`ГОТОВО`); карточка получает «Итог».

Что фича доказала сверх своего охвата — **проверка целевого инструмента не заменяет
проверки на смысл**: у 0045/0050 это показали компиляторы, принимавшие молча
неверный вывод, здесь — зелёный CI, годами не замечавший, что автомат Бюхи
принимает не тот язык. Общий у случаев не инструмент, а форма теста: проверялось
то, что легко проверить (структура, компилируемость), а не то, ради чего код
написан (язык, вердикт, поведение).

Дефектов, требующих исправления, стадия не оставила. Заведены **кандидаты в
фичи** — ограничения осознанные, задокументированные в README:

- сужение области проверки (`lamc verify --scope file|all`) — чтобы нарушенное
  свойство импортированной библиотеки не давало ненулевой код импортёру;
- итеративные обходы (`expand`, nested-DFS) — снять потолок ~3000 состояний;
- верификация свойств **над данными** (атом-предикат вместо атома-состояния) —
  строится поверх готового конвейера; сегодня даёт честный `Unsupported`.

## Итог (что сделано)

Фича **закрыта** 2026-07-16. Отчёт о тестировании —
[`0049-model-checking-ltl.md#отчёт-о-тестировании`](0049-model-checking-ltl.md#отчёт-о-тестировании)
(вердикт «готово»: T1–T47 пройдены, `precheck.sh` зелёный, 1618 тестов).

**Крейт `grammar`.** Конвейер верификации доведён до рабочего: `build_kripke` →
`build_buchi(¬φ)` → `product` → `emptiness` (nested-DFS) → `Verdict`
(`verification/{kripke,product,check,verify}.rs`); публичный API `verify_model` /
`verify_all` / `parse_ltl_property`; подкоманда `lamc verify [--property "φ"]
[--trace]` (код возврата `0`/`1` — пригодно для CI). Абстракция — управляющий
граф (ADR, Option A): атом = имя состояния, условия рёбер и данные
абстрагированы. Отсюда несимметричность вердикта: `Holds` надёжен, `Violated`
может быть ложным срабатыванием, атом-переменная даёт честный `Unsupported`, а
не молчаливое «ложно». Версия языка не менялась (0.3.0), вывод генераторов
неизменен.

**Ключевые решения и правки:**

- **Исправление затравки [вырожденное условие принятия автомата Бюхи (GPVW)](../fixes/0010-01-buchi-acceptance.md)** — `build_buchi`
  принимал **любой** бесконечный прогон (`F p` принимал слово без `p`). Прожил в
  зелёном CI с фичи: тесты проверяли структуру автомата, а не язык, и
  потребителя у затравки не было.
- **Самопетля — не только у тупика** (`kripke.rs::may_stutter`): её получает
  всякое состояние без **безусловного** `ref`. Первая редакция ставила петлю
  лишь вершине без рёбер → Крипке была **недо**-аппроксимацией → ложный
  `Holds`, то есть сломана главная гарантия фичи.
- **Область формулы состояния** — `G (S -> φ)` (0049-06, решение заказчика):
  десахаризация живёт у верификатора, а не у сборщика формул, потому что
  второму потребителю сборщика (диагностикам SE-055/SE-056) нужна **авторская**
  формула.
- **`SE-055` не снят, а переформулирован** (текст указывает на `lamc verify`):
  `lamc compile` LTL по-прежнему не проверяет, и молчать об этом нельзя.

**Живая проверка:** `lamc verify` прогнан на корпусе `examples/` (завершается на
всех) и на 7 фикстурах-примерах/контрпримерах `grammar/tests/data/verify/`,
попавших в README.
