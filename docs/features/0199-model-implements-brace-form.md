### Context

Грамматика принимает `model Имя ["=" Выражение] "{" элементы "}"`, то есть у
модели может быть **реализация** (`= A | B`) наравне с телом. Форма описана в
приложении-грамматике документа (`book/src/appendix-grammar/`), то есть заявлена
как часть языка.

Пробы 2026-08-03 показали **три разных поведения** одной формы:

| Форма | Эталон | Цели `c` / `rust` / `sv` / `st` |
|---|---|---|
| `model M = A \| B { always … }` — тело **без** состояний | пустая трасса `[—]`, завершение на шаге 1 | **все четыре** отказывают: `CC-005`, `RS-013`, `SV-011`, `ST-013` — «состояние ' ()' не найдено» |
| `model M = A \| B { start S … }` — тело **со** своими состояниями | исполняется **только** `S`; `= A \| B` **молча игнорируется** | компилируется, композиции нет |
| `model M = A \| B;` — без тела | — | грамматикой **не принимается** (`SY-002`): блок обязателен |

**Поправки к записи находки.** Кандидат называл отказ только у цели `c`;
отказывают **все четыре**. И, что важнее, кандидат не знал о **второй** форме —
а она хуже первой: там не отказ, а **молчаливая потеря** половины записи.

#### Причина — одна, и она точечная

`ModelNode.implements` заполняется при построении дерева как
`Extend::Unresolved(выражение)` (`semantic/tree.rs:189`) и **никогда не
разрешается**: `extend::unroll_extend_expression` вызывается **только** для
состояний (`StateNode::Implement`, `tree.rs:730`). Модельного вызова нет.

Отсюда всё наблюдаемое:

- симулятор: `build_extend(Extend::Unresolved)` → `Unit::default()` → пустая
  трасса (ветвь, которую фича правила «симметрично», но проверить значением
  не могла — ломается раньше);
- цели: `minimap.rs:489` переводит `Extend::Unresolved` → `StateExtend::None`,
  модель остаётся без состояний, и генератор ищет состояние с пустым именем.

#### Смежная находка (в объём не входит)

Фикстура `takt-lang/tests/data/generator/valid/forward_decl.takt` использует эту
форму и лежит в каталоге **valid**, но сама **не разбирается**: `next` в теле
модели грамматикой не принимается (`SY-002`). Никем не гоняется — тест
`codegen_tests::test_header_has_forward_declarations` использует собственный
inline-исходник. Мёртвая фикстура в `valid` — отдельная запись, кандидат.

### Decision Drivers

1. **Молчаливая потеря хуже отказа.** Сегодня вторая форма теряет `= A | B` без
   единого слова — это худший из трёх исходов, и он существует прямо сейчас.
2. **Грамматика и документ заявляют форму частью языка.** Убирать её — сужение
   языка, а не починка; такое решение принимает заказчик, а не разработчик.
3. **Эквивалент существует и работает.** `model M { always … start Inner = A | B; }`
   исполняется эталоном и переводится всеми четырьмя целями (проверено).
4. **Причина точечная.** Не хватает одного вызова разрешения; это делает
   «доделать» дешёвым, но не делает его автоматически правильным.

### Considered Options

#### Option A. Разрешать реализацию модели — форма начинает работать

Вызвать `unroll_extend_expression` для `ModelNode.implements` там же, где он
вызывается для состояний. Форма становится синонимом «композиция + тело
владельца».

**Pros:**
- грамматика, документ и поведение сходятся: то, что принято разбором,
  исполняется;
- ветвь `build_composition` (заведена 0194) наконец получает вход, который можно
  проверить **значением** — сегодня она не проверена;
- короткая запись для частого случая: композиция с телом владельца.

**Cons:**
- **не отвечает на вторую форму**: что делать, когда у модели есть и
  реализация, и свои состояния? Ответ нужен всё равно — иначе молчаливая потеря
  останется;
- расширяет поверхность языка: форму придётся описать в разделе о моделях
  (сейчас она есть только в приложении-грамматике), а значит документировать
  правило её взаимодействия с телом.

#### Option B. Отвергать реализацию модели диагностикой

`model M = …` → ошибка семантики с указанием эквивалента
(`model M { start Имя = …; }`).

**Pros:**
- честно отражает факт: форма не работает ни в одной стороне и никогда не
  работала;
- убирает **обе** проблемы разом — и отказ, и молчаливую потерю;
- дёшево и проверяемо.

**Cons:**
- **сужает язык** и требует правки приложения-грамматики документа;
- отвергает запись, которую грамматика принимает, — то есть расхождение
  грамматики и семантики остаётся, просто становится громким;
- ломает мёртвую фикстуру `forward_decl.takt` (её всё равно надо чинить или
  удалять — она и сейчас не разбирается).

#### Option C. Разрешать, но назвать конфликт (гибрид)

Реализация модели разрешается (как в A) — **и** случай «реализация + свои
состояния» отвергается диагностикой: модель не может быть одновременно
композицией и автоматом.

**Pros:**
- закрывает **все три** наблюдения: первая форма работает, вторая перестаёт
  молча терять запись, третья остаётся синтаксической ошибкой;
- правило простое и объяснимое: `=` задаёт **реализацию** модели, тело — её
  элементы; собственный `start` в теле противоречит реализации;
- ветвь 0194 получает проверяемый значением вход.

**Cons:**
- работы больше, чем в A и B: разрешение + диагностика + документирование;
- нужно решить смежный вопрос: допустима ли реализация модели с телом, где есть
  `var`/`const`/`always`, но нет `start` (по правилу — да, это и есть основной
  случай).

### Decision

**Рекомендация архитектора — Option C.**

Довод: Option A оставляет молчаливую потерю (драйвер 1) — худшее из трёх
поведений; Option B устраняет её ценой сужения языка, заявленного документом
(драйвер 2), хотя рабочий эквивалент показывает, что смысл у формы **есть**.
Option C — единственный, где все три наблюдения получают ответ, а правило
формулируется одной фразой: `=` задаёт реализацию модели, и собственного
стартового состояния у такой модели быть не может.

Решение заказчика (2026-08-03) — **Option C**, совпало с рекомендацией.
Развилка была: C **доделывает** язык (форма работает, конфликт назван),
B **сужает** его (формы нет), A **оставляет** половину дефекта.

### Consequences

#### Положительные

- `Extend::Unresolved` у модели перестаёт быть состоянием, в котором дерево
  живёт до самого конца;
- ветвь `build_composition` (0194) впервые получает вход, проверяемый значением;
- исчезает форма, молча теряющая часть записи.

#### Отрицательные / Action items

- **A1.** Документирование обязательно: раздел о моделях получает
  форму и правило её взаимодействия с телом; при Option B — наоборот, форма
  убирается из приложения-грамматики.
- **A2.** Проверить **все пять** потребителей (эталон + 4 цели) **значением**,
  а не фактом компиляции: конструкция новая для всех.
- **A3.** Проверить взаимодействие с фичей: тело `always` владельца-
  композиции обязано исполняться **ровно раз за такт** и в этой форме тоже.
- **A4.** Мёртвая фикстура `forward_decl.takt` — починить или удалить; в объём
  фичи не входит, но оставлять её в `valid` нельзя (запись кандидатом).
- **A5.** Проверить `--parameters=specialize`: реализация модели с параметрами
  (`model M = Tuner(gain := 2) | Tuner(gain := 3) { … }`) — законна ли и что
  делает.

#### Acceptance criteria

1. `model M = A | B { always … }` исполняется эталоном и переводится всеми
   четырьмя целями; трассы совпадают потактово.
2. Тело `always` владельца исполняется **ровно раз за такт**.
3. `model M = A | B { start S … }` отвергается диагностикой с обеими позициями
   (реализация и собственный `start`).
4. `model M = A | B;` по-прежнему синтаксическая ошибка.
5. Документ описывает форму и правило; корпус не задет, предкоммит зелёный.

## Анализ

### Цель и контекст

ADR принял **Option C** (рекомендация архитектора и решение заказчика совпали):
реализация модели разрешается, а конфликт «реализация + собственные состояния»
отвергается диагностикой.

### Зависимости фичи

**Нет.** Смежна с [симулятор теряет model-level `always` у модели-композиции](0194-sim-composition-model-always.md): та
завела ветвь `build_composition`, но проверить её значением не могла — вход
ломался раньше. Эта фича даёт такой вход.

### Места правки

| # | Что | Файл | Замечание |
|---|---|---|---|
| М1 | разворот реализации в синтетическое состояние | `semantic/tree.rs::expand_model_implement` | вызывается **до** цикла разрешения состояний — синтетическое состояние проходит тот же путь |
| М2 | диагностика конфликта | там же | **`SE-101`** с двумя позициями (модель и её собственное состояние) |
| М3 | реестр диагностик | `docs/diagnostics/README.md` | запись `SE-101` |
| М4 | документ языка | `book/src/04-models-states/` | форма и правило её взаимодействия с телом |

**Ключевое решение реализации — разворот, а не поддержка новой формы у
потребителей.** Форма есть **синоним** записи `model M { start Имя = A | B; }`,
которая работает у эталона и всех четырёх целей. Развернув её на построении
дерева, мы не заводим для пяти потребителей новый вид узла: за границей
построения формы не существует. Тот же приём, каким свёрнуты выдержка `after`
(0143), начальное значение порта (0187) и инициализатор объявления (0192).

### Ограничения, которые определяют форму решения

- **О1. Разрешить `implements` в поле — недостаточно.** Первая редакция правки
  сделала именно это: эталон заработал, но **все четыре цели остались красными**.
  Причина: карта (`minimap`) строит состояния из `model.states`, и модель без
  состояний даёт стартовое состояние с пустым именем. Значит нужен не
  разрешённый `Extend`, а **состояние**.
- **О2. Имя синтетического состояния не может конфликтовать** — и не конфликтует
  **по построению**: модель с реализацией и собственными состояниями отвергается
  `SE-101`, то есть других состояний у неё нет.
- **О3. Тело владельца остаётся телом модели.** `always` не переносится в
  синтетическое состояние: его исполнение обеспечивает фича (model-level
  `always` — каждый такт до диспетчеризации). Это надо проверить **значением**:
  ровно раз за такт.
- **О4. Форма без тела (`model M = A | B;`) остаётся синтаксической ошибкой** —
  грамматика требует блок. Объём фичи её не меняет.

### Особенности по обратной совместимости

- **Язык расширяется**: форма, которая не работала, начинает работать. Ломающих
  изменений нет — то, что раньше отвергалось целями, теперь переводится.
- **Одно ужесточение**: `model M = A | B { start S … }` раньше принималось
  (молча теряя реализацию), теперь — `SE-101`. Это исправление молчаливой
  потери, а не сужение осмысленного: работавшего поведения у формы не было.
- Корпус и `book/` не задеты: формы там нет.

### Документирование

**Требуется.** Язык получает работающую форму и новое ограничение. Место —
раздел о моделях (`book/src/04-models-states/`): форма, её эквивалент и правило
«модель не может быть и композицией, и автоматом», плюс запись `SE-101` в
«Частые ошибки» и приложение об ошибках.

### Редакторский слой

**Правок не требуется.** Новых токенов и узлов АСД нет — форма уже разбиралась
грамматикой; меняется только её обработка на семантике. Новая диагностика
`SE-101` идёт общим путём `collect_compile_diagnostics` (0130) и доезжает до
редактора без правок LSP.

### Риски

- **Риск «починили эталон, забыли цели»** (О1) — уже случился в первой редакции
  правки и был пойман прогоном целей. Снижение: R2 проверяет все четыре.
- **Риск потерять инвариант** (О3). Снижение: R4 на накапливающем теле.
- **Риск коллизии имени** синтетического состояния (О2). Снижение: `SE-101`
  делает коллизию невозможной по построению.

## Разработка

### Задача

#### Что было

`ModelNode::implements` заполнялся как `Extend::Unresolved` и **никогда не
разрешался**: `unroll_extend_expression` вызывался только для реализаций
**состояний**. Следствия были молчаливыми со стороны компилятора — симулятор
строил `Unit::default()` (пустая трасса), а карта переводила `Unresolved` в
`StateExtend::None`, из-за чего все четыре цели искали состояние с пустым именем.

#### Что сделано

**Разворот в состояние** (`extend::expand_model_implement`): реализация модели
превращается в синтетическое стартовое состояние `Implement`, то есть форма
`model M = A | B { … }` приводится к записи `model M { start Имя = A | B; }`,
работавшей всегда.

**Почему разворот, а не поддержка формы у потребителей.** За границей
построения дерева формы не существует, и пяти потребителям (эталон + четыре
цели) не по чему разойтись — тот же приём, что у выдержки `after` (0143),
начального значения порта (0187) и инициализатора объявления (0192).

**`SE-101`** — реализация вместе с собственным состоянием. Диагностика несёт
обе позиции. Прежде такая запись **работала**, молча теряя реализацию.

#### Две ошибки реализации, пойманные прогоном

**1. Разрешить `implements` в поле было недостаточно.** Первая редакция делала
именно это — и заработал **только эталон**: цели остались красными, потому что
карта строит состояния из `model.states`, а у модели с реализацией их нет.
Поймал прогон целей, а не чтение кода.

**2. Проверка размера отверг правку дважды.** `tree.rs` стоит в реестре долга, и
+83 строки он не принял. Код вынесен — сперва в новый модуль
`semantic/model_implement.rs`, но его объявление добавляло строку в `mod.rs`,
который **тоже** в долге. Итог: функция живёт в существующем `semantic/extend.rs`
(там же, где `Extend` и `unroll_extend_expression`) — и по смыслу это верное
место, а не обход проверки. В `tree.rs` осталась одна строка вызова, а место под
неё освободило удаление мёртвого закомментированного кода.

### Выводы и дальнейшие шаги

**1. Худшим из трёх поведений было не то, что называл кандидат.** Он описывал
отказ у цели `c`. Замер показал: отказывают **все четыре** цели, а вторая форма
(`model M = A | B { start S … }`) вообще **работала**, молча теряя реализацию.
Молчаливая потеря половины записи и определила выбор Option C — вариант, где
ответ получают все три наблюдения.

**2. Починка эталона не означает починки целей.** Первая редакция правки
разрешала `implements` в поле: эталон заработал сразу, а все четыре цели
остались красными — карта строит состояния из `model.states`, и модель без
состояний даёт стартовое состояние с пустым именем. Отсюда форма решения:
разворот в **состояние**, а не разрешение поля. Поймал прогон целей, а не чтение.

**3. Проверка размера отверг правку дважды и оба раза по делу.** `tree.rs` в реестре
долга: +83 строки он не принял. Вынос в новый модуль не помог — его объявление
добавляло строку в `semantic/mod.rs`, тоже стоящий в долге. Итоговое место —
существующий `semantic/extend.rs`, где живут `Extend` и
`unroll_extend_expression`; это не обход проверки, а верное место по смыслу.
Строку под вызов в `tree.rs` освободило удаление мёртвого закомментированного
кода.

**4. Clippy поймал то, чего не поймал бы человек:** дописанный в конец файла
блок оказался **после** модуля тестов (`items after a test module`). Перенесён.

**Исправления (`docs/fixes/`) не требуются.**

## Итог (что сделано)

Форма `model M = A | B { … }` работает у эталона и **всех четырёх** целей:

| Форма | Было | Стало |
|---|---|---|
| реализация + тело без состояний | эталон — пустая трасса; `CC-005`, `RS-013`, `SV-011`, `ST-013` | работает везде |
| реализация + собственный `start` | **работала, молча теряя** `= A \| B` | `SE-101` с двумя позициями |
| реализация без тела | `SY-002` | без изменений |

**Худшим было не то, что называл кандидат.** Он описывал отказ у цели `c`;
отказывают все четыре, а вторая форма вообще работала, **молча теряя** половину
записи. Это и определило выбор Option C — единственного варианта, где ответ
получают все три наблюдения.

Реализация разворачивается на построении дерева в синтетическое стартовое
состояние, то есть форма становится **синонимом** записи
`model M { start Имя = A | B; }`, работавшей всегда. За границей построения
формы не существует, и пяти потребителям не по чему разойтись.

**Починка эталона не означала починки целей.** Первая редакция разрешала
`implements` в поле: эталон заработал, все четыре цели остались красными —
карта строит состояния из `model.states`. Поймал прогон целей, а не чтение.

Правка живёт в `semantic/extend.rs`, а не в `tree.rs`: проверка размера отверг
рост дважды, и это привело к верному по смыслу месту — рядом с `Extend` и
`unroll_extend_expression`.

Побочно: ветвь `build_composition` (заведена [симулятор теряет model-level `always` у модели-композиции](0194-sim-composition-model-always.md))
впервые получила вход, проверяемый **значением**.
