## Краткое описание

Выгрузка консолидированной карты адресов портов наружу — подкомандой
`lamc address-map --emit <fmt>`, чтобы адресами могли пользоваться сторонние
инструменты (генераторы HAL, отладчики, платформенные скрипты). Экспортируется
**фактически разрешённая** карта — та же, что потребляет цель `-t c-hal`: с
учётом приоритета источников (inline `:=` < оператор `address` < внешняя карта
`--address-map`).

Поставляются **два формата**: `map` — тот же `.ld`-подобный формат, который уже
читается флагом `--address-map` (даёт **круговой рейс** export → import), и
`json` — машиночитаемая выгрузка с типом, направлением и источником адреса для
генераторов HAL. **Настоящий CMSIS-SVD не выбран**: у Lam нет данных, которых
требует его схема (группировка в peripherals, reset-значения, достоверная
разрядность регистра), и выпуск правдоподобного-но-неверного SVD для отладчиков
хуже его отсутствия — обоснование в [ADR](0043-address-map-export.md#архитектура-adr).

> Фича зарегистрирована из бэклога кандидатов `FEATURES.md` (вынесена из фичи
> 0020); далее проходит жизненный цикл по своду.

## Приоритет (свод п.3)

**Tier 3 (средний).** Аргументы:

1. **Это интеграционное удобство, а не дефект корректности.** В отличие от
   Tier 1–2 фич генератора C (0026, 0029), которые выдают **невалидный C**, здесь
   ничего не сломано: карта адресов уже работает и потребляется целью `c-hal`.
   Фича добавляет наружный выход к готовым данным.
2. **(профиль проекта) — по касательной.** Основная цель — задание и
   синтез автоматных моделей; экспорт карты обслуживает **смежный** тулинг
   (отладчики, генераторы HAL), а не сам синтез. Поэтому ниже фичи
   (ST-генератор), которая добавляет целевой язык промышленной автоматики и потому
   бьёт прямо в свод.
3. **Никого не блокирует.** Ни одна фича не зависит от 0043 (проверено по
   `docs/features/README.md`), поэтому по своду п.1 её не нужно поднимать
   ради разблокировки.
4. **Но дёшева и хорошо проверяема.** Переиспользует готовые
   `resolve_addresses` и `parse_address_map`; круговой рейс даёт сильный
   тестовый оракул. Это удерживает её на Tier 3, а не ниже.

## Риски

- **Формат выгрузки становится внешним контрактом** — его потребители вне
  репозитория; менять задним числом дорого. → Версионирование формата и
  «открытый» перечень источников с первого выпуска (см. анализ, R7).
- **Плоское пространство имён портов** (`HashMap<String, ResolvedAddress>`,
  `address_map.rs:374`) — одноимённые порты в разных под-моделях делят ключ.
  Латентный дефект ядра 0020, напрямую бьющий по экспорту. → Оформлен отдельным
  кандидатом; в 0043 — задокументированное ограничение (см. анализ, риск Р2).
- **Пересечение с 0042** (`--define`): добавит четвёртый источник адреса →
  значение поля `source` в выгрузке. → Снимается «открытым» перечнем (R7).

### Context

ADR ввёл внутренний слой `AddressMap` и назвал среди будущих потребителей
«**SVD-подобный экспорт**: `lamc address-map --emit …` выгружает карту наружу
(отдельная фича)». Эта фича — тот самый вынос. Решить надо три вопроса:
(1) **в каком формате** выгружать, (2) должен ли результат **читаться обратно**,
(3) **какая форма CLI**.

#### Что реально есть в коде (проверено-15)

Модуль карты лежит в **`grammar/src/address_map.rs`** (не в `semantic/`, как
указано в некоторых описаниях задачи):

| Сущность | Место | Содержимое |
|---|---|---|
| `AddressMapEntry` | `address_map.rs:36` | `name: String`, `addr: i64`, `bit: Option<i64>`, `loc` |
| `parse_address_map` | `address_map.rs:138` | парсер `.ld`-подобного формата, коды `AM-001…006` |
| `AddressSource` | `address_map.rs:350` | `Inline` \| `Operator` \| `External` |
| `ResolvedAddress` | `address_map.rs:361` | `addr: i64`, `bit: Option<i64>`, `source: AddressSource` |
| `AddressResolution` | `address_map.rs:372` | `map: HashMap<String, ResolvedAddress>`, `diagnostics` |
| `resolve_addresses` | `address_map.rs:409` | приоритет inline < `address` < внешняя карта; SE-050/051/052 |

CLI (`grammar/src/bin/lamc.rs`) сегодня имеет **две** подкоманды: `compile`
(строка 474) и `fmt` (строка 462); у `compile` — флаги `-t/--target` (176),
`-o/--output` (183), `-I/--include-dirs` (190), `-v/-q` (201/204),
`--guard-enable/--guard-disable` (207/210), `--address-map` (213). Цели: `c`,
`c-hal`, `plantuml` (551–655).

#### Проба (2026-07-15): что выгружать вообще есть

Компиляция модели с тремя источниками адреса и внешней картой-наложением
(`lamc compile -t c-hal --address-map plat.map probe.lam`) даёт:

```text
Предупреждение [SE-050]: внешняя карта переопределяет адрес порта 'BTN', заданный в модели
Предупреждение [SE-051]: внешняя карта задаёт адрес для несуществующего порта 'GHOST'

static const Probe_In_BitPort__ADDR[]     = { [PROBE_SW]  = { 0x300000u,   3, 4 } };
static const Probe_Out_BitPort__ADDR[]    = { [PROBE_LED] = { 0x200004u,  -1, 4 } };
static const Probe_In_NumericPort__ADDR[] = { [PROBE_BTN] = { 0x40000000u,-1, 1 } };
```

Приоритет источников работает (`BTN`: inline `0x200000` перекрыт картой
`0x40000000`). На реальном примере `examples/elevator_mini.lam` (44 порта) без
карты — ошибка `SE-052`; с полной картой — компилируется, все 44 адреса
разрешены.

#### Ключевая находка: чего в `AddressMap` нет

`ResolvedAddress` содержит **только** `addr`, `bit`, `source`. Всё остальное, что
нужно «настоящему» описанию регистра, живёт **вне карты**:

- **разрядность** — вычисляется в C-генераторе: `width_from_ctype`
  (`generator/c/c_header.rs:617`) поверх `port_ctype` (там же, 628). В карте её
  нет. Более того, для типа `Bit` она **недостоверна**: `get_c_type(Bit) → "int"`
  → `width = 4`, тогда как принятый по умолчанию HAL разыменовывает `uint8_t` (проба выше:
  `PROBE_SW`/`PROBE_LED` имеют `width 4` при однобитовом типе). Дефект известен и
  зафиксирован в `CLAUDE.md` / кандидате 0029;
- **права доступа** — выводимы из `direction: PortDirection`
  (`semantic/mod.rs:847`, `VariableNode::Port`), но в карту **не попадают**;
- **группировка в peripherals, reset-значения, `addressUnitBits`, размер
  регистра** — таких понятий в языке Lam **нет вообще**;
- **квалификация имени** — ключ карты плоский (`HashMap<String, _>`), при том
  что C-генератор индексирует таблицу **квалифицированными** enum-вариантами
  (проба: `ELEVATOR_MINI_CABIN_…` / `ELEVATOR_MINI_MOTOR_…`, тогда как ключ
  карты — голое `CabinButton_DC`).

**Вывод:** карта **стабильна и достаточна** для выгрузки того, что она и есть —
`имя → (адрес, бит, источник)`; и **недостаточна** для схемы, требующей
разрядности/прав/иерархии регистров. Это и определяет выбор формата.

### Decision Drivers

1. **Не врать потребителю.** Отладчик/`svd2rust` доверяют формату. Правдоподобный,
   но выдуманный SVD хуже отсутствия SVD: ошибка уедет в чужой тулчейн молча.
2. **(профиль проекта).** Lam — промышленные системы управления. SVD —
   стандарт ARM Cortex-M; целевая аудитория Lam включает ПЛК/IEC 61131-3, где SVD не применяется.
3. **Соответствие фактическим адресам.** Выгрузка обязана совпадать с тем, что
   потребляет `-t c-hal`, включая приоритет источников. Единственный корректный
   путь — общий `resolve_addresses`, а не повторный разбор источников.
4. **Проверяемость.** Формат должен иметь сильный тестовый оракул в CI без
   внешних зависимостей и сетевых схем.
5. **Переиспользование инфраструктуры** (драйвер из ADR) — не плодить парсеры
   и не тащить обязательных зависимостей в `lamc`.
6. **Формат = внешний контракт.** Выпущенный формат придётся поддерживать; цена
   ошибки выше, чем у внутреннего API.

### Considered Options

#### Option A. Настоящий CMSIS-SVD (XML)

**Pros:**
- Готовая экосистема потребителей: OpenOCD, pyOCD, SEGGER Ozone, `svd2rust`.
- Стандарт ARM со строгой XSD — потребителю ничего не надо адаптировать.

**Cons:**
- **Схема требует данных, которых у Lam нет.** Обязательны `<device>` c
  `addressUnitBits`, `width`, `size`, `resetValue`, и иерархия
  `peripherals → peripheral(baseAddress) → registers → register(addressOffset,
  size, access)`. У Lam нет понятий peripheral, reset-значения и достоверного
  размера регистра (см. Context: `width` для `Bit` заведомо неверна).
- **Заполнение ⇒ фабрикация.** Пришлось бы синтезировать фиктивный peripheral,
  проставить `resetValue = 0` и `size = 32` «по умолчанию». Это нарушает драйвер 1:
  отладчик покажет неверную разрядность регистра как факт.
- **Промах по профилю** (драйвер 2): ARM-специфичный формат для проекта, чей
  целевой стек включает ПЛК.
- Валидация по XSD в CI требует внешнего валидатора/схемы — вес и хрупкость.
- Нет кругового рейса: `--address-map` XML не читает.

#### Option B. Собственный JSON

**Pros:**
- Описывает **ровно то, что есть**, без фабрикации: имя, адрес, бит, источник,
  тип, направление.
- Тривиально потребляется генераторами HAL и скриптами на любом языке.
- Проверяем в CI без внешних схем: `serde_json` уже **безусловная dev-зависимость**
  `grammar` (`Cargo.toml`), при том что в самом бинаре `serde_json` — **опционален**
  (за `lsp`). Значит, эмиссию можно написать руками (плоские записи из строк и
  чисел), а тесты — разбирать `serde_json`. Новых обязательных зависимостей ноль.

**Cons:**
- **Нет готовых потребителей** — каждому нужен свой адаптер (но для генератора
  HAL адаптер нужен в любом случае).
- Круговой рейс не бесплатен: `--address-map` JSON не читает.

#### Option C. Повторный вывод в `.ld`-подобный формат карты

**Pros:**
- **Круговой рейс даром**: `parse_address_map` (`address_map.rs:138`) уже читает
  этот формат — export → `--address-map` замыкается, и это проверяемый инвариант.
- Ноль нового кода парсинга; формат уже документирован (EBNF в
  `address_map.rs:14–21` и в ADR).
- Привычен платформенным инженерам (модель линкер-скрипта).

**Cons:**
- **Лоссовый**: несёт только `имя = адрес[:бит]`. Ни направления, ни типа, ни
  источника — то есть генератору HAL его мало.
- Отладчиками не читается.

#### Option D. Несколько форматов через `--emit <fmt>`

**Pros:**
- Разные потребители получают разное: круговой рейс — из `map`, полнота — из `json`.
- Точка расширения: SVD/иное добавляется позже без слома CLI.

**Cons:**
- Больше поверхности (флаг-матрица, тесты на каждый формат).
- Риск «эмиттер ради эмиттера», если формат не имеет потребителя.

### Decision

Принимается **Option D в ограниченном составе: ровно два формата — `map` и
`json`**; **Option A (настоящий SVD) отклоняется** и выносится в кандидаты.

#### 1. Формат выгрузки (главное решение)

`lamc address-map --emit map|json`, по умолчанию **`map`**.

- **`map`** (Option C) — `.ld`-подобный формат, побайтово тот же, что читает
  `--address-map`. Потребители: сам `lamc`, платформенные скрипты, `diff` карт
  между ревизиями.
- **`json`** (Option B) — полная запись: квалифицированное имя, адрес, бит,
  источник, тип, направление. Потребители: генераторы HAL, внешний тулинг.

Оба берут данные из **одного** `resolve_addresses`, поэтому по построению
совпадают с тем, что эмитит `-t c-hal` (драйвер 3).

**Почему не SVD.** Кандидат назывался «SVD-подобный экспорт», и соблазн выпустить
именно SVD велик — но по факту (Context) Lam не располагает **ни одним** из
обязательных полей схемы SVD, кроме адреса: нет peripherals, нет reset-значений,
а `width` в единственном месте, где она сегодня считается (`c_header.rs:617`), для
типа `Bit` **неверна**. SVD, собранный из адреса плюс проставленных «по
умолчанию» полей, — это не экспорт, а фабрикация, которая уедет в отладчик под
видом факта (драйвер 1). Плюс промах по профилю (драйвер 2): SVD — ARM Cortex-M,
а Lam целится и в ПЛК (0041). Поэтому SVD отложен до появления **реальных**
данных: иерархии портов, достоверных разрядностей (кандидат 0029) и понятия
периферии. Тогда он заводится отдельной фичей и добавляется как третье значение
`--emit` — CLI под это уже готов.

#### 2. Круговой рейс — да, для формата `map`

Выгрузка `--emit map` **обязана** читаться обратно через
`compile --address-map`, а повторный экспорт — давать **побайтово тот же** текст
(идемпотентность). Свойство ценно втройне:

- **практически** — «сними карту с модели → отредактируй под платформу → подай
  назад» есть рабочий процесс платформенного инженера, ради которого 0020 и
  вводила оверлеи;
- **как оракул** — export → import → export = identity ловит расхождения
  эмиттера и парсера в CI без эталонных файлов (драйвер 4);
- **как страховка контракта** — формат уже зафиксирован парсером, то есть
  контракт не выдумывается заново.

Для `json` круговой рейс **не требуется** (это выход, а не вход): читать JSON
как карту адресов — отдельная фича, если появится спрос. Симметрия ради симметрии
здесь дала бы второй парсер входного формата — против драйвера 5.

Важная оговорка: круговой рейс **сохраняет адрес и бит, но не источник** — после
импорта все адреса станут `External`. Это не дефект, а семантика наложения (карта
главнее модели); фиксируется в контракте формата и проверяется тестом.

#### 3. Форма CLI — подкоманда, не флаг у `compile`

Принимается **`lamc address-map [-I …] [--address-map FILE] [--emit map|json]
[-o FILE] <input.lam>`**.

Обоснование против флага `compile --emit-address-map`:

1. **Экспорт — не компиляция.** Он не порождает целевой код; у `compile`
   вид результата уже выбирается `-t`, и ортогональный `--emit` создал бы
   бессмысленную матрицу (`-t c --emit json` — компилировать и выгружать? только
   выгружать?).
2. **Прецедент в самом проекте.** `fmt` (`lamc.rs:462`) — уже подкоманда для
   работы, не являющейся компиляцией. Решение следует сложившейся форме.
3. **Свой набор флагов.** Подкоманде нужны `-I`, `--address-map`, `-o` — и не
   нужны `-t`, `--guard-*`. Подкоманда выражает это честно.

Цена — дублирование разбора `-I`/`--address-map`; снимается вынесением общего
разбора в функции.

#### О диаграмме

Диаграмма **не добавляется**, и это осознанно. свод требует её, когда ADR
меняет **синтаксис или семантику языка** — здесь язык не меняется вовсе (`.lam`
не затронут, версия языка остаётся 0.2.0), — либо когда она **строго необходима**
для понимания. Поток данных «источники → `AddressMap` → потребители» уже
изображён в [ADR](0020-port-address-decl.md#архитектура-adr) (раздел «Ядро: `AddressMap`»);
[экспорт карты адресов во внешний формат](0043-address-map-export.md) лишь добавляет к нему одну стрелку-потребителя, ради которой схема-дубль
понимания не прибавит. Грамматика формата `map` также не нова — её EBNF
зафиксирована в ADR и в `address_map.rs:14–21`, а 0043 обязуется её
воспроизводить, а не менять.

### Consequences

#### Положительные

- Адреса становятся доступны стороннему тулингу — закрывается пункт «потребители»
  из ADR.
- Круговой рейс `map` даёт рабочий процесс платформенного инженера и сильный
  инвариант для CI.
- Проект не выпускает недостоверный SVD и не берёт на себя контракт, который не
  может честно исполнить.
- Новых обязательных зависимостей нет; язык не меняется (версия
  языка **не** повышается).
- CLI готов принять SVD третьим значением `--emit`, когда данные появятся.

#### Отрицательные / Action items

- **Формат `json` становится внешним контрактом.** → Обязательства: поле версии
  формата с первого выпуска; перечень `source` объявляется **открытым**
  (потребитель обязан терпеть незнакомое значение) — иначе фича (`--define`)
  сломает потребителей, добавив четвёртый источник.
- **Обогащение `ResolvedAddress`** (тип, направление, квалифицированное имя) —
  добавление полей в публичную структуру ⇒ **минорный бамп** крейта `grammar` по
  SemVer. Данные брать там, где они уже под рукой (`resolve_model`,
  `address_map.rs:447–453`), а не вторым обходом модели.
- **Плоский ключ карты** (`HashMap<String, _>`, `address_map.rs:374`) —
  одноимённые порты в разных под-моделях делят ключ, тогда как C-генератор
  индексирует квалифицированными вариантами. Латентный дефект **ядра 0020**, не
  созданный 0043, но напрямую бьющий по экспорту. → Оформить кандидатом; в 0043 —
  задокументированное ограничение и тест, фиксирующий текущее поведение.
- **Порт без адреса** (`SE-052`) — политика экспорта: недостижимый порт без
  адреса выгружается **с явной пометкой «адреса нет»** (в `json`) и
  **опускается** в `map` (запись `NAME = ;` формату неизвестна). Категорически
  **не** подставлять `0`, как это делает C-таблица (`c_header.rs:686`,
  `.unwrap_or(0)`): в выгрузке это неотличимо от настоящего адреса `0x0`.
- **Дублирование разбора CLI-флагов** между `compile` и `address-map` — вынести
  общий разбор.

#### Acceptance criteria

1. `lamc address-map --emit map <input.lam>` печатает карту фактически
   разрешённых адресов; приоритет inline < `address` < `--address-map` соблюдён.
2. **Круговой рейс:** вывод `--emit map` принимается `compile --address-map` без
   диагностик формата, а повторный экспорт даёт побайтово тот же текст.
3. `lamc address-map --emit json <input.lam>` печатает валидный JSON, разбираемый
   `serde_json`, с полями: версия формата, имя, адрес, бит, источник, тип,
   направление.
4. Адреса в выгрузке **совпадают** с таблицей `__ADDR[]`, эмитируемой
   `-t c-hal` на той же модели и той же карте.
5. Порт без адреса не порождает фиктивный `0x0`: в `json` — явная пометка, в
   `map` — запись отсутствует.
6. `--emit` с неизвестным форматом → ошибка с ненулевым кодом возврата.
7. Цели `c`, `c-hal`, `plantuml` и подкоманды `compile`/`fmt` не затронуты
   (регресс = 0); версия языка остаётся 0.2.0.
</content>

## Анализ

### Цель и контекст

Выпустить консолидированную карту адресов портов наружу, чтобы ею могли
пользоваться сторонние инструменты (генераторы HAL, отладчики, платформенные
скрипты). Фича вынесена из [адрес порта — размещение и потребление (карта адресов)](0020-port-address-decl.md), где
названа среди будущих потребителей `AddressMap` («SVD-подобный экспорт:
`lamc address-map --emit …`»).

По [ADR](0043-address-map-export.md#архитектура-adr): подкоманда
`lamc address-map --emit map|json`; **настоящий CMSIS-SVD отклонён** (Lam не
располагает обязательными полями его схемы — обоснование в ADR); круговой рейс
поддерживается для формата `map`. Язык **не меняется** → версия языка остаётся
0.2.0 (свод не срабатывает); крейт `grammar` — минорный бамп по SemVer.

#### Оценка «стабильности `AddressMap`» — ключевой вывод анализа

Кандидат ставил условием «стабильный `AddressMap` из ядра 0020». Проверено по
коду (`grammar/src/address_map.rs` — **не** `semantic/address_map.rs`) и живой
пробой 2026-07-15:

| Что нужно выгрузке | Есть в `AddressMap`? | Где на самом деле |
|---|---|---|
| адрес, бит | **да** — `ResolvedAddress { addr, bit }` (`:361`) | — |
| источник адреса | **да** — `AddressSource` (`:350`): `Inline`/`Operator`/`External` | — |
| приоритет источников | **да** — `resolve_addresses` (`:409`), проверено пробой | — |
| тип порта | **нет** | `VariableNode::Port { ty }` (`semantic/mod.rs:847`) |
| направление (права доступа) | **нет** | `VariableNode::Port { direction }` (там же) |
| разрядность | **нет** и **недостоверна** | `width_from_ctype` (`generator/c/c_header.rs:617`); для `Bit` даёт 4 (кандидат 0029) |
| квалифицированное имя | **нет** — ключ плоский `HashMap<String, _>` (`:374`) | C-генератор индексирует квалифицированными enum-вариантами |
| peripherals, reset-значения | **нет** — понятий нет в языке | — |

**Вердикт: условие выполнено частично, и этого хватает для выбранного объёма.**
`AddressMap` стабилен и достаточен для выгрузки `имя → (адрес, бит, источник)` —
то есть для форматов `map` и `json`. Он **недостаточен** для SVD, которому нужны
разрядность, права и иерархия регистров. Именно это, а не вкусовщина, определило
отказ от SVD в ADR: выбранный формат опирается **только** на поля, которые в
карте уже есть и уже проверены целью `c-hal`. Тип и направление добавляются
дёшево — они под рукой в `resolve_model` (`address_map.rs:447–453`), где обход
портов уже идёт.

Побочное следствие: 0043 **не зависит** от кандидата 0029 (исправление
`get_c_type`), потому что не эмитит разрядность. Выбери мы SVD — зависимость от
[генератор C: отображение типов Array/Bit/Rational](0029-c-type-mapping.md) стала бы жёсткой и блокирующей.

### Зависимости фичи

- **Зависит от: нет.**
  - **0020** (`AddressMap`, `resolve_addresses`, `parse_address_map`) —
    единственная содержательная зависимость, и она **закрыта**: статус `ГОТОВО`
    от 2026-07-14 (проверено по [`docs/features/README.md`](README.md),
    строка 31). Условие кандидата снято, статус `ЗАБЛОКИРОВАНА` **не ставится**.
  - **0029** (маппинг типов C) — **не** зависимость: выбранный формат не эмитит
    разрядность (см. выше).
  - **0041**, **0042** — **не** зависимости; пересечения разобраны ниже.
- **Влияние на порядок разработки:** 0043 **никого не разблокирует** — ни одна
  фича от неё не зависит (проверено по реестру). Поэтому по своду п.1 её не
  нужно поднимать; по п.3 она Tier 3 и идёт **после** 0041 (ST-генератор бьёт прямо
  в свод: целевой язык промышленной автоматики). Относительно 0042 порядок
  **свободен** — при условии R7 (см. ниже).

#### Пересечение с 0042 «Инъекция define'ов для адресов» (`--define`)

[инъекция define'ов для адресов (--define)](0042-address-defines.md) добавит **четвёртый источник** адреса. Вопрос задачи — «что выгружать, если
адрес пришёл из define'а?» — разбирается так:

- **Значение:** выгружается **разрешённое числовое** значение адреса, а не имя
  define'а. Экспорт по определению есть снимок факта (драйвер 3 ADR): потребитель
  выгрузки не имеет доступа к `-D`-окружению `lamc` и не может доразрешить символ.
- **Провенанс:** `AddressSource` получит новый вариант (напр. `Define`), и он
  проступит в поле `source` формата `json`. Опционально 0042 может добавить имя
  символа отдельным полем — но это её решение, не 0043.
- **Чей это порядок работ.** Если **0043 раньше** — 0042 обязана расширить
  `AddressSource` и перечень значений `source` в контракте формата (её задача, в
  её тест-плане). Если **0042 раньше** — 0043 сразу покрывает четыре источника.
- **Как развязано:** требованием **R7** — перечень `source` объявляется
  **открытым** с первого выпуска. Иначе выпуск 0042 сломал бы потребителей
  выгрузки, а внешний контракт ломать нельзя. Это и есть причина,
  по которой между 0042 и 0043 **не нужна** зависимость.

#### Пересечение с 0041 «Генератор генерации в Structured Text» (`AT %…`)

[генератор генерации в Structured Text (IEC 61131-3)](0041-st-backend.md) — второй потребитель `AddressMap` (ADR: «ST/PLC: `address → AT %…`»).
Пересечение **не конфликтное, но показательное**: локатор IEC 61131-3
`AT %IX1.0` кодирует не только адрес, а ещё **направление** (`I`/`Q`) и **класс
размера** (`X`/`B`/`W`/`D`). То есть 0041 упрётся ровно в тот же дефицит
метаданных, что описан выше, — направление и разрядность.

Следствия:

- **Обогащение `ResolvedAddress` типом и направлением  работает и
  на 0041** — при её реализации это уже будет в карте. Если 0041 пойдёт первой,
  обогащение, вероятно, сделает она, и 0043-01 сократится до эмиттера.
- **Разрядность** для 0041 (`X`/`B`/`W`/`D`) придётся брать достоверную ⇒ **0041
  вероятно зависит от 0029**, тогда как 0043 — нет. Это довод в пользу того, что
  порядок 0041 → 0043 (а не наоборот) ничего не стоит 0043.
- **Дублирования нет:** 0041 читает карту и печатает ST, 0043 читает карту и
  печатает выгрузку; общий у них — только слой `AddressMap`.

### Требования и проверяемые условия

- **R1. Подкоманда экспорта.** `lamc address-map [-I …] [--address-map FILE]
  [--emit map|json] [-o FILE] <input.lam>` выгружает карту разрешённых адресов;
  по умолчанию `--emit map`, вывод — в stdout, при `-o` — в файл.
- **R2. Соответствие фактическим адресам.** Выгрузка строится **тем же**
  `resolve_addresses` (`address_map.rs:409`), что и цель `-t c-hal`, и потому
  соблюдает приоритет **inline `:=` < `address` < внешняя карта**. Числа в
  выгрузке совпадают с таблицей `__ADDR[]` в порождённом C.
- **R3. Формат `map`.** Выход — `.ld`-подобный формат, принимаемый
  `parse_address_map` (`address_map.rs:138`): `NAME = 0xADDR[:bit];`, комментарии
  `//`. Грамматика **не расширяется**.
- **R4. Круговой рейс.** Вывод `--emit map`, поданный в `compile --address-map`,
  разбирается без диагностик `AM-001…006`; повторный экспорт даёт **побайтово
  тот же** текст (идемпотентность). Источник при этом не сохраняется — после
  импорта все адреса `External` (семантика наложения, не дефект).
- **R5. Формат `json`.** Валидный JSON, разбираемый `serde_json`; на каждый порт:
  имя, адрес, бит, источник, тип, направление. Эмиссия — **без** обязательной
  зависимости от `serde_json` в бинаре (он опционален, за `lsp`); разбор в
  тестах — через `serde_json` (безусловная dev-зависимость).
- **R6. Версия формата.** `json` несёт поле версии формата с первого выпуска.
- **R7. Открытый перечень источников.** В контракте формата `source`
  документируется как **открытый**: потребитель обязан корректно принимать
  незнакомое значение. Развязывает 0043 и 0042 (см. выше).
- **R8. Порт без адреса (SE-052).** Фиктивный `0x0` **не** подставляется: в
  `json` — явная пометка отсутствия адреса, в `map` — записи нет. (Контраст с
  C-таблицей, где `.unwrap_or(0)`, `c_header.rs:686`, — там это безопасно, так как
  SE-052 уже отсеял достижимые порты; в выгрузке `0x0` неотличим от настоящего
  адреса.) Достижимый порт без адреса → та же ошибка SE-052, что и в `c-hal`.
- **R9. Диагностики карты.** SE-050 (наложение) и SE-051 (висячая запись)
  выводятся в stderr и **не** попадают в поток выгрузки (stdout остаётся
  машиночитаемым).
- **R10. Регресс = 0.** `compile` (цели `c`, `c-hal`, `plantuml`) и `fmt` не
  затронуты; версия языка остаётся 0.2.0.
- **R11. Неизвестный формат.** `--emit <мусор>` → сообщение об ошибке и
  ненулевой код возврата.

### Критерии приёмки и способ проверки

### Особенности по обратной функциональности

**Строка для реестра анализа:** *Аддитивно: новая подкоманда `lamc address-map`,
существующие `compile`/`fmt` и цели `c`/`c-hal`/`plantuml` не затронуты (регресс =
0); язык не меняется (версия 0.2.0). Расширяется CLI-контракт, и **формат
выгрузки сам становится контрактом с внешними инструментами** — фиксируется
версией формата и открытым перечнем `source` (R6, R7).*

Развёрнуто:

1. **CLI-контракт расширяется аддитивно.** `address-map` — новое имя подкоманды;
   ранее `lamc address-map …` завершался ошибкой «неизвестная команда»
   (`lamc.rs:474`), так что рабочих сценариев это не отнимает.
2. **Публичный API `grammar` расширяется.** `ResolvedAddress` получает поля ⇒
   **минорный** бамп по SemVer. Язык **не** затронут — версия языка
   остаётся 0.2.0.
3. **Новое обязательство: формат выгрузки — внешний контракт.** Это самое
   долгоживущее следствие фичи. В отличие от внутреннего API, его потребители
   находятся **вне репозитория** (генераторы HAL, скрипты), их нельзя починить
   вместе с изменением. Обязательства фиксируются как требования, а не пожелания:
   - **R6** — версия формата с первого выпуска, чтобы у потребителя была точка
     ветвления;
   - **R7** — `source` объявлен открытым, иначе фича сломает потребителей
     самим фактом добавления `Define`;
   - для `map` контракт **уже** зафиксирован парсером `parse_address_map` — 0043
     обязуется формат воспроизводить, а не менять (R3), и это проверяется
     круговым рейсом (R4/A4).
4. **Замечено попутно (не чинится в 0043).** Сообщение об ошибке неизвестной
   цели (`lamc.rs:651`) гласит «Поддерживается: c, plantuml» — цель `c-hal`
   пропущена. Мелкий дефект справки от 0020; в кандидаты.

### Риски и зависимости

- **Р1. Формат = внешний контракт** (высокий). Ошибку в формате не откатить
  задним числом. → R6/R7; начать с `map`, чей контракт уже фиксирован парсером
  (R3), и держать `json` минимальным — только поля, реально имеющиеся в карте.
- **Р2. Плоское пространство имён портов** (средний, **латентный дефект**).
  `AddressResolution.map: HashMap<String, ResolvedAddress>` (`address_map.rs:374`)
  ключуется **голым** именем порта, тогда как C-генератор индексирует таблицу
  **квалифицированными** вариантами (проба: `ELEVATOR_MINI_CABIN_…` vs
  `ELEVATOR_MINI_MOTOR_…` при ключе `CabinButton_DC`). Два одноимённых порта в
  разных под-моделях делят ключ — побеждает последний записавший
  (`resolve_model`, `:499`). Корпус это сегодня маскирует: авторы **вручную**
  префиксуют имена (`ElevatorMotor_Up`, `CabinButton_DC` в
  `examples/elevator_mini.lam`). Дефект **не создан** 0043, но экспорт делает его
  видимым: выгрузка была бы неоднозначной, а круговой рейс — «согласованным, но
  неверным». → В 0043: **не чинить** (правка ключа задевает `c_header.rs:685` и
  цель `c-hal`), а задокументировать в контракте формата и зафиксировать тестом
  текущее поведение; отдельный кандидат на квалификацию ключа.
- **Р3. Пересечение с 0042** (низкий, разобрано выше). → R7.

  'compile' или 'fmt'» (475–481). То есть `lamc address-map …` сегодня падает —
  **имя свободно**, и его занятие ничего не отнимает (обратная совместимость).
- **Флаги `compile`** (`parse_compile_args`, 162–252): `-t/--target` (176),
  `-o/--output` (183), `-I/--include-dirs` (190) + слитная форма `-I<путь>` (198),
  `-v/--verbose` (201), `-q/--quiet` (204), `--guard-enable`/`--guard-disable`
  (207/210), `--address-map` (213). Взаимоисключение `-v`/`-q` — 232.
- **Цели:** `c` (588), `c-hal` (552), `plantuml` (622); неизвестная → выход с
  кодом 1 (649).
- **Разбор внешней карты уже написан и живёт в `main`** (506–530): чтение файла,
  `grammar::parse_address_map`, печать `AM-*` и `process::exit(1)`. Пере-использовать
  его подкоманде **нельзя без выноса** — он вшит в тело `main`. Отсюда action item
  ADR про дублирование разбора.
- **Прецедент формы:** `fmt` — уже подкоманда, не являющаяся компиляцией; у неё
  свой `parse_fmt_args` (274) с юнит-тестами рядом (666–707) и свой
  исполнитель `run_fmt` (321), возвращающий код процесса. Это образец для
  `address-map` (ADR, обоснование формы CLI п. 2).
- **Диагностики сейчас идут в stderr** (`eprintln!` везде), stdout занят только
  выводом `fmt --stdin` (337). Для машиночитаемой выгрузки это **удачно**: канал
  свободен (R9).
- **Замечено попутно (не чинится здесь):** сообщение о неизвестной цели (651)
  гласит «Поддерживается: c, plantuml» — цель **`c-hal` пропущена**. Мелкий
  дефект справки, оставшийся от 0020; вынесен кандидатом в анализе.

#### Что сделано

> **Планируется (разработка не начата).** Ниже — план задачи по ADR и
> анализу; заполняется фактом по мере реализации.

1. **Подкоманда** (R1) — `lamc address-map [-I …] [--address-map FILE]
   [--emit map|json] [-o FILE] <input.lam>`; диспетчеризация в `main` рядом с
   `fmt` (462) и `compile` (474). Форма выбрана ADR (подкоманда, **не** флаг
   `compile --emit-address-map`): экспорт не порождает целевой код, у `compile`
   вид результата уже выбирается `-t`, и ортогональный `--emit` создал бы
   бессмысленную матрицу (`-t c --emit json`).

2. **`parse_address_map_args`** — по образцу `parse_fmt_args` (274), с
   юнит-тестами в том же модуле (образец — 666–707). Флаги: `-I` (включая
   слитную форму), `--address-map`, `--emit` (по умолчанию `map`), `-o`,
   `-q`/`-v`. **Не** брать `-t` и `--guard-*` — подкоманде они бессмысленны.

3. **Вынести общий разбор** (ADR, action item; риск Р4) — чтение и разбор
   внешней карты сейчас вшиты в `main` (506–530). Вынести в функцию, вызываемую
   и `compile`, и `address-map`; поведение `compile` при этом обязано остаться
   **точно прежним** (те же коды `AM-*`, тот же выход 1). Также переиспользовать
   `split_include_dirs` (105).

4. **Исполнитель `run_address_map`** — возвращает код процесса (как `run_fmt`,
   321): разбирает исходник, строит модель, зовёт `resolve_addresses`
   (`address_map.rs:409`), затем эмиттер из 0043-01/0043-02.

5. **Разделение каналов** (R9) — выгрузка **только в stdout** (или в файл при
   `-o`), диагностики SE-050/051/052 и `AM-*` — **только в stderr**. Инвариант:
   stdout обязан целиком разбираться `parse_address_map` даже при наличии
   предупреждений (T16) — иначе круговой рейс ломается на любой модели с
   наложением.

6. **Коды возврата** — `0` — успех; `1` — ошибка (в т. ч. **SE-052**: достижимый
   порт без адреса, как в `c-hal`; неизвестный `--emit`; битая входная карта).
   Неизвестный формат обязан дать **внятную ошибку**, а не пустой вывод (К4):
   `--emit svd` — вероятный запрос, а SVD отклонён ADR.

7. **Справка** (`print_usage`, 417) — добавить подкоманду `address-map`, её флаги
   и примеры. свод: синхронизировать `README.md`.

## Тест-план

### Область и цель

Проверяем, что выгрузка карты адресов **соответствует факту** (тем адресам, что
разрешает `resolve_addresses` и потребляет `-t c-hal`), что формат `map`
**замыкается** через `--address-map`, что `json` — валиден и полон, и что
поведение на краях (порт без адреса, неизвестный формат, наложение) определено.

Фича **не меняет язык** (версия 0.2.0), поэтому свод применяется к
**формату выгрузки** как к языку интерфейса: примеры и контрпримеры ниже — это
модели и ожидаемые выгрузки, они же идут в документацию по формату.

Покрытие требований анализа: R1–R11; критерии A1–A10.

### Примеры и контрпримеры

#### Примеры (должны выгружаться корректно)

- **П1 — три источника и наложение** (основа T2–T5, воспроизведена пробой
  2026-07-15). Фикстура `tests/data/address_export/probe.lam`:

  ```lam
  type u8 = [bit;8];
  in  BTN: u8 := 0x00200000;
  out LED: bit;
  in  SW:  bit := 0x00300000:3;
  address LED = 0x00200004;
  start Idle { ref On: BTN; }
  state On { ref Idle: SW; }
  ```

  плюс карта `plat.map`:

  ```text
  // оверлей платформы
  BTN = 0x40000000;
  ```

  Ожидаемая выгрузка `--emit map` (`BTN` — из карты, `LED` — из оператора
  `address`, `SW` — inline с битом):

  ```text
  BTN = 0x40000000;
  LED = 0x00200004;
  SW = 0x00300000:3;
  ```

  Сверка с фактом (T9): при `-t c-hal` та же модель и карта дают
  `[PROBE_BTN] = { 0x40000000u, -1, 1 }`, `[PROBE_LED] = { 0x200004u, -1, 4 }`,
  `[PROBE_SW] = { 0x300000u, 3, 4 }` — адреса и биты обязаны совпасть.

- **П2 — полная карта на реальном примере.** `examples/elevator_mini.lam`
  (44 порта) + карта, покрывающая все порты: выгрузка содержит ровно 44 записи;
  круговой рейс замыкается (T20).

- **П3 — `json` полон.** Та же П1 в `--emit json`: на каждый порт — имя, адрес,
  бит (пусто для `LED`/`BTN`), источник (`External`/`Operator`/`Inline`), тип,
  направление; плюс версия формата.

- **К1 — достижимый порт без адреса** (T15). `examples/elevator_mini.lam` без

Реализована подкоманда `lamc address-map --emit map|json`: выгружает

поставляется (решение ADR) — `--emit svd` даёт внятную ошибку.

### Примеры и контрпримеры (формат — свод)

- **П1** (`probe.lam` + `plat.map`) — выгрузка `map`:

  ```
  LED = 0x00200004;
  SW = 0x00300000:3;
  ```
  сверена пробой с таблицей `c-hal`: `PROBE_BTN=0x40000000`, `PROBE_LED=0x200004`,

- **П3** — та же модель в `json`: на каждый порт имя/тип/направление/адрес/бит/
  источник + `format`/`format_version`.
- **К2** (`dead_port.lam`) — `DEAD` без адреса: в `map` **нет** записи и `0x0` не

  им данных».

  записываются в новое поле `AddressResolution::address_less` там же.

## Итог (что сделано)

Подкоманда **`lamc address-map --emit map|json`** выгружает фактически
разрешённую карту адресов портов наружу (фича закрыта, `precheck.sh` EXIT=0).

**Крейт `grammar`** (язык не менялся, 0.2.0; крейт — минорный бамп **0.5.0 →
0.6.0**, добавлен публичный API):

- **`address_map/resolve.rs`** — `ResolvedAddress` обогащён `ty`/`direction`
  (заполняются тем же обходом `resolve_model`, второго прохода нет); мёртвые
  порты пишутся в новое `AddressResolution::address_less` (для выгрузки `json`).
- **`address_map/export.rs`** — эмиттеры: `export_address_map` (формат `map`,
  `{:#010x}`, сортировка по имени, порт без адреса **опускается** — `0x0` не
  эмитится), `export_map_entries` (второе плечо кругового рейса, общий печатник),
  `export_address_map_json` (версионированный JSON: имя/тип/направление/адрес/бит/
  источник; мёртвый порт — `"address": null`). JSON печатается **вручную** — не
  тянет `serde_json` в принятый по умолчанию `lamc`.
- **`address_map/export_cli.rs`** — CLI-обвязка (`run_export_subcommand`): разбор
  флагов, разрешение адресов (как `-t c-hal`), печать. Вынесена сюда, а не в
  `bin/lamc.rs`: тот пришпилен к baseline размера — в бинарнике **тонкий
  диспетчер**. `split_include_dirs` переехал в библиотеку (нужен и обвязке);
  baseline `lamc.rs` понижён 2039 → 2009.

**Форматы и контракты:**

- `map` — тот же `.ld`-синтаксис, что читает `--address-map`: **круговой рейс**
  `export → parse → export` байт-в-байт (R4). Источник после реимпорта — `external`
  (семантика наложения).
- `json` — версионирован (`format_version`), перечень источников **открыт** (R7:
  потребитель терпит незнакомое). Плоский ключ карты (Р2) задокументирован, не
  чинится (правка задевает `c-hal`).
- Приоритет источников (inline `<` `address` `<` внешняя карта) наследуется от
  ядра 0020; сверено с таблицей `__ADDR[]` цели `c-hal` (T9).
- **CMSIS-SVD не поставляется** (ADR): `--emit svd` → внятная ошибка.
- `SE-052` (достижимый порт без адреса) обрывает экспорт; предупреждения — в
  stderr, stdout — чистая выгрузка.
