# Фича: Запись реестра диагностик называет смысл

- **Номер:** 0311
- **Статус:** ГОТОВО
- **Зависит от:** 0290 (закрыта; проставлено на стадии анализа 2026-08-20)
- **Связанные issue (анализ):** кандидат блока 2 `FEATURES.md` — «Разбор ошибок
  приложения покрывает 99 кодов из 264, и полнота не контролируется»

## Стадии жизненного цикла (правило 17)

Все стадии — **разделы этой карточки** (правило 32): «Архитектура (ADR)»,
«Анализ», «Разработка», «Тест-план», «Отчёт о тестировании», «Итог».
Отдельным артефактом остаются только исправления —
[`docs/fixes/`](../fixes/README.md) (при необходимости `0311-YY-*`).

## Краткое описание

Разбор с примером есть у 83 кодов из 229 — для остальных реестр
`docs/diagnostics/README.md` единственное объяснение. Десять его записей
объяснением не были: «ошибка», «предупреждение», имя конструкции. Записи
переписаны по коду эмиссии, а проверка запрещает заводить новые.

> Фича зарегистрирована из блока кандидатов `FEATURES.md`; предмет
> переформулирован — см. «Итог».

## Документирование (правило 24)

**Не требуется** для языковых разделов: правится справочник кодов
(`docs/diagnostics/`), а не описание языка. Сводная таблица приложения
«Ошибки» не задета — её сверяет проверка, и он остался зелёным.

## Архитектура (ADR)

- **Статус:** Accepted
- **Дата:** 2026-08-20
- **Фича:** [../features/0311-diagnostic-descriptions.md](0311-diagnostic-descriptions.md)

### Контекст

У кода диагностики есть **три** места, где он объясняется:

1. текст самого сообщения (его пишет инструмент);
2. реестр `docs/diagnostics/README.md` — колонка «Значение»;
3. приложение «Ошибки» документа: сводная таблица (сверяется проверкой) и
   **разбор с примером** — он есть не у каждого кода.

Замер-20: разбор имеют **83 кода из 229**. Значит для 146 кодов реестр
и сводная таблица — единственное объяснение. И там нашлось **десять** записей,
не объясняющих ничего:

| Код | Описание в реестре |
|---|---|
| `DF-001`…`DF-003` | «ошибка» |
| `DF-004`, `CS-001` | «предупреждение» |
| `FM-001` | «ошибка» |
| `AM-001` | «ожидалось имя порта» (текст сообщения, не смысл) |
| `ST-004` | «оператор address» |
| `SV-005` | «`extern fn`» |
| `SV-006` | «`inout`» |

Слово «ошибка» повторяет то, что видно по колонке кода: справочник, в который
заглянули за смыслом, отвечает тавтологией.

### Решение

1. Десять записей получают описания, снятые **с кода эмиссии** (что именно не
   так у автора и что с этим делать).
2. Проверка `scripts/check-diagnostic-descriptions.py` с самопроверкой и контролем
   `test-diagnostic-descriptions.sh`, шаг предкоммита. Два класса:
   - **D1** — описание есть служебное слово («ошибка», «предупреждение»,
     «отказ»): отвергается **всегда**, исключений нет;
   - **D2** — описание короче 25 символов: отвергается, если кода нет в
     `scripts/diagnostic-description-baseline.txt`.
3. Реестр долга — ратчет: **D3** ловит протухшую запись (описание выросло либо
   код исчез).

### Почему D2 — ратчет, а не запрет

Короткое ≠ плохое: «Модель не найдена» объясняет исчерпывающе, а раздувание
ради длины дало бы шум. Замер: таких записей 15, все осмысленны. Ратчет
фиксирует их и запрещает **новые**.

Служебное слово в долг не вносится никогда — на это стоит отдельная проверка
контроля (условие 3): узаконить «ошибку» значило бы отменить предмет фичи.

### Отвергнутые варианты

1. **Требовать разбор с примером для каждого кода.** Какие коды заслуживают
   разбора — решение о **пользе**, а не о согласованности (это и вывело разбор
   из объёма 0290). Механический запрет заставил бы писать 146 разделов, из
   которых большинство повторяло бы одну строку.
2. **Сверять описание реестра с текстом сообщения в коде.** Тексты
   параметризованы (`формат!` с подстановками) и пишутся для другого места;
   сверка ловила бы расхождение формулировок, а не отсутствие смысла.
3. **Порог длины без ратчета.** Уронил бы проверка на пятнадцати законных записях.

### Последствия

- Справочник отвечает на вопрос «что это значит» для всех 229 кодов.
- Новая безликая запись невозможна: класс D1 без исключений.

## Анализ

### Цель и контекст

Разбор с примером есть у 83 кодов из 229 — для остальных реестр единственное
объяснение, и десять его записей объяснением не были («ошибка»,
«предупреждение», имя конструкции).

### Зависимости фичи (правило 17/19)

- **Зависит от:** 0290 (проверка сводной таблицы) — он и вывел разбор из объёма
  сверки, назвав причину: какие коды заслуживают разбора, машине неизвестно.
- **Влияние на порядок разработки:** закрывает кандидата «Разбор ошибок
  приложения покрывает 99 кодов из 264, и полнота не контролируется» — **не тем**,
  что разбирает все, а тем, что требует смысла там, где разбора нет.

### Требования и проверяемые условия

- **R1.** Десять безликих записей получили описания по коду эмиссии.
- **R2.** Класс D1 (служебное слово) — без исключений, долгом не покрывается.
- **R3.** Класс D2 (короткое) — ратчет по реестру долга.
- **R4.** Класс D3 ловит протухшую запись долга.
- **R5.** Пустой реестр — вырожденная проверка, а не успех.
- **R6.** Проверка с самопроверкой стоит в предкоммите.

### Разбор

#### Почему кандидат переформулирован

Он предлагал «список тех, у кого разбор обязан быть». Замер показал, что это
решение о **пользе** и машине оно недоступно: список пришлось бы вести руками,
и он разошёлся бы с документом. Проверяемая часть того
же беспокойства — «справочник обязан отвечать на вопрос», и она формулируется
без списка.

#### Порог длины

25 символов — не свойство языка, а граница, отделяющая описание от ярлыка.
Проверено на реестре: ниже неё оказались 15 записей, все — краткие, но
осмысленные, и все занесены в долг. Ни одна запись сверх порога находкой не
стала.

### Риски

- **Порог может раздражать** при новой краткой записи. Ответ — долг: запись
  вносится решением человека, а не молча.

## Разработка

### Задача

#### Состав правки

| Файл | Что сделано |
|---|---|
| `docs/diagnostics/README.md` | десять записей получили описания (`DF-001`…`DF-004`, `CS-001`, `FM-001`, `AM-001`, `ST-004`, `SV-005`, `SV-006`) |
| `scripts/check-diagnostic-descriptions.py` | проверка: классы D1 (служебное слово), D2 (короткое вне долга), D3 (протухший долг); самопроверка |
| `scripts/diagnostic-description-baseline.txt` | узаконенный долг — 15 кратких, но осмысленных записей |
| `scripts/test-diagnostic-descriptions.sh` | контроль проверки: 7 условий на копии дерева (`DD_ROOT`) |
| `scripts/precheck.sh` | шаг рядом с проверкой |

#### Откуда взяты описания

Каждое снято **с кода эмиссии**, а не придумано: `DF-001` — из двух ветвей
`address_map/env.rs` (нет `=`; недопустимое имя символа), `DF-003` — из
комментария о симметрии с `AM-006`, `SV-006` — из текста отказа про третье
состояние.

#### Проверено

- `sh scripts/test-diagnostic-descriptions.sh` — 7/7.
- `python3 scripts/check-diagnostic-descriptions.py` — 229 записей, долга 15.
- `python3 scripts/check-book-diagnostics.py` — 265 кодов сверены (проверка не
  задет).

## Тест-план

### Условия

| # | Условие | Проверка |
|---|---|---|
| П1 | Годный реестр принимается | `test-diagnostic-descriptions.sh` (1) |
| П2 | Служебное слово ловится (D1) | там же (2) |
| П3 | **Долг не покрывает служебное слово** | там же (3) |
| П4 | Короткое описание ловится и покрывается долгом (D2) | там же (4) |
| П5 | Протухшая запись долга ловится (D3) | там же (5) |
| П6 | Пустой реестр — вырожденная проверка | там же (6) |
| П7 | Самопроверка проверки проходит | там же (7) |
| П8 | Рабочий реестр зелёный | `check-diagnostic-descriptions.py` |
| П9 | Проверка не задет | `check-book-diagnostics.py` |
| П10 | Предкоммит | `./scripts/precheck.sh` |

### Почему тесты именно такие

- **П3 — главное условие фичи:** узаконить «ошибку» долгом значило бы отменить
  её предмет. Без этой проверки класс D1 держался бы на дисциплине.
- **П6:** проверка, у которого нечего проверять, обязан падать, а не рапортовать
  об успехе (класс исправления и урок).
- **Контроль работает на копии дерева** (`DD_ROOT`): проверка рабочих файлов
  ничего не доказывает про поведение проверки на плохом входе.

### Что показал прогон

1. **Предмет кандидата пришлось переформулировать.** «Разобрать нужные коды» —
   решение о пользе; проверяемая часть — «справочник обязан отвечать».
2. **Безликих записей два вида, а не один.** Кроме служебных слов нашлись
   ярлыки — имя конструкции (`inout`, `extern fn`) вместо объяснения, почему
   она не переводится. Первый вид ловится машиной, второй нашёлся глазами при
   чтении коротких записей.
3. **Отдельное условие «долг не покрывает служебное слово»** появилось потому,
   что первая редакция проверки проверяла D1 **после** долга — и «ошибка»,
   внесённая в реестр долга, прошла бы.
