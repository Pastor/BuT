## Краткое описание

Описать **стиль оформления кода на Takt** — так, как PEP 8 описывает стиль
Python: отступы, переносы, расстановка скобок и пробелов, порядок элементов
модели, именование, комментарии. Заказчик предлагает взять за отправную точку
**K&R** (язык си-подобный) и скорректировать под Takt.

> Фича зарегистрирована **по запросу заказчика 2026-08-02**; он же намерен
> скорректировать содержание свода по существу. Далее проходит жизненный цикл
> по своду.

## Что известно на входе

Проверено чтением кода и корпуса 2026-08-02.

1. **Канон уже существует — в виде программы, а не текста.** [канонический форматтер.lam (lamc fmt)](0024-lam-formatter.md) закрыта: `taktc fmt` приводит `.takt` к
   канонической форме, `taktc fmt --check` контролирует её в предкоммите по всему
   `examples/`. То есть правила де-факто **уже действуют**, но нигде не описаны
   словами — прочитать их можно только по выводу форматтера или по коду
   `takt-lang/src/format/`.
2. **Наблюдаемая форма уже близка к K&R:** открывающая скобка на той же строке
   (`model Regulator {`), отступ 4 пробела, вложенные блоки со своим уровнем,
   `;` после операторов. То есть предложение заказчика, скорее всего, узаконит
   существующее, а не сменит его.
3. **Раздела о стиле в документе нет.** `book/src/` содержит разделы 01–20
   (лексика, типы, модели, … практический пример), раздела об оформлении среди
   них нет.
4. **Форматтер намеренно не канонизирует синонимы:** `while`/`loop` и
   `: [Guard] x;` / `: x;` сохраняются как написал автор (`ast::LoopKeyword`,
   `Guard::explicit`). Свод обязан либо объяснить этот выбор, либо предложить
   его пересмотр — умолчать нельзя, это видимая пользователю непоследовательность.

## Направление решения (наметка, не решение)

Главный вопрос — **кто источник истины**, и он должен быть решён ADR до того,
как будет написана первая строка свода:

- **Свод описывает форматтер.** Тогда работа — прочитать `format/` и корпус и
  изложить действующие правила; расхождение текста и `fmt` будет дефектом
  текста. Дёшево, но лишает заказчика возможности изменить стиль.
- **Свод предписывает, форматтер приводится в соответствие.** Тогда часть
  правил K&R, которых `fmt` сегодня не соблюдает, потребует правок форматтера —
  и **дифф всего корпуса** `examples/` вместе с фикстурами тестов, завязанными
  на позиции.

Двух источников истины быть не должно: свод, расходящийся с `taktc fmt`, хуже
отсутствия свода — он обещает то, чего инструмент не делает. Механическая
сверка «текст ↔ поведение» невозможна, значит связь придётся держать
дисциплиной и примерами, которые прогоняются проверкой документа.

свод: раздел документа описывает **язык**, без номеров фич и деталей
реализации. Место раздела в `book/src/main.typ` определяет ADR; по своду
раздел нуждается в функциональном примере, по своду — в блоке типичных
ошибок.

Окончательный выбор — за стадиями **архитектуры** (ADR) и **анализа**;
содержание свода по существу корректирует **заказчик**.

### Context

Заказчик просит описать стиль оформления кода на Takt «по типу PEP 8», взяв за
отправную точку K&R.

**Канон уже существует — но в виде программы, а не текста.** `taktc fmt`
приводит `.takt` к канонической форме, `taktc fmt --check` контролирует её в
предкоммите по всему `examples/`. Правила действуют, но прочитать их можно
только по выводу инструмента или по коду `takt-lang/src/format/`.

#### Что показала проба

Прогон `taktc fmt --stdin` на файле с нарочно сбитым оформлением:

```takt
model M {
start S { always { v := 1; } }
      var v: u8 := 0;
   const K := 3;
}
```

вернул

```takt
model M {
    start S {
        always {
            v := 1;
        }
    }
    var v: u8 := 0;
    const K := 3;
}
```

Отсюда три факта, определяющих форму работы:

1. **Предложение заказчика узаконивает существующее.** Наблюдаемый канон уже
   K&R-подобен: открывающая скобка на строке заголовка, отступ 4 пробела,
   тело блока — на своих строках, `;` завершает оператор.
2. **`fmt` разворачивает однострочные тела.** `start S { always { v := 1; } }`
   стал пятью строками — то есть «компактная» запись каноном не является.
3. **`fmt` Не трогает порядок элементов.** `start S` остался перед `var` и
   `const`, хотя в корпусе преобладает обратный порядок (объявления → состояния).

Факт 3 — главный: свод неизбежно содержит правила **разной силы**. Часть из них
инструмент исполняет сам и предкоммит стережёт; часть (порядок элементов,
именование, содержание комментариев, длина строки) не проверяет никто.

### Decision Drivers

1. **Двух источников истины быть не должно.** Свод, расходящийся с `taktc fmt`,
   хуже отсутствующего: он обещает то, чего инструмент не делает.
2. **Обещание должно быть исполнимым.** Проект трижды подряд закрывал дефекты
   этого класса (0201 — мёртвые слова в списках, 0202 — формат, обещанный
   документом и не выдаваемый инструментом, 0202-01 — сверка, ничего не
   сверявшая). Свод не должен стать четвёртым.
3. **Стоимость правки форматтера — дифф всего корпуса** и фикстур, завязанных
   на позиции.
4. **свод:** раздел описывает язык, без номеров фич и деталей реализации;
   свод требует блока типичных ошибок, свод: функционального
   примера; примеры раздела проходят проверка документа.

### Considered Options

#### Option A. Свод описывает форматтер

Истина — `taktc fmt`; текст излагает действующее поведение. Расхождение текста и
инструмента есть дефект **текста**.

**Pros:** код не меняется, корпус не сдвигается; свод верен по построению в день
написания; работа сводится к чтению `format/` и корпуса.
**Cons:** заказчик этой фичей стиль не меняет — для смены нужна отдельная фича;
связь «текст ↔ поведение» держится дисциплиной, машинной сверки нет.

#### Option B. Свод предписывает, форматтер приводится в соответствие

**Pros:** позволяет изменить стиль там, где он не нравится.
**Cons:** каждое расхождение даёт дифф всего `examples/` и фикстур; объём
непредсказуем до выбора правил; риск, что текст уедет вперёд инструмента и
временно окажется ложным.

#### Option C. Свод как отдельный документ вне `book/`

**Pros:** не трогает структуру документа.
**Cons:** нарушает (описание языка живёт только в `book/`) и заводит
второе место, где написано про язык.

### Decision

Принимается **Option A** — решение заказчика (2026-08-04).

**Форма свода — единый сплошной список правил** (решение заказчика). Архитектор
предлагал разделить его на два блока — «исполняет `taktc fmt`» и «остаётся на
авторе», — потому что факт 3 пробы делает разницу существенной; заказчик выбрал
форму PEP 8. Риск («читатель решит, что инструмент поддерживает всё
перечисленное») снимается **внутри** формулировок: там, где правило исполняет
форматтер, это сказано в самом предложении. Отдельных блоков и пометок не
заводится — свод остаётся сплошным.

**Синонимы объясняются, выбор остаётся автору** (решение заказчика). `while`/
`loop` и `: [Guard] x;` / `: x;` свод называет равноправными, объясняет уместность
каждого и советует держаться одного в пределах файла. АСД (`ast::LoopKeyword`,
`Guard::explicit`) хранит выбор автора именно ради этого — правок не требуется.

**Место раздела:** новый `book/src/21-code-style/` в блоке «Применение», последним
пунктом. Стиль — не описание языка, а способ им пользоваться, поэтому блок
«Описание языка» (01–16) не трогается; перенумеровывать существующие разделы
ради «правильного» места не станем — цена (все ссылки и пути) несопоставима с
пользой.

### Consequences

#### Положительные

- Действующий канон становится читаемым: его можно прочесть, а не выводить из
  поведения инструмента.
- Свод верен по построению: он описывает то, что уже проверяется предкоммитом.
- Примеры раздела проходят проверка документа — неверный пример не переживёт прогон.

#### Отрицательные / Action items

- **Машинной сверки «текст ↔ форматтер» нет и не будет** в этой фиче. Связь
  держится примерами и дисциплиной. Отсюда обязанность: фича, меняющая
  поведение `taktc fmt`, обязана проверить этот раздел — записать в живой
  контекст.
- Стиль этой фичей **не меняется**; если заказчику что-то в нём не нравится,
  нужна отдельная фича с правкой форматтера (Option B).
- Правила, которые инструмент не проверяет (порядок элементов, именование,
  комментарии), остаются советами. Формулировки обязаны это показывать, иначе
  свод пообещает несуществующее.

#### Acceptance criteria

1. Раздел `book/src/21-code-style/` заведён и подключён в `SUMMARY.md`.
2. Каждое правило о расстановке пробелов, отступов и скобок **проверено пробой**
   `taktc fmt` — текст не расходится с инструментом.
3. Правила, которые форматтер не исполняет, сформулированы как советы, и это
   видно из самой формулировки.
4. Синонимы `while`/`loop` и `[Guard]` объяснены, выбор оставлен автору.
5. Есть функциональный пример и блок типичных ошибок.
6. Примеры раздела проходят проверка документа (компиляция целью `c` + симуляция).
7. `./scripts/precheck.sh` — код возврата 0.

### Ограничения, определяющие форму

**О1. Каждое утверждение о расстановке — из пробы, а не из чтения кода.**
Свод, расходящийся с инструментом, хуже отсутствующего. Поэтому все правила о
скобках, пробелах, отступах и переносах получены прогоном `taktc fmt --stdin` на
нарочно сбитом входе, а не выведены из `format/`.

**О2. Правила, которые инструмент не исполняет, обязаны читаться как советы.**
Замер: `fmt` не трогает порядок элементов, именование, содержание комментариев и
длину строки. Заказчик выбрал единый список без деления на блоки — значит
различие несёт **сама формулировка** («форматтер порядок не меняет — он ваш»,
«инструмент имена не проверяет»).

**О3. Примеры раздела проходят проверка документа** (фича: компиляция целью `c`
+ прогон симулятора). Значит функциональный пример обязан быть самостоятельной
моделью, а не фрагментом.

**О4. Эмодзи в `book/` недопустимы** — шрифт документа их не содержит, и проверка
символов  их ловит.

## Разработка

### Задача 0197-01

#### Что было

Канон оформления существовал **в виде программы**: `taktc fmt` приводил `.takt`
к нему, предкоммит сторожил по всему корпусу, но прочитать правила словами было
негде — только по выводу инструмента или по коду `takt-lang/src/format/`.

#### Что сделано

Заведён `book/src/21-code-style/index.typ` и подключён в `SUMMARY.md` последним
пунктом блока «Применение».

Свод описывает: отступы и скобки, пробелы, пустые строки, порядок элементов
модели, именование, комментарии, равноправные написания, длину строки. Плюс
функциональный пример (правило 27) и блок типичных ошибок (правило 26).

Форма — **единый сплошной список** (решение заказчика). Различие между тем, что
исполняет форматтер, и тем, что остаётся автору, несёт сама формулировка:
«это делает `taktc fmt`» против «форматтер порядок не меняет — он ваш».

#### Что дала проба, а не чтение кода

Каждое правило о расстановке получено прогоном `taktc fmt --stdin` на нарочно
сбитом входе. Три факта, которые чтением `format/` я бы не получил или получил
неверно:

1. **`else` начинается с новой строки** — Takt здесь расходится с K&R, который
   заказчик назвал отправной точкой. Свод называет это отступление прямо.
2. **Однострочное тело разворачивается.** `start S { always { v := 1; } }`
   форматтер превращает в пять строк: компактная запись каноном не является.
3. **Хвостовые комментарии по колонке не выравниваются** — между оператором и
   `//` всегда один пробел.

Факт 3 найден **отказом собственного примера**: первая редакция раздела
выравнивала комментарии столбиком, и `fmt --check` её отверг. То есть свод о
стиле нарушал стиль, который описывает. Правило дописано, пример исправлен.

#### Проверки

- Все шесть блоков ```takt извлечены и прогнаны через `fmt --check`: три
  самостоятельных — каноничны, три фрагмента (не разбираются отдельно)
  проверены прямой пробой.
- Функциональный пример: `taktc compile -t c` — успешно, `takt-sim -n 10` —
  успешно.
- `./scripts/precheck.sh` — код возврата 0 (включая проверка примеров документа и

### Выводы и дальнейшие шаги

1. **Предложение заказчика узаконило существующее — но не целиком.** K&R был
   назван отправной точкой, и наблюдаемый канон к нему действительно близок. Три
   отступления, найденных пробой, свод называет прямо:
   - **`else` начинается с новой строки**, а не `} else {`;
   - **однострочное тело разворачивается** — компактная запись каноном не является;
   - **хвостовые комментарии не выравниваются по колонке**.

2. **Свод о стиле нарушил стиль, который описывает.** Первая редакция раздела
   выравнивала комментарии столбиком; `fmt --check` её отверг. Отсюда и найдено
   третье отступление — правило, которого в тексте не было. Урок общий:
   документ, описывающий поведение инструмента, обязан прогоняться этим
   инструментом; чтения кода недостаточно.

3. **Форма свода — решение заказчика, и риск принят осознанно.** Архитектор
   предлагал разделить правила на «исполняет `fmt`» и «остаётся на авторе»,
   потому что замер показал: порядок элементов, именование и комментарии
   инструмент не трогает. Заказчик выбрал единый список в духе PEP 8. Риск
   («читатель решит, что поддерживается всё перечисленное» — тот же класс, что
   закрывали 0201 и 0202) снят внутри формулировок, отдельных блоков не
   заведено.

4. **Машинной сверки «текст ↔ форматтер» нет и не будет** (решение ADR): её
   невозможно построить в общем виде. Связь держится примерами, которые
   прогоняет проверка документа, и дисциплиной. Отсюда обязанность, внесённая в
   живой контекст: фича, меняющая поведение `taktc fmt`, обязана проверить этот
   раздел.

5. **Стиль этой фичей не менялся.** Если заказчику что-то в нём не нравится
   (например, `else` на своей строке), нужна отдельная фича с правкой
   форматтера — она даст дифф всего корпуса и фикстур.

Исправления (`docs/fixes/`) не требуются.

Заведён раздел [`book/src/21-code-style/`](../../book/src/21-code-style/index.typ)

**Предложение заказчика узаконило существующее — но не целиком.** K&R назван
отправной точкой, и канон к нему близок; проба нашла **три** отступления, и свод
называет их прямо:

| Отступление от K&R | Как в Takt |
|---|---|
| ~~`} else {`~~ | ~~**`else` с новой строки**~~ — **снято** исправлением [канон стиля — K&R `else`, заглавные имена `cond`/`invariant`, перечисление по варианту на строке](../fixes/0197-01-kr-else-cond-case-enum-lines.md): канон приведён к K&R (`} else {`, цепочка `} else if c {`) |
| компактное тело в одну строку | **разворачивается** форматтером |
| выравнивание хвостовых комментариев | **не выравниваются**, всегда один пробел |

**Третье отступление найдено отказом собственного примера.** Первая редакция
раздела выравнивала комментарии столбиком, и `fmt --check` её отверг: свод о
стиле нарушал стиль, который описывает. Правило дописано, пример исправлен.
Урок: документ о поведении инструмента обязан прогоняться этим инструментом.

**Форма свода — решение заказчика.** Архитектор предлагал разделить правила
на «исполняет `fmt`» и «остаётся автору» (замер: порядок элементов, именование и
комментарии инструмент не трогает); заказчик выбрал единый список в духе PEP 8.
Риск того же класса, что закрывали 0201 и 0202, снят внутри формулировок.

**Стиль этой фичей не менялся.** Смена любого правила требует отдельной фичи
с правкой форматтера — она даст дифф всего корпуса и фикстур. Предсказание
сбылось: исправление
[канон стиля — K&R `else`, заглавные имена `cond`/`invariant`, перечисление по варианту на строке](../fixes/0197-01-kr-else-cond-case-enum-lines.md) сменил **три**
правила по требованию заказчика (K&R `else`, `UpperCamelCase` для
`cond`/`invariant`, перечисление по варианту на строке) — и стоил правки
форматтера, слоя стиля, корпуса, фикстур и Takt-примеров внутри Rust.
