# Фича: Приведение q из поля структуры масштабируется

- **Номер:** 0371
- **Статус:** ГОТОВО
- **Зависит от:** нет (0061, 0349, 0358, 0370 закрыты)
- **Связанные issue (анализ):** кандидат, заведённый закрытием
  [понижение q-литерала доходит до полей структуры](0370-struct-field-fixed.md)

## Стадии жизненного цикла (правило 17)

Все стадии — **разделы этой карточки** (правило 32): «Архитектура (ADR)»,
«Анализ», «Разработка», «Тест-план», «Отчёт о тестировании», «Итог».
Отдельным артефактом остаются только исправления —
[`docs/fixes/`](../fixes/README.md) (при необходимости `0371-YY-*`).

## Краткое описание

Замер-21 на `one := g.kp as u8;` при `struct Gains { kp: q(8, 8), … }`
и `g.kp = 1.5`:

| Потребитель | Печать | Значение |
|---|---|---|
| эталон | — | **1** |
| `c`, `c-hal` | `(uint8_t)model->g.kp` | **128** |
| `rust` | `self.g.kp as u8` | **128** |
| `sv`, `sv-mmio` | `8'(…g.kp)` | **128** |
| `st`, `st-at` | `INT_TO_USINT(g.kp)` | **128** |

Все четыре цели теряли **масштабирование** (деление на 2ⁿ), и все — молча, при
нулевом коде возврата `taktc`. На выражении над полями (`(g.kp + g.ki) as u8`)
цель `st` вдобавок отказывала `ST-011`.

Контроль: та же запись **над переменной** (`(a + b) as u8`) печатается
верно у всех целей — тип терялся именно у поля.

## Документирование (правило 24)

**Не требуется** — язык не меняется: запись законна и исполняется эталоном;
правится вывод типа операнда у четырёх целей и в семантике.

- **Status:** Accepted
- **Date:** 2026-08-21
- **Authors:** Архитектор + лид разработки
- **Related issues:** [Фича](0371-fixed-cast-from-field.md);

### Context

Масштабирование при приведении `q → целое` цель применяет, **только когда
знает**, что тип операнда — `q(m, n)`. Вывод этого типа у каждой цели свой:
`c` зовёт семантический `extract_type`, `rust` и `sv` — собственные
`expression_type`/`fixed_format`, `st` — `inner_expr_type`.

Ни один из них не выводил тип **поля структуры**: `extract_type` отвечал на
`BitAccess` `Unsupported`, у `rust` поле давало `None` (граница названа фичей), у `sv` ветви поля не было вовсе, а `st` знал поле только в
`inner_expr_type_in` (0349) — и та функция в q-пути не звалась.

### Decision Drivers

1. **Молчаливое расхождение значений — самый дорогой класс.** Здесь оно у
   четырёх целей сразу.
2. **Тип поля объявлен рядом** — догадываться не о чем.
3. **Правила округления не трогаются:** носитель прежний (0061), правится
   только вывод типа операнда.

### Considered Options

#### Option A. Научить типу поля семантический `extract_type` и вывод каждой цели

**Pros:**
- Цель `c` чинится сразу (она зовёт семантику).
- У остальных правка сводится к «спросить тип с оглядкой на модель», а
  объявления структур у них уже есть (`Scope.model` у `rust`,
  `Scope.structs` у `sv`, `ModelNode` у `st`).

**Cons:**
- Правка в четырёх местах плюс семантика.

#### Option B. Только семантика

**Pros:** одно место.

**Cons:** `rust`, `sv` и `st` семантический вывод не зовут — правка их не
починит. Проверено прогоном.

#### Option C. Отказ целей на приведении из поля

**Pros:** громче молчания.

**Cons:** запись исполняет эталон и переводят все цели — отказ сузил бы язык
без нужды.

### Decision

Принимается **Option A**:

- `semantic::type_inference::extract_type` выводит тип **поля структуры**
  (`BitAccess` с `Member::Identifier`); доступ к разряду не трогается — его
  тип есть вопрос правила;
- `rust_fixed::fixed_format_in(expr, model)` и
  `sv_fixed::fixed_format_in(expr, structs)` — вывод с оглядкой на объявления;
- у цели `st` `fixed_format` принимает модель и спрашивает
  `inner_expr_type_in` (0349) вместо `inner_expr_type`.

### Consequences

#### Положительные

- Приведение из поля, из выражения над полями и из поля элемента массива
  масштабируется у всех четырёх целей.
- Побочно: цель `st` перестала отказывать `ST-011` на выражении над полями.

#### Отрицательные / Action items

- Вывод типа поля появился в **четырёх** местах (по одному на цель) плюс
  семантика: это следствие того, что у каждой цели свой вывод типа операнда.
  Сведение к одному носителю — отдельная работа, вынесена кандидатом.

#### Acceptance criteria

1. Инструменты всех целей принимают вывод.
2. Потактовая сверка с целью `c` совпадает на трёх формах: поле, выражение над
   полями, поле элемента массива.
3. Мутация «семантика без типа поля» роняет сверку.
4. Предкоммит зелёный; вывод корпуса не изменился.

## Разработка

### Задача

#### Что было

Масштабирование при `q → целое` применяется, только когда цель знает тип
операнда. Тип **поля структуры** не выводил никто: `extract_type` отвечал
`Unsupported`, у `rust` поле давало `None`, у `sv` ветви не было, а `st` знал
поле лишь в `inner_expr_type_in`, который в q-пути не звался.

#### Что сделано

**`takt-lang/src/semantic/type_inference.rs`** — `extract_type` выводит тип
поля структуры (`BitAccess` с `Member::Identifier`), разряд не трогает.
Этим чинится цель `c`: она зовёт семантику.

**`takt-lang/src/generator/rust/rust_fixed.rs`** — `fixed_format_in(expr,
model)`: собственный вывод, затем разбор с оглядкой на объявления (поле,
арифметика, скобки); `cast` и четыре вызова в `rust_expr` переведены на него.

**`takt-lang/src/generator/sv/sv_fixed.rs`** — то же с `Scope.structs`
(снимок карты), включая поле **элемента массива** (тип базы даёт
`sv_array::array_type_expr`).

**`takt-lang/src/generator/st/st_fixed.rs`** — `fixed_format` принимает модель
и спрашивает `inner_expr_type_in` (0349); `storage_of` тоже.

**Сверка**: `fixed_cast_from_field_matches_generated_c` — три формы (поле,
выражение над полями, поле элемента массива) с **разными** значениями.

**Одной правкой в семантике класс не закрывается:** `rust`, `sv` и `st`
семантический вывод не зовут — у каждого свой. Проверено прогоном после
первой правки.

#### Проверки

```sh
cargo test --test conformance fixed_cast_from_field
cargo test --test conformance   # 170
cargo test --test targets       # 391
cargo test -p takt-lang --lib   # 1108
for f in examples/*.takt; do scripts/probe.sh -n 1 "$f"; done   # корпус чист
./scripts/precheck.sh
```

Мутация «семантика без типа поля» — сверка красная («расхождение one»).

### Выводы и дальнейшие шаги

- **Класс был у четырёх целей сразу и молчал у всех.** Ни один инструмент его
  не видит: вывод валиден, значение неверно — 128 против 1. Ровно тот случай,
  ради которого заведены потактовые сверки.
- **Одной правки в семантике мало:** `rust`, `sv` и `st` семантический вывод
  типа не зовут — у каждого свой. Это и есть корень того, что класс дожил.
- **Кандидат:** вывод типа операнда живёт **четырьмя** носителями (по одному
  на цель) плюс семантика; их сведение к одному — отдельная работа, и она
  сняла бы целый класс подобных расхождений.
- Исправлений (`docs/fixes/`) не потребовалось.

## Итог (что сделано)

- Приведение `q → целое` из поля структуры, из выражения над полями и из поля
  элемента массива **масштабируется** у всех четырёх целей.
- **Класс был у четырёх целей сразу и молчал у всех:** вывод валиден,
  значение неверно (128 против 1). Вердикт дала только потактовая сверка.
- **Одной правки в семантике мало:** тип операнда выводят четыре носителя, и
  каждый пришлось научить полю. Их сведение вынесено кандидатом.
- Доступ к разряду (`x.N`) не трогался — его тип есть вопрос правила.
- Побочно снят отказ `ST-011` на выражении над полями; вывод корпуса не
  изменился.
