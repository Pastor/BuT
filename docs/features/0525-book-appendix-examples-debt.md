- **Статус:** ГОТОВО

- **Связанные issue (анализ):** долг проверки (две записи ратчета)

## Стадии жизненного цикла (правило 17)

Все стадии — **разделы этой карточки** (правило 32). Исправлений нет.

## Краткое описание

Проверка оставил две записи долга: разборы `SE-062` и `SY-005` показывали
предел вложенности **многоточием** («несколько десятков вложенных скобок»), и
проверить обещание было нечем. Замер показал, что настоящий вход умещается в
книгу: тридцать одна скобка для `SE-062` и девяносто шесть для `SY-005`. Оба
примера записаны целиком, долг проверки пуст.

## Документирование (правило 24)

Язык не меняется. В приложении два примера получили настоящий вход, а цитаты —
фактические координаты. Заодно исправлены **числа в прозе**: раздел обещал
`SY-005` при «вложенности в сотни», тогда как разбор отказывает уже на
восьмидесяти девяти.

## Архитектура (ADR)

- **Status:** Accepted
- **Date:** 2026-09-03
- **Authors:** редактор, разработчик

### Context

Приложение — место, куда автор приходит с кодом из вывода и повторяет пример.
Многоточие вместо входа делает разбор нечитаемым буквально: повторить его
нельзя, а проверка такую пару принять не может.

### Considered Options

1. **Оставить многоточие в долге.** Отвергнуто: ратчет — место для того, что
   пока нельзя сделать, а здесь замер показал, что можно.
2. **Вынести вход в файл рядом с приложением** (`#example(read(…))`). Отвергнуто:
   проверка читает блоки ```` ```takt ````, и пара просто исчезла бы из проверки —
   долг сменился бы слепым пятном.
3. **Записать вход целиком** (принято): одна строка для `SE-062`, шесть строк
   для `SY-005`.

### Decision

Пример показывает ровно тот вход, который даёт диагностику. Границы взяты
прогоном, а не из констант: `MAX_NESTING_DEPTH` и `MAX_PARSE_DEPTH` считаются по
узлам дерева, и число скобок с ними не совпадает.

### Consequences

Проверяемых пар стало 91 вместо 89, долг пуст. Побочно снята неточность прозы
про «сотни».

#### Acceptance criteria

- проверка зелёный при пустом ратчете;
- документ собирается; соседние проверки не затронуты.

## Анализ

### Замер (правило 30, 2026-09-03)

Границы сняты перебором на форме примера — скобки вокруг имени:

| Скобок | Ответ инструмента |
|---|---|
| ≤ 28 (тело) / ≤ 30 (условие ребра) | принимается |
| 29…88 (тело), 31…88 (условие) | `SE-062` — предел смысла (32 узла) |
| ≥ 89 | `SY-005` — предел разбора (96 узлов) |

Отсюда две правки прозы: «вложенность глубже трёх десятков» → «в три десятка»,
«вложенность в сотни» → «под сотню». Прежние формулировки читались как обещание,
которого инструмент не даёт.

Число скобок и предел из сообщения — **разные** величины: предел считается по
узлам дерева, поэтому условие ребра доходит до него на единицу позже
присваивания в теле. Это названо прямо в разборе — иначе читатель, отсчитав
тридцать две скобки, получил бы принятую программу.

### Требования и проверяемые условия

- П1: обе пары воспроизводятся, координаты цитат совпадают;
- П2: ратчет пуст;
- П3: соседние проверки книги не затронуты.

## Разработка

### Задача — `SE-062`

#### Что было
`ref S: ((((((( … ))))))) = 1;` — вход показан многоточием, цитата обещала
позицию `3:41`.

#### Что сделано
Тридцать одна скобка целиком, цитата с фактической позицией `3:43`, плюс фраза о
том, почему скобок не тридцать две.

### Задача — `SY-005`

#### Что было
`always { x := (((( … ))))1; }` и цитата с позицией `3:3017`.

#### Что сделано
Девяносто шесть скобок, разложенных по строкам (разбор к переносам
безразличен), цитата с фактической позицией `6:10`.
