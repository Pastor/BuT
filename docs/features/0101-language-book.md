### Context

У языка Takt нет отдельного справочного описания: сведения о синтаксисе и
семантике рассредоточены по `README.md`, `CLAUDE.md` (живой контекст для
разработки инструментов) и карточкам фич (артефакты процесса). Ни один из этих
источников не является **описанием языка для его пользователя**: `CLAUDE.md`
намеренно смешан с деталями реализации и номерами фич, `README` — обзорный.

Нужен документ, который: (1) описывает **только язык** (синтаксис, семантику,
модель исполнения, конструкции, примеры), (2) структурирован по разделам с
автонумерацией, (3) собирается из исходников скриптом, (4) поддерживается **в
актуальном состоянии вместе с языком**, (5) **не** содержит деталей процесса
разработки, номеров фич и внутренностей компилятора.

Референсы структуры: *The Rust Book*/*Rust Reference* (mdBook, разделы,
автонумерация), *Java Language Specification* (формальная: лексика → типы →
выражения → грамматика в приложении), *IEC 61131-3* и *IEEE 1800* (стандарты:
обзор → лексика → типы → конструкции → приложение с грамматикой).

> **(диаграмма PlantUML) неприменимо:** ADR не меняет синтаксис или
> семантику языка и потоки данных между компонентами — заводит **документ** и
> процессное правило.

### Decision Drivers

1. **Барьер входа для контрибьютора.** Наполнять разделы будут по одной фиче;
   формат должен быть простым для правки.
2. **Доступность результата.** Описание языка удобнее читать как искомый
   гипертекст, а не только PDF.
3. **Автонумерация и структура из исходников** (требование заказчика): порядок и
   номера разделов — свойство одного управляющего файла, а не ручная разметка.
4. **Каждый раздел — в своей папке** с примерами кода и ресурсами (требование
   заказчика).
5. **Единый скрипт сборки** (Makefile) и внешняя зависимость, не входящая в
   основной тулчейн Rust (документ собирается отдельно от `precheck.sh`).

### Considered Options

#### Option A. mdBook (Markdown)

Инструмент, на котором написана *The Rust Book*. Структура — `src/SUMMARY.md`
(оглавление + автонумерация), главы в Markdown, папка на раздел. Вывод — HTML с
поиском; PDF — вторично (плагины).

**Pros:** низкий барьер (Markdown); HTML с полнотекстовым поиском; автонумерация
из `SUMMARY.md`; де-факто стандарт для книг по языкам; папка на раздел с ресурсами
(`{{#include}}` для примеров кода).
**Cons:** качественный PDF требует плагина; меньше типографского контроля, чем у
Typst/LaTeX.

#### Option B. Typst

Проект уже использует Typst (`README.typ`). `#include` разделов, встроенная
автонумерация, качественный PDF.

**Pros:** единый с проектом тулчейн; отличная типографика; PDF из коробки.
**Cons:** HTML-экспорт незрел (Typst — PDF-ориентирован); для широкого доступа к
описанию языка HTML-поиск ценнее PDF.

#### Option C. AsciiDoc (Asciidoctor)

Мощный формат для больших технических книг/стандартов; HTML+PDF, includes,
нумерация из коробки.

**Pros:** зрелый и для HTML, и для PDF; богатые возможности.
**Cons:** тяжелее setup (Ruby/Java); синтаксис менее распространён среди
контрибьюторов, чем Markdown.

### Decision

Принимается **Option A (mdBook)** — решение заказчика (2026-07-24). Определяет
барьер входа (Markdown), доступный HTML с поиском и статус де-факто стандарта для
книг по языкам; автонумерация и «папка на раздел» реализуются штатно.

**Структура** (`book/`):

- `book.toml` — конфигурация (заголовок, автор, язык `ru`, **вывод PDF** — см.
  «Обновление решения»).
- `Makefile` — цели `build`/`check`/`clean`; зависимости задокументированы,
  не входят в `precheck.sh`.
- `src/SUMMARY.md` — **управляющий файл**: вводная часть (титул, введение,
  назначение) как prefix-главы, разделы под заголовком части (автонумерация),
  приложения. Порядок и номера — отсюда.
- `src/title.md`, `src/introduction.md`, `src/purpose.md` — вводная часть (титул +
  автор + общее описание; введение; назначение документа).
- `src/NN-slug/index.md` — **каждый раздел в своей папке**; рядом `examples/`
  (примеры на Takt), при необходимости `images/` и прочие ресурсы.
- `src/appendix-grammar/`, `src/appendix-references/`, `src/appendix-glossary/` —
  приложения (грамматика EBNF, **литература**, глоссарий).

**Состав разделов** (1–15): Обзор; Лексическая структура; Типы данных; Модели и
состояния; Выражения и условия; Управляющие конструкции; Функции; Порты и адреса;
Импорты и композиция; Именованные условия и блоки; Модель исполнения; Верификация
свойств; Цели генерации; Симуляция; Диагностики. Плюс приложения (грамматика,
литература, глоссарий). Обоснование состава — в [анализе](0101-language-book.md#анализ).

**Процессное правило.** Каждая фича, меняющая **язык**, обязана в
карточке иметь раздел **«Документирование»** с указанием затронутого раздела
`book/` и нужных изменений; документ поддерживается в актуальном состоянии вместе
с языком. **Каждый новый раздел документа — отдельная фича.** В документ **не**
попадают детали реализации, номера фич и процесс разработки.

### Consequences

#### Положительные

- У языка появляется единый пользовательский источник истины, отделённый от
  `CLAUDE.md` (реализация) и карточек фич (процесс).
- Структура и нумерация — свойство `SUMMARY.md`; добавление раздела локально.
- свод не даёт документу устареть: изменение языка тянет за собой правку
  раздела в той же фиче.

#### Отрицательные / Action items

- **Внешняя зависимость `mdbook`** — не входит в тулчейн; `precheck.sh` её **не**
  требует (сборка документа — отдельный `make -C book`). Возможный будущий проверка
  «документ собирается» — по установке mdBook в CI (кандидат).
- **Наполнение 15 разделов — отдельные фичи** (0101 заводит инфраструктуру + seed
  «Обзор» + приложения-заготовки).
- **Шаблон карточки** дополнен разделом «Документирование» — новые фичи получают
  его автоматически; у существующих незакрытых фич раздел добавляется по мере
  правки.

### Обновление решения (2026-07-24): вывод PDF, шрифт Fira Code

По требованию заказчика **вывод по умолчанию — PDF** (вместо HTML), шрифт **текста
и кода — Fira Code**. mdBook остаётся системой управления исходниками (Markdown,
`SUMMARY.md`, «папка на раздел», `{{#include}}` примеров), но HTML-генератор **не**
подключён; PDF порождается генератором **`mdbook-pandoc`** (профиль `pdf` в
`book.toml`): движок `xelatex`, `mainfont`/`monofont = "Fira Code"`, оглавление с
нумерацией. Драйвер 2 (HTML-поиск) тем самым **отменён** в пользу PDF —
осознанный выбор заказчика (формальный печатный спец-документ). Новые зависимости
сборки: `mdbook-pandoc`, `pandoc`, `xelatex` (TeX Live/MacTeX), установленный
шрифт Fira Code — все вне `precheck.sh`.

#### Acceptance criteria

1. Каталог `book/` содержит `book.toml`, `Makefile`, `src/SUMMARY.md`, вводную
   часть, seed-раздел «Обзор» с примером, приложения; структура «папка на раздел»
   соблюдена.
2. `make -C book build` собирает документ при установленном `mdbook` (иначе
   Makefile даёт понятную ошибку про зависимость).
3. Автонумерация разделов работает из `SUMMARY.md` (проверяется сборкой).
4. свод внесено в `docs/RULE.md`; шаблон карточки содержит «Документирование».
5. `check-links.py` зелёный (внутренние ссылки документа и на `book/` целы).

### Зависимости фичи

- **Зависит от:** нет. Инфраструктура самодостаточна.
- **Влияние на порядок:** порождает **пул фич-разделов** (наполнение разделов 2–15
  + приложений); каждая — отдельная фича по своду, приоритет расставит
  аналитик (базовые разделы «Лексика»/«Типы»/«Модели» логично раньше). свод вводит стадию «Документирование» во **все** будущие фичи, меняющие язык.

### Состав документа (обоснование)

Структура опирается на референсы описаний языков:

- **Rust** (*The Book* + *Reference*) — разделы с автонумерацией, HTML с поиском
  (⇒ выбор mdBook); деление «обзор → конструкции → приложения».
- **Java** (*JLS*) — формальная последовательность: лексика → типы → выражения →
  операторы → грамматика в приложении.
- **IEC 61131-3 (ST)** и **IEEE 1800 (SystemVerilog)** — стандартный порядок:
  обзор/область → лексические соглашения → типы и значения → объявления →
  конструкции → модель исполнения → приложение с формальной грамматикой.

### Требования и проверяемые условия

- **R1. Только язык.** Документ описывает синтаксис/семантику/модель исполнения/
  конструкции/примеры; **не** содержит деталей реализации инструментов, номеров
  фич, ссылок на ADR/анализ/отчёты, истории процесса.
- **R2. Структура из исходников.** Порядок и **автонумерация** разделов — из
  `src/SUMMARY.md`; каждый раздел — в своей папке с `index.md`, `examples/`,
  ресурсами.
- **R3. Сборка скриптом.** `make -C book build` собирает документ в **PDF**
  (mdBook + `mdbook-pandoc` + `xelatex`; шрифт текста/кода **Fira Code**);
  зависимости задокументированы, `precheck.sh` их не требует (обновление решения
  ADR — вывод PDF вместо HTML).
- **R4. Вводная часть и приложения.** Есть титул/введение/назначение и приложения
  «Грамматика»/«Литература»/«Глоссарий».
- **R5. Правило актуализации.** свод в `docs/RULE.md`; шаблон карточки
  содержит раздел «Документирование»; «каждый новый раздел — фича».
- **R6. Ссылочная целостность.** `check-links.py` зелёный (ссылки внутри `book/` и
  на `book/` из доков целы).

### Особенности по обратной функциональности

свод неприменимо (новая инфраструктура, обратной совместимости не нарушает).
`precheck.sh`/CI не затрагиваются (mdBook — вне тулчейна). Код `takt-lang`/
`takt-sim` не меняется.

### Риски и зависимости

- **mdBook не установлен в среде** — сборка документа локально/в CI требует
  `cargo install mdbook`. Снижение: Makefile даёт явную диагностику; проверка «документ
  собирается» — отдельный кандидат (не в `precheck.sh`).
- **Дрейф документа от языка** — снижается сводом (стадия «Документирование» в
  каждой языковой фиче) и шаблоном карточки.
- **Проникновение процесса в документ** — снижается R1/A6 (греп-проверка) и
  формулировкой своду.
- **Объём наполнения** — 15 разделов; декомпозирован на фичи-преемники (по разделу
  на фичу), 0101 несёт только инфраструктуру + seed.
