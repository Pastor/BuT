**Форматтер выносит комментарий из тела блока наружу.** Вскрыто при разработке
[раздел документа «Практический пример: процессор» (шины, кеш, ядра)](0186-book-processor-example.md#разработка)
(2026-07-30). Проба в четыре строки: комментарий, стоящий **первой строкой
внутри** `always { … }`, после `taktc fmt` оказывается **после** закрывающей
скобки — то есть привязывается к следующему элементу состояния (`ref`). Текст
не теряется, теряется **место**: в примерах раздела 20 пояснение к телу стало
читаться как пояснение к переходу. Это не «синоним, который не
канонизируется» (`while`/`loop`, `Guard`), а перемещение авторского
комментария — форматтер обязан сохранять его позицию либо честно отказывать.
Обход в примерах: комментарий ставится **перед** `always`. Корпус класс не
ловит: в `examples/` комментарии внутри тел стоят не первой строкой.

### Context

Комментарий, стоящий **внутри тела блока**, после `taktc fmt` оказывается
**снаружи** — привязанным к следующему элементу. Текст не теряется, теряется
**место**, а с ним и смысл: пояснение к телу начинает читаться как пояснение к
переходу.

```takt
start Run {
    always {
        // пояснение к телу
        n := n + 1;
    }
    ref Run;
}
```

после `taktc fmt`:

```takt
start Run {
    always {
        n := n + 1;
    }
    // пояснение к телу
    ref Run;
}
```

#### Дефект шире, чем было записано в кандидате

Кандидат описывал комментарий, стоящий **первой строкой** внутри `always`.
Пробы 2026-08-03 показали, что условие иное — переезжает **любой** комментарий
из **любого** тела:

| Проба | Результат |
|---|---|
| первой строкой в `always` | уезжает за `}` к следующему элементу |
| **между операторами** тела | уезжает туда же |
| **последней строкой** тела | уезжает туда же |
| внутри вложенного `if` | уезжает **через два уровня** — на уровень состояния |
| в теле **функции** | уезжает **за пределы функции**, к следующему элементу файла |
| между элементами (не в теле) | **сохраняется на месте** |

То есть это не «комментарий первой строки», а **граница печати**: место
сохраняется ровно там, где комментарии кто-то спрашивает.

#### Причина — одна строка кода, точнее её отсутствие

Механизм 0024 сшивает комментарии по смещениям: `Comments::leading(offset)`
выдаёт все непогашенные комментарии, начинающиеся раньше `offset`. Замер:
`leading()` вызывается **только в двух местах** `format/mod.rs` — при печати
элементов верхнего уровня и элементов модели/состояния. Печатники `format/stmt.rs`
и `format/expr.rs` не спрашивают комментарии **вовсе** (ноль вызовов).

Следствие ровно то, что наблюдается: комментарий внутри тела остаётся
непогашенным до следующего **элемента**, и там его выдаёт `leading()` — уже
снаружи. Этим же объясняется идемпотентность (после переезда комментарий стоит
перед элементом, где его и печатают) и сохранность комментариев вне тел.

Инвариант R2 фичи («потерять комментарий нельзя») при этом **не
нарушен** — комментарий цел. Нарушено то, о чём 0024 не говорила: его **место**.

### Decision Drivers

1. **Форматтер не вправе менять смысл текста.** Перемещение комментария меняет
   то, к чему он относится, — это хуже, чем отказ форматировать.
2. **Позиции есть у всех операторов.** `ast::Statement` несёт `Location` в
   каждом варианте (в кортежных — первым полем), поэтому спросить комментарии
   перед оператором технически ничего не стоит.
3. **Корпус класс не покрывает** — в `examples/` комментарии внутри тел не
   стоят так, чтобы дефект проявился. Значит приёмка идёт на фикстурах, а
   проверка `fmt --check` регресс не поймает.
4. **Цена ошибки в другую сторону.** Печать комментариев в теле — это правки
   `stmt.rs`/`expr.rs`, то есть риск сдвинуть форматирование всего корпуса;
   дифф обязан быть проверен глазами.

### Considered Options

#### Option A. Печатники операторов спрашивают комментарии

Перед печатью каждого оператора — `leading(start оператора)`, после — `trailing`.
Комментарий печатается на своём месте и с отступом тела.

**Pros:**
- **чинит класс целиком**: тело блока, тело функции, вложенные `if`/`while`,
  ветви `match` — все они идут через печатник операторов;
- механизм не изобретается: тот же `Comments`, что уже работает для элементов;
- поведение совпадает с ожиданием от форматтера любого языка.

**Cons:**
- правки в двух печатниках, а не в одном;
- дифф корпуса **возможен** (там, где комментарии в телах уже есть) — надо
  прочитать глазами, а не довериться `fmt --check`;
- остаётся вопрос хвостовых комментариев внутри тела (`n := n + 1; // счёт`) —
  он решается тем же `trailing`, но требует отдельной проверки.

#### Option B. Отказ форматтера при комментарии внутри тела

`taktc fmt` отвергает файл с внятной диагностикой вместо перемещения.

**Pros:**
- дёшево и честно: смысл текста не меняется молча;
- прецедент в проекте есть — форматтер **отказывает** на непокрытом узле АСД
  (правило сопровождения 0024), потому что «молча потерять кусок исходника
  хуже».

**Cons:**
- ломает рабочий сценарий: комментарии в телах — норма, и `fmt` перестанет
  работать на большой доле файлов. Прецедент 0024 касается **непокрытого узла**
  (редкий случай при развитии языка), а здесь — обычная запись;
- `precheck.sh` гоняет `fmt` по корпусу и `fmt --check` в строгом режиме:
  отказ сделал бы предкоммит красным на первом же примере с таким комментарием.

#### Option C. Оставить как есть, задокументировать

**Pros:**
- ноль работы.

**Cons:**
- форматтер продолжает **молча менять смысл** авторского текста. Это ровно тот
  класс, который проект последовательно закрывает (0192, 0193, 0194, 0195):
  инструмент рапортует об успехе и делает не то.

### Decision

**Рекомендация архитектора — Option A.**

Довод решающий: причина дефекта — не сложность задачи, а **пропущенный вызов**.
Механизм привязки уже существует и уже работает для элементов; печатники
операторов просто им не пользуются. Option B закрывал бы симптом ценой рабочего
сценария, Option C оставляет инструмент, меняющий смысл текста.

Решение заказчика (2026-08-03) — **Option A**, совпало с рекомендацией.

### Consequences

#### Положительные

- комментарий сохраняет место во всех телах — блоков, функций, вложенных
  конструкций;
- `Comments::is_exhausted` (страховка R2 фичи) начинает означать то, что
  обещает: непогашенных комментариев не остаётся **потому что** каждый напечатан
  на своём месте, а не потому что всплыл наружу.

#### Отрицательные / Action items

- **A1.** Дифф `examples/` после правки — **прочитать глазами**: `fmt --check`
  докажет стабильность, но не верность расстановки.
- **A2.** Проверить **хвостовые** комментарии внутри тела (`n := n + 1; // счёт`)
  — сегодня они тоже уезжают, и `trailing` обязан их удержать.
- **A3.** Проверить **идемпотентность** после правки: второй прогон `fmt` не
  должен двигать комментарий (сегодня форматтер идемпотентен, и это свойство
  терять нельзя).
- **A4.** Контроль — фикстурный, с прогоном `fmt` на всех формах из таблицы
  Context; корпус этот класс не ловит (драйвер 3).

#### Acceptance criteria

1. Комментарий в теле `always`/`enter`/функции остаётся **на своём месте** и с
   отступом тела — первой строкой, между операторами и последней строкой.
2. Комментарий во вложенном `if`/`while`/`match` остаётся внутри своей вложенности.
3. Хвостовой комментарий оператора остаётся на строке этого оператора.
4. `taktc fmt` идемпотентен: повторный прогон ничего не двигает.
5. Дифф `examples/` объяснён построчно; предкоммит зелёный, включая `fmt --check`
   в строгом режиме.

## Анализ

### Цель и контекст

ADR принял **Option A** (рекомендация архитектора и решение заказчика совпали):
печатники операторов обязаны спрашивать комментарии, как это уже делают
печатники элементов.

**Уточнение к ADR, найденное при разборе кода.** Формулировка «печатники не
спрашивают комментарии» верна, но причина ещё уже: в `Out` **уже есть** метод
`node_line(loc, text)`, чья док-строка гласит — «единственный путь печати
содержательных строк, так комментарий не может потеряться». Печатник операторов
им просто не пользуется: зовёт `out.line(…)` напрямую, минуя привязку.

### Зависимости фичи

**Нет.** Механизм привязки заведён фичей и работает.

### Места правки

| # | Что | Файл | Замечание |
|---|---|---|---|
| М1 | операторы с позицией печатаются через `node_line` | `format/stmt.rs` | `Expression`, `Variable`, `Continue`, `Break`, `Return`, `Match` — у всех `Location` первым полем кортежа |
| М2 | комментарий последней строкой тела | `format/stmt.rs::close_body` + `Out::comments_before` | ведущих ему никто не выдаст: следующего оператора нет |
| М3 | — | `format/expr.rs` | **правок не потребовалось**: выражения печатаются внутри строки оператора, своих строк не занимают |

### Ограничения, которые определяют форму решения

- **О1. Позиция есть у каждого оператора.** В кортежных вариантах `ast::Statement`
  `Location` стоит **первым полем**; поиск по `loc:` его не находит, отсюда
  первоначальное впечатление, что позиций нет у 13 из 16 вариантов.
- **О2. Комментарий последней строки тела — отдельный случай.** Он не «ведущий»
  ни для чего: до конца блока операторов больше нет. Без явного вызова перед
  `}` его выдаст `leading()` следующего **элемента** — то есть привяжет к чужому
  узлу. Это ровно тот случай, который остался невылеченным после М1.
- **О3. Блочные операторы (`If`, `Loop`, `For`) печатаются через
  `block_with_head`,** и их ведущие комментарии выдаются при печати **первого
  оператора тела** или заголовка вложенного блока. Отдельной привязки заголовку
  не потребовалось — проверено пробой на вложенном `if`.
- **О4. Идемпотентность — свойство, которое нельзя потерять.** До правки
  форматтер был идемпотентен (комментарий уезжал **один раз**), и после правки
  обязан остаться таким.

## Разработка

### Задача

#### Что было

Печатник операторов (`format/stmt.rs`) печатал строки через `out.line(…)` —
минуя `Out::node_line(loc, text)`, чья док-строка прямо гласит: «единственный
путь печати содержательных строк, так комментарий не может потеряться».

Следствие: комментарий внутри тела оставался непогашенным до следующего
**элемента**, и там его выдавал `leading()` — уже за закрывающей скобкой.

#### Что сделано

**М1 — операторы печатаются через `node_line`.** Переведены `Expression`,
`Variable`, `Continue`, `Break`, `Return`, `Match`. Позиция у каждого есть:
в кортежных вариантах `ast::Statement` `Location` стоит **первым полем** (поиск
по `loc:` его не находит — отсюда первоначальное впечатление, что позиций нет).

**М2 — комментарий последней строкой тела.** Отдельный случай: ведущих ему никто
не выдаст, следующего оператора нет. Добавлены `Out::comments_before(offset)` и
`stmt::close_body`, вызываемый **перед** печатью `}` с концом блока в качестве
границы. Без него такой комментарий подхватывал бы `leading()` следующего
элемента.

**М3 — правок не потребовалось** в `format/expr.rs`: выражения печатаются внутри
строки оператора и своих строк не занимают.

#### Проверки

```sh
cargo test -p takt-lang --test format_tests
./target/debug/taktc fmt examples/   # дифф пуст
```

Пробы до и после (все пять форм, найденных на стадии архитектуры):

| Форма | Было | Стало |
|---|---|---|
| первой строкой в `always` | уезжал за `}` | на месте |
| между операторами | уезжал | на месте |
| последней строкой тела | уезжал | на месте (М2) |
| во вложенном `if` | всплывал на уровень состояния | на своей глубине |
| в теле функции | уезжал за пределы функции | на месте |

- существующие тесты форматтера (15) — зелёные;
- `fmt` по `examples/` и `book/` — **пустой дифф**: правка форматирование не
  сдвинула.

### Задача

#### Что было

Контрольных тестов у **места** комментария не было. Существующие тесты форматтера
проверяли, что комментарий не **теряется** (инвариант R2 фичи), — и он
действительно не терялся, поэтому дефект жил при зелёном покрытии.

Корпус класс не покрывает: в `examples/` комментарии внутри тел не стоят так,
чтобы дефект проявился, и проверка `fmt --check` регресс бы не поймал.

#### Что сделано

`takt-lang/tests/syntax/format_comment_position_tests.rs` — 7 фикстурных тестов, по
одному на форму: первой строкой тела, между операторами, последней строкой,
вложенный `if`, тело функции, хвостовой комментарий, идемпотентность.

Проверяется **отступ строки**, а не факт наличия: место — это и есть предмет
фичи.

#### Мутационная проверка вскрыла слабый тест

Мутация «печатать `Expression` через `line`» роняет **5 из 7**. Двое выживают, и
это разобрано, а не принято:

- **идемпотентность** переживает дефект по построению (до фичи форматтер тоже
  был идемпотентен — комментарий уезжал ровно один раз). Тест контролирует **другое
  свойство**, терять которое нельзя;
- **тело функции** выжило по иной причине — и это оказался **дефект теста**.
  При мутации `Return` комментарий остаётся внутри тела (его подхватывает выдача
  перед `}`), но встаёт **после** оператора, к которому относится. Тест проверял
  только отступ и потому дефект пропускал.

Тест усилен: теперь он проверяет **порядок** (`line_no(комментарий) <
line_no("return")`) и на своей мутации краснеет.

Урок: проверка отступа доказывает «внутри тела», но не «на своём месте».

#### Проверки

```sh
cargo test -p takt-lang --test format_comment_position_tests
```

- 7 тестов зелёные;
- мутация `Expression` роняет 5, мутация `Return` — усиленный тест функции;
- после снятия мутаций — снова зелёные.

### Выводы и дальнейшие шаги

**1. Дефект оказался шире записи находки, и это выяснила проба, а не чтение.**
Кандидат описывал комментарий **первой строкой** внутри `always`. На деле
уезжает **любой** комментарий из **любого** тела: между операторами, последней
строкой, из вложенного `if` (через два уровня) и из тела функции — за её
пределы. Форма записи была ни при чём: граница проходит там, где кончается
печать элементов и начинается печать операторов.

**2. Причина ещё уже, чем сформулировал ADR.** Не «печатники не спрашивают
комментарии», а «печатник не пользуется механизмом, который для этого и
сделан»: `Out::node_line` существует, его док-строка называет себя
«единственным путём печати содержательных строк», и печатник операторов зовёт
`out.line` в обход. Комментарий **последней строкой** тела при этом остаётся
отдельным случаем — ведущих ему никто не выдаст, и понадобился явный вызов
перед `}`.

**3. Мутационная проверка вскрыла слабый тест — мой собственный.** Из семи
контрольных тестов мутация уронила пять. Двое выживших разобраны:

- идемпотентность переживает дефект **по построению** (до фичи форматтер тоже
  был идемпотентен: комментарий уезжал ровно один раз) — тест контролирует другое
  свойство и остаётся нужным;
- тест «тело функции» выжил **по дефекту теста**: при печати `return` в обход
  привязки комментарий остаётся внутри тела, но встаёт **после** своего
  оператора, а тест проверял только отступ. Усилен проверкой порядка строк — и
  на своей мутации краснеет.

Урок: у форматтера проверка отступа доказывает «внутри тела», но **не** «на
своём месте». Порядок надо проверять отдельно.

**4. Корпус не сдвинулся ни на строку** — правка не изменила форматирование
существующих файлов. Это подтверждает, что механизм был не сломан, а не
задействован.

**Исправления (`docs/fixes/`) не требуются.**

## Итог (что сделано)

Комментарий сохраняет **место** при форматировании — во всех телах:

| Форма | Было | Стало |
|---|---|---|
| первой строкой в `always` | уезжал за `}`, к следующему элементу | на месте |
| между операторами тела | уезжал | на месте |
| последней строкой тела | уезжал | на месте |
| во вложенном `if` | всплывал **через два уровня** | на своей глубине |
| в теле функции | уезжал **за пределы функции** | на месте, перед своим оператором |

**Дефект оказался шире записи находки**: она называла только «комментарий
первой строкой внутри `always`», а уезжает любой комментарий из любого тела.
Форма записи ни при чём — граница проходит там, где кончается печать элементов
и начинается печать операторов.

**Причина — не сломанный механизм, а незадействованный.** `Out::node_line`
существует, и его док-строка называет себя «единственным путём печати
содержательных строк, так комментарий не может потеряться»; печатник операторов
звал `out.line` в обход. Комментарий **последней строкой** тела остался
отдельным случаем: ведущих ему никто не выдаст, понадобился явный вызов перед
`}` (`close_body` + `Out::comments_before`).

**Мутация вскрыла слабый контроль — мой собственный.** Тест «тело функции»
проверял только отступ и пропускал дефект: при печати в обход привязки
комментарий остаётся внутри тела, но встаёт **после** своего оператора. Усилен
проверкой порядка строк. Урок: у форматтера отступ доказывает «внутри тела», но
не «на своём месте».

Корпус не сдвинулся ни на строку — правка не изменила форматирование
существующих файлов.

**Граница фичи оказалась уже класса дефекта — вскрыто исправлением
[печать структуры теряет место комментария](../fixes/0198-01-struct-comment-placement.md)** (2026-08-14). Правка
шла по печати **операторов** (тела блоков, `close_body`), а печать **элементов
модели** разбиралась поэлементно — и ветка `ModelElement::Struct`, кладущая всю
запись через `out.line`, осталась с прежним поведением: комментарий обо всей
структуре уезжал за `}` и становился ведущим у следующего элемента. То есть
таблица выше верна для тел, но «во всех телах» — не то же, что «везде». Корпус
класс не ловил: 21 запись `struct` на 308 файлов и **ни одного** комментария в
них.
