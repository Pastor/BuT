## Краткое описание

Добавляет `taktc verify --emit-graph <kripke\|buchi\|product>`: выгружает
структуру Крипке, автомат Бюхи для `¬φ` или их произведение — те же структуры,
что использует проверка, — в формат **Graphviz DOT** (stdout). DOT рендерится
`dot -Tsvg` в SVG для встраивания в документ (`book/`). `kripke` без `--property`
даёт управляющую абстракцию (0049); `buchi`/`product` требуют `--property`
(строятся по `¬φ`).

> Фича зарегистрирована по запросу заказчика; проходит жизненный цикл по своду.

### Context

Движок верификации строит структуру **Крипке** (`verification/kripke.rs`), автомат
**Бюхи** для `¬φ` (`buchi.rs`) и их **произведение** (`product.rs`), но наружу
отдаёт только **текст**: вердикт, текстовый `--trace` (дампы `Kripke::trace`,
`BuchiAutomaton::dump`, `Product::trace`) и контрпример-лассо. Графического вывода
нет. Разделу документа «Практический пример» нужны **наглядные диаграммы**
построения модели Крипке и автомата Бюхи для разных спецификаций, чтобы показать,
как работает model-checking. Рисовать их вручную — значит оторвать иллюстрацию от
настоящего вывода инструмента (расхождение при любой правке движка).

Требуется: из тех же структур, что использует проверка, породить граф в формате,
который **локально рендерится в SVG** для встраивания в book (PDF собирается
`xelatex`, картинки — SVG через `rsvg-convert`).

### Decision Drivers

1. **Диаграмма = настоящий вывод движка.** Граф строится из тех же
   `Kripke`/`BuchiAutomaton`/`Product`, что и вердикт; правка движка автоматически
   отражается в диаграмме, расхождение невозможно.
2. **Локальный рендер в SVG доступной утилитой.** В окружении сборки есть
   `dot` (Graphviz, `/opt/homebrew/bin/dot`), а `plantuml` — **нет**. Формат должен
   рендериться тем, что установлено.
3. **Идиоматичность.** Автоматы и структуры Крипке в литературе рисуют графами
   переходов (кружки-состояния, двойной кружок — принимающее, стрелки-рёбра) —
   ровно модель Graphviz.
4. **Минимальная и согласованная CLI-поверхность.** Экспорт живёт в существующей
   подкоманде `verify`, а не в новой; не ломает прежние вызовы (аддитивность).
5. **Единый источник истины отбора Крипке.** Экспорт обязан выбирать
   управляющую/данными Крипке (0049 vs 0068) **той же** логикой, что проверка, —
   иначе диаграмма покажет не тот граф, что проверялся.

### Considered Options

#### Option A. PlantUML (state diagram)

**Pros:**
- Единый формат с ADR-диаграммами проекта и целью `plantuml` компилятора.

**Cons:**
- `plantuml` в окружении **не установлен** — нечем рендерить в SVG для book.
- State-diagram PlantUML плохо выражает автомат Бюхи (множества формул в узле,
  двойной кружок принятия) — пришлось бы бороться с нотацией.

#### Option B. Graphviz DOT (`taktc verify --emit-graph <kind>`)

**Pros:**
- `dot` установлен → `dot -Tsvg` рендерит SVG для book сразу.
- Идиоматично для автоматов/Крипке; принятие рисуется `shape=doublecircle`,
  старт — точкой-источником, разметка атомов — меткой узла.
- Экспорт — аддитивный флаг существующей подкоманды `verify`.
- DOT-строку легко проверять тестом (детерминированный порядок из `BTreeMap`).

**Cons:**
- Ещё один текстовый формат в кодовой базе (но узкий, только под верификацию).

#### Option C. Собственный SVG-эмиттер

**Pros:**
- Без внешних зависимостей рендера.

**Cons:**
- Раскладка графа (layout) — сложная задача; переизобретать Graphviz неоправданно.

### Decision

Принимается **Option B — Graphviz DOT**. Добавляется флаг
`taktc verify --emit-graph <kripke|buchi|product>` (при необходимости с
`--property φ`): строит запрошенную структуру тем же конвейером и печатает **DOT**
в stdout (перенаправляется в файл, рендерится `dot -Tsvg`). Эмиттеры — новый модуль
`verification/dot.rs` (`kripke_to_dot`/`buchi_to_dot`/`product_to_dot`). Отбор
Крипке (управление 0049 vs данные 0068) выносится в общий помощник
`verify::select_kripke`, которым пользуются и проверка (`run`), и экспорт, — чтобы
диаграмма показывала **ровно** проверявшийся граф.

- `kripke` — без `--property` даёт **управляющую** Крипке; с `--property` — ту, что
  реально проверялась бы (данными, если атомы φ — предикаты).
- `buchi`/`product` требуют `--property` (строятся по `¬φ`); без него — понятный
  отказ, а не молчание.

Форматом рендера в book остаётся **SVG**: `.dot` → `dot -Tsvg` при подготовке
раздела; в репозиторий кладутся и `.dot` (воспроизводимость), и порождённый `.svg`.

### Consequences

#### Положительные

- Диаграммы Крипке/Бюхи/произведения — настоящий вывод движка, привязанный к его
  коду; правка верификации отражается в картинке.
- Прежние вызовы `verify` не затронуты (флаг аддитивен); текстовый `--trace`
  остаётся.
- Общий `select_kripke` убирает риск расхождения «проверили одно — нарисовали
  другое».

#### Отрицательные / Action items

- Рендер в SVG — внешний шаг (`dot`), не в `precheck.sh` (как и сборка PDF). Проверка
  проверяет **порождение DOT** (юнит-тест на валидность/структуру), а не картинку.
- `verify` инструмент, а не библиотека: эмиттеры — публичные функции
  `verification::dot`, CLI лишь вызывает их и печатает.

#### Acceptance criteria

1. `taktc verify --emit-graph kripke m.takt` печатает валидный DOT структуры
   Крипке (старт помечен, тотальность/самопетли видны); `dot -Tsvg` рендерит.
2. `taktc verify --emit-graph buchi --property "F S" m.takt` печатает DOT автомата
   `¬φ`: начальные и **принимающие** (`doublecircle`) состояния различимы.
3. `--emit-graph product --property φ` печатает DOT произведения с пометкой
   принимающих пар.
4. `buchi`/`product` без `--property` → понятный отказ (код ≠ 0), не молчание.
5. Отбор Крипке экспорта совпадает с проверкой (общий `select_kripke`): для
   свойства над данными экспортируется data-Крипке.
6. Юнит-тесты на DOT-вывод (захват зондом, затем ассерты); `./scripts/precheck.sh`
   зелёный; прежний вывод `verify`/`--trace` неизменен.

## Анализ

### Цель и контекст

Разделу документа «Практический пример» (исправление `0118-01`) нужны наглядные
диаграммы построения структуры Крипке и автомата Бюхи — **настоящим выводом
инструмента**, а не ручным рисунком (иначе картинка разойдётся с движком при
любой правке). Движок 0049/0068 строит эти структуры в памяти, но экспорта нет.
Фича добавляет экспорт в Graphviz DOT (обоснование формата — ADR: `dot`
установлен, `plantuml` нет; DOT идиоматичен для автоматов).

### Зависимости фичи

- **Зависит от:** нет. Использует уже закрытые 0049 (верификация) и 0068
  (абстракция по данным); аддитивна — прежний путь `verify` не
  затронут.
- **Влияние на порядок разработки:** завершение **разблокирует** исправление `0118-01`
  (раздел «Практический пример»), которому нужны эти диаграммы.

### Требования и проверяемые условия

- **R1. Диаграмма = вывод движка.** Граф строится из тех же
  `Kripke`/`BuchiAutomaton`/`Product`, что и вердикт.
- **R2. Рендерится установленным инструментом.** DOT → SVG через `dot -Tsvg`.
- **R3. Отбор Крипке совпадает с проверкой.** Управляющая (0049) vs данными
  (0068) — единый `select_kripke`.
- **R4. Отказ, а не молчание.** `buchi`/`product` без `--property`, негодное
  значение флага, `NoStartState`/`Unsupported` — явный отказ с кодом ≠ 0.
- **R5. Аддитивность.** Прежний вывод `verify`/`--trace` — байт-в-байт неизменен.

### Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | Валидный DOT Крипке (старт, узлы) | юнит-тест `verification::dot` + `dot -Tsvg` |
| A2 | Автомат: принимающие `doublecircle`, начальные — источники | юнит-тест |
| A3 | Произведение: пары `состояние,qN` | юнит-тест |
| A4 | Отказ без свойства/при негодном значении | юнит-тесты CLI |
| A5 | Отбор Крипке = проверке (data-path метки) | юнит-тест на bit-var |
| A6 | Прежний вывод неизменен | существующие тесты `verify` + проверка |

### Особенности по обратной функциональности

Только **Rust** (движок + CLI). Цели генерации, симулятор, LSP — не затронуты
(язык/цели/симуляция не меняются).

### Риски и зависимости

- **Расхождение «нарисовали не то, что проверили».** Снят общим `select_kripke`
  (R3): проверка и экспорт выбирают Крипке одним кодом.
- **Двойное экранирование меток** (`\n` разделитель против экранирования кавычек).
  Снято раздельным экранированием компонентов; регресс-тест
  `labels_use_real_newline_not_escaped_backslash`.

## Разработка

### Задача

#### Что было

Движок верификации строил `Kripke`/`BuchiAutomaton`/`Product` в памяти и отдавал
наружу только текст (вердикт, `--trace`-дампы, контрпример). Графического вывода
не было — раздел документа «Практический пример» не мог показать наглядное
построение модели Крипке и автомата Бюхи настоящим выводом инструмента.

#### Что сделано

- **`verify::select_kripke`** (`verification/verify.rs`) — извлечён из `run`
  общий отбор «управляющая (0049) vs данными (0068)» Крипке; им пользуются и
  проверка, и экспорт (единый источник истины — диаграмма = проверявшийся граф).
- **`verify::build_graphs`/`build_control_kripke`** — публичные строители
  промежуточных структур (`VerificationGraphs { kripke, automaton, product }`)
  для экспорта; `Err` несёт вердикт-отказ.
- **`verification/dot.rs`** (новый модуль) — эмиттеры `kripke_to_dot`/
  `buchi_to_dot`/`product_to_dot`. Соглашения: старт — `shape=point`; принимающее
  — `doublecircle`; id узла — индекс вершины (в пути данных имя состояния делят
  несколько вершин); метки — компонентно экранированы, разделитель `\n` —
  настоящий перенос строки DOT.
- **CLI** (`bin/taktc.rs`) — `GraphKind` + флаг `--emit-graph <kind>` (раздельная
  и слитная формы, валидация значения) в `VerifyOptions`; ветка `run_emit_graph`
  в `run_verify` печатает DOT и возвращает код. `buchi`/`product` без `--property`
  → отказ.

Стек: **Rust** (движок + CLI) — основная работа. C/ST/rust/sv-генераторы,
симулятор, LSP — **н/п** (фича не трогает ни язык, ни цели, ни симуляцию).

#### Проверки

- `cargo test -p takt-lang --lib verification::dot -- --test-threads=1` — 6/6.
- `cargo test --bin taktc verify_args -- --test-threads=1` — 12/12 (в т.ч. 2 новых
  на `--emit-graph`).
- Ручной рендер: `taktc verify --emit-graph kripke dispenser.takt | dot -Tsvg` —
  валидный SVG. `--emit-graph buchi -p "F Filling"` — принимающее состояние
  `doublecircle`. `--emit-graph buchi` без `-p` — отказ, код 1.
- `./scripts/precheck.sh` — зелёный (прежний вывод `verify`/`--trace` неизменен).

## Итог (что сделано)

Реализован экспорт графов верификации в Graphviz DOT (ADR, Option B —
`dot` установлен, `plantuml` нет; DOT идиоматичен для автоматов):

- **CLI**: `taktc verify --emit-graph <kripke|buchi|product>` (раздельная и
  слитная `--emit-graph=…` формы; негодное значение — отказ, не молчание).
  Экспорт печатает DOT в stdout и завершает без проверки пустоты. `buchi`/
  `product` без `--property` → понятный отказ (код ≠ 0).
- **Эмиттеры** — новый модуль `verification/dot.rs`: `kripke_to_dot`
  (старт — точка-источник, тотальность/самопетли видны, для пути данных 0068
  метка несёт истинные атомы), `buchi_to_dot` (принимающее — `doublecircle`,
  начальные — точки-источники), `product_to_dot` (узел — пара
  `состояние,qN`). Порядок детерминирован (`BTreeMap`/индексный обход) —
  DOT воспроизводим (согласуется с 0048).
- **Единый источник истины отбора Крипке**: логика «управляющая (0049) vs
  данными (0068)» вынесена в `verify::select_kripke`, которым пользуются и
  проверка (`run`), и экспорт (`build_graphs`/`build_control_kripke`) — диаграмма
  показывает **ровно** проверявшийся граф. Прежний путь `run`/`--trace` —
  байт-в-байт неизменен.
- **Тесты**: 6 юнит-тестов эмиттеров (`verification::dot`) — старт, все узлы,
  `doublecircle` у принимающих, пары произведения, метки пути данных, регресс
  двойного экранирования `\n`, экранирование кавычек; 2 CLI-теста разбора
  `--emit-graph`. Рендер `dot -Tsvg` подтверждён вручную.

**Живая проверка:** `taktc verify --emit-graph …` порождает валидный DOT
(рендерится `dot -Tsvg`); `./scripts/precheck.sh` зелёный. Язык не менялся →
версия языка та же.
