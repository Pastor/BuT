## Краткое описание

Подсветка прогона на схеме сопоставляет активные состояния с узлами по имени, и
на листе композиции с несколькими экземплярами одной модели (`Middle = Engine +
(Engine | Engine) + …`) узел подсвечивается, если активен **любой** экземпляр:
какой именно шаг цепочки идёт сейчас, схема не показывает. Фича даёт эталону и
модулю адрес экземпляра рядом с именем состояния (путь по дереву юнитов) и учит
лист композиции подсвечивать только свой шаг и свою ветвь, а лист модели — все
активные экземпляры разом с числом на узле.

> Фича зарегистрирована из кандидатов итога закрытой фичи о схеме состояний (2026-09-08, [карточка](0539-model-layout-ui.md));
> далее проходит жизненный цикл по своду.

### Context

Подсветка прогона сопоставляет активные состояния с узлами по имени — так
записано в задаче закрытой фичи о схеме как названная граница первой
редакции. На листе композиции лифта (`Middle = Engine + (Engine | Engine) +
Engine + Engine + Engine`) все шесть шагов — экземпляры одной модели, и
горят все, когда идёт любой; какой шаг цепочки исполняется, схема не
показывает. Экспорт проекта рисует цветной вид тем же правилом, поэтому
дефект уехал бы и в картинки.

**Что уже есть (снято чтением дерева 2026-09-11):**

| Слой | Что есть | Чего не хватает |
|---|---|---|
| эталон | `Unit::active_states()` собирает имена по дереву юнитов плоским списком (`collect_active_states`: узел, его реализация, ветви параллели, активный шаг цепочки); `Step.states` и `Step.next` (пары «из, в» от `peek_transitions`); строку трассы печатает `trace::step_line` из того же списка | адреса экземпляра нет ни в узле, ни в шаге; признака «шаг завершён» наружу нет |
| дерево юнитов | `UnitKind::Node { model_name, state, state_impls, … }`, `Parallel { units }`, `Sequential { units, index }`; `build_extend` строит по `Extend`, а `add`/`union` **расплющивают** вложенные `+` и `\|` (`Sequential.add(Sequential)` сливает списки), порядок листьев сохраняется; модель с единственным состоянием-реализацией без блоков сворачивается в композицию без узла (`single_compound`) | дерево юнитов не равно дереву выражения, и адрес по структуре после сборки не восстановить |
| модуль | `takt_sim_tick` отдаёт `states` и `next` по списку на строку; `worker.js` передаёт их странице; `app.js` зовёт `setRunning(states, next)` для последнего такта порции | поля адресов нет |
| холст | `setRunning`: классы `running`/`expected`/`reachable` по имени узла; `nextEdgeKeys` по парам; `paintInner`: у квадрата композиции миниатюра и плашка по `innerLabel` (имена активных внутренних состояний через запятую); на листе композиции шаг `Модель#номер` — квадрат, плашка берёт активные внутренние состояния модели шага — **у всех шагов одной модели одинаково** | различение экземпляров; счётчик на узле; стрелка шага цепочки |
| книга оформления | «Узел-состояние»: три вида подсветки прогона, плашка композиции, стрелка ожидаемого перехода | контрол «счётчик экземпляров» |
| тесты | `layout-tests.mjs`: плашка композиции, стрелка ожидаемого перехода, мост отдаёт списки по строкам; сверки эталона читают `states` и строку трассы (пять мест) | ничего об экземплярах |

### Decision Drivers

1. **Строка трассы и `states` не меняются**: на них стоят сверки целей и
   тест моста; адрес — новое поле рядом.
2. **Адрес даёт эталон, а не страница.** Страница знает граф выражения, но
   не порядок исполнения; о том, какой экземпляр идёт, знает только тот, кто
   тикает.
3. **Правило сопоставления одно** и записано словами: его повторит
   Rust-носитель цветного вида в экспорте проекта.
4. **Дерево юнитов не перестраивается**: слияние `add`/`union` держит
   исполнение блоков владельца; адрес переживает слияние, потому что
   хранится на листе, а не выводится из структуры.

### Considered Options

#### Вопрос 1 — форма адреса (архитектор)

- **A (принято): путь по владельцам реализаций, хранимый на узле.** Адрес
  активного состояния — `{ path, model, state, done }`, где `path` — список
  сегментов `{ owner, step }`: `owner` — имя состояния с реализацией (у
  свёрнутой модели — имя её единственного состояния, у модели без
  собственных состояний — имя модели), `step` — порядковый номер листа
  выражения при обходе слева направо, с единицы; `model` — имя модели узла;
  `done` — узел терминален (шаг завершён). Путь записывает `build_extend`
  при спуске в `Extend::Model` и хранится полем узла; сбор — рядом с
  `collect_active_states`.
- **B (отвергнуто): вывод адреса обходом дерева юнитов** — после слияния
  `add`/`union` шаг из модели без собственных состояний неотличим от скобок.
- **C (отвергнуто): менять слияние, чтобы дерево совпадало с выражением** —
  блоки `always` модели-владельца исполняются владельцем слитого списка
  (исправление про двойной `always`), и вложенный композит их потерял бы.

#### Вопрос 2 — сопоставление на странице (архитектор)

- **A (принято): один носитель `scheme-run.js`.** Лист модели `M`: узел
  `S` горит, если есть адрес с `model = M` и `state = S`; число экземпляров
  — количество таких адресов. Лист композиции с ключом `<лист>#<владелец>`:
  шаг с номером `k` горит, если есть адрес, в чьём пути стоит сегмент
  `{ owner: владелец, step: k }`; номер листа переводится в узел листа
  композиции по порядку обхода `composeSheet` (тот же порядок, что у
  эталона); плашка шага — состояние своего экземпляра. Ожидаемые и
  достижимые считаются от горящих узлов по рёбрам листа, как сегодня.
- **B (отвергнуто): сопоставление в эталоне** — эталон не знает листов
  страницы; граф — у компилятора, порядок — у эталона, встречаются они на
  странице.

#### Вопрос 3 — второй экземпляр владельца (архитектор)

Лист композиции вложенной модели, у которой несколько экземпляров (лист
`Engine#Load`, когда `Engine` шесть), показывает объединение по всем
экземплярам владельца с тем же счётчиком, что лист модели: путь до
владельца в ключе листа не хранится (ключ — путь модели и имя состояния).
Граница названа в документе; уточнение по конкретному экземпляру — кандидат.

#### Вопрос 4 — число на узле листа модели (решение заказчика)

- **Принято: счётчик у края круга, только при двух и более.** Малый
  кружок с числом у правого верхнего края узла (кегль `xs`, пара
  «выбранное»); один экземпляр — как сегодня. Контрол заводится в книге и
  витрине.
- **Отвергнуто:** число в плашке под узлом; без числа.

#### Вопрос 5 — стрелка между шагами цепочки (решение заказчика)

- **Принято: подсвечивать, когда шаг завершён.** Признак `done` адреса:
  завершённый шаг цепочки даёт ребру `next` к следующему шагу вид
  «ожидаемый переход», следующему шагу — пару «тревога». Параллель
  завершена, когда завершены все её ветви; это считает страница по шагам
  ветви.
- **Отвергнуто:** вне объёма.

#### Вопрос 6 — плашка квадрата композиции (решение заказчика)

- **Принято: шаг и его состояние** — `Engine#2: Idle, Engine#3: Moving`
  (подпись автора шага и состояния, если есть); один активный шаг — без
  имени шага, как сегодня.
- **Отвергнуто:** состояние с числом.

#### Решения без вопросов заказчику

- **`states` и `next` остаются** в `Step` и в ответе модуля; `active` —
  третье поле, по списку на строку.
- **Снимок состояния** (`--save-state`) адрес не хранит: он ставится при
  построении, а восстановление меняет только состояние.
- **Миниатюра квадрата** горит по тем же адресам: внутреннее состояние —
  по `model` и `state` экземпляров этого владельца.
- **Экспорт проекта** повторит правило сопоставления на Rust — правило
  записано словами в этой карточке и в документе, контроль паритета — у той
  фичи.

### Decision

Принять вариант A по вопросам 1–3 и решения заказчика по вопросам 4–6.
Целевой поток:

```plantuml
@startuml
|takt-sim|
:build_extend: лист выражения получает
путь {owner, step}, узел хранит его;
:такт → Step { states, next, active:
[{path, model, state, done}] };
|takt-wasm / worker|
:takt_sim_tick: active по списку на строку;
|scheme-run.js|
if (лист?) then (модели M)
  :узлы по model = M и state;
  счётчик экземпляров ≥ 2;
else (композиции <лист>#owner)
  :шаг k по сегменту {owner, k};
  плашка "шаг: состояние";
  done → стрелка к следующему шагу;
endif
:expected / reachable по рёбрам листа;
stop
@enduml
```

### Consequences

- `Step` и ответ такта модуля получают поле `active`; прежние поля и
  строка трассы неизменны — сверки не трогаются.
- Узел юнита несёт путь; `builder` передаёт его при спуске.
- На странице появляется носитель сопоставления, а `scheme.js` (1766 строк)
  не растёт; книга получает контрол счётчика.
- Модель без собственных состояний как шаг адресуется именем модели;
  страница такого листа не имеет (граница закрытой фичи о схеме) — подсветка
  внутри него не показывается, граница названа.
- Язык не меняется; версия крейта `takt-sim` и модуля растёт.

#### Acceptance criteria

1. На лифте после нескольких тактов лист композиции `Middle` подсвечивает
   ровно идущий шаг (и обе ветви параллели, когда идёт она), плашка шага
   называет состояние своего экземпляра.
2. Лист модели `Engine` подсвечивает все состояния активных экземпляров, а
   узел с двумя и более экземплярами несёт счётчик.
3. Завершённый шаг цепочки подсвечивает стрелку к следующему шагу и сам
   следующий шаг.
4. Плашка квадрата `Middle` на корне перечисляет шаги с состояниями.
5. `states`, `next` и строка трассы байт в байт прежние на всём корпусе
   сверок; тест моста проходит.
6. Документ называет правило сопоставления и границы; предкоммит зелёный.

## Анализ

### Цель и контекст

ADR принял адрес экземпляра, хранимый на узле эталона и отдаваемый шагом
рядом с прежними полями, и один носитель сопоставления на странице. Анализ
переводит это в требования с проверками и задачи. Фича не блокирует
экспорт проекта, но задаёт ему правило цветного вида.

### Замер (2026-09-11)

### Зависимости фичи

**Зависит от: нет.** Всё в дереве. Связи: [раскладка листа композиции](0542-scheme-composition-layout.md)
хранит координаты шагов и на подсветку не влияет; [экспорт проекта](0590-project-export.md)
повторяет правило сопоставления на Rust и берёт его из этой карточки.

### Требования и проверяемые условия

- **Адрес на узле.** `build_extend` получает префикс пути; лист выражения
  `Extend::Model` получает сегмент `{ owner, step }`, где `owner` —
  состояние с реализацией (из `build_node`), имя единственного состояния при
  свёртке либо имя модели без состояний, `step` — номер листа слева направо
  с единицы; путь хранится полем узла. Проверка: тест эталона на лифте —
  шесть узлов `Engine` с путями `[{Middle, 1}]`…`[{Middle, 6}]`; тест на
  вложенной реализации — путь из двух сегментов; тест на свёрнутой модели.
- **Поле `active` шага.** `Step.active: Vec<ActiveState { path, model,
  state, done }>` в том же порядке, что `states`; `states`, `next` и строка
  трассы неизменны. Проверка: тест «имена `active` равны `states`
  поэлементно» на корпусе `examples/simulations/`; существующие сверки
  зелёные.
- **Признак `done`** — `is_terminal()` узла после такта. Проверка: тест на
  цепочке из двух шагов — у первого `done` становится истиной на такте
  завершения и пропадает при передаче хода.
- **Модуль и воркер.** `takt_sim_tick` отдаёт `active` по списку на строку;
  `worker.js` передаёт; `bridge.js` разбирает. Проверка: тест моста — длина
  `active` равна длине `lines`, имена совпадают со `states`.
- **Носитель сопоставления** `web/static/scheme-run.js`: чистые функции
  `runningOnModelSheet(active, model)` → карта «состояние → число»,
  `runningOnCompositionSheet(active, owner, nodes)` → карта «шаг → адреса»,
  `chainNext(active, edges, nodes)` → ключи рёбер и ожидаемые шаги по
  `done`, `innerLabel` переезжает сюда с новой формой «шаг: состояние».
  Проверка: тесты `node` на данных лифта без DOM.
- **Холст.** `setRunning(names, next, active)`: классы узлов и рёбер ставит по
  ответу носителя; счётчик `.node-count` рисуется при числе два и более;
  плашка шага на листе композиции и плашка квадрата на родителе — по
  носителю; миниатюра — по экземплярам владельца. Проверка: прогон страницы
  на лифте; тесты `node` на составление классов.
- **Оформление.** Контрол «счётчик экземпляров» в книге (раздел
  «Узел-состояние»), образец в витрине, стили в `app.css` только из шкал и
  пар. Проверка: `check-design.py`.
- **Документ.** Подраздел «Схема состояний»: на листе композиции горит
  идущий шаг и его ветвь, плашка называет состояние экземпляра, стрелка к

## Разработка

### Задача — эталон: адрес экземпляра

#### Что было

Активные состояния собирались плоским списком имён. Два экземпляра одной модели
на листе композиции давали одинаковые имена, и какой шаг идёт, эталон не
сообщал; признака «шаг завершён» наружу не было.

#### Что сделано

- Модуль `unit/instance.rs`: сегмент адреса (`Segment`: владелец, номер листа,
  модель листа), активное состояние с адресом (`ActiveState`: путь, модель
  узла, состояние, `done`), сбор `Unit::active_instances`. `active_states`
  стал его проекцией: обход один, и имена адресов совпадают со строкой трассы
  по построению, а не по договорённости двух обходов.
- Узел несёт поле `path`. Построитель передаёт владельца (`Owner`: путь и имя) в
  `build_extend`, лист выражения получает следующий номер при обходе слева
  направо и модель; `build_node` делает владельцем состояние с реализацией,
  свёрнутая модель — своё единственное состояние.
- `Step.active` — рядом с `states` и `next`; строка трассы и `states` прежние.
- Версия `takt-sim` — 0.15.0: у публичного `Step` новое поле, наружу открыты
  типы адреса.

#### Уточнения ADR, принесённые работой

- **Сегмент несёт модель листа.** ADR назвал сегмент `{ owner, step }`. Одно и
  то же имя состояния-владельца бывает у разных моделей (`Run` в двух моделях с
  реализациями), и сегмент без модели дал бы ложное совпадение на странице:
  лист `A#Run` загорелся бы от экземпляров `B#Run`. Модель листа говорит, чей
  экземпляр адресует путь до сегмента, и страница сверяет владельца вместе с
  моделью предыдущего сегмента.
- **У реализации модели владелец — состояние `Implement`.** Запись
  `model Duo = E + E { }` семантика разворачивает в состояние `Implement`, и
  модель сворачивается: владельцем листов выступает оно, а не имя модели, как
  предполагал ADR. Ветвь «модель без собственных состояний» из разбора так не
  достижима. Для страницы это ничего не меняет: у такой модели в графе нет узлов,
  и лист не показывается — это названная граница ADR.
- **Лифт до листа `Middle` на прогоне не доходит.** `Engine` зациклен
  (`DoorOpening → Idle`) и не завершается, поэтому `Main = Engine { next
  Middle; }` не отдаёт хода. Первый критерий приёмки проверяется на
  `pid_heater`: там два экземпляра `Heater` идут цепочкой и проходят одни и те
  же состояния — ровно тот случай, где имя шага не различает. Лифт остаётся
  входом для структуры листа.

#### Проверки

`takt-sim/tests/sim/instance_tests.rs`, шесть тестов: цепочка с параллелью
нумерует листы слева направо, ветви идут вместе; имена адресов равны
`active_states`; вложенная реализация даёт путь из двух сегментов с нумерацией
внутри своего владельца; свёрнутая модель и реализация модели владеют своими
листами; `done` взводится на такте завершения шага и пропадает с передачей
хода; бегун на `pid_heater` отдаёт в шаге адреса, имена которых равны
`states`, а экземпляры идут первым и вторым листом. Весь `takt-sim` зелёный,
включая сверки с целями: строка трассы не изменилась.

### Задача — модуль и воркер

#### Что сделано

`takt_sim_tick` отдаёт поле `active` по списку на строку трассы
(`{ path: [{ owner, step, model }], model, state, done }`); воркер передаёт его
странице рядом с `states` и `next`, мост отдаёт ответ модуля как есть. Версия
`takt-wasm` — 0.3.0.

#### Проверки

Тест модуля `ticks_yield_instance_addresses`: адресов столько же, сколько строк,
имена равны `states`, два экземпляра различимы номером листа. Тест моста на
лифте: `active` по списку на строку, имена — `states`, форма адреса. Проверка
тождественности модуля с `taktc` и `takt-sim` зелёная.

### Задача — холст и оформление

#### Что было

Холст зажигал узлы по имени: на листе композиции горели все шаги одной модели,
на листе модели — состояние, если его несёт любой экземпляр любой модели с тем
же именем состояния. Стрелка между шагами цепочки не горела никогда, а плашка
квадрата композиции на родительском листе пустовала: имён шагов в списке
активных нет.

#### Что сделано

- Носитель правила — `web/static/scheme-run.js`, чистые функции без DOM:
  `placeOf` (чей лист и где он стоит), `stepsOf` (экземпляры листов выражения
  владельца), `sheetRun` (горящие, ожидаемые, достижимые узлы, стрелки и число
  экземпляров), `squareInstance` (экземпляр за квадратом), `innerLabel` и
  `stepsLabel` (текст плашек). Правило записано словами в заголовке модуля.
- Холст спрашивает носитель на каждой отрисовке и на каждом такте:
  `setRunning(адреса, ожидаемые переходы)` хранит последний такт, лист считает
  своё. Счётчик экземпляров `.node-count` рисуется у края узла при числе два и
  более. Плашка шага и миниатюра квадрата горят по своему экземпляру; плашка
  квадрата композиции перечисляет идущие шаги с состояниями.
- Лист композиции называет владельца и лист, где он стоит, — по ним прогон
  находит экземпляры. `innerLabel` и `nextEdgeKeys` ушли из `scheme.js` в
  носитель; сам холст почти не вырос.
- Оформление: правило счётчика в `app.css` на паре «выбранное», пункт в
  разделе «Узел-состояние» книги, образец «два экземпляра» в витрине; строка
  словаря `scheme.instances` на двух языках. Ресурсы панели IntelliJ
  пересобраны — модуль `scheme-run.js` вошёл в них по графу импортов.

#### Проверки

Тесты `node`, шесть новых и два переписанных: лист модели горит экземпляром
своей модели, чужая модель с тем же именем состояния его не зажигает, два
экземпляра дают число; корневой лист горит по пустому пути; лист композиции
горит идущим шагом, завершённый шаг подсвечивает стрелки и следующий шаг,
параллель ждут, только когда завершены обе ветви; одноимённый владелец другой
модели чужой лист не зажигает; плашка квадрата перечисляет шаги, один шаг —
без имени; прогон `pid_heater` через модуль: шаги `Heater#1` и `Heater#2`
горят по очереди, и на передаче хода второй ожидается. Прогон: 137 тестов,
провалов нет; `check-design.py` (523 правила) и сверка ресурсов панели чистые.

Прогон страницы на модели `Line = Heater + (Heater | Heater) + Heater`: на
листе `Line` первые шесть тактов горит один первый шаг, на седьмом (шаг
завершён) обе ветви параллели ожидаются, дальше горят обе ветви со своими
плашками, последний шаг достижим; плашка квадрата `Line` на корне —
«Heater#2: Heating, Heater#3: Heating», в миниатюре горят ровно два шага; на
листе модели `Heater` узел `Heating` несёт счётчик «2». В консоли только
ответ 404 на запрос входа — у статического стенда нет сервера.

Полный прогон нашёл, что сторож веб-части кладёт в свою копию дерева только
лифт, и тест на `pid_heater` падал там на чтении файла: копия дерева несёт
ровно то, что читают тесты. В неё добавлены нагреватель и его библиотека.

### Задача — документ и журнал

Подраздел «Схема состояний» главы «Инструментарий» получил два абзаца:
подсвечивается экземпляр, а не имя (идущий шаг и ветви параллели, стрелка к
следующему шагу после завершения, плашки «шаг: состояние», число у узла на
листе модели) и две границы правила — лист композиции вложенной модели при
нескольких её экземплярах показывает объединение, а модель, реализованная
одним выражением, своего листа не имеет. Пример в документе — модель `Line`,
а не лифт: лифт до листа `Middle` на прогоне не доходит. `README.md` называет
поле `active` и правило, `CHANGES.md` — добавленное, `CLAUDE.md` — инвариант:
адрес хранит узел, обход один, модель в сегменте нужна. Документ собирается.
