# Фича: Состояние стабильно — автомат не покидает его сам

## Стадии жизненного цикла

Все стадии — разделы этой карточки. Исправлений не заводилось.

## Краткое описание

`start Run { always { lamp := 1; } }` исполнял тело **ровно один раз** и уходил
в `END`: терминальным считалось всякое состояние без исходящих рёбер. Автор
пишет «всегда», а получает «однажды» — и получает это согласованно у эталона и
всех восьми целей, то есть без единой подсказки о том, что происходит.

Решением заказчика правило изменено: **состояние стабильно** — автомат уходит
из него только по переходу. Работу завершает состояние, у которого нет ни
переходов, ни тела, исполняемого каждым тактом.

### Context

Замер-04 на `out lamp: bit; start Run { always { lamp := 1; } }`:
эталон — «Завершено за 1 шаг», цель `c` — `model->state = LAMP_END;` сразу
после записи порта, то же у `st`, `rust`, `sv`. Расхождения между
инструментами нет: правило было принято  и исполнялось всеми. Цена
— в том, что оно противоречит ожиданию автора.

### Considered Options

- **A. Конец — пустое состояние**: `state Done;` завершает, состояние с телом
  работает вечно. Примеры корпуса сохраняют смысл, `is_done()` осмыслен.
- **B. Конца нет вовсе**: никакое состояние не завершает автомат. Отменяет
  `is_done()`, состояние `END` и предупреждение `SE-010`; все трассы книги и
  сверок теряют «Завершено».

### Decision

**A**, решением заказчика 2026-09-05. Уточнение по ходу разработки: тело — это
то, что исполняется **каждый такт** (`always`, `every`, вставка в вывод цели);
`enter` и `exit` одноразовы и состояние не удерживают. Иначе конечное
состояние, прибирающееся на входе (`state Done { enter { count := 0; } }` —
запись из корпуса), перестало бы быть концом, а `exit` без рёбер стал бы
мёртвым кодом.

### Consequences

- Правило живёт **одним носителем** `semantic::terminal`: его спрашивают
  построение дерева (вид `End`), признак узла, предупреждение `SE-010`,
  печатники четырёх целей и эталон. Прежде решение принимали четверо порознь.
- Модели, у которых конечное состояние несёт `always`, больше не завершаются —
  и это ровно то, чего просил заказчик: «держи выход поднятым» значит каждый
  такт. Контракты трёх примеров (`regulator`, `pid_regulator`, `batch_cycle`,
  `float_regulator`) переведены на `must_terminate: false` с причиной.

#### Acceptance criteria

Эталон и восемь целей ведут себя одинаково на обеих формах; сверки зелены;
предкоммит зелёный.

## Разработка

### Задача — правило одним носителем

- `semantic::terminal::{is_terminal, holds_machine}` — правило и признак
  «удерживает ли блок».
- `StateNode::is_terminated` считает тело наравне с рёбрами; `tree.rs` тем же
  правилом присваивает вид `End`; `SE-010` спрашивает признак узла.
- Цели: `c` (`c_model`), `st` (`st_model`, `st_compose`), `rust`
  (`rust_tick`), `sv` (`sv_compose`), `plantuml` (стрелка в `[*]` — только у
  терминального; признак доехал полем `Element::State::terminal`).
- Эталон: `Unit::state_has_body` — общий признак для `is_terminal` и ухода в
  терминал на такте.

**Проверка стоит до печати `exit`** у `rust`, `st` и `sv`: иначе `exit`
исполнялся бы каждый такт после завершения композиции, тогда как эталон не
исполняет его ни разу.

**Пустая ветвь `CASE` у `st`** — следствие правила: состояние, всё тело
которого `enter`, без рёбер оставляет ветвь пустой, а MatIEC отвечает «invalid
statement in case element». Тело ветви печатается в буфер, пустое заменяется
само-присваиванием (приём был у табличной формы — стал общим).

### Тест-план

- Модуль: правило и признак блока (`holds_machine`), включая `enter`/`exit`.
- Сверки: `always` без рёбер идёт каждый такт у эталона и у целей; пустое
  состояние с `exit` завершает и исполняет `exit` **ровно один раз**.
- Контроль: состояние с телом не завершает автомат (`is_terminal` = false).

## Отчёт о тестировании

- `cargo test` — зелёный; сверки эталона с восемью целями совпали на обеих
  формах.
- `scripts/probe.sh` на `lamp.takt`: `cc принял`, `iec2c принял · cc собрал`,
  `rustc принял · clippy принял`; трасса эталона — `[Run]` каждый такт.
- Предкоммит зелёный.

### Что нашёл прогон

1. **`enter` удерживал состояние** в первой редакции правила, и примеры
   корпуса (`state Done { enter { … } }`) перестали завершаться. Граница
   уточнена: удерживает то, что идёт каждый такт.
2. **`exit` печатался целями каждый такт** после завершения композиции —
   проверка стояла после его печати.
3. **Пустая ветвь `CASE`** у `st` (см. выше).

## Итог (что сделано)

Состояние стало стабильным: автомат уходит из него только по переходу.
Правило живёт одним носителем и одинаково понимается эталоном и восемью
целями; конец автомата — состояние без переходов и без исполняемого каждым
тактом тела. Версия языка поднята до 0.18.0.
