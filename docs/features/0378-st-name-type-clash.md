# Фича: Имя переменной, совпавшее с именем типа, у цели st

- **Номер:** 0378
- **Статус:** ГОТОВО
- **Зависит от:** нет (0065, 0293 закрыты)
- **Связанные issue (анализ):** кандидат, заведённый закрытием
  [локальная переменная структурного типа у цели sv](0373-sv-struct-local.md)

## Краткое описание

Замер-21 на `struct Pair { … } var pair: Pair := {1, 2};`:

| Потребитель | Ответ |
|---|---|
| эталон, `c`, `c-hal`, `rust`, `sv`, `sv-mmio` | исполняют / инструменты приняли |
| `st`, `st-at` | **`iec2c` ОТВЕРГ:** «invalid located variable declaration» |

`taktc` возвращал **ноль**, а ответ `iec2c` указывает на `AT %…`, которых в
объявлении нет вовсе: по тексту причину не найти. Причина — идентификаторы IEC
61131-3 **регистронезависимы** и делят одно пространство имён, поэтому `pair` и
`Pair` для MatIEC одно имя.

Класс найден **пробой чужой фичи** (0373): там он дважды увёл замер не туда.

## Документирование (правило 24)

реестр `docs/diagnostics/README.md` и в сводную таблицу приложения «Ошибки»
(проверка требует тождества множеств).

## Архитектура (ADR)

- **Status:** Accepted
- **Date:** 2026-08-21
- **Authors:** Архитектор + лид разработки
- **Related issues:** [Фича](0378-st-name-type-clash.md);
  связь с [ADR](0065-st-namespace-isolation.md#архитектура-adr) (`ST-014`, плоское
  пространство имён IEC), [ADR](0195-target-name-collisions.md#архитектура-adr)
  (столкновения имён у цели `c`)

### Context

`var pair: Pair;` — естественная запись (переменная названа по своему типу).
Шесть потребителей её принимают, `iec2c` отвергает: идентификаторы IEC
регистронезависимы и делят одно пространство имён. Ответ инструмента обманчив
(«invalid located variable declaration» с указанием на `AT %…`), а `taktc`
возвращает ноль.

### Decision Drivers

1. **Молчаливо невалидного вывода быть не должно.**
2. **Причина обязана называться:** ответ `iec2c` её не называет.
3. **Правило цели согласовано само с собой:** у `st` уже есть два отказа того
   же рода.

### Considered Options

#### Option A. Отказ `ST-023` с названной причиной (принято)

**Pros:**
- Согласуется с `ST-014`/`ST-020` той же цели и с `SV-012` цели `sv`: отказ
  принадлежит **цели**, текст говорит, что модель валидна для прочих.
- Автор узнаёт причину, которую `iec2c` не называет.
- Дёшево и не может ошибиться в тихую сторону.

**Cons:** модель приходится править ради одной цели.

#### Option B. Переименование переменной у цели

**Cons:** имя переменной пришлось бы строить одним носителем для объявления и
**всех** обращений; пропуск одного печатника даёт ссылку в
пустоту. И это расходилось бы с `ST-014`, где цель отказывает, а не
переименовывает.

#### Option C. Диагностика семантики (сузить язык)

**Cons:** запись законна и исполняется эталоном; шесть потребителей её
переводят. Сужать язык ради одной цели — решение заказчика, а не разработки.

### Decision

Принимается **Option A**. Проверка живёт в `st_reserved` — там же, где
`ST-014`: класс один (плоское регистронезависимое пространство имён IEC),
меняется лишь источник занятого имени. Имена типов собираются у карт
`structs`/`enums`/`types` модели **и её предков** — тех же, из которых цель
печатает раздел `TYPE`.

### Consequences

#### Положительные

- Молчаливо невалидного вывода на этой записи больше нет.
- Автор получает причину и обход в одном сообщении.

#### Отрицательные / Action items

- Проверка стоит на объявлении **переменной**; столкновение имени типа с именем
  функции или состояния не измерялось — граница названа.

#### Acceptance criteria

1. Столкновение даёт `ST-023`, называющий оба имени.
2. Регистр не спасает (`PAIR` тоже отвергается).
3. Контрпример: непересекающееся имя переводится, `iec2c` вывод принимает.
4. Код внесён в реестр и в сводную таблицу приложения.
5. Вывод корпуса не изменился; предкоммит зелёный.

## Анализ

### Цель и контекст

Класс найден **пробой чужой фичи**: при работе над 0373 проба назвала локальную
`pair` при типе `Pair`, и `iec2c` отверг файл по причине, к предмету 0373
отношения не имевшей. Дважды подряд это уводило замер не туда — потому класс и
записан отдельно.

#### Замер (`scripts/probe.sh -n 2`, 2026-08-21)

Вход: `struct Pair { lo: u8, hi: u8 } var pair: Pair := {1, 2};` с чтением и
записью полей.

| Потребитель | Ответ |
|---|---|
| эталон | исполняет (`a=1,2`, `b=11,12`) |
| `c`, `c-hal` | `cc` принял |
| `rust` | `rustc` принял · `clippy` принял |
| `sv`, `sv-mmio` | verilator принял · yosys синтезировал |
| `st`, `st-at` | **`iec2c` ОТВЕРГ:** `invalid variable(s) declaration` |

`taktc` во всех восьми случаях вернул **ноль**.

Ответ `iec2c` **обманчив**: на голом `pair : Pair;` он отвечает «invalid
located variable declaration» и «unexpected token after 'VAR' in located
variable(s) declaration» — то есть указывает на размещение `AT %…`, которого в
объявлении нет вовсе. Проба с переименованным типом (`PairT`) проходит: это и
доказало, что дело в столкновении имён, а не в структуре как таковой.

### Зависимости фичи (правило 17/19)

- **Зависит от:** нет. 0065 (`ST-014`, плоское пространство имён IEC) и 0293
  (структуры у целей) закрыты.
- **Влияние на порядок разработки:** снимает кандидат «Переменная, названная как
  её тип, ломает вывод цели `st`».

### Требования и проверяемые условия

- **R1. Отказ с причиной.** Столкновение даёт `ST-023`, называющий имя
  переменной и имя типа.
- **R2. Отказ принадлежит цели.** Текст говорит, что модель остаётся валидной
  для прочих шести целей (образец `ST-014`, `SV-012`).
- **R3. Регистронезависимость.** `PAIR`, `Pair`, `pair` — одно и то же.
- **R4. Контрпример.** Непересекающееся имя переводится, и `iec2c` вывод
  принимает.
- **R5. Один список имён.** Имена типов берутся у тех же карт, из которых цель
  печатает раздел `TYPE` (включая предков).
- **R6. Реестры.** Код внесён в `docs/diagnostics/README.md` и в сводную
  таблицу приложения «Ошибки» (проверка требует тождества множеств).

### Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | R1, R2 | `variable_named_like_type_is_refused` |
| A2 | R3 | юнит-тест `test_variable_named_like_type_is_st023` |
| A3 | R4 | `distinct_name_is_translated_and_accepted` (прогон `iec2c`) |
| A4 | R5 | код: `declared_type_names` читает `structs`/`enums`/`types` |
| A5 | R6 | `scripts/check-book-diagnostics.py` |

### Особенности по обратной функциональности

Ломающее изменение **формально**: модель, где переменная названа как тип,
перестаёт транслироваться целью `st`. Но прежде она транслировалась в файл,
который `iec2c` **не принимает**, то есть работоспособного вывода не было и
раньше — меняется лишь то, кто и как об этом говорит.

### Риски и зависимости

- **Ложное срабатывание** запретило бы валидное имя. Снижение: сравнение идёт
  только с **объявленными в файле** типами, и контрпример стоит рядом.
- **Граница:** воронка стоит на объявлениях переменной, порта и константы;
  столкновение имени типа с именем функции или состояния не измерялось.

## Разработка

### Задача

#### Что было

`var pair: Pair;` цель переводила молча, а `iec2c` отвергал файл сообщением о
размещённых переменных, которых в объявлении нет.

#### Что сделано

- `st_reserved::check_st_type_clash(name, model, loc)` — новая проверка рядом с
  `ST-014` (класс тот же: плоское регистронезависимое пространство имён IEC,
  меняется лишь источник занятого имени).
- `declared_type_names` собирает имена у `structs`, `enums` и `types` модели
  **и её предков** — тех же карт, из которых цель печатает раздел `TYPE`.
- Проверки имени сведены в **одну воронку** `check_st_declaration(name, model,
  loc)`: `ST-014` (стандартная библиотека), `ST-020` (алфавит) и `ST-023`
  (имя типа). Её зовут все три места объявления в `st_decl` — переменная,
  порт и константа; там, где модели нет (имя POU, имя состояния), остаётся
  `check_st_name`.
- Вызовы стоят **после** фильтра использования (неиспользуемую переменную цель
  не эмитит, и `iec2c` её не увидит — тот же довод, что у `ST-014`).
- Код `ST-023` внесён в реестр диагностик и в сводную таблицу приложения
  «Ошибки».

**Текст диагностики проверен прогоном, а не чтением**: первая
редакция несла переносы строк без `\`, и в сообщение ушли десятки пробелов
подряд.

**Статус по функциональности (правило 11).** Затронуты `st`/`st-at`; прочие
цели и эталон — **н/п**.

1. **Класс нашла чужая проба.** В работе над 0373 имя `pair` при типе `Pair`

## Итог (что сделано)

- Столкновение имени переменной с именем объявленного типа отвергается
  **`ST-023`**, называющим оба имени и говорящим, что модель остаётся валидной
  для прочих шести целей (прецеденты `ST-014`, `SV-012`).
- **Отказ, а не переименование:** внутри самой цели уже два отказа того же
  рода (`ST-014` — столкновение со стандартной библиотекой, `ST-020` — символ
  вне алфавита), и переименование за автора расходилось бы с ними; кроме того,
  оно потребовало бы одного носителя имени для объявления и **всех** обращений.
- Сравнение **без учёта регистра** — иначе проверка не ловила бы ничего:
  совпадение по регистру в IEC не значит ничего.
- **Имена берутся из того, что цель печатает, а не из того, что объявлено**
  (исправление [`ST-023` отвергала тёзку перечисления](../fixes/0378-01-enum-namesake-false-positive.md)): в разделе
  `TYPE` у цели `st` есть только **структуры** — перечисление идёт целым типом
  плюс `VAR CONSTANT` (откат Option C, 0041-02), псевдоним раскрывается. Первая
  редакция брала все три карты модели и отвергала `var mode: Mode;` — вход,
  который `iec2c` принимает.
- Проверки имени сведены в **одну воронку** `check_st_declaration`, и её
  зовут все три места объявления: переменная, порт и константа. Прежде каждое
  звало `check_st_name` по отдельности — а новая проверка, добавленная в одно
  из трёх, разошлась бы с остальными.
- Контрпример обязателен: непересекающееся имя переводится, и `iec2c` вывод
  принимает.
- Вывод корпуса не изменился.

Детали — в [отчёте](0378-st-name-type-clash.md#отчёт-о-тестировании).
