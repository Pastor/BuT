### Context

Цель `c` печатает тело `case` состояния так: сначала `always`/`every`, затем
рёбра переходов, затем — общий `break;`, закрывающий ветвь `switch`
(`c_model.rs`, печать хвоста ветви). Ребро **условное** печатается блоком
`if (…) { … break; }` — его `break` обязателен, он выходит из `switch` изнутри
блока. Ребро **безусловное** (`ConditionNode::None`) печатается без обёртки, и
за ним следует такой же `break;` — уже в теле самой ветви. Общий `break;` в
конце `case` печатается всегда, поэтому получается пара подряд.

Замер на корпусе `examples/generated/c` (2026-08-17, 391 файл дерева, C-корпус —
8 моделей): **7 мест** с `break; break;` в шести файлах — `elevator.c`,
`elevator_mini.c`, `float_regulator.c`, `pid_regulator.c`, `regulator.c`,
`stacker.c` (×2). Проба минимальной модели воспроизводит и второй вид того же
корня: ребро, записанное **после** безусловного, печатается целиком и
недостижимо вместе со своим `if`:

```c
case PROBE_RUN: {
    model->n = model->n + 1;
    model->state = PROBE_DONE;
    break;
    if (model->n == 3) {      // недостижимо
        model->state = PROBE_LATE;
        break;
    }
    break;                    // недостижимо
}
```

Инструменты молчат: `cc -Wall -Wextra -Wunreachable-code` на корпусе даёт только
`-Wunused-parameter` (известный кандидат [флаг -Wextra для проверки цели c: 38 предупреждений одного класса](0220-c-gate-wextra.md)) — недостижимый `break` clang не
считает достойным сообщения. То есть цена — не отказ сборки, а **шум в коде,
который читает пользователь**: порождённый C для прошивки читают глазами.

**Главный факт замера — цель `c` в этом одинока.** Три остальные цели на
безусловном ребре **прекращают** эмиссию рёбер, потому что всё дальнейшее
недостижимо:

| Цель | Поведение на безусловном ребре | Место |
|---|---|---|
| `rust` | `return Ok(true)` — эмиссия рёбер прекращается; комментарий прямо ссылается на цель `c`: «в C это молча, в Rust валит `-D warnings`» | `rust_tick.rs` |
| `st` | `return Ok(())` — «цепочка на нём заканчивается» | `st_model.rs` |
| `sv` | ветвь `begin`/`else begin`, дальше цикл не идёт | `sv_fsm.rs` |
| `c` | печатает переход, печатает `break;`, **продолжает** цикл по рёбрам | `c_model.rs` |

Эталон (симулятор) на пробе выбирает `Done` — то есть недостижимость хвоста есть
свойство языка (порядок рёбер), а не расхождение цели с эталоном. Поведение
цели `c` верно; неверна только **форма** вывода.

### Decision Drivers

1. **Читаемость порождённого кода.** Вывод цели `c` — артефакт для человека
   (его кладут в прошивку, читают на ревью, отлаживают на объекте). Два `break`
   подряд и недостижимый `if` заставляют читателя искать смысл там, где его нет.
2. **Единый контракт целей.** Три цели из четырёх уже решают этот вопрос
   одинаково; отставание одной — знакомый проекту класс (0084/0193/0195: «два
   списка одного набора расходятся», «отставала одна цель»).
3. **Поведение не меняется.** Правка обязана быть тождественной по семантике:
   удаляется только код, до которого исполнение не доходит.
4. **Детерминированность и снапшоты.** Вывод корпуса
   (`examples/generated/`) — снапшот под проверкой; изменение формы обязано пройти
   через пересборку корпуса, а не остаться расхождением.

### Considered Options

#### Option A. Не печатать `break;`, когда безусловное ребро — последнее печатаемое

Печать хвоста сохраняется; `break;` подавляется только у последнего по счёту
ребра (с учётом фильтра «цель вне достижимых состояний»).

**Pros:**
- Минимальная правка, вывод в случае «безусловное ребро не последнее» остаётся
  байт-в-байт прежним.
- Недостижимый хвост остаётся **виден** автору в порождённом коде.

**Cons:**
- Лечит следствие, а не причину: недостижимый `if` и его собственный `break`
  остаются — то есть «лишнего кода» после правки по-прежнему сколько угодно.
- Цель `c` остаётся единственной, кто печатает хвост, — расхождение с тремя
  соседями сохраняется, и следующая правка целей снова обойдёт `c`.
- Заводит в печатнике новое знание («какое ребро последнее»), которого нет ни у
  одной другой цели.

#### Option B. Прекращать эмиссию рёбер на первом безусловном и `break;` не печатать

Как в `rust`/`st`/`sv`: безусловное ребро завершает цепочку. Собственного
`break;` у него нет — ветвь закрывает общий `break;` в конце `case`.

**Pros:**
- Устраняет **оба** проявления одного корня: и пару `break; break;`, и
  недостижимый хвост.
- Приводит цель `c` к контракту трёх остальных целей — «безусловное ребро
  завершает цепочку», один ответ на один вопрос у четырёх генераторов.
- Печатник становится проще: цикл выходит на первом безусловном ребре, знания «я
  последний» не требуется.

**Cons:**
- Ребро, написанное после безусловного, исчезает из вывода — автор перестаёт
  видеть в C то, что написал в `.takt`. Смягчается тем, что три другие цели
  ведут себя так уже сейчас, а сама запись бессмысленна (ребро недостижимо
  всегда) и заслуживает **диагностики**, а не отражения в выводе.
- Диагностики о недостижимом ребре сегодня нет — вопрос выносится кандидатом.

#### Option C. Оставить как есть, объяснив комментарием в коде генератора

**Pros:**
- Ноль риска.

**Cons:**
- Шум остаётся; расхождение с тремя целями остаётся; фича закрывается ничем.

### Decision

Принимается **Option B**. Он лечит причину, а не проявление, и снимает
расхождение цели `c` с тремя остальными целями — то самое, что уже описано
комментарием в `rust_tick.rs` как известное отставание. Поведение при этом
тождественно: удаляется исключительно код, до которого исполнение не доходит
(безусловное ребро завершает ветвь `case` через общий `break;`).

Недостижимое ребро остаётся **законной записью языка** — фича его не запрещает и
диагностики не заводит: это отдельный предмет (кандидат в `FEATURES.md`,
по образцу проверки недетерминированных переходов).

### Consequences

#### Положительные

- В порождённом C не остаётся ни `break; break;`, ни недостижимых блоков рёбер.
- Четыре цели отвечают на «что после безусловного ребра» одинаково.
- Печать ветви `case` короче на одну ветвь логики.

#### Отрицательные / Action items

- Снапшоты `examples/generated/c` меняются — обязательна пересборка корпуса и
  проверка проверки детерминированности.
- Нужен **контроль формы**: греп-тест по порождённому C всего корпуса «нет двух
  `break;` подряд». Без него класс вернётся незамеченным (уроки —
  падать контроль обязан **списком** мест).
- Нужен фикстурный контроль на случай «ребро после безусловного»: корпус его не
  содержит (проверено), значит один корпус класс не покрывает.
- Кандидат в `FEATURES.md`: диагностика «ребро недостижимо — стоит после
  безусловного перехода» (сегодня об этом молчат все пять потребителей).

#### Acceptance criteria

1. В `examples/generated/c/*.c` нет ни одной пары `break;` подряд (грепом).
2. Ребро, записанное после безусловного, целью `c` не печатается; поведение
   пробы (симулятор ≡ порождённый C) совпадает с прежним.
3. Потактовые сверки `conformance_*` и проверки корпуса зелены; вывод
   детерминирован (два прогона → `diff -r` без отличий).
4. Контроль формы падает **списком** мест при возврате дефекта (проверено
   мутацией).

## Анализ

### Цель и контекст

Печать рёбер состояния в цели `c` (`takt-lang/src/generator/c/c_model.rs`,
`generate_state_transitions`) на **безусловном** ребре (`ConditionNode::None`)
печатает переход и свой `break;`, после чего **продолжает** цикл по остальным
рёбрам. Ветвь `case` в конце закрывается общим `break;`, поэтому в выводе
появляется пара `break; break;`, а рёбра, записанные после безусловного, —
недостижимый код.

`rust`, `st`, `sv`), собственного `break;` у него нет — ветвь закрывает общий
`break;`.

### Зависимости фичи (правило 17/19)

- **Зависит от:** `нет`. Правка локальна для печатника цели `c`; ни семантика,
  ни грамматика, ни другие цели не затрагиваются.
- **Влияние на порядок разработки:** ничего не разблокирует и не блокируется.
  Следующая по таблице — [цель sv-mmio: reg_wdata и reg_wen не используются на модели без входных битов](0214-sv-mmio-unused-write-signals.md).

### Требования и проверяемые условия

- **R1. Безусловное ребро завершает цепочку.** После печати безусловного ребра
  `generate_state_transitions` прекращает обход `references()` — остальные рёбра
  состояния в вывод не попадают.
- **R2. Собственного `break;` у безусловного ребра нет.** Ветвь `case`
  закрывается единственным общим `break;` (хвост печати ветви `switch`).
- **R3. Поведение тождественно.** Порождённый автомат не меняется: удаляется
  только код, до которого исполнение не доходило. Проверяется потактовой
  сверкой (`conformance_*`) и совпадением трасс симулятора и C на пробе.
- **R4. Условное ребро не затронуто.** Блок `if (…) { … break; }` печатается как
  прежде — его `break` обязателен (выход из `switch` изнутри блока).
- **R5. Прочие места печати `break;` не затронуты.** `generate_extend_transition`,
  `generate_concat_tick`, ветвь `StateExtend::Model` печатают `break;` **внутри**
  блока `if (…)`, где он обязателен; `case … _END`, `default:` и `switch`
  оператора `match` (`c_expr/stmt.rs`) — тоже.
- **R6. Вывод детерминирован.** Проверка двух прогонов с `diff -r` остаётся зелёным.
- **R7. Корпус пересобран.** `examples/generated/` отражает новую форму (снапшот
  под проверкой канона), дифф содержит **только** удаления `break;`.

### Особенности по обратной функциональности

**Обратная совместимость языка — не затрагивается** (правило 11): синтаксис,
семантика, диагностики и наблюдаемое поведение автомата прежние. Меняется
**форма** порождённого C:

- у потребителей, хранящих порождённый C в репозитории, следующий прогон даст
  дифф (удалённые `break;`, удалённые недостижимые блоки рёбер) — изменение
  ожидаемое и объяснимое;
- ребро, записанное **после** безусловного, из вывода исчезает. Это законная,
  но бессмысленная запись (недостижима всегда и у эталона), и три другие цели
  ведут себя так уже сейчас. Диагностики о ней проект не имеет — вопрос вынесен
  кандидатом в `FEATURES.md`.

**Редакторский слой (правило 29): правки не требуется.** Фича не меняет ни
лексику, ни синтаксис, ни семантику — новых токенов, узлов АСД и форм объявления
нет; диагностик не заводит. LSP (`takt-lang/src/lsp/`) и плагины (`extensions/`)
работают с исходным текстом и семантическим деревом, а не с выводом цели `c`.
Ответ фиксируется здесь и повторяется в отчёте (стадия 6).

**Документирование (правило 24): не требуется.** Документ `book/` описывает
язык, а не форму порождённого кода; примеры кода на C в нём — иллюстрации
разделов «Инструментарий»/«Развёрнутый пример». Проверено: показанных фрагментов
с `break; break;` в `book/` нет.

### Риски и зависимости

- **Риск: молчаливое исчезновение рёбер из вывода.** Автор, написавший ребро
  после безусловного, увидит в C только первое. Снижение: поведение и раньше
  было таким (хвост недостижим), три цели уже так делают, а вопрос диагностики
  вынесен кандидатом.
- **Риск: снапшоты корпуса.** Пересборка `examples/generated/` обязана дать
  дифф **только** ожидаемого вида — проверяется чтением диффа перед коммитом.
- **Риск: контроль, ничего не контролирующий** (класс исправления). Снижение:
  греп-контроль проверяется **мутацией**, а фикстурный тест — на пробе, которой в
  корпусе нет.

## Разработка

### Задача

#### Что было

`generate_state_transitions` (`takt-lang/src/generator/c/c_model.rs`) на
безусловном ребре печатала переход, свой `break;` и **продолжала** обход
`references()`. Ветвь `case` закрывается общим `break;`, поэтому вывод содержал
пару `break; break;` (7 мест в корпусе), а рёбра после безусловного печатались
недостижимым кодом:

```c
case PROBE_RUN: {
    model->n = model->n + 1;
    model->state = PROBE_DONE;
    break;
    if (model->n == 1) {          // недостижимо
        model->state = PROBE_LATE;
        break;
    }
    break;                        // недостижимо
}
```

Три другие цели этот вопрос решают одинаково и обратного не печатают
(`rust_tick.rs`, `st_model.rs`, `sv_fsm.rs`).

#### Что сделано

**`takt-lang` (цель `c`).** Ветвь безусловного ребра печатает `exit → enter →
state` и **возвращает управление** (`return Ok(())`): собственного `break;` у
неё больше нет, обход рёбер на ней заканчивается. Условная ветвь не тронута — её
`break;` обязателен (выход из `switch` изнутри блока `if`). Док-комментарий
функции переписан под новый контракт, причина правки и цена прежнего устройства
записаны рядом с кодом.

**Контроля.**

- `takt-lang/tests/targets/c_redundant_break_tests.rs` — четыре проверки: корпус без пар
  `break;` (падает **списком** «файл: строки»), фикстура «хвост после
  безусловного», контр-примеры на условное ребро и терминальное состояние.
- `takt-sim/tests/conformance/conformance_c_unconditional_edge_tests.rs` — **потактовая**
  сверка эталона и порождённой прошивки на модели с хвостом; условие хвоста
  истинно на том же такте, поэтому сверка отличает верную правку от
  половинчатой.
- Фикстуры — `takt-lang/tests/data/cbreak0213/{tail_after_unconditional,
  conditional_and_terminal}.takt` (корпус этот класс не покрывает: записи «ребро
  после безусловного» в `examples/` нет ни одной).

**Корпус и документ.** Пересобран `examples/generated/c` (4 отслеживаемых файла,
−5 строк). Обновлён снимок порождённого C в документе —
`book/src/18-showcase/generated/c/lift.{c,h}` и цитата в
`book/src/18-showcase/index.typ`; попутно снят долг фичи (снимок нёс имена
портов без сегмента `PORT_`, то есть отставал от вывода инструмента).

**`takt-sim`, семантика, грамматика, LSP, плагины — правки не требуется** (н/п):
фича меняет только форму вывода одной цели; язык, диагностики и наблюдаемое
поведение прежние (правило 29 — ответ зафиксирован в анализе и отчёте).

#### Проверки

```sh

cargo test -p takt-sim --test conformance conformance_c_unconditional_edge_tests::  # сверка
./scripts/precheck.sh                                          # полный предкоммит
```

**Мутационная проверка контрольных тестов** (прогнана 2026-08-17):

| Мутация | Кто падает | Наблюдаемое |
|---|---|---|
| M1: вернуть `break;` и продолжение обхода (полный откат) | `corpus_has_no_two_breaks_in_a_row`, `edge_after_unconditional_is_not_emitted` | список из 7 мест в 6 файлах — ровно замер ADR |
| M2: `break;` снят, обход **не** оборван (половинчатая правка) | `unconditional_edge_trace_matches_generated_c` | `sim=[1, 0, 0, 0]` против `C=[1, 9, 9, 9]` |

## Тест-план

### Область и цель

Проверяется **форма вывода** цели `c` и **тождественность поведения**: после
безусловного ребра цель не печатает ни собственный `break;` (R2), ни рёбра,
стоящие за ним (R1), при этом условное ребро (R4), терминальное состояние и
прочие места печати `break;` (R5) не затронуты, автомат прежний (R3), вывод
детерминирован (R6), корпус пересобран (R7).

Инструменты в этой области не свидетели: `cc -Wall -Wextra -Wunreachable-code`
принимает и прежний вывод, и новый, и вывод половинчатой правки. Поэтому
проверки — на **текст порождённого C** и на **потактовую трассу**.

### Выводы и дальнейшие шаги

1. **Корень был один, проявлений — два.** Кандидат называл только пару
   `break; break;`; замер стадии архитектуры вскрыл второе проявление — печать
   рёбер после безусловного — и главное: цель `c` отставала от трёх остальных,
   которые обход прекращают. Правка поэтому не «убрать лишнюю строку», а
   привести цель к общему контракту.
2. **Инструменты этот класс не видят.** `cc -Wall -Wextra -Wunreachable-code`
   молчит и о прежнем выводе, и о новом, и о выводе половинчатой правки —
   поэтому контроля два и оба свои.
3. **Попутная находка (за объёмом фичи).** Снимок порождённого C в документе
   отставал от инструмента с фичи (имена портов без сегмента `PORT_`).
   Снимок цели `c` обновлён; то, что снимки `book/src/18-showcase/generated/`
   никем не сверяются (и прочие цели там не проверялись), вынесено **кандидатом**
   в `FEATURES.md`.
4. **Кандидат по языку.** Ребро после безусловного законно, но недостижимо
   всегда, и об этом молчат все потребители. Предложено предупреждение уровня
   семантики по образцу Ce14 — запись заведена в `FEATURES.md`.
5. **Исправлений (`docs/fixes/`) не потребовалось.**
