# Фича: Устранение переполнения стека на глубине выражений и операторов

- **Номер:** 0129
- **Статус:** **ГОТОВО** (закрыта 2026-07-27)
- **Зависит от:** нет
- **Tier:** 1
- **Связанные issue (анализ):** кандидат блока 2 `FEATURES.md` (аудит 2026-07-27, проба)

## Стадии жизненного цикла

Все стадии — **разделы этой карточки**: «Архитектура (ADR)»,
«Анализ», «Разработка», «Тест-план», «Отчёт о тестировании», «Итог».

## Краткое описание

Глубоко вложенное выражение или оператор роняют **все три инструмента**
(`taktc compile`, `taktc verify`, `takt-sim`) сигналом `SIGABRT` без диагностики.
Тот же класс, что закрытая [итеративные обходы — снятие потолка стека](0052-verify-iterative-traversal.md), но
там итеративными сделаны обходы **по числу состояний**, а глубина
**выражения/оператора** осталась рекурсивной.

> Фича зарегистрирована из бэклога кандидатов (отобрана заказчиком 2026-07-27); далее проходит жизненный цикл по своду.

## Что известно на входе

Проба (аудит 2026-07-27):

- 300 вложенных скобок (`((…x…)) = 1`) либо 300 вложенных `if` → `SIGABRT`,
  `has overflowed its stack`, **без диагностики**;
- глубина 100 — успех; порог между 100 и 300;
- `taktc fmt` **тот же файл обрабатывает штатно** → парсер выживает, потолок
  находится в **семантике**;
- падают одинаково `taktc compile`, `taktc verify` и `takt-sim`.

## Направление решения (наметка, не решение)

- Либо итеративный обход выражений и операторов, либо **явный предел
  вложенности с диагностикой** (прецедент — `MAX_CALL_DEPTH = 256`).
- Контроль по образцу `takt-lang/tests/semantic/deep_model_tests.rs`: поток теста с малым
  стеком падает **раньше**, чем у пользователя, — иначе тест проверяет удачу.

Окончательный выбор — за стадиями **архитектуры** (ADR) и **анализа**: раздел
выше фиксирует то, что уже проверено, а не предрешает реализацию.

## Документирование

**Требуется, если выбран предел вложенности** (появляется новая диагностика →
приложение «Ошибки»). При итеративном обходе — не требуется:
наблюдаемое поведение корректных программ не меняется.

## Архитектура (ADR)

- **Status:** Accepted
- **Date:** 2026-07-27
- **Authors:** Системный аналитик, архитектор, лид разработки
- **Related issues:** [Фича](0129-semantic-deep-nesting.md)

### Context

Построение семантического дерева рекурсивно **по структуре текста**:
`construct_expression` спускается во вложенные выражения, `resolve_condition` —
во вложенные условия. Глубина такой рекурсии задаётся не размером модели, а тем,
сколько скобок написал автор, — и на достаточной глубине кончается стек.

Наблюдалось это как `SIGABRT` (`has overflowed its stack`) **без диагностики**,
причём у всех трёх инструментов: `taktc compile`, `taktc verify`, `takt-sim`.
Локализация (`lldb`) дала две точки: `semantic::condition::resolve_condition` и
`semantic::expression::construct_expression`. Парсер ту же программу переживал
(`taktc fmt` отрабатывал штатно) — потолок находился именно в семантике.

Замеры глубины (сборка debug): в основном потоке (8 МиБ) порог лежал между 240 и
280; в потоке с 2 МиБ — столько по умолчанию у потока теста `cargo test` —
глубина 48 проходила, 64 роняла процесс. То есть один кадр рекурсии стоит
десятки килобайт.

[итеративные обходы — снятие потолка стека](0052-verify-iterative-traversal.md#архитектура-adr) уже решала родственную задачу —
но там глубина рекурсии равнялась **числу состояний модели**, и итеративный
обход был единственным ответом. Здесь глубина равна вложенности **одного
выражения**, что меняет и характер задачи, и допустимые решения.

### Decision Drivers

1. **Инструмент не падает на пользовательском вводе.** Отказ без сообщения —
   худший из возможных исходов: пользователь не знает ни что случилось, ни где.
2. **Библиотеку зовут из LSP.** Переполнение стека в `takt-lang` обрушивает
   редактор целиком; ограничение должно работать в **любом** потоке.
3. **Соразмерность.** Переписывание трёх семейств рекурсии ради ввода, который в
   реальных спецификациях не встречается, — плохая сделка.

### Considered Options

#### Option A. Явный предел вложенности с диагностикой

Счётчик глубины (потоковый) + RAII-отметка; при превышении — диагностика
`SE-062`.

**Pros:**
- Отказ превращается в **сообщение с позицией**; поведение одинаково во всех
  инструментах и в любом потоке.
- Малый объём: один модуль и по строке в каждой рекурсивной точке.
- Прецедент в проекте есть — `MAX_CALL_DEPTH = 256` для цепочек вызовов.
- Ограничивает не только сами рекурсивные функции, но и **всё, что идёт следом**:
  дерево глубже предела не строится, поэтому обходы `validate`, кодогенераторы и
  симулятор получают заведомо неглубокое дерево.

**Cons:**
- Вводит искусственную границу языка (которую надо документировать).
- Значение предела приходится обосновывать замером, а не выводить.

#### Option B. Итеративный обход (как в фиче)

**Pros:**
- Границы нет вовсе; глубина ограничена только памятью кучи.

**Cons:**
- Переписывание **трёх** семейств взаимной рекурсии (выражения, условия,
  операторы) с ручным стеком — правка высокого риска в ядре семантики.
- Не спасает от других рекурсий над тем же деревом: производные `Clone`/`Drop`
  и печать форматтера рекурсивны **по построению** и переполняют стек на глубине
  порядка тысяч (замерено, см. отчёт). То есть цена огромная, а гарантии нет.
- 0052 решала задачу, где глубина = размер модели (то есть неизбежно большая);
  здесь глубина = вложенность одного выражения, и ограничить её осмысленно.

#### Option C. Увеличить стек (запуск работы в потоке с большим стеком)

**Pros:**
- Одна строка в бинарнике.

**Cons:**
- Лечит симптом и **только у CLI**: библиотека остаётся источником падения для
  LSP и любого встраивающего кода, который своим потоком не управляет.
- Порог просто сдвигается: тот же ввод вдвое глубже снова роняет процесс.

### Decision

Принимается **Option A**: модуль `semantic::validate::depth` со счётчиком
глубины и диагностикой **`SE-062`**; контроля поставлены в
`construct_expression`, `resolve_condition` и `resolve_ast_statement`.

**Предел — 32**, обоснование замером: в самом стеснённом из поддерживаемых
окружений (поток 2 МиБ) безопасно проходит глубина 48, поэтому 32 оставляет
полуторакратный запас; для написанной руками спецификации вложенность глубже
трёх десятков недостижима — это признак либо забытой скобки, либо порождённого
текста.

**Вынужденное следствие.** Правка требовала строки в
`semantic/expression.rs`, а тот стоял в реестре узаконенного долга (1360 строк) и
расти права не имел. Поэтому модуль разделён по приёму [остальные нарушители лимита размера модуля (17 файлов)](0088-module-size-remaining.md#архитектура-adr): `expression/mod.rs` (461 строка) +
`expression/tests.rs` (905). Файл **выбыл из реестра долга** — записей стало пять
вместо шести.

### Consequences

#### Положительные

- Глубоко вложенное выражение даёт `SE-062` с позицией вместо `SIGABRT`;
  проверено на `taktc compile`, `taktc verify` и `takt-sim`.
- Библиотека перестала быть источником падения для LSP.
- Реестр долга размера уменьшился на один файл.

#### Отрицательные / Action items

- **Предел искусственный** и задан числом: изменение требует правки двух мест
  (константа и продублированное число в интеграционном тесте). Синхронность
  держит парный контроль `constant_matches_documented_limit`.
- **Остаточные потолки за пределами семантики** (замерено при приёмке): вывод
  форматтера на выражении с ~3000 скобок и производный `Clone` АСД на ~2000
  вложенных операторов по-прежнему переполняют стек. Это **другие** рекурсии
  (печать и обход структуры данных), контроль семантики их не покрывает — вынесено
  кандидатом.
- **Контроль операторов сегодня недостижим:** тела вложенных `if` семантикой не
  разрешаются вовсе (побочная находка приёмки, вынесена кандидатом), поэтому
  глубокой рекурсии операторов не возникает. Контроль оставлен как защита на
  случай, когда эти тела начнут разрешать.

#### Acceptance criteria

1. Вложенность 300 даёт `SE-062` у `compile`, `verify` и `takt-sim` — не `SIGABRT`.
2. Обычная вложенность (в пределах лимита) строится как прежде.
3. Диагностика называет предел числом.
4. Счётчик не «протекает» между сборками в одном потоке.
5. `SE-062` в реестре; проверка `check-diagnostic-codes.sh` зелёный.
6. Реестр размера модулей: `expression.rs` выбыл, новых нарушителей нет.
7. `./scripts/precheck.sh` зелёный.

> Диаграмма по своду **не требуется**: синтаксис не меняется — вводится
> ограничение на глубину и диагностика при его нарушении.

## Анализ

### Цель и контекст

Превратить аварийное завершение на глубоко вложенном вводе в диагностику.
Решение — Option A [ADR](0129-semantic-deep-nesting.md#архитектура-adr): предел
вложенности + `SE-062`.

### Зависимости фичи

- **Зависит от:** `нет`.
- **Влияние на порядок разработки:** побочно **уменьшает долг размера модулей**
  (см. ниже), то есть облегчает работу [вынос оставшихся нарушителей размера модуля (ядро семантики + пришпиленные)](0099-module-size-core.md).

### Локализация (чем измерено)

`lldb -b -o run -o bt` по аварийному процессу — две точки рекурсии:

| Ввод | Падало в |
|---|---|
| 300 вложенных скобок в условии `ref` | `semantic::condition::resolve_condition` |
| 300 вложенных скобок в выражении / вложенные `if` | `semantic::expression::construct_expression` |

Пороги (сборка debug): основной поток (8 МиБ) — между 240 и 280; поток 2 МиБ
(столько по умолчанию у потока `cargo test`) — 48 проходит, 64 роняет. Отсюда
оценка кадра рекурсии — десятки килобайт, и отсюда же выбран предел **32**.

### Требования и проверяемые условия

- **R1. Никакого `SIGABRT`.** На любой глубине инструмент возвращает диагностику.
- **R2. Одинаково у всех потребителей.** `taktc compile`, `taktc verify`,
  `takt-sim` — одно и то же поведение (общий семантический слой).
- **R3. Работает в любом потоке.** Счётчик потоковый: библиотеку зовут из LSP.
- **R4. Счётчик не протекает.** Ранний выход по `?` обязан уменьшать глубину,
  иначе вторая компиляция в том же потоке упрётся в чужой остаток.
- **R5. Обычный код не задет.** Вложенность реальных спецификаций (единицы
  уровней) строится как прежде; вывод корпуса `examples/` байт-в-байт неизменен.
- **R6. Предел назван пользователю.** Сообщение содержит число, документация —
  объяснение и способ обхода.
- **R7. Реестр размера модулей не нарушен.** Правка затрагивает файл из реестра
  долга, которому расти нельзя.

### Критерии приёмки и способ проверки

| # | Критерий | Способ проверки |
|---|---|---|
| A1 | глубина 300 → `SE-062`, не падение | тест `deep_nesting_that_used_to_crash_is_diagnosed` + сквозная проба CLI |
| A2 | то же для выражения в теле | тест `deep_nesting_in_expression_is_diagnosed_too` |
| A3 | вложенность в пределах лимита строится | тест `nesting_within_limit_is_accepted` |
| A4 | превышение на единицу диагностируется | тест `nesting_beyond_limit_is_diagnosed_not_crash` |
| A5 | сообщение называет предел | тест `diagnostic_names_the_limit` |
| A6 | счётчик не протекает | тесты `counter_does_not_leak_between_builds`, `early_return_does_not_leak_depth`, `guard_releases_depth_on_drop` |
| A7 | одинаково у трёх инструментов | проба: `compile`/`verify`/`takt-sim` на одной модели |

| A9 | реестр размера | `./scripts/check-module-size.sh` (записей 5, новых нарушителей нет) |

### Особенности по обратной функциональности

Формально это **ужесточение**: ввод, который прежде принимался, теперь может
быть отвергнут. Практически затронут только ввод, который **ронял инструмент**
(глубина в сотни уровней) либо был к этому близок: предел 32 при наблюдаемом
пороге 240–280 в CLI-потоке отсекает лишь заведомо патологические тексты.
Корпус `examples/` и книга не содержат вложенности глубже единиц уровней —
порождённый код не изменился.

Альтернатива «не ограничивать» проверена и отвергнута (ADR, Option B): она не
даёт гарантии, потому что производные `Clone`/`Drop` и печать форматтера
рекурсивны по построению.

### Риски и зависимости

- **Риск: предел мешает настоящему коду.** Снижается замером (реальная
  вложенность — единицы уровней) и документированным обходом (именованные
  условия `cond`, промежуточные переменные).
- **Риск: рассинхрон предела с тестом.** Константа продублирована числом в
  интеграционном тесте (модуль `pub(crate)`); держит парный контроль
  `constant_matches_documented_limit`.
- **Риск: правка не влезет в реестр размера.** Реализовался: `expression.rs`
  (1360 строк) расти не имел права. Снят разделением на `expression/mod.rs` +
  `expression/tests.rs` — файл **выбыл** из реестра долга.
- **Остаточный риск (принят):** потолки вне семантики — форматтер на ~3000
  скобок и производный `Clone` АСД на ~2000 вложенных операторов. Замерено при
  приёмке, вынесено кандидатом.

## Разработка

### Задача

#### Что было

Рекурсия по структуре текста без ограничения: `construct_expression`,
`resolve_condition`, `resolve_ast_statement`. Глубоко вложенный ввод (сотни
уровней) завершал процесс сигналом, без диагностики, у всех трёх инструментов.

#### Что сделано

1. **Модуль `semantic/validate/depth.rs`** — потоковый счётчик глубины,
   RAII-отметка `DepthGuard` (учёт выхода при разрушении, поэтому ранний возврат
   по `?` не «залипает»), функция `enter(Option<Location>)`, константа
   `MAX_NESTING_DEPTH = 32`, диагностика **`SE-062`**.
2. **Контроля** — по строке в `construct_expression` (позиция из `expr.loc()`),
   `resolve_condition` (`cond.loc()`) и `resolve_ast_statement` (без позиции:
   `ast::Statement` хранит её не во всех вариантах, а выдумывать координаты
   нельзя).
3. **Разделение `expression.rs`** (вынужденное, см. ниже): `expression/mod.rs`
   (461 строка) + `expression/tests.rs` (905). Запись `1360 …/expression.rs`
   удалена из `scripts/module-size-baseline.txt` — записей долга стало **5**.
4. **Реестр и документация:** строка `SE-062` в `docs/diagnostics/README.md`;
   в книге — строка сводной таблицы, подробный разбор с примером и выводом,
   строка в блоке «Частые ошибки» раздела «Выражения».
5. **Тесты:** три юнит-теста механизма в самом модуле (учёт выхода, срабатывание
   ровно за пределом, отсутствие утечки при раннем возврате) + парный контроль
   значения константы; шесть интеграционных в `tests/deep_nesting_tests.rs`.

#### Почему пришлось делить модуль

`expression.rs` стоял в реестре узаконенного долга (1360 строк). Правило проверки:
файл сверх лимита **расти не имеет права**, допустимая правка записи — только
уменьшение. Контроль требовал одной строки в этом файле, поэтому единственный
честный путь — уменьшить файл: тесты вынесены в подмодуль по приёму фичи
(«директория-подмодуль + `use super::*`»). Побочный выигрыш — минус один
нарушитель в реестре.

#### Замеры, на которых стоит предел

| Окружение | Глубина проходит | Глубина роняет |
|---|---|---|
| основной поток CLI (8 МиБ, debug) | 240 | 280 |
| поток теста `cargo test` (2 МиБ, debug) | 48 | 64 |

Предел 32 оставляет запас в самом стеснённом окружении. Счётчик меряет глубину
**узлов дерева**, а не число скобок: условие `(((x))) = 1` добавляет к скобкам
узел сравнения, поэтому «ровно 32 скобки» — уже перебор (учтено в тестах).

#### Что вскрылось попутно (вынесено кандидатами)

- **Тела вложенных `if` семантикой не разрешаются.** Проба: `always { x :=
  unknown_var_zzz; }` даёт `SE-003`, но та же строка внутри одного `if`
  компилируется **молча**. Из-за этого контроль операторов сегодня недостижим —
  глубокой рекурсии операторов просто не возникает.
- **Остаточные потолки вне семантики:** `taktc fmt` на выражении с ~3000 скобок и
  производный `Clone` АСД на ~2000 вложенных `if` по-прежнему переполняют стек.
  Это рекурсии печати и обхода структуры данных, контроль семантики их не
  покрывает.

| A2 то же в выражении тела | ✅ |
| A3 вложенность в пределах лимита | ✅ строится |

## Тест-план

### Область и цель

Фича **языковая**: вводится ограничение и новая диагностика `SE-062`, поэтому
свод применяется полностью — проверки, примеры и контрпримеры.

Особенность области: проверяется поведение при **отказе**, а не вычисление.
Поэтому центральные проверки идут через **публичный API и через CLI**: тест на
внутренний счётчик доказал бы работу механизма, но не то, что точки входа
прикрыты. Это не теория — ровно так и вышло со контролем операторов: механизм
работает, а путь до него в сегодняшних проходах недостижим.

### Примеры и контрпримеры

**Контрпример — отвергается с `SE-062`:**

```takt
var x: u8 := 0;
start S {
    ref S: (((( … ))))  = 1;   // несколько сотен вложенных скобок
}
```

**Пример — принимается как прежде** (вложенность реальных спецификаций):

```takt
var x: u8 := 0;
const LIMIT: u8 := 5;
start S {
    ref Done: ((x + 1) * 2) >= LIMIT;
}
```

Контрпример с разбором и способом обхода (именованные условия `cond`,
промежуточные переменные) вынесен в приложение «Ошибки и предупреждения»;
упоминание — в блок «Частые ошибки» раздела «Выражения».

тесты проверяют **правило** (предел срабатывает и не мешает обычному коду), а не

### Найденные смежные дефекты (вне объёма фичи)

**Н1. Тела вложенных `if` семантикой не разрешаются.** Проба:

```takt
always { x := unknown_var_zzz; }              // SE-003 — ошибка выдаётся
always { if (x = 1) { x := unknown_var_zzz; } }  // компилируется МОЛЧА
```

Неизвестный идентификатор внутри `if` не диагностируется вовсе. Прямое следствие
для этой фичи: **контроль операторов недостижим** — глубокой рекурсии операторов в
сегодняшних проходах не возникает (проверено: 1000 вложенных `if` проходят
семантику). Контроль оставлен как защита на случай, когда эти тела начнут
разрешать. Вынесено кандидатом.

**Н2. Остаточные потолки стека вне семантики.** Замерено при приёмке:

| Что | Порог | Где рекурсия |
|---|---|---|
| `taktc fmt` на вложенных скобках | ~3000 | печать форматтера |
| `taktc verify`/`compile` на вложенных `if` | ~2000 | производный `Clone` для `ast::Expression` |

Это **другие** рекурсии — печать и обход структуры данных, а не семантический
спуск; контроль их не покрывает по построению. Порог на порядок выше прежнего
(240–280) и достижим только порождённым текстом. Вынесено кандидатом с
предложением: ограничивать вложенность на уровне лексера/парсера, чтобы глубокое
дерево вообще не строилось.
