## Краткое описание

Изменить смысл базовых операторов языка Lam:

- **`<=`** — сделать оператором **присваивания** (сейчас — «меньше или равно»);
- **`=`** — сделать оператором **сравнения на равенство** (сейчас — присваивание
  в выражениях `Expression::Assign` и равенство в условиях `Condition::Equal`;
  `==` — равенство в выражениях).

Цель — убрать классический «C-footgun» (случайное присваивание `=` вместо
сравнения `==` в условиях) и снять контекстно-зависимую двусмысленность `=`
(инвариант из `CLAUDE.md`). Форма `<=` для присваивания привычна инженерам асу тп
из VHDL (присваивание сигнала), что созвучно целевой аудитории проекта (правило 12).

## Мотивация / контекст

- **Целевая аудитория (правило 12)** — инженеры промышленных систем управления;
  для них `<=` как «присваивание сигнала» из VHDL нагляднее и безопаснее, чем
  `=`, легко путаемый со сравнением.
- **Устранение инварианта `=`/`==`** — контекстная семантика `=` (равенство в
  `Condition`, присваивание в `Expression`) сегодня источник сложности парсера и
  диагностик; смена операторов делает `=` однозначным (всегда сравнение).

## Риски

- **Слом обратной совместимости (правило 11) — тотальный.** Каждый существующий
  `.lam` использует `=` (присваивание/связывание), `==` (равенство), `<=`
  (меньше-или-равно). Требуется миграция всех файлов и фикстур.
- **Коллизия `<=`.** Реляционный «меньше-или-равно» теряет обозначение —
  нужен новый токен (`=<` / ключевое слово) либо контекстное различение
  (риск LR(1)-конфликтов LALRPOP).
- **Инверсия ожиданий C/Python-программистов** (`=` присваивание, `==`
  сравнение) — рост когнитивной нагрузки для части пользователей.
- Затрагивает всю цепочку: лексер, грамматику, семантику условий, LTL/Бюхи,
  C-генератор, LSP-подсветку, документацию и примеры.

### Context

Заказчик предлагает поменять роль двух базовых операторов языка Lam:

- **`<=`** — сделать **присваиванием** (по образцу присваивания сигнала в VHDL);
- **`=`** — сделать **сравнением на равенство**.

**Текущее состояние (`grammar/src/grammar.lalrpop`, `lexer.rs`).**

| Токен | Сейчас в `Expression` | Сейчас в `Condition` | Сейчас в декларациях |
|---|---|---|---|
| `=`  | присваивание `Expression::Assign` | равенство `Condition::Equal` | связывание: `var x = e;`, `const`, `model … = …`, `type T = …`, `enum V = n`, `cond C = …`, `in/out/inout … = …` |
| `==` | равенство `Expression::Equal` | — (в условиях равенство пишут `=`) | — |
| `<=` | «меньше-или-равно» `Expression::LessEqual` | «меньше-или-равно» `Condition::LessEqual` | — |

Ключевой **инвариант `=`/`==`** (`CLAUDE.md`): смысл `=` контекстно-зависим —
равенство в условиях, присваивание в выражениях. На нём держатся существующие
`.lam` (`ref Next: BTN.0 = 1;`, `cond C = x = y;`).

**Силы, действующие на решение.**

1. **`<=` уже занят** реляционным «меньше-или-равно» в обеих грамматиках. Отдать
   его под присваивание — значит либо потерять реляционный оператор, либо ввести
   для него новый токен, либо различать по контексту (в VHDL это возможно, т.к.
   присваивание сигнала — позиция *оператора*, а `<=`-сравнение — позиция
   *выражения*; в LR(1) LALRPOP это отдельный источник конфликтов).
2. **`=` перегружен связыванием** в декларациях (`var x = e;`). Даже сделав `=`
   «сравнением» в выражениях/условиях, придётся сохранить `=` как *связыватель*
   в декларациях — иначе ломается вся сетка объявлений. То есть `=` останется
   двусмысленным (связывание vs сравнение), просто иначе.
3. **Обратная совместимость (правило 11)** — затрагиваются **все** `.lam`.
4. **Целевая аудитория (правило 12)** — инженеры асу тп; VHDL-стиль `<=` им
   ближе, но большинство инструментов (C-генерация — цель компиляции) остаются
   в C-семантике `=`/`==`.

```plantuml
@startebnf
title Текущее состояние операторов
Assignment      = lvalue, "=", Expression;          (* = присваивание *)
EqualityExpr    = Expression, "==", Expression;     (* == равенство *)
EqualityCond    = Condition, "=", Condition;        (* = равенство в условиях *)
Relational      = Operand, ( "<=" | ">=" | "<" | ">" ), Operand;  (* <= меньше-или-равно *)
Binding         = "var", ident, "=", Expression;    (* = связывание в декларациях *)
@endebnf
```

### Decision Drivers

1. **Устранить путаницу `=`/`==`** — снять «C-footgun» случайного присваивания в
   условии и контекстную двусмысленность `=` (инвариант из `CLAUDE.md`).
2. **Сохранить выразительность** — не потерять реляционный «меньше-или-равно».
3. **Обратная совместимость (правило 11)** — минимизировать слом `.lam`, а при
   неизбежности — обосновать и дать миграцию.
4. **Устойчивость LALRPOP LR(1)** — не плодить грамматические конфликты.
5. **Согласованность с целью компиляции** — язык транслируется в C; сильное
   расхождение операторной семантики с C усложняет чтение сгенерированного кода
   и отладку.

### Considered Options

#### Option A. Прямой запрос: `<=` — присваивание, `=` — сравнение

`<=` становится присваиванием; `=` — равенством (в т.ч. в условиях `=` уже
означает равенство — там смысл сохраняется). Реляционный «меньше-или-равно`»
переобозначается новым токеном (`=<`) или различается по контексту.

**Pros:**
- Достигает запрошенной формы; `<=`-присваивание привычно из VHDL.
- В условиях `=` уже равенство — эта часть согласуется.
- Убирает «C-footgun»: в выражении `=` больше не присваивает.

**Cons:**
- **Тотальный слом совместимости**: все присваивания `a = b` → `a <= b`; все
  `==` → `=`; все реляционные `<=` → новый токен. Требует миграции 100% `.lam`.
- **Потеря/переобозначение `<=`-сравнения** — либо уродливый `=<`, либо
  контекстное различение с риском LR(1)-конфликтов.
- `=` **остаётся** связывателем в декларациях (`var x = e;`) — двусмысленность
  «связывание vs сравнение» не исчезает, лишь меняет форму.
- Расхождение с C (цель компиляции): `<=` в C — сравнение; читаемость
  сгенерированного кода и отладка страдают.
- Инверсия ожиданий большинства программистов (C/Python/Rust).

#### Option B. `:=` — присваивание, `=` — сравнение (Pascal/Ada/ST)

Присваивание — `:=` (как в Pascal, Ada и **ST/IEC 61131-3** — языке асу тп!);
`=` — сравнение на равенство; `<=` **остаётся** «меньше-или-равно».

**Pros:**
- Достигает **той же цели** (убрать путаницу `=`/`==`), но **без коллизии** с
  `<=` — реляционный оператор сохраняется.
- `:=` — стандарт **Structured Text (IEC 61131-3)**, ещё ближе целевой аудитории
  асу тп, чем VHDL-`<=`.
- `=` как сравнение — единообразно и в условиях, и в выражениях (устраняет
  инвариант `=`/`==` по-настоящему: `==` можно вывести из языка).
- Меньше грамматических конфликтов: `:=` — свежий токен, не пересекается ни с чем.

**Cons:**
- Всё ещё слом совместимости (`=`-присваивание → `:=`, `==` → `=`), но **уже**
  прямого запроса: нет переобозначения `<=`.
- `=` остаётся связывателем в декларациях — та же оговорка, что и в A (решается
  трактовкой: в декларации `=` — «инициализатор», семантически отделён от
  сравнения на уровне позиции грамматики).

#### Option C. Статус-кво (ничего не менять) + линт на `=` в условии

Оставить `=`/`==`/`<=` как есть; добавить диагностику-предупреждение при
подозрительном `=` (потенциальном случайном присваивании) в булевой позиции.

**Pros:**
- Нулевой слом совместимости; нулевой риск грамматики.
- Снимает основной риск «footgun» дёшево (диагностикой, не сменой синтаксиса).

**Cons:**
- Не выполняет запрос заказчика по существу.
- Контекстная двусмысленность `=` остаётся.

#### Option D. Контекстное `<=`-присваивание (VHDL-подобное), `<=`-сравнение в выражениях

`<=` = присваивание **только в позиции оператора-присваивания** (statement),
`<=` = «меньше-или-равно» **внутри выражения**. `=`/`==` не трогаем.

**Pros:**
- Даёт VHDL-стиль `<=` без потери реляционного `<=`.
- Совместимость выражений сохраняется частично.

**Cons:**
- Высокий риск **LR(1)-конфликтов** LALRPOP (одна лексема, две роли по контексту).
- Ломает существующие присваивания `a = b` (если `<=` вводится как единственная
  форма) **или** плодит две формы присваивания (`=` и `<=`) — рост когнитивной
  нагрузки и неоднозначность стиля.
- Самая сложная в реализации и объяснении.

### Decision

Принимается **Option B** (`:=` присваивание, `=` сравнение). **Заказчик выбрал
вариант B (2026-07-10); фича взята в разработку.**

**Обоснование.** Запрошенная цель — устранить путаницу `=`/`==` и приблизить
синтаксис к инженерам асу тп — достигается полнее и дешевле вариантом B:

- `:=` — оператор присваивания из **ST/IEC 61131-3** (прямой отраслевой стандарт
  асу тп), точнее попадает в целевую аудиторию, чем VHDL-`<=`;
- сохраняется реляционный `<=` (нет коллизии, нет `=<`-костыля);
- `=` становится единообразным сравнением, `==` выводится из языка — инвариант
  `=`/`==` устраняется по-настоящему (в отличие от Option A, где `=` остаётся
  и связывателем, и сравнением).

**Option A (прямой запрос)** отвергается архитектурно: коллизия с реляционным
`<=`, расхождение с C-целью компиляции, тот же остаточный дуализм `=` в
декларациях — при том же масштабе слома совместимости, что и B, но с бо́льшими
рисками.

```plantuml
@startebnf
title Целевое состояние (Option B)
Assignment      = lvalue, ":=", Expression;         (* := присваивание (ST) *)
EqualityExpr    = Expression, "=", Expression;      (* = равенство везде *)
EqualityCond    = Condition, "=", Condition;        (* = равенство (без изменений) *)
Relational      = Operand, ( "<=" | ">=" | "<" | ">" ), Operand;  (* <= сохранён *)
Binding         = "var", ident, ":=", Expression;   (* инициализатор — тоже := *)
@endebnf
```

### Consequences

#### Положительные

- Устраняется «C-footgun» и контекстная двусмысленность `=` (снимается инвариант
  `=`/`==`).
- Синтаксис ближе к ST/IEC 61131-3 — целевой отрасли (правило 12).
- Реляционный `<=` не теряется; грамматика без коллизий по операторам.

#### Отрицательные / Action items

- **Слом совместимости (правило 11):** повышение **мажорной** версии языка
  (правило 22); нужен **скрипт-мигратор** `.lam` (`= → :=` в присваиваниях/
  инициализаторах, `== → =`) и обновление **всех** фикстур/примеров/доков.
- Переработка: `lexer.rs` (токен `:=`, роль `=`), `grammar.lalrpop` (Assign по
  `:=`, Equal по `=`, вывод `==`), семантика условий, LTL/Бюхи, C-генератор,
  LSP-подсветка, README (правило 15), doctests.
- **Решение принято (2026-07-10): вариант B, фича в разработке.** Декомпозиция —
  4 подзадачи (`0021-01…04`, см. анализ и `docs/development/`).
- Зафиксировать в анализе связь с фичей (обе трогают инвариант `=`/`==`):
  внедрение 0021 меняет вводные 0019.

#### Acceptance criteria

3. Мажорная версия языка повышена; README и doctests синхронизированы.

## Анализ

### Цель и контекст

Заказчик предлагает `<=` сделать присваиванием, а `=` — сравнением. Цель —
убрать путаницу `=`/`==` (случайное присваивание в условии) и приблизить синтаксис
к инженерам асу тп. По **ADR** прямой запрос (Option A) отвергнут из-за
коллизии с реляционным `<=` и расхождения с C-целью компиляции; рекомендован
**Option B** — `:=` присваивание, `=` сравнение (стиль ST/IEC 61131-3), где
реляционный `<=` сохраняется. Настоящий документ разбирает **последствия для
понятности, читаемости, многословности** и совместимости — как просил заказчик.

### Зависимости фичи (правило 17/19)

- **Зависит от:** формально — **нет** (не требует закрытия других фич для старта).
  Есть **пересечение** с фичей **0019** (унификация `Condition`/`Expression`): обе
  трогают инвариант `=`/`==`. Внедрение 0021 (Option B) **устраняет** этот
  инвариант (`=` всюду сравнение, `==` выводится), что меняет вводные 0019 —
  часть её обоснований («разделение `=`/`==` намеренно») отпадает. Это **связь по
  контексту, не блокирующая зависимость**: фичи не обязаны идти в строгом порядке,
  но при принятии 0021 к разработке 0019 должна быть пересмотрена (и наоборот).
- **Влияние на порядок разработки:** 0021 никого не разблокирует и сама не
  заблокирована. Приоритет низкий: фича — крупный слом совместимости с неясной
  окупаемостью; держится в конце последовательности до решения заказчика.
  Рекомендация — **не брать в разработку** до явного подтверждения варианта.

### Влияние на понятность, читаемость и многословность (ключевой разбор)

Сравнение по вариантам ADR (A — прямой запрос, B — рекомендуемый, C — статус-кво).

#### Понятность (семантическая однозначность)

- **Статус-кво (C):** `=` двусмыслен — присваивание в выражении, равенство в
  условии (инвариант `=`/`==`). Источник ошибок и сложности парсера/диагностик.
- **Option A (`<=` присв., `=` сравн.):** `=` в выражении больше не присваивает —
  «footgun» снят. **Но** `=` остаётся **связывателем** в декларациях
  (`var x = e;`) → двусмысленность «связывание vs сравнение» не исчезает. Плюс
  `<=` теперь перегружен: присваивание против «меньше-или-равно». Понятность
  **улучшается частично, но появляется новая перегрузка `<=`**.
- **Option B (`:=` присв., `=` сравн.):** `:=` — отдельный однозначный токен
  присваивания; `=` — всегда сравнение; `<=` — всегда «меньше-или-равно».
  **Максимальная однозначность**, инвариант `=`/`==` устраняется полностью.

#### Читаемость

- `:=` (B) и `<=` (A) визуально читаются как «получает значение» (стрелка) — оба
  нагляднее `=` для присваивания в глазах инженера асу тп.
- **A ухудшает читаемость реляционных выражений**: `x <= 10` в старом коде читалось
  «x не больше 10», в новом — «x получает 10». Немой конфликт значений на одном
  символе — высокий риск неверного прочтения при code review и миграции.
- **B не трогает `<=`** — реляционные выражения читаются как раньше; новый смысл
  несёт только новый значок `:=`. Меньше «ложных друзей».
- Расхождение с C: сгенерированный C-код использует `=`/`==`/`<=` в классическом
  смысле. При A читатель, знающий и Lam, и C, постоянно переключает контекст
  (`<=` там и там значит разное) — когнитивная нагрузка. При B расхождение локализовано
  в `:=` (в C его нет вовсе — визуально явный «это Lam-присваивание»).

#### Многословность

- Присваивание: было `=` (1 символ) → стало `:=`/`<=` (2 символа). Рост на 1
  символ на каждое присваивание — присваивания частотны, суммарно код чуть
  многословнее. Эффект одинаков для A и B.
- Равенство: было `==` (2) → стало `=` (1). Экономия 1 символа на сравнение.
  Сравнения в условиях частотны → частично компенсирует рост присваиваний.
- Итог по объёму: близко к нейтральному; знак меняется в пользу того, чего в
  коде больше (присваиваний или сравнений). Для FSM-моделей с обилием условий
  переходов экономия на `=` заметна.

#### Вывод по понятности/читаемости

Цель заказчика (снять путаницу `=`/`==`) достигается. Но **`<=`-присваивание
(Option A) создаёт новую, более коварную путаницу** — совмещение присваивания и
сравнения на одном символе `<=`, плюс расхождение с C. **Option B даёт тот же
выигрыш без этих минусов** и потому рекомендован. Чистый статус-кво (C) сохраняет
двусмысленность `=`, но её можно частично закрыть диагностикой без слома языка.

### Требования и проверяемые условия (для варианта B, если будет принят)

- **R1. Однозначность присваивания.** `:=` — единственный оператор присваивания
  (в выражениях и инициализаторах деклараций); `=` в позиции выражения/условия —
  только сравнение на равенство.
- **R2. Сохранение реляционного `<=`.** `x <= y` остаётся `LessEqual` во всех
  грамматиках; коллизии с присваиванием нет.
- **R3. Устранение `==`.** Токен `==` выводится из языка (или помечается
  устаревшим с миграцией) — равенство пишется `=`.
- **R4. Миграция совместимости.** Существующие `.lam` переводятся мигратором
  (`=`-присваивание/инициализатор → `:=`; `==` → `=`); поведение после миграции
  идентично исходному (регресс = 0).
- **R5. Версия языка.** Слом синтаксиса → **мажорное** повышение версии языка
  (правило 22); README и doctests синхронизированы (правила 15, 16).
- **R6. Без LR(1)-конфликтов.** `grammar.lalrpop` собирается без новых конфликтов
  LALRPOP.

### Риски и зависимости

- **Риск: коллизия `<=` (только Option A).** Реляционный оператор теряет знак. →

  Рекомендация: **решение о внедрении за заказчиком**; по умолчанию — не брать в

## Тест-план

### Область и цель

Проверить корректность языка и компилятора после смены операторов (Option B):
`:=` — присваивание, `=` — сравнение, `<=` — «меньше-или-равно» (сохранён),
`==` — выведен. Покрываем требования R1–R6 и критерии A1–A6 из анализа.
Формируется **параллельно** разработке (правило 17); включает примеры и
контрпримеры (правило 16).

### Примеры и контрпримеры (правило 16)

**Примеры (valid):**
- `x := 0; y := x + 1;` — присваивания.
- `cond Ready = level = 5;` — равенство в условии.
- `cond Low = temp <= 20;` — реляционный `<=`.
- `var eq := (a = b);` — сравнение в выражении.

**Контрпримеры (invalid):**
- `x = 5;` в позиции присваивания значения — ошибка (нужно `:=`).
- `a == b` — ошибка (`==` выведен, использовать `=`).
- `x <= 5;` в позиции присваивания — трактуется как реляционное выражение, а не
  присваивание (нет «немого» присваивания через `<=`).

## Отчёт о тестировании

### Резюме

Фича **готова к закрытию (ГОТОВО)**. Реализован Option B: `:=` — присваивание,
`=` — сравнение на равенство (в выражениях и условиях), `<=` — реляционный
(сохранён), `==` — выведён. AST-узлы не менялись — переключена привязка токенов

(141 `.lam` + inline-Lam в тестах и `#[cfg(test)]` обоих крейтов + doctests)
мигрирован AST-мигратором. Версия языка `0.0.5 → 0.1.0`.

## Итог (что сделано)

Реализован **Option B** (не исходный запрос — см. ADR): присваивание — `:=`,
сравнение на равенство — `=` (в выражениях и условиях), реляционный `<=`
сохранён, `==` **выведен**. Прямой запрос (`<=` присваивание, `=` сравнение)
отвергнут архитектурно: коллизия с реляционным `<=` и расхождение с C-целью
компиляции.

  инициализаторы `var`/`const`/портов — на `:=`; определения имён
