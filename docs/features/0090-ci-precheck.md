## Краткое описание

CI (`.github/workflows/ci.yml`) выполняет только `cargo build/check/test` — **весь
предкоммит-проверка в CI не идёт**. Не покрыты:

- **живая проверка порождённого C** (cmake/ninja по `examples/`);
- **ST-проверка `iec2c`**: работает и **включён в `precheck.sh`** (валит предкоммит на
  невалидном ST), но в CI не идёт — связывать не с чем;
- **`scripts/check-links.py`** (правило 14): заведён 2026-07-14 и подключён в
  `precheck.sh`; остаток исходного пункта бэклога — ровно «подключить в CI».

То есть предкоммит проверяет живьём **две** цели (`c` и `st`), и обеих CI не видит.

**Урок закрытой [генератор C: typedef корневой структуры для одиночной модели](0026-c-root-typedef.md):** дефект «порождённый C не
компилируется для одиночной модели» дожил до своего исправления именно потому, что
дыра была **не в коде, а в покрытии** — все пять `examples/*.lam` имеют под-модели,
а простейший класс моделей живой проверкой не покрывался вовсе. `precheck.sh` эту
дыру **по-прежнему не закрывает** (там всё те же пять примеров).

**Инструмент CI-пригоден:** MatIEC собирается из исходников
(`scripts/ensure-iec2c.sh`), лицензия открытая, на `ubuntu-latest` bison 3.x (на
macOS системный bison 2.3 сборку **валит** — нужен `brew` bison ≥ 2.4).

> **Объединены два пункта** процессного бэклога («подключить `check-links.py` в CI»
> и «CI не запускает `precheck.sh`»): `check-links.py` уже **часть** `precheck.sh`,
> поэтому второй пункт поглощает первый (решение заказчика 2026-07-17).
>
> **Матрица Windows в объём не входит:** пункт «Windows отсутствует в матрице CI»
> остаётся за фичей [сбои тестов на Windows (пути include, ресурс viewport)](0037-windows-test-failures.md)  —
> решение заказчика 2026-07-17. Там же: CI не соблюдает `--test-threads=1` (при том
> что `CLAUDE.md` требует), `actions-rs/*` архивированы.

> Фича зарегистрирована **2026-07-17** переводом пункта **процессного бэклога**
> `FEATURES.md` (решение заказчика: «завести фичи по кандидатам и процессному
> бэклогу, пока без проработки»). **Проработка не проводилась:** ADR, анализ,
> зависимости, Tier и объём — за стадиями 2–3 (правило 17). Приоритет процессной
> фичи определяется по влиянию на разблокировку других (правило 19, критерий 3).

### Context

Предкоммит-проверка `scripts/precheck.sh` за время проекта вырос до полутора сотен
строк живых проверок. CI (`.github/workflows/ci.yml`) за ним **не поспевал**:
он выполняет только `build`/`check`/`clippy`/`check-module-size`/`test` и **один**
живой проверка — SV (verilator + yosys, добавлен фичей). Всё остальное CI **не
видит**.

#### Замер расхождения (2026-07-20): что делает `precheck.sh` и чего нет в CI

| Проверка `precheck.sh` | Есть в CI? |
|---|---|
| `check-links.py` (правило 14) | **нет** |
| `cargo +nightly fmt` | **нет** (CI не проверяет формат вовсе) |
| `cargo check` / `clippy -D warnings` / `check-module-size` / `test` | да |
| `lamc fmt --check examples/` (канон, 0024) | **нет** |
| проверка воспроизводимости (0048) | **нет** |
| проверка float→q встраиваемых профилей (0096) | **нет** |
| **живая сборка C** (cmake/ninja по `examples/`) | **нет** |
| **проверка `c-hal`** (`cc -c`) | **нет** |
| проверка цели `rust` (rustc + clippy-driver + исполнение) | **нет** |
| проверка цели `sv` (verilator + yosys) | **да** (единственный) |
| проверка цели `sv-mmio` (0062) | **нет** |
| проверка тестбенчей `sv` (verilator `--binary`) | **нет** |
| **проверка ST** (`iec2c` по порождённым `.st`, 0041) | **нет** |

То есть **живьём в CI проверяется одна цель из семи** (`sv`), а остальные шесть
живых проверок — только у разработчика на его машине. Это ровно тот класс дыры,
что дал дожить до своего исправления двум дефектам Tier 1: **0026** (C не
компилируется для одиночной модели — дыра **в покрытии**, а не в коде),
**0020-01** (UB в принятом по умолчанию HAL цели `c-hal`, которую «не компилирует ни один
проверка»), **0041-01** (`iec2c` молча принял склеенные POU). Каждый жил, потому что
арбитр был **необязателен**.

#### Находка проработки (2026-07-20): ST-проверка уже зелёный, 0041 не блокирует

CLAUDE.md утверждал, что ST-проверка «пока не включён» (у `FUNCTION_BLOCK` нет тела →
`iec2c` отвергает). **Проба опровергла:** прогон `iec2c` по всему корпусу (8
примеров) — **все валидны**. Генератор ST дозрел (задачи…05 сделаны), проверка в
`precheck.sh` активен (строки 600–630) и на машине с собранным `iec2c` **не
дремлет**. Следствие: фича **не зависит** от 0041 — включать ST-проверка в CI
безопасно. (Текст CLAUDE.md — устаревший, правится в объёме фичи.)

#### Находка проработки: проверки `precheck.sh` **мягко пропускаются** без инструмента

`precheck.sh` при отсутствии инструмента печатает `[пропуск]` и идёт дальше
(python3, cc, iec2c, verilator/yosys). Исключение — SV: там уже есть флаг
`SV_GATE_REQUIRED=1`, превращающий пропуск в ошибку **специально для CI** («в CI
мягкость недопустима: пропущенный проверка зелёный, то есть неотличим от
пройденного»). Значит **механизм строгости уже придуман** — но живёт только у
одной проверки из шести.

### Decision Drivers

1. **Причина фичи — дрейф.** `precheck.sh` и CI разошлись, потому что это **две**
   реализации набора проверок. Любое решение, оставляющее две реализации, лечит
   симптом, а не причину: они разойдутся снова при следующей фиче-генераторе.
2. **Единый источник истины — сквозной принцип проекта.** Формат позиции
   диагностики, вычисление ширины перечисления, порядок эмиссии — везде проект
   сводит дубли в один слой, потому что «дублирование — механизм расхождения, а
   не стиль». Проверки — тот же случай.
3. **Пропущенный проверка неотличим от пройденного.** В CI отсутствие арбитра обязано
   быть **ошибкой**, а не тихим зелёным (прецедент `SV_GATE_REQUIRED`).
4. **Стоимость дубля выше стоимости прогона.** Полный `precheck.sh` в CI дороже по
   времени (~15–20 мин), но это цена за то, что `main` защищён тем же барьером,
   что и коммит разработчика.

### Considered Options

#### Option A. CI вызывает `./scripts/precheck.sh` целиком (единый источник истины)

CI-джоб ставит инструменты (apt + сборка `iec2c` из исходников) и выполняет
`precheck.sh` **строгим** (все мягкие пропуски → ошибка). Никакой логики проверок в
`ci.yml` не остаётся.

**Pros:**
- **Дрейф исключён конструктивно:** одна реализация проверок. Новая проверка, добавленный
  в `precheck.sh`, автоматически идёт и в CI — без правки `ci.yml`.
- Ровно исполняет заголовок фичи («CI прогоняет весь `precheck.sh`»).
- `--test-threads=1` (требование CLAUDE.md) приходит бесплатно — `precheck.sh` его
  уже задаёт; сегодняшний CI его нарушает.

**Cons:**
- Один крупный шаг GH Actions — гранулярность в UI грубее (какой проверка упал видно
  по `echo`-строкам и `exit 1`, а не по красному шагу). Принимаемо.
- Нельзя раздельно кешировать быстрый линт и долгие проверки. → action item (кеш).

#### Option B. Продублировать недостающие проверки отдельными шагами `ci.yml`

Как сейчас сделан SV-проверка: каждый живой проверка переписывается шагом workflow.

**Pros:**
- Гранулярный UI: каждая проверка — свой шаг.

**Cons:**
- **Воспроизводит ровно причину фичи** — вторую реализацию проверок рядом с
  `precheck.sh`. Они разойдутся снова (драйверы 1, 2). Именно так возник дрейф,
  который фича закрывает.
- Дублирование десятков строк логики (списки `SV_TRANSLATABLE`, флаги `--float-as-q`,
  обёртка `#![no_std]` для rust-проверки, эмуляция MMIO) — источник ошибок копирования.

#### Option C. Гибрид: быстрые проверки шагами, живые проверки — одним вызовом части `precheck.sh`

Оставить `build`/`check`/`clippy`/`test` отдельными шагами (быстрый фидбек), а
живые проверки вынести в один шаг.

**Pros:**
- Быстрый фидбек по линту раньше долгих проверок.

**Cons:**
- Требует **распилить** `precheck.sh` на «быструю» и «живую» части с общими
  переменными — новый шов и новый источник рассинхрона.
- Полу-дубль: часть логики в `ci.yml`, часть в скрипте. Драйвер 1 не закрыт.

### Decision

Принимается **Option A**. Причина фичи — **дрейф двух реализаций проверок**;
единственное решение, устраняющее его конструктивно, — иметь **одну** реализацию
(`precheck.sh`) и звать её из CI. Это прямо соответствует сквозному принципу
проекта (драйвер 2) и букве заголовка фичи. Гранулярность UI (довод Option B) —
меньшая ценность, чем отсутствие рассинхрона; она возмещается `echo`-прогрессом
скрипта.

Чтобы «мягкость недопустима в CI» (драйвер 3) выполнялась для **всех** проверок, а
не только SV, **обобщаем** существующий механизм `SV_GATE_REQUIRED` до единого
флага `PRECHECK_STRICT=1`: под ним каждый мягкий пропуск (`python3`, `cc`,
`iec2c`, cmake/ninja, verilator/yosys) становится **ошибкой**, а `cargo fmt` идёт
как `fmt --check` (падает на неканоне вместо тихой переформатации). Локально без
флага поведение `precheck.sh` **не меняется** (мягкие пропуски остаются мягкими —
машина разработчика вправе быть без `verilator`).

### Consequences

#### Положительные

- CI впервые проверяет **живьём все семь целей** и все инфраструктурные проверки
  (воспроизводимость, float→q, канон формата, ссылки). Класс дефектов «дыра в
  покрытии» (0026/0020-01/0041-01) в `main` больше не проходит.
- `ci.yml` **не содержит логики проверок** — только установку инструментов и вызов
  скрипта. Добавление проверки в `precheck.sh` автоматически покрывает и CI.
- `--test-threads=1` в CI выполняется (устранён латентный источник гонок).

#### Отрицательные / Action items

- **Обобщить строгий режим `precheck.sh`** (`PRECHECK_STRICT=1`): свести
  `SV_GATE_REQUIRED` и новые проверки инструментов к одному флагу; `fmt --check`
  под флагом..
- **Переписать `ci.yml`** на единый ubuntu-джоб: `checkout@v4` +
  `dtolnay/rust-toolchain` (nightly, rustfmt+clippy) + apt-инструменты + сборка
  `iec2c` (`ensure-iec2c.sh`, bison ≥ 2.4 на ubuntu есть) + прогон `precheck.sh`
  под `PRECHECK_STRICT=1`.. Архивные `actions-rs/*` при этом
  **уходят** — их замена в объёме этой фичи неизбежна (без toolchain-шага скрипт
  не запустить). Это **пересекается** с пунктом, номинально закреплённым за 0037
  («`actions-rs/*` архивированы», «CI не соблюдает `--test-threads=1`»): фича
  закрывает **CI-модернизацию** как побочный, неизбежный результат Option A, а за
  0037 остаётся **только матрица Windows**. Аналитик фиксирует
  пересмотр (правило 19); окончательное подтверждение — за заказчиком.
- **Время прогона CI растёт** до ~15–20 мин (apt-инсталл + сборка `iec2c` +
  cmake/ninja + verilator/yosys + однопоточные тесты). Кеширование (`Swatinem/
  rust-cache`, кеш `iec2c`, кеш apt) — **кандидат** в бэклог, не в объёме фичи.
- **CLAUDE.md устарел** про ST-проверка («пока не включён») — правится в объёме фичи.

#### Acceptance criteria

1. `ci.yml` состоит из установки инструментов и **одного** вызова `./scripts/
   precheck.sh` под `PRECHECK_STRICT=1`; grep по `ci.yml` не находит собственных
   вызовов `verilator`/`yosys`/`cmake`/`iec2c`/`rustc` (нет дублей логики проверок).
2. Под `PRECHECK_STRICT=1` **каждый** проверка исполняется (не пропущен): в логе CI
   присутствует строка успеха каждого проверки (C, c-hal, ST, rust+исполнение, sv,
   sv-mmio, тестбенчи, воспроизводимость, float→q, fmt-check примеров,
   check-links).
3. Строгость доказана пробой: искусственное удаление одного инструмента (или
   искусственно-невалидный вывод) → CI **красный**, а не зелёный-с-пропуском.
4. Локальный `precheck.sh` без флага ведёт себя байт-в-байт как прежде (мягкие
   пропуски остаются мягкими) — негативный контроль против регресса DX.
5. `precheck.sh` зелёный на чистом `main` в CI (полный прогон).

## Анализ

### Цель и контекст

CI видит один живой проверка из семи (`sv`); шесть остальных (C, c-hal, ST, rust,
sv-mmio, тестбенчи sv) плюс инфраструктурные (воспроизводимость 0048, float→q
0096, канон формата, check-links) исполняются только на машине разработчика.
ADR принял **Option A**: CI вызывает `./scripts/precheck.sh` целиком под
строгим режимом — одна реализация проверок, дрейф исключён конструктивно.

### Зависимости фичи (правило 17/19)

- **Зависит от:** **нет.** Проверены две подозреваемые зависимости:
  - **0041 (генератор ST).** CLAUDE.md утверждал, что ST-проверка «пока не включён»
    (пустые `FUNCTION_BLOCK`). **Опровергнуто пробой 2026-07-20:** `iec2c` принял
    **все 8** примеров корпуса (`comprehensive`…`stacker`). Проверка активен и зелёный
    — 0041 **не блокирует**.
  - **Инструментальная готовность.** Полный `precheck.sh` прогнан локально
    2026-07-20 (все инструменты присутствуют) → **EXIT=0**, рабочее дерево не
    изменилось (идемпотентность). Живых препятствий к прогону в CI нет.
- **Влияние на порядок разработки:** фича **разблокирующая по покрытию** —
  защищает `main` от класса «дыра в покрытии» (0026/0020-01/0041-01), но формально
  ни одну фичу очереди не разблокирует (у хвоста 0070–0094 колонка «Зависит от»
  пуста). **Пересмотр (правило 19):** Option A неизбежно модернизирует `ci.yml`
  (замена архивных `actions-rs/*`, соблюдение `--test-threads=1`) — эти два
  под-пункта номинально числились за 0037. После 0090 за **0037 остаётся только
  матрица Windows**. Зависимости между 0090 и 0037 **нет** (обе
  правят `ci.yml`, но 0037 — последняя в очереди по решению заказчика; при её
  взятии базой станет уже переписанный workflow).

### Требования и проверяемые условия

- **R1. Единственная реализация проверок.** Логика живых проверок существует **только**
  в `precheck.sh`; `ci.yml` её не дублирует, а вызывает скрипт.
- **R2. Строгость в CI.** Под `PRECHECK_STRICT=1` отсутствие любого инструмента
  (`python3`, `cc`, `cmake`/`ninja`, `iec2c`, `verilator`, `yosys`) — **ошибка**,
  не пропуск. Обобщает существующий `SV_GATE_REQUIRED`.
- **R3. Формат под строгим режимом.** Под `PRECHECK_STRICT=1` формат проверяется
  (`cargo +nightly fmt --check`), а не применяется — неканоничный коммит валит CI.
- **R4. Мягкость сохранена локально.** Без флага `precheck.sh` ведёт себя как
  прежде: мягкие пропуски мягкие, `fmt` применяется. DX разработчика не тронут.
- **R5. Все живые проверки исполняются в CI.** C (cmake/ninja), c-hal (`cc -c`), ST
  (`iec2c`), rust (rustc + clippy-driver + исполнение), sv (verilator + yosys),
  sv-mmio, тестбенчи sv, воспроизводимость, float→q, канон формата примеров,
  check-links — каждый даёт строку успеха в логе.
- **R6. Инструменты ставятся в CI.** apt: `cmake ninja-build verilator yosys bison
  flex build-essential`; `iec2c` — сборкой из исходников (`ensure-iec2c.sh`);
  `python3` присутствует на `ubuntu-latest`; toolchain — nightly + rustfmt +
  clippy (даёт `rustc`/`clippy-driver`).

## Разработка

### Задача

#### Что было

`precheck.sh` при отсутствии инструмента печатает `[пропуск]` и продолжает
(python3 → пропуск проверки ссылок; cc → пропуск проверки c-hal; iec2c → пропуск
проверки ST; verilator/yosys → пропуск проверок sv/sv-mmio/тестбенчей). Строгость
существует **только** у SV-проверки — флаг `SV_GATE_REQUIRED=1` (превращает пропуск
verilator/yosys в `sv_failed=1`). Формат идёт как `cargo +nightly fmt` — **применяется**,
а не проверяется. То есть в CI пять из шести классов проверок остались бы мягкими:
пропущенный проверка зелёный, неотличим от пройденного (риск R2/R3 анализа).

#### Что сделано

Вводится **единый** флаг строгости `PRECHECK_STRICT` (умолчание `0`). Под
`PRECHECK_STRICT=1`:

1. **`SV_GATE_REQUIRED` подчиняется общему флагу.** В начале скрипта:
   `SV_GATE_REQUIRED="${SV_GATE_REQUIRED:-$PRECHECK_STRICT}"` — строгий режим
   автоматически включает и SV-строгость, но явный `SV_GATE_REQUIRED` по-прежнему
   уважается (обратная совместимость с CI-шагом до переписывания).
2. **Общий хелпер `require_tool <имя> <как поставить>`** для каждого мягкого
   пропуска: под флагом печатает ошибку и валит скрипт (`exit 1`), без флага —
   прежний `[пропуск]`. Заменяет разрозненные `else echo [пропуск]` в:
   - проверка ссылок (`python3`);
   - проверка c-hal (`cc`);
   - проверка ST (`iec2c` — проверка `-x $IEC2C_BIN`);
   - живая сборка C (`cmake`/`ninja` — сейчас безусловны; под флагом отсутствие →
     ошибка, а не падение с неясным сообщением).
   Существующий `sv_tool_missing` переиспользует тот же флаг (уже делает через
   `SV_GATE_REQUIRED`, теперь связанный с `PRECHECK_STRICT`).
3. **Формат под флагом — `--check`.** Строка `$CARGO_CMD +nightly fmt` заменяется
   на условную: `PRECHECK_STRICT=1` → `$CARGO_CMD +nightly fmt --check` (падает на
   неканоне), иначе — прежнее применение `fmt`.

Изменения **аддитивны** (правило 11): без `PRECHECK_STRICT` (умолчание) поведение
байт-в-байт прежнее — мягкие пропуски мягкие, `fmt` применяется, `SV_GATE_REQUIRED`
управляется как раньше. Строгость — свойство **среды вызова**, а не скрипта.

Лимит размера модуля (правило 27/0027) на `precheck.sh` не распространяется
(это не Rust-модуль), но скрипт близок к 630 строкам — хелпер `require_tool`
сокращает дублирование, а не наращивает.

#### Проверки

- **A4 (негативный контроль DX):** снять `verilator` из PATH, запустить без флага →
  строка `[пропуск] verilator …`, `EXIT=0`. Локальное поведение неизменно.
- **A3 (строгость):** `PRECHECK_STRICT=1` + недоступный `verilator` → `EXIT≠0` с
  явным сообщением про обязательность проверки.
- **A6 (формат):** испортить формат любого `.rs`, `PRECHECK_STRICT=1 ./scripts/
  precheck.sh` → провал на шаге `fmt --check` до долгих проверок.
- **Регресс:** полный `./scripts/precheck.sh` (без флага) на машине со всеми
  инструментами → `EXIT=0`, `git status` чист (правило 5).

### Задача

#### Что было

`.github/workflows/ci.yml` — единственный ubuntu-джоб на архивных `actions-rs/*`
(`toolchain@v1`, `cargo@v1`) и `actions/checkout@v2`. Прогоняет `build`/`check`/
`clippy -D warnings`/`check-module-size`/`test` (без `--test-threads=1`) и **один**
живой проверка — SV, **переписанный руками** в шаге workflow (свой цикл по
`examples/*.lam`, свой список обязательных `stacker`/`elevator_mini`, свои вызовы
`verilator`/`yosys`). То есть CI несёт **вторую реализацию** SV-проверки рядом с
`precheck.sh` — источник дрейфа (причина фичи).

#### Что сделано

`ci.yml` переписан на **единый источник истины** (Option A ADR): установка
инструментов + один вызов `./scripts/precheck.sh` под `PRECHECK_STRICT=1`. Вся
логика проверок уходит из workflow.

Каркас джоба (`ubuntu-latest`):

1. `actions/checkout@v4`.
2. Toolchain: `dtolnay/rust-toolchain@nightly` с `components: rustfmt, clippy`
   (даёт `rustc`/`clippy-driver` на PATH — их требует rust-проверка `precheck.sh`).
3. Системные инструменты одним `apt-get install -y`: `cmake ninja-build verilator
   yosys bison flex build-essential` (`python3`, `cc`/gcc — уже на образе).
4. Сборка `iec2c`: `./scripts/ensure-iec2c.sh` (bison 3.x на ubuntu; кладёт в
   `~/.local/bin/iec2c` + библиотеку). Отдельным шагом — чтобы отказ сборки был
   виден именно как сборка арбитра, а не внутри прогона.
5. Прогон: `env: { PRECHECK_STRICT: 1 }` → `run: ./scripts/precheck.sh`.

`SV_GATE_REQUIRED` явно **не** задаётся — он наследует `PRECHECK_STRICT` (0090-01).
Логики проверок (циклы, списки, вызовы инструментов) в `ci.yml` **не остаётся**
(A1): workflow только ставит инструменты и зовёт скрипт.

Замена `actions-rs/*` (архивированы) на `dtolnay/rust-toolchain` — неизбежна: без
toolchain-шага `run:`-скрипт не выполнить. Это закрывает CI-модернизацию,
номинально числившуюся за 0037; за 0037 остаётся только матрица Windows
(зафиксировано в анализе 0090, пересмотр по правилу 19).

#### Проверки

- **A1:** grep по `ci.yml` — нет `verilator`/`yosys`/`cmake`/`iec2c -T`/`rustc`
  как команд проверок; есть ровно один `./scripts/precheck.sh`.
- **A2 + A5:** зелёный прогон workflow на push; в логе — строка успеха каждого
  живого проверки (C, c-hal, ST 8/8, rust+исполнение, sv, sv-mmio, тестбенчи,
  воспроизводимость, float→q, fmt-check примеров, check-links).
- **A3 (в CI):** временная проба на служебной ветке — убрать `verilator` из шага
  установки → workflow **красный** (доказывает, что проверка обязателен, а не мягко
  пропущен). После доказательства проба откатывается.
- **Локальный регресс:** `./scripts/precheck.sh` без флага по-прежнему зелёный и
  идемпотентный (правило 5).
