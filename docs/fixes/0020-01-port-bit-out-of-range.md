# Исправление: бит адреса порта не проверяется — `c-hal` читает не тот бит либо даёт UB

> Фича: [../features/0020-port-address-decl.md](../features/0020-port-address-decl.md) (задача — принятый по умолчанию HAL) · обнаружено при проработке [фичи](../features/0062-sv-mmio-target.md)

- **Статус:** **ИСПРАВЛЕН** (2026-07-20, фича-владелец
  [проверка диапазона бита адреса порта и безопасный принятый по умолчанию HAL](../features/0098-port-bit-range-safe-hal.md), `precheck.sh` зелёный). Tier
  1 — **молчаливо неверное чтение** и **неопределённое поведение**;
  воспроизводился **на корпусе**.
- **Владелец исправления — [проверка диапазона бита адреса порта и безопасный принятый по умолчанию HAL](../features/0098-port-bit-range-safe-hal.md)**
  (заведена как отдельная). Диапазон бита разрешён на **[0, 63]** (предел
  `uint64_t`), ширина доступа HAL — минимальное слово, содержащее бит; заведён проверка
  компиляции `c-hal`. Открытый вопрос ниже разрешён: «ширина типа порта» отвергнута
  (несовместима с битовой упаковкой), принята Option C ADR.

## Что не так

Бит адреса порта (`адрес:бит`) **не проверяется нигде**:

- `address_map.rs:42` и `:365` — `pub bit: Option<i64>`; **греп по всему
  `grammar/src`** не находит ни одной проверки диапазона (`bit > 7`, `bit >= 32`,
  «бит вне разрядности»). Единственная такая проверка в проекте —
  `st_expr.rs:514`, и она про **битовый доступ `x.0` в выражении**, а не про
  адрес порта.
- Тип `i64` допускает и **отрицательный** бит — и принятый по умолчанию HAL это косвенно
  подтверждает, защищаясь `b.bit < 0 ? 0 : b.bit`.

## Корпус уже содержит дефектный случай

`examples/extend_complex.lam`:

```
out IDLE: bit := 0x44533932:1;
out WORK: bit := 0x44533932:2;
in  WAIT: bit := 0x44533932:33;    // ← бит 33
```

Три порта делят **одно слово**, причём **разных направлений**, а бит `33` выходит
за пределы чего угодно байтового.

## Что порождает цель `c-hal` (проба 2026-07-17)

```c
[EXTEND_COMPLEX_WAIT] = { (uintptr_t)0x44533932u, 33, 1 },
…
static bool ExtendComplex_default_read_bit(ExtendComplex_In_BitPort p, void *userdata) {
    ExtendComplex_PortBinding b = ExtendComplex_In_BitPort__ADDR[p];
    return ((*(volatile uint8_t*)b.addr) >> (b.bit < 0 ? 0 : b.bit)) & 1u;
}
```

Читается **один байт** (`uint8_t`), затем сдвиг на `b.bit`. Отсюда две беды:

| Бит | Что происходит | Класс |
|---|---|---|
| 0…7 | верно | — |
| **8…31** | загружен **один байт**; после целочисленного продвижения до `int` сдвиг даёт **всегда 0** | **молча неверно** |
| **≥ 32** | `int >> 33` — **undefined behavior** (C11 6.5.7p3: сдвиг на величину ≥ ширины продвинутого типа) | **UB** |

**Проба:** `cc -Wall` компилирует это **без единого предупреждения** и печатает
`1`. Предупредить компилятор **не может**: `b.bit` — значение времени выполнения
(поле структуры), а не константа.

## Почему дожило

**Цель `c-hal` не компилируется ни одним проверкой.** В `scripts/precheck.sh` она
встречается **единственный раз** — в проверке **детерминизма** (строка 118: два
прогона + `diff`), то есть её вывод сверяют сам с собой, но **никогда не подают
компилятору**. Проверка цели `c` (cmake + ninja) собирает `examples/generated/c`;
каталога `c-hal` в `examples/generated/` **нет вовсе**.

Класс — тот же, что у [генератор C: typedef корневой структуры для одиночной модели](../features/0026-c-root-typedef.md) и
[цель `c` теряет знак перечисления — переход мёртв молча](../fixes/0005-01-c-enum-signedness.md): **дыра в покрытии, а не в
коде**. Здесь она особенно обидна: `c-hal` — единственная цель, ради которой
адреса вообще существуют.

## Как чинить (эскиз; решение — за фичей-владельцем)

1. **Диагностика** в семантике: бит вне диапазона → ошибка. Что считать
   диапазоном — решение: разрядность **типа порта** (для `bit` — 0) или
   разрядность **адресуемого слова** (тогда язык обязан её выражать; сегодня не
   выражает — см. «Открытый вопрос»).
2. **Принятый по умолчанию HAL** не вправе эмитить UB: ширина чтения обязана соответствовать
   биту (`uint8_t` при бите 0…7, `uint32_t` при 0…31 и т. д.).
3. **Завести проверка**: `c-hal` обязан **компилироваться**, а не только сверяться на
   детерминизм.

## Открытый вопрос (для фичи-владельца)

`0x44533932:33` подразумевает слово **шириной ≥ 34 бита**, но язык ширину
адресуемого слова **не выражает** — есть только адрес и бит. Пока это не решено,
любая проверка диапазона будет угадыванием. Смежно с
[инициализатор порта — это адрес, но проверяется как значение](../features/0070-port-initializer-address-role.md) (инициализатор порта
играет две роли) и [ключ карты адресов — голое имя порта](../features/0084-address-map-qualified-key.md).

## Критерии закрытия

1. Бит вне диапазона → **диагностика**, а не тихое чтение нуля.
2. Принятый по умолчанию HAL цели `c-hal` не содержит сдвига на величину ≥ ширины типа (нет
   UB) — проверяется тестом на значениях, а не грепом.
3. `c-hal` **компилируется** проверкой `precheck.sh` (сегодня — не компилируется
   вовсе).
4. `extend_complex.lam` либо исправлен, либо его бит 33 обоснован решением по
   «Открытому вопросу».
