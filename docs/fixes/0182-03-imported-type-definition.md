# Исправление: импорт переносит имя типа, но не его устройство

> Фича: [../features/0182-pid-library-and-application.md](../features/0182-pid-library-and-application.md) · смежно: [общие переменные библиотечного файла в импортёре](../features/0184-imported-shared-variables.md) (усыновление импортированных объявлений) · связанные исправления: [пИД-регулятор — тип данных с операциями, а не модель-автомат](0182-01-pid-law-as-type-and-functions.md), [файл без стартового состояния — библиотека, а не ошибка](0182-02-library-file-without-start.md)

- **Статус:** **ИСПРАВЛЕН** (2026-08-14), заведён в тот же день.
- **Обнаружено:** при работе над [пИД-регулятор — тип данных с операциями, а не модель-автомат](0182-01-pid-law-as-type-and-functions.md)
  — первым же прогоном применения, которое подключает `struct` из библиотеки.
- **Tier 1 — молчаливо неверный вывод.** Отказа нет; `taktc` рапортует об
  успехе, а порождённый файл не компилируется.

## Проблема

`import { Pid } from "library.takt";` переносил **имя** структуры и не переносил
её устройство. Оба потребителя отвечали неверно, каждый по-своему:

| Потребитель | Ответ до исправления |
|---|---|
| цель `c` | печатала `Pid p;` **без `typedef`** — `cc` отвергал: `error: unknown type name 'Pid'` |
| симулятор | строил агрегатный инициализатор `{…}` **массивом** и отвечал `SIM-012` «доступ к полю возможен только у структуры, а не у значения массив» |

Отказа компилятора при этом не было **ни одного**: `taktc compile`
заканчивался словом «Скомпилировано». Ошибку приносил чужой инструмент — `cc` на
порождённом файле, — по которому исходную причину не опознать.

## Причина

Устройство типа живёт **не там же, где имя**. У `ModelNode` две карты:

```rust
pub types:   BTreeMap<String, TypeNode>,              // имя типа
pub structs: BTreeMap<String, StructDefinitionNode>,  // поля
pub enums:   BTreeMap<String, EnumDefinitionNode>,    // варианты
```

Выборочный импорт (`semantic/import/select.rs`) знает **четыре** категории —
модели, типы, переменные, условия — и для типа переносил только запись из
`types`. Поэтому `import { Pid }` не давал `SE-017` («имя не найдено»): имя
находилось. Находилось — и приезжало пустым.

**Почему дожило.** Единственная запись `struct` в корпусе примеров —
`examples/extend_complex.takt`, и она объявлена **в том же файле**, где
используется; ни один пример структуру не импортировал. Проверки цели `c`
компилируют корпус, а корпус этой формы не содержал.

## Решение

`select::apply` при переносе имени типа переносит и его устройство —
`carry_definition`: структура из `structs`, перечисление из `enums`.

**Под псевдонимом** (`import { Pid as Loop }`) определение переименовывается
**вместе с ключом карты**: потребители — генераторы и симулятор — ищут
устройство по тому имени, которое видят в объявлении переменной. Оставив
исходное имя, исправление поменял бы один отказ на другой.

## Проверки

- `takt-lang/tests/semantic/import_type_definition_tests.rs` — три контроля: структура,
  перечисление, псевдоним. Проверяется **вывод**, а не карта семантики:
  наличие `typedef struct Pid` в порождённом заголовке. Юнит-тест на карту
  прошёл бы и в тот день, когда карту наполнили, а генератор научить забыли.
- Мутация «снять `carry_definition`» валит все три контроля.
- `examples/pid_heater.takt` — применение подключает `struct Pid` из библиотеки
  и **симулируется**: контур сходится за 33 такта, обе ступени отрабатывают.
  Прежде тот же вход давал `SIM-012` на первом шаге.
- `./scripts/precheck.sh` — код возврата 0.

## Что осталось не сделанным

**Функции не импортировались** (`SE-017`) — отсутствующая категория, а не
дефект переноса. **Устранено** исправлением
[импорт переносит функции библиотеки](0182-04-import-functions.md) в тот же день: `examples/pid_heater.takt`
больше не повторяет закон, а зовёт `pid_compute` библиотеки.
