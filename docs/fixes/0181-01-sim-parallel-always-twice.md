# Исправление: симулятор исполняет `always` композиции дважды за такт

> Заголовок и первая редакция говорили о **параллельной** композиции — так
> дефект был замечен. Повторная проба (2026-07-29, прототип корпусного примера
> фичи) показала, что он бьёт и по **последовательной**: причина общая —
> `Unit::execution` спускается в детей у обоих композитов.

> Фича: [../features/0181-sim-state-implementation-tick.md](../features/0181-sim-state-implementation-tick.md) · анализ: [../features/0181-sim-state-implementation-tick.md#анализ](../features/0181-sim-state-implementation-tick.md#анализ) · отчёт: [../features/0181-sim-state-implementation-tick.md#отчёт-о-тестировании](../features/0181-sim-state-implementation-tick.md#отчёт-о-тестировании)

- **Статус:** **ИСПРАВЛЕН** (2026-07-29). Заведён в тот же день. **Tier 2 —
  эталон молча неверен.** Симулятор — эталон поведения проекта; порождённый код
  (`c`/`rust`/`st`/`sv`) **верен** и правки не потребовал.
- **Обнаружено:** при разработке фичи (проба на композите `|`, поставленная
  для того, чтобы новый спуск в реализацию состояния не добавил третьего
  исполнения).
- **Класс:** «эталон А и эталон Б разошлись» — тот же, что у
  [симулятор не исполняет композицию с переходом `next`](0057-01-sim-composition-next.md), но на **параллельной** композиции.
- **Почему всё же исправлен сразу.** Первая оценка («нужен отдельный разбор:
  какое из двух исполнений лишнее») не подтвердилась замером: у
  `Unit::execution` оказался **ровно один** внешний вызыватель — `tick_body`, —
  и лишним однозначно является спуск композита, потому что ребёнок обязан
  исполнять свои блоки сам (иначе одиночный узел их не получил бы). Правка
  свелась к снятию рекурсии. Оценку изменил прототип корпусного примера фичи
  [корпусной SV-транслируемый пример на последовательную композицию `+`](../features/0166-sv-example-sequential-composition.md): дефект бьёт и по
  `+`, то есть новый пример нёс бы удвоенный счётчик в эталоне.

## Проблема

Тело `always` под-модели **параллельной** композиции исполняется **дважды** за
один такт. Накапливающее присваивание (`n := n + 1`) даёт удвоенный результат.

Проба 2026-07-29 (дерево до и после правок 0181 — поведение одинаково):

```
var n: u8 := 0;
model A { start S { always { n := n + 1; } } }
model B { start T; }
start P = A | B;
```

| Эталон | Значение `n` после такта 1 |
|---|---|
| Порождённый C (`cc` + харнесс) | **1** |
| Симулятор (`takt-sim -n 3`) | **2** |

## Причина

Двойной обход в такте композита:

1. `tick_body` (`takt-sim/src/unit/tick.rs`) зовёт `self.execution("always")`;
   `Unit::execution` для `Parallel`/`Sequential` **рекурсирует в детей** и
   исполняет их блоки `always`;
2. затем `tick_parallel`/`tick_sequential` тикают тех же детей через
   `tick_mode`, и `tick_body` **каждого ребёнка** снова зовёт
   `execution("always")`.

То есть шаг «исполнить `always`» выполняется и родителем за ребёнка, и самим
ребёнком.

## Почему дожило

Корпусные композиции пишут **идемпотентные** присваивания (`x := <выражение>`),
а не накопления: `stacker` (`CR | MC | LC`) и `elevator_mini` (`Cabin | Motor`)
дают один и тот же результат при любом числе исполнений. Потактовые сверки
(`conformance_c_tests`, `conformance_sv_tests`) наблюдают именно такие
переменные, поэтому удвоение в них не проявляется.

Значит, дефект **невидим для всего существующего покрытия** — воспроизводится
только накапливающим телом, которого в корпусе нет.

## Решение

Из `Unit::execution` снят **шаг 4** — спуск в дочерние юниты
(`takt-sim/src/unit/mod.rs`). Ребёнок исполняет свои блоки сам, в собственном
`tick_body`, и множество исполняемых детей от снятия рекурсии **не изменилось**:
у `Parallel` тикаются все, у `Sequential` — активный шаг, ровно те же, в которые
спуск и шёл. То есть удаляется дубль, а не работа.

Опасение «метод публичный, вызывающих много» замером **не подтвердилось**:
внешний вызыватель ровно один — `tick_body`; остальные два вхождения были самой
снятой рекурсией.

## Проверки

Регресс — `takt-sim/tests/sim/sequential_composition_tests.rs`, два значенческих
теста с **накапливающим** телом (`n := n + 1`):
`parallel_executes_always_once_per_tick` и
`concatenation_executes_always_once_per_tick`. Именно накопление и ловит дефект:
идемпотентные тела корпуса к числу исполнений безразличны.

| Проба | До | После | Эталон `c` |
|---|---|---|---|
| `start P = A \| B;`, `n := n + 1` | `n = 2` за такт | `n = 1` | `n = 1` |
| `start P = A + B;` (прототип 0166) | счётчик фазы +2 за такт | +1 | +1 |

`cargo test --all-features -- --test-threads=1` — зелёный, провалов нет;
`./scripts/precheck.sh` — зелёный; `examples/generated/**` не изменился.
