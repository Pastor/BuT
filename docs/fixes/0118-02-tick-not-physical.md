# Исправление: такт — не единица физической величины (лифт и др. примеры)

> Фича: [../features/0118-book-showcase.md](../features/0118-book-showcase.md) · правило: [../RULE.md](../RULE.md) (правило 27, подпункт (е)) · затрагивает примеры разделов 04/05/10/17

## Проблема

Пример лифта (раздел 17) и ряд других содержали **ложный посыл**: физическая
величина вычислялась **счётом тактов**. В лифте — `always { floor := floor + 1; }`
(«один такт = один этаж»), в баке (раздел 10) — `always { level := level + RATE; }`.
Это вводит в заблуждение: частота тактирования произвольна (может быть 1 МГц), а
такт — шаг **логики**, не единица времени или расстояния. Реальное перемещение
создают приводы и фиксируют датчики; автомат не «интегрирует» положение по тактам.
Заказчик потребовал привести примеры в инженерный вид и зафиксировать принцип
(2026-07-…).

## Причина

При написании примеров положение/уровень моделировались самодвижущимися
переменными (тик-костыль) вместо чтения датчика — искусственная конструкция,
наряженная в реальные одежды. Свод (правило 27) требовал «функциональности из
практики», но прямо не запрещал подделку физики тактами.

## Решение

**Принцип — в свод** (`docs/RULE.md`, правило 27, новый подпункт **(е)**): такт —
не единица физической величины; положение/уровень/температуру и пр. Нельзя считать
тактами — они приходят с **датчиков** (входные порты) и меняются **приводами**;
единственное законное завязывание на такты — измерение **отрезков времени**, и оно
**подстраивается под частоту** устройства (константа = такты для длительности при
заявленной частоте), а не выдаёт число за физическую единицу.

**Примеры приведены в порядок** (все компилируются без предупреждений, проверены
симуляцией; лифт — ещё и верификацией):

- **Лифт (17)** `lift.takt`: убран `floor := floor + 1`; введён датчик положения
  `in at_floor: u8` (шахтная система позиционирования). Остановка — по показанию
  датчика (`ref Stopping: at_floor >= call;`), `display` следует за датчиком.
  Выдержка дверей `DWELL_TICKS` оставлена (это **время**), но подписана как
  подстраиваемая под частоту. Разбор/трасса/фрагменты C и SV/приложение (все цели)
  перегенерированы. LTL-вердикты и графы верификации не изменились (структура та же).
- **Бак (10)** `tank.takt`: уровень — с датчика `in level: u8`; `Full`/`Empty`
  читают датчик; `display` следует за уровнем; счётчик `cycles` (в `exit`) считает
  **события** (завершённые откачки).
- **Светофор (04)** `traffic.takt`: длительности фаз вынесены в именованные
  константы `RED_TICKS`/`GREEN_TICKS`/`YELLOW_TICKS` с пояснением про частоту (это
  законный **таймер времени**, но без магических чисел).
- **Бойлер (05)** `expr.takt`: `cycles := cycles + 1` перенесён из `always` в
  `enter` — теперь считает **циклы** нагрева (события), а не такты.

Прочие примеры проверены: `types` (03), `functions` (07), `ports` (08), `climate`
(09), `control` (06, счёт деталей в `enter` — событийный) — физику берут с датчиков,
дефекта нет.

## Проверки

- Все затронутые примеры: `taktc compile -t c` — без предупреждений; симуляция
  осмысленна (лифт: движение по датчику `at_floor`, остановка по нему; бак:
  колебание уровня с датчика, `cycles` растёт по откачке; светофор: Red 30 → Green
  30 → Yellow 5; бойлер: `cycles` = число включений нагрева, не тактов).
- Лифт: `taktc verify` — `F Boarding` нарушено (абстракция), `G (Stopping ->
  F Boarding)` держится (как прежде); графы перегенерированы `make build`
  байт-в-байт те же.
- `make -C book build` — PDF собирается; `./scripts/precheck.sh` зелёный.
