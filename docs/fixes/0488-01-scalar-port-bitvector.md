# Исправление: Носитель ширины пропустил бит-вектор

> Фича: [../features/0488-scalar-port-width.md](../features/0488-scalar-port-width.md)
> (разделы [«Архитектура (ADR)»](../features/0488-scalar-port-width.md#архитектура-adr) и
> [«Отчёт о тестировании»](../features/0488-scalar-port-width.md#отчёт-о-тестировании))

## Проблема

Носитель `semantic::scalar_port`, заведённый фичей, обещает ответ на
вопрос «каким машинным целым цель представляет это скалярное значение». Замер-02 показывает, что одного скаляра он не знает — **упакованного
бит-вектора**:

```takt
out sig: [bit; 12] at 0x300;   // st-at: ST-004 «размещаются только скаляры»
```

| Потребитель | `[bit; 12]` |
|---|---|
| эталон, `c`, `c-hal`, `st`, `rust`, `sv`, `sv-mmio`, `plantuml` | переводят |
| **`st-at`** | **`ST-004`** |

Между тем `[bit;N]` при N ≤ 64 — это упакованное беззнаковое целое родной
ширины: `[bit;12]` ≡ `u16`, и цель `st` печатает его именно так.

## Причина

Фича переносила в носитель те типы, которые **назвал замер** — целое,
длительность, `q(m, n)`, перечисление. Бит-вектор в замер не попал: у цели
`rust` он нормализуется **раньше** классификации порта (своя ветвь в
`port_class`), поэтому там всё работало, а `st-at` своей такой
ветви не имел — и остался единственным отказавшим.

Класс ровно тот, ради которого 0488 и заводилась: правило «что считать
скаляром» жило в целях по частям. Сведя его в носитель, я перенёс не все части
— то есть повторил исходный дефект в меньшем масштабе.

## Решение

1. `scalar_repr` знает бит-вектор: `Scalar { width }` → беззнаковое целое той
   же ширины, `Words { .. }` → `None` (массив слов целым не представим, и
   отказы целей на нём верны).
2. Набор `scalar_port_types_tests` получил ось бит-вектора **и контроль**:
   `[bit;96]` по-прежнему отвергается `c`, `rust` и `st-at` своими кодами.
3. Модульные тесты носителя проверяют обе стороны границы слова.

## Побочное следствие: `ST-004` ушёл из достижимых корпусом

Проверка качества диагностик (0467) отвечает `D5`: код в реестре есть, а корпус его
больше не даёт. Так и есть — единственным входом, доводившим до `ST-004`, был
порт-битвектор, и он теперь размещается. Остальные составные типы до
размещения не доходят: массив и структуру разворачивает `port_split` (0390,
0417). Код внесён в `scripts/diagnostic-coverage-baseline.txt` с этой причиной;
сам отказ остаётся достижимым — его проверяет модульный тест `st_at` на массиве
целых.

## Проверки

- `probe.sh -n 2` на `[bit;12]`: восемь целей переводят, инструменты приняли
  (`cc`, `iec2c` + `cc`, `rustc` + `clippy`, `verilator` + `yosys`).
- `probe.sh -n 2` на `[bit;96]` (контроль): `CC-015`, `ST-004`, `RS-016`,
  `SV-013` — границы на месте.
- `cargo test --test targets scalar_port` — 8 тестов; `./scripts/precheck.sh`
  зелёный.
